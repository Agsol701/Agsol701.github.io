Claude Code 架构与实现机制：从官方文档理解编码 Agent

source: claude-code-architecture-and-implementation
Jul 01, 2026

写在前面

Claude Code 不是一个只会回答代码问题的聊天窗口。

按照官方中文概览页的定义，Claude Code 是一个代理编码工具，可以读取代码库、编辑文件、运行命令，并与开发工具集成。它可以在终端、IDE（Integrated Development Environment，集成开发环境）、桌面应用和浏览器中使用。

这句话里其实已经包含了 Claude Code 的核心架构：

  • 它要理解整个代码库，而不是只理解一段粘贴进去的代码。
  • 它要能修改文件、执行命令，而不是只生成文本建议。
  • 它要接入终端、IDE、桌面、Web 等多个入口，而不是绑定在单一界面里。
  • 它要能连接 MCP（Model Context Protocol，模型上下文协议）、Hooks、Skills、CI/CD（Continuous Integration / Continuous Delivery，持续集成与持续交付）等扩展能力，而不是封闭运行。

所以，理解 Claude Code 的关键不是问"它用了哪个命令行界面"，而是理解它背后的编码 Agent Runtime（智能体运行时）。

本文基于 Anthropic Claude Code 官方中文文档整理，并在公开信息范围内做工程化解读。不会引用非公开源码，也不会把推测包装成官方实现细节。

官方概览地址：

https://code.claude.com/docs/zh-CN/overview

一、Claude Code 是什么

1.1 一句话理解

Claude Code 是面向软件工程任务的 AI 编码 Agent。

它的工作方式不是"你问一句，它答一句"，而是围绕一个真实代码库完成一轮工程任务：

  • 读取项目文件
  • 理解代码结构
  • 修改多个文件
  • 运行命令验证结果
  • 连接外部系统
  • 生成提交或拉取请求
  • 在不同开发入口之间延续工作

从用户视角看，它像一个能进入项目目录工作的开发助手。

从系统视角看，它是模型推理、上下文管理、工具调用、权限控制、会话编排和扩展系统共同组成的 Agent Runtime。

1.2 Claude Code 与普通聊天机器人的区别

普通聊天机器人主要处理文本输入和文本输出。

Claude Code 的输入和输出则更接近工程环境：

维度 普通聊天机器人 Claude Code
上下文 用户粘贴的文本 代码库、文件、命令输出、项目说明、会话历史
输出 文本回答 文件修改、命令执行、差异、提交、PR、任务结果
工具 通常较少或不可见 文件、Shell、搜索、MCP、IDE、CI/CD 等
工作模式 问答式 多步 Agent Loop
风险控制 主要靠提示词 权限、确认、配置、Hooks、托管策略
使用入口 聊天界面 CLI、VS Code、JetBrains、Desktop、Web、CI、Slack 等

官方概览页里反复出现的关键词是：读取代码库、编辑文件、运行命令、集成开发工具、自动化开发任务。这些能力共同决定了 Claude Code 不是"代码问答工具"，而是"编码任务执行系统"。

1.3 核心任务类型

官方概览页列出的典型用法可以归纳为六类。

第一类是自动化繁琐工作。例如补测试、修复 lint 问题、解决合并冲突、更新依赖、编写发布说明。这里的 lint 指静态代码检查，通常用于发现格式、风格、未使用变量、导入顺序和部分潜在错误。

第二类是构建功能和修复缺陷。用户用自然语言描述目标，Claude Code 规划实现路径，跨多个文件修改代码，并运行验证命令。

第三类是处理 Git 工作流。Claude Code 可以暂存更改、生成提交信息、创建分支、发起拉取请求，也可以在 CI 中做代码审查和问题分类。

第四类是连接外部工具。通过 MCP，Claude Code 可以接入 Google Drive、Jira、Slack 或团队自定义工具。

第五类是自定义工作方式。通过 CLAUDE.md、自动记忆、Skills 和 Hooks，把团队规范、复用流程和确定性自动化沉淀下来。

第六类是运行多代理或自定义代理。官方概览提到可以生成多个 Claude Code 代理并行处理任务，也可以通过 Agent SDK 构建自己的代理工作流。

二、从官方概览看整体架构

2.1 总体分层

从公开文档可以把 Claude Code 抽象成七层：

flowchart TD
    A[产品入口层<br/>CLI / IDE / Desktop / Web / CI / Slack] --> B[会话编排层<br/>任务、历史、状态、恢复]
    B --> C[上下文层<br/>代码库、CLAUDE.md、自动记忆、工具结果]
    C --> D[模型推理层<br/>理解目标、规划步骤、生成工具调用]
    D --> E[权限与策略层<br/>确认、配置、Hooks、托管策略]
    E --> F[工具执行层<br/>文件、Shell、搜索、Git、MCP、IDE]
    F --> G[结果反馈层<br/>差异、日志、提交、PR、最终总结]
    G --> B

这张图不是 Anthropic 内部源码结构图，而是基于官方功能边界整理出的工程模型。

它强调一个重点：Claude Code 的核心不是某个界面，而是一个可以被多个入口复用的编码 Agent 引擎。

2.2 产品入口层

官方概览页明确列出 Claude Code 可以在多个环境中使用：

  • Terminal
  • VS Code
  • Desktop app
  • Web
  • JetBrains

此外，概览页还提到 GitHub Actions、GitLab CI/CD、Slack、Chrome 扩展、Agent SDK 等集成方式。

这些入口面向不同工作场景：

入口 适合场景
Terminal 本地项目开发、命令行自动化、脚本管道
VS Code 编辑器内差异查看、上下文选择、对话历史
JetBrains IntelliJ IDEA、PyCharm、WebStorm 等 IDE 工作流
Desktop app 可视化查看差异、并行会话、定期任务、云会话
Web 无需本地设置，适合远程仓库、长任务、多任务并行
CI/CD 自动代码审查、问题分类、构建失败分析
Slack 从团队聊天触发错误修复或拉取请求
Agent SDK 构建自定义代理和内部自动化系统

这说明 Claude Code 的产品设计不是"一个 CLI 工具外加几个插件"，而是"一个底层 Agent 能力，接上多种工作入口"。

2.3 会话编排层

一次 Claude Code 任务通常不是单轮回答，而是一段持续会话。

会话编排层需要管理：

  • 用户目标
  • 对话历史
  • 已读取文件
  • 工具调用结果
  • 待办事项
  • 文件修改状态
  • 命令执行状态
  • 用户审批
  • 中断与恢复
  • 多入口迁移

官方概览页提到，用户可以从手机或浏览器继续本地会话，也可以把 Web 或 iOS 上启动的长任务通过 claude --teleport 拉回终端，还可以使用 /desktop 把终端会话交给桌面应用做可视化差异审查。

这背后意味着会话不是只存在于单一终端输入输出流里，而是被抽象成可迁移、可恢复、可展示的任务状态。

2.4 上下文层

Claude Code 能理解代码库，前提是它有一套上下文组织机制。

官方概览页提到 CLAUDE.md、自动记忆、Skills、MCP 服务器、设置等内容可以在不同界面中工作。这说明上下文不是临时拼接的一段文本，而是由多种来源组成：

  • 当前用户输入
  • 项目文件
  • 命令输出
  • Git diff
  • CLAUDE.md
  • 自动记忆
  • Skills
  • MCP 工具描述和返回结果
  • IDE 或 CI 提供的上下文

其中 CLAUDE.md 的角色很关键。官方概览把它描述为可以放在项目根目录的 Markdown 文件，Claude Code 会在每个会话开始时读取它，用来设置编码标准、架构决策、首选库和审查清单。

换句话说，CLAUDE.md 是项目长期上下文，不是一次性提示词。

2.5 模型推理层

模型推理层负责把上下文变成下一步行动。

它要判断：

  • 现在应该读哪个文件
  • 是否需要搜索代码
  • 应该修改哪些位置
  • 是否需要运行测试
  • 命令失败后如何定位原因
  • 什么时候应该请求用户确认
  • 任务是否已经完成

在 Claude Code 中，模型输出不只是自然语言回答，还可能是工具调用意图。例如读取文件、编辑文件、执行命令、请求 MCP 工具、发起子任务等。

这就是 Agent Loop 的核心：

flowchart LR
    A[理解任务] --> B[规划下一步]
    B --> C[调用工具]
    C --> D[观察结果]
    D --> E{是否完成}
    E -- 否 --> B
    E -- 是 --> F[总结结果]

这个循环让 Claude Code 可以处理多步工程任务，而不是只给出一段建议。

2.6 权限与策略层

Claude Code 可以编辑文件、运行命令、连接外部工具，这些能力很强，也必须有边界。

官方概览页没有展开所有权限细节，但从它列出的能力可以看出，Claude Code 至少需要在以下位置做风险控制：

  • 执行 Shell 命令前
  • 修改文件前后
  • 连接外部系统时
  • 创建提交和 PR 时
  • 在 CI/CD 中自动执行时
  • 通过 Slack 或远程入口触发任务时
  • Hooks 拦截工具调用时

权限层的目标不是让 Claude Code 变弱，而是让它可以在真实工程环境中可控地变强。

如果没有权限与策略层，文件编辑、命令执行、远程触发、外部系统写入都会变成高风险操作。

2.7 工具执行层

工具执行层负责把模型决策变成真实动作。

官方概览页中能看到的工具能力包括：

  • 读取代码库
  • 编辑文件
  • 运行命令
  • 使用 Git
  • 创建提交和拉取请求
  • 接入 MCP 外部数据源
  • 在 CI 中做审查和分类
  • 调用浏览器、Slack、IDE 等集成

工具执行层有三个工程重点。

第一，工具输入必须结构化。模型不能只说"我想改文件"，而要形成明确的文件路径、修改内容和执行参数。

第二，工具输出必须回到上下文。否则模型不知道文件内容、命令结果、错误日志和外部系统返回了什么。

第三，工具执行必须受策略约束。越接近真实系统，越需要权限、日志、确认和审计。

三、Claude Code 的主要能力模块

3.1 CLI：终端里的 Agent

官方推荐的终端启动方式很直接：

1
2

cd your-project
claude

CLI（Command Line Interface，命令行界面）适合本地工程开发，因为它天然靠近文件系统、Shell、Git 和测试命令。

官方概览页还给出了一些管道化使用方式，例如把日志输入 Claude Code，或者把 git diff main --name-only 的文件列表交给它做安全审查。

这体现了 Claude Code 的一个重要设计取向：它遵循 Unix 式组合思路，可以被命令、脚本和 CI 流程串起来。

3.2 IDE：把 Agent 放进编辑器

VS Code 扩展提供内联差异、@ 提及、计划审查和对话历史。

JetBrains 插件则面向 IntelliJ IDEA、PyCharm、WebStorm 等 IDE，提供交互式差异查看和选择性上下文共享。

IDE 集成的价值在于：

  • 更容易看 diff
  • 更容易选中局部上下文
  • 更容易结合编辑器诊断
  • 更容易在人类开发者和 Agent 之间切换注意力

CLI 更像任务执行入口，IDE 更像协作和审查入口。

3.3 Desktop 与 Web：多会话和长任务

官方概览页把桌面应用描述为可以在 IDE 或终端之外运行 Claude Code 的独立应用，支持可视化查看差异、并行运行多个会话、安排定期任务和启动云会话。

Web 则适合无需本地设置的场景：

  • 启动长时间运行的任务
  • 稍后回来检查结果
  • 处理本地没有的仓库
  • 并行运行多个任务
  • 在桌面浏览器或 Claude iOS 应用中使用

这类入口说明 Claude Code 的任务模型已经超出"本机终端的一次交互"。它更接近可调度、可迁移、可远程继续的开发任务系统。

3.4 MCP：连接外部数据和工具

MCP 是 Claude Code 扩展工具能力的重要机制。

官方概览页把 MCP 描述为一个开放标准，用于将 AI 工具连接到外部数据源。通过 MCP，Claude Code 可以读取 Google Drive 中的设计文档、更新 Jira 工单、从 Slack 拉取数据，或使用自定义工具。

可以把 MCP 理解成 Agent 与外部世界之间的标准工具接口。

flowchart LR
    A[Claude Code] --> B[MCP Client]
    B --> C[MCP Server]
    C --> D[Google Drive]
    C --> E[Jira]
    C --> F[Slack]
    C --> G[Custom Tools]

在企业场景里，MCP 的价值很大：很多工程任务不是只改代码，还需要读需求、查工单、同步文档、通知团队、访问内部系统。

3.5 CLAUDE.md、自动记忆、Skills 与 Hooks

官方概览页把自定义能力分成四类。

CLAUDE.md 用来保存项目说明。它适合写编码标准、架构决策、首选库、审查清单等长期规则。

自动记忆用于保存 Claude Code 在工作中学到的内容，例如构建命令、调试经验和项目习惯。它解决的是跨会话经验复用问题。

Skills 用来打包可重复工作流。比如团队可以把 /review-pr、/deploy-staging 这类流程做成可共享技能。

Hooks 用来在 Claude Code 操作前后运行 Shell 命令。比如每次文件编辑后自动格式化，或者提交前运行 lint。

它们的职责不同：

模块 主要作用
CLAUDE.md 项目长期说明和协作规则
自动记忆 跨会话保存项目经验
Skills 打包和复用工作流
Hooks 在生命周期事件上执行确定性自动化

一个简单判断方法是：需要告诉 Claude “应该怎么想"时，用 CLAUDE.md 或 Skills；需要系统"每次都自动做某件确定动作"时，用 Hooks。

3.6 多代理与 Agent SDK

官方概览页提到两种更高级的 Agent 能力。

第一种是运行多个 Claude Code 代理，让它们同时处理任务的不同部分。主代理可以协调工作、分配子任务并合并结果。

第二种是使用 Agent SDK 构建完全自定义的工作流。SDK 让开发者可以用 Claude Code 的工具和能力构建自己的代理，并控制编排、工具访问和权限。

这说明 Claude Code 不只是一个成品工具，也是一套可以被二次集成的 Agent 能力平台。

四、一次任务如何运行

4.1 典型执行流程

假设用户输入：

1

为 auth 模块补测试，运行测试，并修复失败用例。

Claude Code 的执行过程可以抽象成：

sequenceDiagram
    participant U as 用户
    participant C as Claude Code
    participant FS as 文件系统
    participant SH as Shell
    participant M as 模型

    U->>C: 提出任务
    C->>FS: 读取 CLAUDE.md 和项目文件
    C->>M: 组织上下文
    M->>C: 规划搜索与修改步骤
    C->>FS: 搜索 auth 模块和测试目录
    C->>M: 返回文件内容
    M->>C: 生成测试修改
    C->>FS: 编辑测试文件
    C->>SH: 运行测试命令
    SH->>C: 返回测试结果
    C->>M: 分析失败原因
    M->>C: 生成修复方案
    C->>FS: 修改代码或测试
    C->>SH: 再次运行测试
    C->>U: 总结修改、验证结果和风险

这里最关键的是闭环：模型不会只给出一次答案，而是不断根据工具结果调整下一步。

4.2 为什么上下文管理重要

代码库往往远大于模型一次能处理的上下文窗口。

因此 Claude Code 不可能简单地把整个仓库塞给模型。它更合理的方式是：

  • 先读取项目说明和目录结构
  • 根据任务搜索相关文件
  • 只加载必要文件片段
  • 把命令输出和错误日志作为新证据
  • 在需要时压缩或摘要历史
  • 把可复用经验沉淀到记忆或项目说明里

这也是为什么 CLAUDE.md、自动记忆、Skills 和工具结果会成为架构上的一等公民。

Agent 的聪明程度不只来自模型本身，也来自它能不能拿到正确、适量、及时的上下文。

4.3 为什么 Hooks 重要

模型擅长推理和生成，但工程环境里还有大量确定性规则。

例如：

  • 每次改 Python 文件后运行格式化
  • 禁止执行危险命令
  • 提交前必须跑 lint
  • 会话结束时写操作日志
  • 工具调用前扫描敏感路径

这些事情不适合完全交给模型自由发挥，因为它们应该稳定、可审计、可重复。

Hooks 的价值就在这里：把确定性自动化挂到 Claude Code 的生命周期上，让团队规则不只停留在提示词里。

五、工程实现视角下的关键设计

5.1 多入口共享同一底层能力

官方概览页明确写到，每个界面都连接到相同的底层 Claude Code 引擎，因此 CLAUDE.md、设置和 MCP 服务器可以在所有界面中工作。

这句话非常关键。

Claude Code 的能力越强，权限系统越重要。

5.4 扩展系统让 Agent 适配团队

不同团队的工程流程差异很大。

Claude Code 通过几类扩展点适配这些差异：

  • CLAUDE.md：写项目知识
  • 自动记忆：积累跨会话经验
  • Skills：封装复用流程
  • Hooks：接入确定性自动化
  • MCP：连接外部系统
  • Agent SDK：构建自定义代理工作流

这套扩展模型的方向很明确：把通用 Agent 变成团队自己的工程 Agent。

六、Prompt 管理：不要把所有指令都塞进一句话

6.1 Prompt 在 Claude Code 里不是单一文本

很多人把 prompt 理解成用户输入框里的一句话。

在 Claude Code 这种编码 Agent 里，prompt 更像一个由多层信息拼出来的上下文包。它至少包括：

  • 系统级行为约束
  • 当前用户请求
  • 会话历史
  • CLAUDE.md
  • CLAUDE.local.md
  • .claude/rules/
  • 自动记忆
  • Skills 的名称、描述和按需加载内容
  • Subagent 的专用 system prompt
  • MCP 工具说明和返回结果
  • 文件内容、命令输出、diff 和错误日志

因此，Prompt 管理的核心不是"写一个万能提示词”，而是回答三个问题：

第一，哪些内容每次会话都应该出现？

第二，哪些内容只在相关任务出现时加载？

第三，哪些内容不应该放进模型上下文，而应该交给 Hooks、权限或工具处理？

6.2 Prompt 分层模型

可以把 Claude Code 的 prompt 管理拆成五层：

flowchart TD
    A[系统层<br/>Claude Code 默认行为、工具协议、权限边界] --> B[用户层<br/>个人偏好、全局 CLAUDE.md、全局 settings]
    B --> C[项目层<br/>项目 CLAUDE.md、rules、settings、MCP 配置]
    C --> D[任务层<br/>当前用户请求、计划、文件、命令输出]
    D --> E[扩展层<br/>Skills、Subagents、Plugins、MCP 返回结果]

这五层的职责不同。

层级 适合放什么 不适合放什么
系统层 产品默认行为、工具调用格式、权限协议 项目私有知识
用户层 个人偏好、常用输出风格、通用开发习惯 团队强制规范
项目层 架构约定、测试命令、代码风格、发布流程 临时任务细节
任务层 本次要做什么、当前错误、当前 diff 长期规则
扩展层 专用流程、外部工具说明、子任务约束 所有任务都要读的大段背景

这也是为什么官方文档建议从 CLAUDE.md 开始，再按需要增加 Skills、Subagents、Hooks、MCP 和 Plugins。

6.5 Skills 与 Prompt 的关系

Skills 也是 prompt，但它不是普通 prompt。

它更像"带名称、描述和触发条件的工作流包"。官方 SDK 文档说明，Skills 与 CLAUDE.md 的区别在于：CLAUDE.md 每个会话都会加载，而 Skills 按需加载。Agent 启动时先看到 skill 描述，只有相关时才加载完整内容。

这意味着 Skills 适合承载比较长、比较专门的流程，例如：

  • PR 审查
  • 发布检查
  • 事故复盘
  • API 文档生成
  • 迁移脚本审查
  • 安全扫描流程

不要把这些流程全塞进 CLAUDE.md。否则每次做一个小改动，模型都要读一大段不相关流程。

6.6 Prompt 管理的常见错误

第一种错误是"万能提示词依赖"。

把所有规则都写进一个超长 prompt，看起来信息很全，实际会制造噪音。模型会在不相关任务中看到过多约束，反而更难抓重点。

第二种错误是"规则和动作混在一起"。

例如"每次提交前必须运行测试"可以写进 CLAUDE.md，但如果团队真的要求强制执行，就应该配 Hooks 或 CI。提示词是建议，Hooks 和 CI 才是约束。

第三种错误是"把临时事实写进长期记忆"。

比如"今天临时跳过某个测试"不适合进入 CLAUDE.md 或自动记忆。长期上下文应该稳定，否则以后会误导 Agent。

第四种错误是"不给验证命令"。

只写"保证质量"没有意义。应该写清楚 npm test、pytest、ruff check .、go test ./... 这类命令。

6.7 推荐的 Prompt 管理策略

一个团队可以按这个顺序建设：

flowchart LR
    A[先写 CLAUDE.md] --> B[拆分 rules]
    B --> C[沉淀常用 Skills]
    C --> D[为高风险任务建 Subagents]
    D --> E[用 Hooks 强制关键动作]
    E --> F[用 Plugins 分发团队能力]

简单说：

  • 长期项目知识放 CLAUDE.md
  • 局部规则放 .claude/rules/
  • 可复用流程放 Skills
  • 专业角色放 Subagents
  • 确定性动作放 Hooks
  • 跨项目分发放 Plugins
  • 外部系统上下文放 MCP

七、上下文管理：让 Agent 在正确的信息里工作

7.1 上下文管理解决什么问题

Claude Code 的能力很大一部分来自上下文。

但上下文不是越多越好。代码库、日志、diff、命令输出、需求文档、MCP 工具结果都可能进入会话，信息太少会让 Agent 判断错误，信息太多又会挤占上下文窗口、增加噪音和成本。

上下文管理要解决四个问题：

  • 该给 Agent 看什么
  • 什么时候给 Agent 看
  • 看完后哪些信息需要保留
  • 哪些信息应该摘要、隔离或丢弃

官方文档提到，当上下文接近限制时，Claude Code 会自动管理上下文：先清除较旧的工具输出，必要时总结对话；用户请求和关键代码片段会被保留，但早期细节可能丢失。

这意味着团队不能把重要规则只留在聊天历史里。长期规则应该进入 CLAUDE.md、Rules、Skills 或配置系统。

7.2 上下文来源

Claude Code 的上下文大致来自七类信息。

来源 内容 管理重点
用户输入 本次任务、约束、目标 表达清楚完成标准和限制
项目记忆 CLAUDE.md、自动记忆、rules 保持短、准、可维护
代码文件 当前读取的源代码、测试、配置 只读相关文件，避免全仓库灌入
工具输出 Shell、测试、lint、构建日志 保留关键错误，压缩冗长日志
Git 信息 diff、提交、分支、PR 关注本次变更影响面
扩展能力 Skills、Subagents、Hooks 按需加载，不要全量常驻
外部系统 MCP 返回的工单、文档、日志 结构化、带来源、控制权限

一个常见误区是把上下文等同于"文件内容"。

实际上，错误日志、测试失败、用户约束、项目规则和外部工单往往比源代码片段更关键。上下文管理不是单纯读文件，而是为当前任务组织证据。

7.3 CLAUDE.md 与自动记忆

官方 memory 文档把 CLAUDE.md 和自动记忆称为两个互补的记忆系统，它们都会在每次对话开始时加载，并被 Claude 当作上下文，而不是强制配置。

两者差异可以这样理解：

机制 谁维护 适合内容 风险
CLAUDE.md 人维护 编码标准、工作流、架构说明、测试命令 写太长、过期、像 README 一样泛
自动记忆 Claude 维护 构建命令、调试经验、项目偏好、发现的模式 记录临时事实、记住错误经验

CLAUDE.md 更适合放"团队想让 Agent 稳定遵守的项目知识"。

自动记忆更适合放"Agent 在工作中学到的经验"。

如果某个规则必须强制执行，例如禁止读取密钥文件或禁止执行发布命令，不应该只写进记忆。官方文档也强调，要阻止某个操作，应使用 PreToolUse hook，而不是依赖 Claude 是否记得。

7.4 上下文窗口与自动压缩

上下文窗口可以理解成当前会话能携带的信息容量。

当会话变长时，Claude Code 会自动压缩上下文。压缩的目标不是删除所有旧信息，而是保留任务目标、关键代码片段、重要结论和当前状态。

但压缩会带来损耗：

  • 早期讨论细节可能丢失
  • 冗长工具输出可能被删掉
  • 未结构化的重要信息可能被摘要错
  • 模糊的用户偏好可能被弱化

所以长任务里要主动管理上下文。

常用命令包括：

命令 作用 适合场景
/context 查看当前上下文占用 不知道空间被什么占满时
/compact 压缩当前会话 长任务继续推进前
/compact focus on ... 带焦点压缩 想保留某个主题的关键信息
/clear 开启空上下文新对话 切换到不相关任务
/resume 恢复历史会话 回到之前任务

比如做完 auth bug 修复后，如果要继续做 billing 重构，不应该让旧 auth 日志一直占着上下文。可以先 /clear，或者在同一任务内用 /compact focus on billing refactor。

7.5 工具输出如何进入上下文

工具输出是 Agent 判断现实状态的证据。

例如：

  • 测试失败日志告诉 Agent 哪个断言失败
  • lint 输出告诉 Agent 哪些文件不合规
  • git diff 告诉 Agent 这次改了什么
  • ls 和 rg 告诉 Agent 文件在哪里
  • MCP 工具返回工单状态或设计文档内容

但工具输出很容易膨胀。

例如一次全量测试可能输出几千行日志。如果直接塞进上下文，模型会被大量无用信息淹没。更好的做法是：

  • 优先保留失败摘要
  • 保留最小复现命令
  • 保留关键 stack trace
  • 删除重复日志
  • 把长日志保存到文件，只让 Agent 读取相关片段

对 Verify Agent 来说，最有价值的输出不是完整日志，而是：

7.6 文件上下文：按影响面读取

Claude Code 理解代码库，不代表每次都应该读完整代码库。

更好的策略是按影响面逐步读取：

flowchart TD
    A[用户任务] --> B[读 CLAUDE.md 和目录结构]
    B --> C[搜索入口符号和相关文件]
    C --> D[读取核心实现]
    D --> E[读取相邻测试和配置]
    E --> F[根据错误日志补充文件]
    F --> G[形成最小可用上下文]

比如修登录 bug 时，通常不需要先读完整个后端项目，而是应该从路由、service、session、测试和配置开始。

文件上下文管理有三个原则。

第一，先读入口，再读依赖。不要一开始就撒网式读取。

第二，读代码也要读测试。测试往往解释了项目期望行为。

第三，读配置。很多 bug 不在业务代码，而在开关、环境变量、依赖版本或构建配置。

7.7 外部上下文：MCP 不等于复制粘贴

没有 MCP 时，用户经常把 Jira、Slack、设计文档、监控日志复制进聊天框。

这样有几个问题：

  • 内容容易过期
  • 来源不清楚
  • 格式不稳定
  • 复制时可能遗漏关键字段
  • 大段文本会占用上下文

MCP 的价值是让 Claude Code 按需读取外部系统，并用结构化结果进入上下文。

例如 Jira MCP 工具可以返回：

例如主 Agent 要分析一个大模块，可以让 Research Agent 做大范围阅读：

7.9 上下文污染

上下文污染指的是：进入会话的信息误导了 Agent。

常见污染来源包括：

  • 过期的 CLAUDE.md
  • 自动记忆里保存了临时 workaround
  • 用户粘贴了不完整日志
  • 子 Agent 返回了没有证据的结论
  • MCP 工具返回了过期工单状态
  • 长会话里残留了上一个任务的假设
  • 过度压缩导致关键限制被弱化

上下文污染比上下文不足更隐蔽，因为 Agent 看起来掌握了信息，但信息是错的。

减少污染的方法：

  • 长期规则保持短而准
  • 任务切换时用 /clear
  • 长任务压缩时用明确焦点
  • 子 Agent 输出必须带证据
  • MCP 返回结果带时间和来源
  • 重要结论用测试、diff 或命令输出验证
  • 定期审查自动记忆和 CLAUDE.md

7.10 上下文管理的推荐流程

一个比较稳的上下文管理流程是：

flowchart TD
    A[接收任务] --> B[加载长期上下文]
    B --> C[识别任务类型和影响面]
    C --> D[读取最小相关文件]
    D --> E[调用工具或 MCP 补充证据]
    E --> F[结构化保留关键结果]
    F --> G{上下文是否膨胀}
    G -- 是 --> H[委托 Subagent 或 /compact]
    G -- 否 --> I[继续实现和验证]
    H --> I
    I --> J[输出结果和残余风险]
    J --> K[必要时更新 CLAUDE.md 或记忆]

实践中可以记住一句话：把规则放在长期上下文，把证据放在任务上下文，把探索放在子 Agent，把强制动作放在 Hooks。

八、多 Agent 分工：把一个大任务拆成多个专业角色

8.1 为什么需要多 Agent

单个 Agent 可以完成很多任务，但它也会遇到三个限制。

第一，上下文会膨胀。一个大型任务可能需要读大量文件、日志和文档，主会话很容易变长。

第二，角色会混杂。实现、测试、审查、安全分析、文档编写需要不同关注点，让一个 Agent 同时扮演所有角色，容易顾此失彼。

第三，任务无法并行。多个相对独立的模块如果串行处理，会浪费时间。

多 Agent 的价值就是把任务拆成多个边界清楚的工作单元：

  • 主 Agent 负责目标理解、任务拆分和结果整合
  • 实现 Agent 负责代码修改
  • 验证 Agent 负责测试和质量检查
  • Review Agent 负责审查 diff 和潜在缺陷
  • Research Agent 负责查资料、读文档和分析依赖
  • Migration Agent 负责数据库或接口迁移
  • Security Agent 负责安全风险扫描

官方 subagents 文档也说明，可以创建具有自定义提示、工具限制、权限模式、hooks 和 skills 的专门 subagents。

需要注意：下面这些 Research Agent、Implement Agent、Verify Agent、Review Agent、Security Agent 不是 Claude Code 官方固定内置的一组系统 Agent，而是基于 subagents 机制整理出的工程角色。Claude Code 提供 subagent 机制和部分内置 subagents；具体专业角色通常需要用户或团队通过自定义 subagent、command、skill 或 batch 工作流定义出来。

8.2 多 Agent 分工模型：基于 subagents 机制的工程抽象

可以把多 Agent 系统理解成一个小型工程团队：

flowchart TD
    A[Main Agent<br/>任务理解与调度] --> B[Research Agent<br/>代码和文档调研]
    A --> C[Implement Agent<br/>实现修改]
    A --> D[Verify Agent<br/>测试和验证]
    A --> E[Review Agent<br/>代码审查]
    A --> F[Security Agent<br/>安全检查]
    B --> A
    C --> A
    D --> A
    E --> A
    F --> A

这张图不是官方拓扑图，也不表示 Claude Code 默认内置了这些固定名称的 Agent。它表达的是：主会话 Agent 可以基于 subagents 机制，把调研、实现、验证、审查、安全检查等不同职责委派给专门的工作单元。这里的 Verify Agent 表示专门负责验证的子 Agent：运行测试、检查 lint、分析失败原因，并给主 Agent 一个明确结论。

8.3 常见 Agent 角色设计

角色 主要职责 推荐工具权限 输出形式
Main Agent 拆任务、调度、合并结果、对用户总结 读写文件、调用子 Agent、有限 Shell 计划、决策、最终总结
Research Agent 搜索代码、阅读文档、定位影响面 只读文件、搜索、MCP 相关文件列表、依赖关系、风险点
Implement Agent 修改代码、补测试、处理失败 读写文件、测试命令 修改说明、diff 摘要、验证建议
Verify Agent 跑测试、lint、类型检查、构建 Shell、只读文件、必要日志读取 PASS / FAIL / PARTIAL 和证据
Review Agent 审查正确性、可维护性、边界条件 只读 diff、只读文件 问题清单和严重级别
Security Agent 检查密钥、注入、权限、依赖风险 只读文件、扫描工具、MCP 安全风险和修复建议
Release Agent 生成 changelog、检查版本、发布前清单 Git、只读文件、有限 Shell 发布摘要和检查项

角色设计要避免两个极端。

一种极端是所有 Agent 都拥有全部工具权限。这会让隔离失去意义。

另一种极端是角色太碎。每个小任务都新建一个 Agent，会增加调度成本和上下文合并成本。

8.4 Verify Agent：验证不是"看起来没问题"

验证 Agent 的核心职责不是赞同实现，而是主动寻找实现是否真的成立。

一个好的 Verify Agent 应该做这些事：

  • 识别本次变更影响哪些模块
  • 找到应该运行的测试、lint、类型检查和构建命令
  • 执行验证命令
  • 保存关键错误日志
  • 判断失败是实现问题、测试环境问题还是既有问题
  • 必要时建议最小修复方向
  • 给出明确状态：PASS、FAIL 或 PARTIAL

8.6 多 Agent 的权限隔离

多 Agent 不是只为了并行，也为了权限收敛。

例如：

  • Research Agent 只读，不允许编辑
  • Verify Agent 可以运行测试，但不允许修改代码
  • Implement Agent 可以编辑代码，但不允许推送分支
  • Security Agent 可以读配置，但不能读取密钥文件内容
  • Release Agent 可以生成 changelog，但发布命令需要人工确认

权限越清楚，系统越可控。

如果一个子 Agent 的职责只是审查，就不应该给它写文件权限。这样即使它判断错误，也不会直接改坏项目。

九、Agent 调度链：从用户目标到可验证结果

9.1 调度链是什么

Agent 调度链指的是：主 Agent 如何把用户目标拆成任务，选择合适的子 Agent 或工具，收集结果，再决定下一步。

它不是简单的"多开几个 Agent"，而是一条有状态的任务链路：

flowchart TD
    A[用户目标] --> B[主 Agent 澄清目标和约束]
    B --> C[拆分任务]
    C --> D{选择执行方式}
    D --> E[直接调用工具]
    D --> F[委派 Subagent]
    D --> G[调用 Skill]
    D --> H[调用 MCP]
    E --> I[收集结果]
    F --> I
    G --> I
    H --> I
    I --> J{是否需要继续}
    J -- 是 --> C
    J -- 否 --> K[验证、总结、交付]

调度链的质量，决定了 Claude Code 是"想到哪做到哪"，还是像工程师一样有节奏地推进。

9.2 调度链的四个阶段

第一阶段是 intake，也就是接收任务。

主 Agent 要判断用户真正想要什么：是修 bug、加功能、查原因、写文档，还是做审查。它还要识别约束：不能改哪些文件、必须跑哪些测试、是否允许联网、是否需要保持兼容。

第二阶段是 planning，也就是拆解任务。

主 Agent 把目标拆成若干可执行单元。例如"升级登录模块"可以拆成：阅读现有实现、定位测试、修改代码、补测试、运行验证、整理风险。

第三阶段是 dispatch，也就是调度。

主 Agent 决定每个单元交给谁：

  • 简单读文件：直接工具调用
  • 大范围搜索：Research Agent
  • 代码修改：Implement Agent 或主 Agent 自己做
  • 质量检查：Verify Agent
  • 外部系统查询：MCP
  • 固定流程：Skill

第四阶段是 reduce，也就是归并。

主 Agent 汇总子 Agent 输出、工具结果和验证证据，决定是否继续修复，最后给用户交付结论。

9.3 什么时候直接做，什么时候调 Agent

不是所有任务都需要多 Agent。

可以用这个判断表：

情况 推荐方式
改一个小文件、上下文清楚 主 Agent 直接做
需要搜索很多模块 Research Agent
需要跨多个目录并行修改 多个 Implement Agent
需要独立质量判断 Verify / Review Agent
需要访问外部系统 MCP
流程固定且可复用 Skill
要跨项目分享能力 Plugin

多 Agent 的成本是真实存在的：调度需要 token，结果合并需要判断，子 Agent 可能理解偏差。

所以最佳实践不是"所有任务都多 Agent"，而是"复杂任务才多 Agent"。

9.4 调度链中的状态设计

一个清晰的调度链应该维护任务状态。

可以用下面这种状态机理解：

stateDiagram-v2
    [*] --> Intake
    Intake --> Plan
    Plan --> Dispatch
    Dispatch --> Execute
    Execute --> Verify
    Verify --> Rework: 验证失败
    Rework --> Dispatch
    Verify --> Review: 验证通过
    Review --> Rework: 审查发现阻塞问题
    Review --> Deliver
    Deliver --> [*]

这条链路里，验证失败不是异常，而是正常反馈。

一个成熟的 Agent 系统应该允许失败结果回流到实现环节，而不是在第一次测试失败后就把错误日志丢给用户。

9.6 调度链与命令系统

官方 commands 文档展示了 Claude Code 在任务期间和任务之间的命令体系。

从调度角度看，这些命令可以理解成不同的调度入口：

  • /plan：先进入规划再执行，适合大改动
  • /agents：管理子 Agent
  • /tasks：查看后台任务
  • /batch：把大型修改拆成独立单元并行运行

  • /resume：恢复历史会话

这些命令说明 Claude Code 的调度不只是模型内部推理，也暴露成用户可控的工作流界面。

十、Skills、Plugins、MCP：生态管理和使用

10.1 三者分别解决什么问题

Skills、Plugins 和 MCP 很容易混在一起，但它们解决的是不同问题。

# PR Review

## 何时使用

当用户要求审查当前 diff、PR 或 merge request 时使用。

## 工作步骤

1. 读取当前 diff。
2. 判断改动类型：功能、修复、重构、依赖、配置。

- 非阻塞建议

10.3 Skills 的管理策略

Skills 不应该无限增长。

建议按三个层级管理：

层级 位置 内容
个人 Skills ~/.claude/skills/ 个人写作、调试、常用工作流
项目 Skills <repo>/.claude/skills/ 当前仓库专用流程

命名要稳定，描述要明确。

例如 /deploy 太宽泛，容易误触；/deploy-staging、/review-pr、/generate-api-docs 更清晰。

还要定期清理：

  • 长期不用的 Skill 关掉或删除
  • 重复 Skill 合并
  • 过时命令更新
  • 高风险 Skill 加权限说明
  • 输出格式保持一致

10.5 Plugins 的治理重点

Plugin 带来复用，也带来治理问题。

建议至少管理五件事。

第一，版本。

团队插件要有版本号和变更日志。否则不同项目使用不同版本时，很难定位行为差异。

第二，权限。

插件可能带 hooks、agents 和 MCP servers，必须审查它会执行什么命令、访问什么系统、读取哪些路径。

第三，默认启用范围。

不是所有能力都应该默认打开。高风险 hooks、发布类 Skill、外部写入类 MCP 工具应该谨慎启用。

第四，配置。

插件应该把环境差异放到用户配置或项目配置里，不要把团队私有路径、token、机器名写死。

第五，回滚。

如果某个插件版本导致 Claude Code 行为异常，团队需要能快速禁用或回退。

10.6 MCP：让 Agent 使用外部系统

MCP 的核心是把外部系统包装成 Claude Code 可以理解和调用的工具。

例如：

  • Jira：查任务、改状态、写评论
  • Slack：读取讨论、发送通知
  • Google Drive：读取设计文档
  • 数据库元数据服务：查询表结构
  • 内部发布平台：查询发布状态
  • 日志平台：拉取错误日志

典型调用链是：

sequenceDiagram
    participant C as Claude Code
    participant M as MCP Server
    participant S as 外部系统

    C->>M: 调用工具，例如 get_issue
    M->>S: 请求外部 API
    S->>M: 返回结构化数据
    M->>C: 返回工具结果
    C->>C: 把结果纳入上下文并继续推理

MCP 的价值不是"让 Claude 多几个插件"，而是把业务上下文纳入 Agent Loop。

10.7 MCP 的使用原则

第一，工具描述要清楚。

模型是否会正确调用 MCP，很大程度取决于工具名称、参数说明和返回结构。

第二，返回结果要结构化。

不要返回一大段不可解析文本。更好的方式是返回字段明确的数据，例如 issue id、标题、状态、负责人、相关链接、错误栈、时间戳。

第三，权限要最小化。

读 Jira 和改 Jira 状态不是同一类权限。读取日志和删除日志更不是同一类权限。

第四，写操作要谨慎。

凡是会修改外部系统的 MCP 工具，例如关闭工单、发布版本、发送通知，最好加确认或限制触发条件。

第五，MCP 不能替代项目上下文。

MCP 提供外部事实，CLAUDE.md 和代码库提供项目规则。两者应该配合，而不是互相替代。

10.8 三者如何组合

Skills、Plugins、MCP 可以组合使用。

例如团队要做一个"发布前检查"能力：

flowchart TD
    A[release-check Plugin] --> B[Skill: /release-check]
    A --> C[Agent: Release Agent]
    A --> D[Agent: Verify Agent]
    A --> E[Hook: 阻止未验证发布]
    A --> F[MCP: Jira / Slack / 发布平台]
    B --> C
    C --> D
    C --> F
    E --> C

实际工作流可能是：

  1. 用户运行 /release-check
  2. Skill 定义发布检查流程
  3. Release Agent 汇总版本、diff、变更说明
  4. Verify Agent 运行测试和构建
  5. MCP 查询 Jira 是否还有阻塞 issue
  6. MCP 查询发布平台当前状态
  7. Hook 在缺少验证结果时阻止发布命令
  8. 主 Agent 输出发布是否可继续

这就是生态能力的组合：Skill 定流程，Agent 做分工，MCP 接外部系统，Hook 做强约束，Plugin 负责打包分发。

十一、实践建议

11.1 先写好 CLAUDE.md

如果一个项目首次接入 Claude Code，最值得优先做的是写好 CLAUDE.md。

建议至少包含：

  • 项目是什么
  • 主要目录结构
  • 本地启动命令
  • 测试命令
  • lint / format（静态检查 / 格式化）命令
  • 代码风格
  • 常见坑
  • 提交或 PR 规范
  • 禁止事项

这能显著降低 Claude Code 每次重新摸索项目的成本。

11.2 把重复流程沉淀成 Skills

如果团队经常让 Claude Code 做同一类任务，例如：

  • 审查 PR
  • 写接口文档
  • 生成发布说明
  • 分析 CI 失败
  • 做依赖升级
  • 扫描安全风险

就应该考虑把流程沉淀成 Skills。

Skills 的意义不是"多写一个提示词文件"，而是让团队把可复用的工作方法标准化。

11.3 用 Hooks 处理确定性动作

不要把所有规则都写进提示词。

提示词适合表达偏好和方法，Hooks 适合表达强制动作和自动化流程。

例如：

  • 编辑后自动格式化
  • 提交前运行测试
  • 禁止访问密钥文件
  • 高风险命令前阻断
  • 会话结束时记录审计日志

这些事情越确定，越适合 Hooks。

11.4 用 MCP 接入真实业务上下文

很多开发任务失败，不是因为模型不会写代码，而是因为它缺少业务上下文。

例如：

  • 需求文档在 Google Drive
  • 任务状态在 Jira
  • 错误报告在 Slack
  • 接口契约在内部平台
  • 发布记录在自建系统

MCP 的价值就是把这些外部上下文变成 Claude Code 可以调用的工具。

11.5 为不同入口设计不同工作流

不要把所有场景都塞进终端。

更合理的分工是：

场景 推荐入口
快速本地修改 CLI
查看差异和手工审查 IDE 或 Desktop
长时间任务 Web 或 Desktop
自动 PR 审查 GitHub Actions / GitLab CI/CD
团队聊天触发 Slack
内部平台集成 Agent SDK

Claude Code 的优势正是多入口共享底层能力。

十二、总结

Claude Code 的本质是一个面向软件工程的编码 Agent Runtime。

它的核心不是"会写代码的模型"，而是这一整套系统：

  • 多入口产品层：CLI、IDE、Desktop、Web、CI、Slack、SDK
  • 会话编排层：任务状态、历史、恢复、迁移
  • 上下文层：代码库、CLAUDE.md、自动记忆、Skills、MCP
  • 上下文管理层：上下文窗口、压缩、清理、子 Agent 隔离和证据保留
  • 模型推理层：规划、判断、生成工具调用
  • Prompt 管理层：长期规则、任务上下文、按需加载流程和局部规则
  • 权限策略层：确认、配置、Hooks、托管约束
  • 工具执行层：文件、Shell、Git、外部系统
  • 调度协作层：多 Agent 分工、验证闭环、后台任务和调度链
  • 扩展生态层：MCP、Hooks、Skills、Plugins、Agent SDK

如果只把 Claude Code 当成"更聪明的代码补全"，会低估它。

更准确的理解是：Claude Code 把大语言模型放进真实工程环境里，通过 prompt 管理、上下文、工具、权限、多 Agent 调度和扩展生态，让模型能够参与完整的软件开发流程。

这也是它和普通 AI 聊天工具最大的区别。
