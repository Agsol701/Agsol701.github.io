May 22, 2026

agent-hub 项目知识卡片

智能体编排引擎，AppBuilder 核心子系统之一

项目概述

agent-hub 是百度千帆 AppBuilder 平台的智能体编排引擎，负责 Agent 的创建、调度和执行。包含四种智能体：single_agent（单 Agent ReAct）、multi_agent（多 Agent 协同）、ai_assistant（AI 助手+深度思考）、deepresearch（深度研究），通过 api-server 统一对外暴露 API。

技术栈：Go 1.24+ / Gin / Eino（cloudwego 图编排框架） / MongoDB / SSE

整体架构 

1
2
3
4
5

用户请求 → api-server(网关聚合)
              ├── single_agent     → ReAct 循环（Planner → Executor → Generator）
              ├── multi_agent      → HostAgent(Plan) → ToolAgent(Execute) → Replan/Summary
              ├── ai_assistant     → Router → Executor → Generator（四阶段管线）
              └── deepresearch    → Parser → Coordinator → Outliner → Planner → Executor → Reporter

关键依赖：

  • agent-core：Agent 引擎核心（compose.DynamicGraph、master.Agent）
  • agent-infra：基础设施（dte、console、memory、ce/model、safety 等）
  • CopilotEngine：LLM 调用服务，通过 AppToken 区分不同 prompt 应用
  • DTE (next-gen-dte)：组件执行引擎

一、Single-Agent（ReAct 模式）

架构

single_agent 是基于 agent-core master.Agent 引擎的 ReAct 模式单智能体实现，是 DTE Python AgentPro 的 Go 重写版，修复了 DTE 的多个 bug。

HTTP POST /v3/function_call/integrated
  → SingleAgentAPI (streaming/blocking 双模式)
  → NewReactAgentWithRequest()
    → PrepareContexts(): Request → RunInput + AppConfig
    → 知识干预搜索 + 行业术语改写 + 规则干预检查
    → (命中干预则直接推送答案，跳过 LLM)
  → ReactAgent.Run()
    → 创建 AgentEngine (engine_config.yaml)
    → agentEngine.Run(ctx, input, WithMaxIteration, WithUserState)
      → ReAct 循环: Planner → Executor → (检查退出) → 下一轮或 Generator

核心设计

1. ReAct 循环

  • 默认最大迭代 3 次，可通过 AppConfig.MaxThoughtRound 覆盖（上限 100，默认赋 4）
  • 每轮：Planner 思考 → Executor 执行工具 → 检查是否提前退出
  • 提前退出条件：Planner 输出 subtask_type=generation / 工具在 StopTools 列表中

2. Router 是静态路由

engine_config.yaml 中 jmes-path-rule: "true" 恒为真，所有请求直接命中 planner，不经过 Router LLM 调用，节省一次模型调用。

3. 三路组件执行

类型 判断条件 执行方式
MCP impl.IsMCPComponent(tool.Type) HTTP POST 到 MCP /mcp/api/v1/tool/call
Workflow tool.ToolName == "Workflow" HTTP POST 到 workflow engine
DTE 组件 默认 HTTP POST 到 DTE /dte/api/v2/components/<name>/version/latest?action=tool_eval

4. 两阶段 Function Calling

  • Planner 阶段：CE 模型输出 thought + actions（含 tool_name）
  • 抽参阶段：调用 CE 抽参模型 ab-online-ai-assistant-tool-parameter-builder，输入工具定义 + Planner 输出，输出具体 arguments

这种设计解耦了"选工具"和"填参数"，让 Planner 专注意图理解，抽参模型专注参数提取。

5. 干预机制（三层）

层级 实现 场景
规则干预 Redis 关键词匹配 精确匹配的 FAQ
知识干预 向量搜索 + Rerank 语义相似的知识库内容
行业术语 术语搜索 + LLM Query 改写 专业术语理解

命中干预后直接推送答案，跳过所有 LLM 调用，降低延迟和成本。

6. ReActState 三层嵌入结构

1

3

ReActState
  ├── UIRenderingState    # 运行时频繁更新：事件推送、防重复、状态机
  ├── DataCacheState      # 初始化一次只读：请求、配置、历史、组件工厂
  └── BusinessFlowState   # 业务控制流：重试、中断、轮次控制

7. 软错误处理

所有 DTE/MCP 硬错误转为软错误（SoftErrorIterator），避免 graph 中断。工具执行失败不会导致整个 ReAct 循环崩溃，而是将错误信息返回给 Planner 重新决策。

和 multi_agent 的核心区别

并行能力 无（串行 ReAct） DynamicGraph 并行执行
适用场景 简单对话、单步工具调用 复杂任务、多组件协同
API 端点 /v3/function_call/integrated /v3/function_call/multiagent_integrated/inner

架构

MultiAgent.Run()
  1. SafetyCheck(文本安全检测)
  2. NewHostAgent(初始化主控)
  3. compose.NewDynamicGraph(hostAgent, eventChannel) -- 动态图执行
     -> HostAgent.Orchestrate() -- 生成 Plan
        -> cePlan() / ceReplan() -- 调用 CopilotEngine 生成计划
     -> 动态图并行执行 ToolAgent 节点
        -> DefaultAgentRun() -- 调用 DTE
        -> UserAgentRun()    -- 调用 Console
        -> ReportAgentRun()  -- 报告生成
  4. HostAgent.outputMessage() -- 返回结果

核心设计

1. Plan-and-Execute 而非 ReAct

为什么选择 Plan-and-Execute？因为 multi-agent 场景需要一次性规划多个并行任务，ReAct 的单步决策无法支持并行。Plan 结果包含任务间依赖关系（Requires），DynamicGraph 据此调度并行/串行执行。

2. 多轮规划容错

  • currentIteration == 0：cePlan（首次规划）
  • currentIteration < maxIterations(3)：ceReplan（重新规划）
  • currentIteration == maxIterations && 有失败任务：ceChatSummary（兜底总结）
  • 最多迭代 3 次

3. 任务依赖

ToolAgent 通过 task.Requires 字段实现任务间依赖：

  • 前置任务失败 → 取消后续
  • 前置任务未完成 → 跳过
  • RequiredContext 将前置任务结果注入当前任务参数

4. 三种执行路径

执行路径 调用目标 场景
DefaultAgentRun DTE (dte.RunAgent) 标准组件执行
UserAgentRun Console (console.RunAgent) 用户自定义 Agent
ReportAgentRun DTE (ToolChoice 强制 ReportAgent) 报告生成

三、DeepResearch（多阶段有状态工作流）

架构

基于 Eino compose.Graph 的状态机工作流：

1
2

START → Parser → Coordinator → CoordinatorHuman → Preparer → Outliner
→ OutlinerHuman → Planner → Executor → Reporter → END

支持 compose.Interrupt 实现人机交互（大纲确认、澄清问答）。

核心设计

1. Human-in-the-Loop

  • 使用 compose.Interrupt 抛出中断
  • 中断信息持久化到 MongoDB (interrupt_events 集合)
  • 恢复时通过 CheckpointID + StateModifier 注入用户反馈

2. 并行执行

Executor 为每个 Step 启动 goroutine 并行执行：

  • sync.Mutex 保护 EventChannel push 和 ReferenceMapping 更新
  • sync.WaitGroup 等待所有步骤完成

六、面试 Q&A

Q0: Single-Agent 和 Multi-Agent 分别适合什么场景？为什么需要两种架构？

A: Single-Agent（ReAct）适合简单对话和单步工具调用场景——用户问一个问题、调一个组件就完成。它的优势是延迟低、成本低、逻辑简单。Multi-Agent（Plan-and-Execute）适合复杂任务场景——用户一个请求需要多个组件协同完成，比如同时搜索多个知识库、调用多个 API、生成报告。它的优势是支持并行执行和任务依赖管理。两种架构并存是因为实际业务中简单场景和复杂场景并存，用 ReAct 处理简单请求可以避免 Plan-and-Execute 的开销，用 Plan-and-Execute 处理复杂请求可以弥补 ReAct 无法并行的短板。

Q0.1: Single-Agent 的两阶段 Function Calling 是怎么设计的？为什么不直接一步到位？

A: 分两步：第一步 Planner 只负责意图理解和工具选择，输出 thought + actions（含 tool_name）；第二步抽参模型专门负责参数提取，输入工具定义 + Planner 输出，输出具体 arguments。这样设计的好处是解耦了"选工具"和"填参数"——Planner 专注意图理解不需要关心每个工具的参数细节，抽参模型专注参数提取可以利用工具的完整 schema 做精确提取。如果一步到位，Planner 的 prompt 会非常长（需要包含所有工具的完整参数定义），而且意图理解和参数提取互相干扰，准确率下降。

Q0.2: 干预机制的三层设计是怎么考虑的？

A: 规则干预（Redis 关键词匹配）最轻量，适合精确匹配的 FAQ，延迟最低；知识干预（向量搜索+Rerank）适合语义相似的知识库内容，覆盖面更广但延迟稍高；行业术语（术语搜索+LLM Query 改写）不是直接回答，而是改写用户 query 让 LLM 更好理解。三层各有分工：规则干预做精确拦截，知识干预做语义兜底，行业术语做输入优化。命中干预后直接推送答案跳过所有 LLM 调用，既降低延迟又节省成本。

Q0.3: 软错误处理的设计思路是什么？

A: 所有 DTE/MCP 执行的硬错误转为软错误（SoftErrorIterator），不会导致 ReAct 图中断。工具执行失败时，错误信息会作为工具结果返回给 Planner，Planner 可以选择换一个工具重试、调整参数再试、或者直接让 Generator 生成回答。这比硬中断更合理，因为实际场景中工具调用失败是常态（网络超时、参数错误等），不应该因为一个工具失败就整个对话崩溃。

Q1: 为什么 Multi-Agent 选择 Plan-and-Execute 而不是 ReAct？

A: ReAct 是单步决策，每次只选择一个工具执行，无法支持并行。Multi-Agent 场景下，用户一个复杂请求可能需要多个组件同时执行（比如同时搜索多个知识库、调用多个 API）。Plan-and-Execute 允许 HostAgent 一次性生成包含多个并行任务的 Plan，DynamicGraph 根据任务间的依赖关系（Requires）调度并行/串行执行，大幅提升执行效率。同时支持 Replan 机制，如果执行结果不理想可以重新规划，兼具效率和容错能力。

Q2: DynamicGraph 是怎么工作的？

A: DynamicGraph 来自 agent-core 的 compose 包。HostAgent 实现了 Orchestrate 和 Judge 两个接口方法。每次 Orchestrate 返回 compose.Plan{Nodes: []compose.Node}，每个 Node 是一个 Callable（ToolAgent）。DynamicGraph 根据节点间的依赖关系构建执行图，无依赖的节点并行执行，有依赖的节点串行执行。执行完所有节点后，如果 Judge 判断需要继续，会再次调用 Orchestrate 生成新的 Plan（Replan）。

Q3: 人机交互 (HITL) 是怎么实现的？

A: 基于 Eino 框架的 compose.Interrupt 机制。当 DeepResearch 执行到需要用户确认的节点（如大纲确认），会调用 compose.Interrupt 抛出中断，前端收到 interrupt 事件后展示确认界面。中断信息（包括当前状态、待确认内容）持久化到 MongoDB 的 interrupt_events 集合。用户确认后，通过 CheckpointID 恢复执行，使用 StateModifier 注入用户反馈，继续后续流程。

Q4: 流式消息合并器 StreamingMerger 是怎么设计的？

A: StreamingMerger 是一个精密的流式消息合并器，解决的问题是：Agent 执行过程中会产生大量 SSE 事件（文本分片、工具调用结果、引用信息等），需要按逻辑维度合并后推送给前端。设计了一个四维匹配键：event.id + event.name + content.type + content.name，同一匹配键的事件会被合并处理。text 类型做累积拼接，references 做去重聚合，plan 有状态机（preparing→running→done），code 片段做拼接。这样前端只需根据合并后的事件更新 UI，避免了频繁重渲染。

Q5: Prompt 是怎么管理的？

A: 所有核心 prompt（Planner、Replanner、Router 等）托管在 CopilotEngine 上，通过 AppToken 区分不同功能。agent-hub 不直接管理 prompt 模板，而是通过 Inputs 参数注入变量（instruction、history_talk、upload_file_content 等）。好处是 prompt 迭代不需要重新部署 agent-hub 服务，只需在 CE 端更新。另外 memory.GenerateInstructionFromTemplate 支持从记忆变量中生成指令，实现用户级定制化。

Q6: DTE 的两种调用方式有什么区别？为什么这么设计？

A: multi_agent 使用 dte.RunAgent()，传入任务描述和工具列表，由 DTE 自行决策调用哪个工具——这是"Agent 模式"，适合需要 LLM 做决策的场景。deepresearch 使用 components.DTEComponentClient.Run()，直接指定组件和参数——这是"工具模式"，适合流程确定、不需要 LLM 决策的场景。这样设计的原因是 deepresearch 的工作流是预定义的（Parser→Coordinator→Outliner→…），每个阶段该调用什么组件是确定的，不需要 DTE 再做决策，减少 LLM 调用开销，提高确定性和效率。

Q7: 记忆系统是怎么设计的？

A: 多层级记忆：

  • 历史对话：memory.GetHistoryDialogues() 按 conversation_id + rounds 获取
  • 记忆变量：appConfig.Memory.Variable 支持长期变量存储（跨会话）
  • 记忆表格：MemoryTableAgent 支持结构化数据记忆
  • 任务间上下文传递：ToolAgent 的 RequiredContext 机制将前置任务结果注入后续任务参数

Q8: 如果 Plan 生成的任务全部失败了怎么办？

A: 有多级容错：1）单次 Plan 内，HostAgent 会判断失败任务，如果有失败则触发 Replan，将失败信息和新需求一起发给 CopilotEngine 重新规划；2）最多 Replan 3 次（maxIterations=3）；3）如果超过最大迭代次数仍有失败任务，执行 ceChatSummary，让 LLM 基于已有的部分结果生成一个总结性回答作为兜底；4）HostAgent.cePlan 本身还有 3 次重试逻辑，应对 CopilotEngine 调用不稳定的情况。
