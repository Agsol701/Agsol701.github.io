GitHub 可用项目分析：单 Agent 与多 Agent 可观测性工具的实现、部署和选型

source: agent-observability-github-projects
Oct 12, 2026

写在前面

本文独立分析 GitHub 上可获取代码、具有接入或部署入口的 Agent（智能体）可观测性项目。重点是：仓库提供了什么、如何采集执行过程、如何支持多个 Agent、部署需要哪些组件，以及哪些限制会影响实际接入。

调研覆盖 8 个仓库，按 7 组方案逐项分析。事实来源为仓库源码、部署配置、示例和官方文档，核对日期为 2026-10-13。关键源码链接固定到本次读取的提交，便于后续复查。本文没有实际部署这些平台；“可用”表示发现了具体实现和使用入口，不表示已经通过生产环境验证。

先约定几个术语：LLM（Large Language Model，大语言模型）；SDK（Software Development Kit，软件开发工具包）；OTel（OpenTelemetry，开放遥测框架）；Trace（追踪链路）；Span（链路中的执行片段）。下面直接围绕项目展开。

一、项目范围与初步结论

1.1 哪些是完整平台，哪些是采集组件

项目 仓库提供的主要内容 多 Agent 证据入口 首轮试用定位

Phoenix + OpenInference 分析平台、独立埋点插件 CrewAI 多 Agent 示例与插件 本地分析和集成研究

二、Langfuse：完整平台，重点看图展示与部署成本

2.1 仓库实际提供什么

Langfuse 仓库包含 web/、worker/、共享包和部署配置；产品提供调用追踪、提示词管理、数据集与评估。它适合需要开发者共同检索、审阅执行记录的场景。

核对的 docker-compose.yml定义了 Web 服务、后台 Worker，以及 PostgreSQL、ClickHouse、Redis、MinIO。配置中的应用镜像使用主版本 4。

**部署判断：**本地试用有明确入口，但长期运行需要管理多种存储和后台服务。不能按“启动一个网页服务”的成本估算维护工作。

2.2 单 Agent 能看什么

可围绕一次任务组织模型调用、检索、工具与普通函数操作，再关联用户反馈。对单 Agent，主要价值是把多轮调用放回同一任务上下文，而不是逐条翻模型请求日志。官方仓库能力说明

2.3 多 Agent 的具体实现入口

官方 LangGraph Notebook包含协调者路由、多个执行 Agent 和嵌套执行示例，使用回调接入。集成教程

Agent 图有两种来源：框架集成提供的信息，以及根据观测类型、时间和嵌套关系推断的图。聚合视图将同名步骤合并，展开视图区分每次调用。Agent Graphs

**可用性判断：**已有清楚的多 Agent 接入示例与图展示机制。需要进一步验证的是跨队列、跨服务后的上下文，以及推断图是否符合真实业务依赖；不能仅凭图中存在连线就认定存在消息因果关系。

2.4 建议试用路线

先按仓库部署说明启动平台，接入一个单 Agent；再运行上述 Notebook 中的协调者示例。重点查看同一个工具连续执行三次时，展开视图能否区分三次参数和输出，再验证两个子 Agent 是否归属正确。

三、Phoenix + OpenInference：多 Agent 示例和埋点实现较容易对照

3.1 为什么把两个仓库放在一起

Phoenix 提供追踪查询、评估、数据集和实验界面；OpenInference 提供语义约定与框架埋点。两者组成完整分析链路，但采集层并不只能连接 Phoenix。Phoenix、OpenInference

Phoenix 的本地入口是：

1
2

pip install arize-phoenix
phoenix serve

这是官方 README的使用方式，本文未执行安装。仓库根目录的 Compose 配置包含 Phoenix 与 PostgreSQL，适合继续研究持久化部署。

3.2 单 Agent 与多 Agent 的源码证据

单 Agent 可以从模型、工具和普通操作埋点开始。多 Agent 则有明确的 CrewAI 示例目录，其中包含入口、路由、计算器和数据库查询模块；入口使用统一的框架埋点辅助函数。

OpenInference 的 CrewAI 插件说明给出了两种模式：

  • 默认包装 Python 方法，推荐用于普通 CrewAI 应用。
  • use_event_listener=True 从 CrewAI 事件总线构造观测，适用于执行通过事件暴露的集成环境。

事件监听模式默认也生成模型调用 Span；若已经对底层模型客户端埋点，可以通过 create_llm_spans=False 避免重复记录。这个配置直接影响 Token 用量统计是否重复，其中 Token 指模型处理输入输出的计量单元。

3.3 接入片段与边界

下面是配置好 trace_provider 后的接入片段，完整初始化见插件说明：

1
2
3

from openinference.instrumentation.crewai import CrewAIInstrumentor

CrewAIInstrumentor().instrument(tracer_provider=trace_provider)

**可用性判断：**示例、插件和分析平台分层清晰，适合研究“框架事件怎样变成 Trace”。但切换后端之后，能否获得相同展示效果仍需验证。

Phoenix 当前根目录为 Elastic License 2.0，其中限制向第三方提供具备其主要功能的托管服务。评估自用部署与对外提供服务时，应分别核对适用条件。

四、AgentOps：Agent、任务和工具层级明确，但应以源码核对旧示例

4.1 仓库完整度与部署

AgentOps 仓库既有 SDK，也包含 app/ 应用代码。官方应用说明列出后端、仪表盘、ClickHouse 与 Supabase，并提供 Docker Compose 配置。

**部署判断：**能自托管，不代表默认配置已经脱离所有外部服务。需要按实际环境配置认证、数据库和收集端点，不能只运行 SDK 初始化后就认为本地系统完整可用。

4.2 单 Agent 的实现

SDK 提供 agent、task、workflow、trace、tool 等装饰器。核对的装饰器定义中，旧 session 已标记弃用并转向 trace。

这也是实际接入中的注意点：README 中仍有旧会话用法，复制代码之前，应检查安装版本的源码与迁移说明。

4.3 多 Agent 的实现

CrewAI 埋点源码包装了以下执行入口：

包装对象 采集层级
Crew.kickoff 整组任务执行
Agent.execute_task Agent 执行任务
Task.execute_sync 任务执行
LLM.call 模型调用
工具执行方法 工具活动

实现还整理 Agent 标识、角色与任务输出，并将工具执行详情关联到 Agent Span。这比仅记录模型请求多了一层框架执行结构。

**可用性判断：**适合以角色和任务为中心定位故障。源码中的包装依赖框架方法路径，因此升级 CrewAI 后应重验；对并行、异步和跨进程的覆盖，本文没有运行验证，不据此承诺完整支持。

五、Opik：多 Agent 追踪可以接到评估实验，但部署组件较多

5.1 平台与部署结构

Opik 仓库提供追踪、评估与实验能力，平台采用 Apache-2.0 许可证。仓库包含应用代码、Python SDK 和部署脚本。

核对的 Compose 文件列出了 MySQL、Redis、ClickHouse、ZooKeeper、MinIO、应用前后端及若干辅助服务。部分服务取决于配置或启动组合，这不表示所有条目都会默认运行。

**部署判断：**官方提供启动脚本降低试用门槛，但生产维护需要理解数据库、对象存储和后台组件，不能把脚本简短等同于架构简单。

5.2 多 Agent 接入不是一句产品宣传

CrewAI 跟踪器源码包装 Crew、Agent 与 Task 方法，并调用 Flow、模型客户端和 LiteLLM 的补丁模块。

其中对 CrewAI 1.0.0 及以后版本的模型客户端补丁依赖传入 Crew 实例；因此接入通常写成：

1
2
3
4

from opik.integrations.crewai import track_crewai

track_crewai(project_name="agent-observability", crew=my_crew)
result = my_crew.kickoff()

my_crew 是应用已创建的 Crew 对象；该片段还需要事先完成 Opik 连接与模型配置。源码说明要求全局初始化一次，并提示不要同时使用其 OpenAI 跟踪器，以免模型调用和 Token 用量重复记录。

5.3 单 Agent 与多 Agent 的使用价值

单 Agent 可检查模型、工具和检索步骤，再把失败输入加入评估数据集。多 Agent 可以先查看 Crew 执行中的角色与任务，再对整个任务结果进行实验比较。官方能力与示例

**可用性判断：**适合需要把排障样本变成回归评估的团队。对于只想临时查看一条链路的个人项目，完整平台的维护成本可能超过需求；对多 Agent，应特别验证初始化位置与重复埋点问题。

六、OpenLIT：源码明确处理了 CrewAI 异步入口和线程上下文

6.1 部署与采集入口

OpenLIT 仓库包含平台与 SDK。核对的根目录 Compose 配置主要定义 ClickHouse 与 OpenLIT 两个服务，默认试用拓扑比前面某些平台更少。

应用可以通过 openlit.init() 初始化采集，配置 OTLP（OpenTelemetry Protocol，开放遥测协议）接收地址。平台还关注调用成本与资源指标。官方接入说明

6.2 多 Agent 源码中值得看的部分

CrewAI 集成入口列出了同步、异步和批量 Crew 启动方法，以及任务、工具、Flow 和独立 Agent 的执行入口。该提交声明的 CrewAI 依赖下限是 1.10.0。

实现中的 _ContextPropagatingDescriptor 专门处理线程执行时的上下文传递，目的是让子任务和工具 Span 保留正确的上级 Agent 或工作流关系。

**这一点有实际价值：**多 Agent 观测的常见故障不是“没有数据”，而是子任务有记录却挂错了父节点。该实现说明项目对具体框架中的这一问题做了处理；它仍不等于自动解决任意消息队列或跨主机传播。

6.3 可用性判断

单 Agent 可先验证模型与工具的采集；多 Agent 则重点测试同步与异步执行、并行任务、父子关系和重复模型记录。仓库也提供 CrewAI 示例。

**本文建议：**对已经采用 OTel、又希望有独立平台的团队，OpenLIT 值得进入首轮测试。源码依赖框架内部方法，应固定兼容版本后再评价稳定性。

七、OpenLLMetry：有专门的多 Agent 框架埋点，适合接已有后端

7.1 它实际提供什么

OpenLLMetry主要提供 OTel 埋点组件与 Traceloop SDK。模型、数据库或框架数据可以发送到兼容后端；仓库本身不等同于一套完整的业务分析平台。

已有后端时，这种定位减少了重复建设。没有后端时，则还需要解决存储、查询和展示。

7.2 多 Agent 能力不能只归类为模型调用采集

仓库具有独立的 CrewAI 包，不是只能追踪底层模型。

核对的实现包装 Crew.kickoff、Agent.execute_task、Task.execute_sync、LLM.call，分别生成不同层级的执行记录，并包含耗时与用量指标处理。该提交声明 CrewAI 1.0.0 及以上依赖。

示例位于 crewai_example.py。

7.3 可用性判断

**适合：**已有 OTel 采集、存储和查询链路，希望增加模型与 Agent 框架信息的团队。

**要补验：**所用后端是否理解 Agent 与 Task 属性，是否能按角色、任务和调用层级检索。当前查看的包装列表不足以证明所有异步入口、工具路径都覆盖；不能将未查到某种包装直接写成全项目不支持，也不能反过来假定全部支持。

八、AgentSight：独立分析机器上的 Agent 活动

8.1 这个仓库解决的问题

AgentSight提供本地会话、进程、文件和网络活动的观测入口。它适合检查编程 Agent 启动了什么子进程、访问了哪些文件，以及时间与资源消耗在哪里。

其系统层模式使用 eBPF（extended Berkeley Packet Filter，扩展伯克利包过滤器）与 TLS（Transport Layer Security，传输层安全协议）调用边界追踪。当前实现同时支持读取 Agent 原生会话文件。固定提交 README

8.2 使用入口与平台条件

官方提供以下入口，本文未执行安装与录制：

1
2
3

cargo install agentsight
agentsight top
agentsight report --local

原生会话模式可用于 Windows、macOS 和 Linux；eBPF 录制需要满足 Linux 内核与权限要求。它们采集的信息范围不同，因此在 macOS 上读取会话记录，不能称为完成了 Linux 内核级观测验证。

8.3 单 Agent 与多 Agent 的实际边界

单 Agent 场景可以关联执行步骤与机器活动。多个 Agent 同时运行时，可以从会话和进程角度观察活动；但进程父子关系不等同于业务中的任务委派关系。

**可用性判断：**应作为应用级观测的补充工具，单独验证目标 Agent 的会话格式与录制环境。若核心需求是跨服务多 Agent 的任务分配与消息追踪，仅靠系统活动记录还不够。

九、横向比较：怎样决定先试哪一个

9.1 按实际需求选首轮候选

下面是依据源码与部署结构做出的工程判断，未做统一跑分。

当前情况 首轮候选 原因 优先核验
从零搭建追踪与反馈平台 Langfuse 平台与多 Agent 图入口完整 图关系、存储维护
本地分析、研究框架埋点 Phoenix + OpenInference 平台和插件分开，示例清楚 插件模式、重复 Span
CrewAI 角色与任务排障 AgentOps、OpenLIT 有明确的 Agent/Task 实现 版本、异步与并发

9.2 多 Agent 支持应当怎么读

本次源码检查得到的较强证据，是 Crew、Agent、Task 等框架入口已有包装，或存在实际多 Agent 示例。对任意跨进程、自定义队列、动态任务恢复的完整支持，本文没有足够证据给任何项目直接打满分。

建议用同一个小应用测试两个候选：两个 Agent，一次任务委派，一个并行工具调用，以及一次可控失败。不要同时启用多个自动埋点库，否则重复数据会干扰比较。

检查项 应看到的具体结果
两个同名 Agent 同时运行 执行实例不串线
工具第一次失败、第二次成功 两次参数、结果与错误记录可区分
子 Agent 在线程中运行 工具记录归到正确的父执行
模型调用被多层框架包装 没有重复计费统计
跨进程发送任务 接收端保留可检索的上游关联
观测后端短暂不可用 可明确衡量对业务与数据完整性的影响

9.3 读源码之后最值得保留的结论

项目是否可用，首先取决于它能否覆盖当前应用的真实执行路径。此次检查发现的版本下限、装饰器弃用、线程传播和模型客户端补丁，比“支持多 Agent”这个功能标签更能指导接入。

完成上述最小验证，再比较资源占用、检索体验和维护成本。本文的仓库分析可以作为候选清单，不能替代对实际业务版本的集成测试。
