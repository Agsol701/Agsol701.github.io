merge 和 rebase 的区别

git pull origin main 和 git pull --rebase origin main 都能把远程代码拉到本地，但它们处理分叉历史的方式完全不同。

假设当前提交历史如下：

1
2
3

A---B---C  origin/main
     \
      D---E  main
  • C 是远程分支上的新提交
  • D、E 是你本地分支上的提交
  • 这时本地和远程都向前发展了，历史出现分叉

执行 git pull origin main 时，Git 通常会采用 merge：

1
2
3

A---B---C---------M  main
     \           /
      D---E-----'
  • Git 会创建一个新的合并提交 M
  • 原来的 D、E 仍然保留，提交 ID 不变
  • 历史保留了“先分叉、再合并”的轨迹
  • 优点是不会改写已有提交
  • 缺点是提交图可能变复杂，出现额外的 merge commit

执行 git pull --rebase origin main 时，Git 会采用 rebase：

1

A---B---C---D'---E'  main
  • Git 会先拿到远程最新提交 C
  • 再把本地的 D、E 重新应用到 C 后面
  • 因为是重新生成，提交会变成新的 D'、E'
  • 优点是历史线性、简洁，更适合查看日志
  • 缺点是会改写本地提交历史

可以简单理解为：

  • merge：保留分叉，然后增加一个合并点
  • rebase：不保留分叉，把本地提交“搬到”远程最新提交后面

日常建议：

  • 个人功能分支同步主分支时，优先使用 rebase
  • 公共分支或多人共享分支，优先使用 merge
  • 如果本地提交已经推送并被他人依赖，再做 rebase 要谨慎

2.9 超大文件管理

Git 适合管理源码、文档和中小型文件，但并不适合频繁变更的大二进制文件。
如果把模型文件、视频、压缩包、数据库备份这类超大文件直接放进 Git 历史，通常会带来几个问题：

  • 仓库体积迅速膨胀
  • clone、pull、checkout 变慢
  • 大文件每次修改都可能生成新的历史版本
  • 多人协作和 CI 拉取成本明显增加

方案一：大文件不进 Git

如果文件本身不是源码的一部分，最稳妥的做法通常是把它放到外部存储中，例如：

  • 对象存储：S3、OSS、COS
  • 制品仓库：Nexus、Artifactory
  • 发布平台：GitHub Releases

Git 仓库中只保留：

  • 下载脚本
  • 文件版本号
  • 校验值
  • 使用说明

这种做法最适合：

  • 数据集
  • 训练模型
  • 视频资源
  • 备份文件
  • 构建产物

方案二：使用 Git LFS

如果大文件需要和代码一起版本管理，可以使用 Git LFS（Large File Storage）。

它的核心思路是：

  • Git 仓库中只保存一个轻量的指针文件
  • 真正的大文件内容交给 LFS 后端存储
  • 使用方式仍然接近普通 Git

常见用法如下：

适合使用 Git LFS 的场景：

  • 模型权重
  • 设计稿
  • 音视频素材
  • 需要保留多个版本的大型二进制资源

方案三：源码和产物分离

很多团队会犯一个常见错误：把构建后的产物直接提交到源码仓库，例如：

  • dist/
  • build/
  • .tar.gz
  • .jar
  • .exe

更合理的做法是：

  • 源码进入 Git
  • 产物进入制品仓库或发布平台

这样可以避免源码仓库逐渐演变成“文件仓库”。

已经误提交大文件怎么办

如果大文件已经提交过，仅仅把它加入 .gitignore 是不够的，因为历史中仍然保存着这个文件。

这时需要清理历史，常见工具有：

  • git filter-repo，推荐
  • BFG Repo-Cleaner

示例：删除某个误提交的大文件

1

git filter-repo --path big-file.zip --invert-paths

示例：删除某一类大文件

1

git filter-repo --path-glob "*.mp4" --invert-paths

清理历史后通常还需要强制推送：

1
2

git push --force --all
git push --force --tags

注意：

  • 这会改写 Git 历史
  • 团队成员需要重新同步仓库
  • 对共享仓库必须提前沟通

Hugging Face 如何管理大文件

Hugging Face 的做法本质上也是 Git + 大文件后端存储，只是它针对模型文件和数据集这类超大二进制文件做了更深的优化。

可以把它理解为两层：

  • Git 仍然负责版本管理、提交历史和仓库结构
  • 真正的大文件内容交给专门的大文件存储系统处理

在 Hugging Face Hub 中，传统方案主要依赖 Git LFS：

  • 仓库中保存的是 pointer file（指针文件）
  • .gitattributes 用来声明哪些文件走大文件存储
  • 实际的模型权重、数据集文件存放在远端对象存储中

这种模式和通用 Git LFS 的思路是一致的，也就是：

  • Git 不直接管理超大文件本体
  • Git 只管理“这个版本对应哪一个大文件对象”

不过 Hugging Face 近年正在把一部分仓库迁移到 Xet 存储后端。

Xet 和传统 Git LFS 最大的区别在于去重粒度：

  • Git LFS 更接近文件级管理
  • Xet 会把大文件拆成更小的数据块，再做分块级去重

这意味着：

  • 如果一个超大模型文件只改动了一小部分
  • 使用传统 LFS 时，往往需要重新上传整个文件版本
  • 使用 Xet 时，只需要上传发生变化的那部分数据块

对于模型权重、Parquet 数据集、GGUF 文件这类超大文件，这种方式会更节省上传时间、下载流量和存储空间。

所以，如果把 Hugging Face 的方案和前面的通用方案对应起来，可以这样理解：

  • 基础层面：它符合“使用 Git LFS 管理大文件”的思路
  • 进阶层面：它在此基础上进一步使用 Xet 做更细粒度的分块去重优化

对使用者来说，日常工作流通常还是比较接近 Git：

  • 提交仓库元数据和 pointer
  • 大文件由后端单独存储
  • 下载和上传时由 Hub 帮你完成实际的大文件传输

这也是为什么 Hugging Face 能在保留 Git 工作流的同时，管理几十 GB 甚至更大的模型和数据集文件。

实用建议

  • 尽量不要把几十 MB 以上且频繁变化的二进制文件直接提交到 Git
  • node_modules/、日志文件、缓存文件、导出产物应加入 .gitignore
  • 大模型、数据集、媒体资源优先考虑对象存储或 Git LFS
  • 构建产物优先放到 Release 或制品仓库
  • 定期检查仓库大小和对象数量

可以使用下面的命令做基本检查：

1

git count-objects -vH

如果仓库已经明显变大，还可以结合 git-sizer 分析历史膨胀原因。

┌─────────────────────────────────────────────────────────────────┐
│                      Git 合并原理                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   1. Fast-forward 合并                                          │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  main: A ──► B ──► C                                    │   │
│   │  feature:         D ──► E                              │   │
│   │                                                             │   │
│   │  合并后: main: A ──► B ──► C ──► D ──► E               │   │
│   │  (只需移动 main 指针)                                    │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│   2. 三方合并                                                   │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  base: A ──► B ──► C (共同祖先)                        │   │
│   │           │           │                                 │   │
│   │           ▼           ▼                                 │   │
│   │  main:    D ──► E   (当前分支)                         │   │
│   │  feature: F ──► G   (要合并的分支)                      │   │
│   │                                                             │   │
│   │  合并: 比较 C, E, G                                      │   │
│   │       解决冲突                                            │   │
│   │       创建新提交 H                                        │   │
│   │                                                             │   │
│   │  结果: A ──► B ──► C ──► D ──► E ──► F ──► G ──► H    │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│   3. 变基原理                                                   │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │  原始:                                                    │   │
│   │  main: A ──► B ──► C                                    │   │
│   │  feature:       D ──► E                                 │   │
│   │                                                             │   │
│   │  git rebase main 后:                                    │   │
│   │  main: A ──► B ──► C ──► D' ──► E'                     │   │
│   │                                                             │   │
│   │  原理:                                                    │   │
│   │  1. 保存 D, E 的 patch                                   │   │
│   │  2. 移动 feature 到 C                                   │   │
│   │  3. 重新应用 patch                                       │   │
│   │  4. 产生 D', E' (新的 SHA)                              │   │

特性 Git SVN
架构 分布式 集中式

Q3: 什么是分支？

分支是指向某个提交的指针，本质是一个文件，存储提交的 SHA-1 值。创建分支只是创建一个新指针，不影响原有提交。

原理相关

Q4: Git 如何保证数据完整性？

  • 使用 SHA-1 哈希算法
  • 每个对象都有唯一哈希值
  • 任何内容变化都会导致哈希变化
  • 哈希冲突概率极低

Q5: 什么是 SHA-1？

SHA-1 是 Git 用来标识对象的哈希算法，生成 40 位十六进制字符串。两个不同的内容产生相同哈希的概率极低，保证 Git 数据的完整性和去重。

Q6: Git 对象有哪些类型？

  • Blob：存储文件内容
  • Tree：存储目录结构
  • Commit：存储提交信息
  • Tag：存储标签信息

Q9: git fetch 和 git pull 的区别？

  • git fetch：拉取远程更新，但不会合并

Q10: 什么是 Fast-forward？

当目标分支是当前分支的直接祖先时，合并只需移动指针，不需要创建新提交。可以通过 --no-ff 禁用。
