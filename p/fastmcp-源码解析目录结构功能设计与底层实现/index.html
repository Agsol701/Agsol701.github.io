FastMCP 源码解析：目录结构、功能设计与底层实现

May 03, 2026

写在前面

如果你想系统学习：

  • Python 里怎么开发 MCP server
  • 一个高层 MCP 框架怎么设计
  • 工具、资源、提示模板是怎么被封装出来的

那么 PrefectHQ/fastmcp 是一个非常适合读源码的项目。

它的价值不只在于“能快速写一个 server”，更在于它把 MCP 开发里最常见的几类问题都整理成了统一框架能力：

  • server 生命周期
  • tool / resource / prompt 注册
  • schema 自动生成
  • transport 适配
  • context 注入
  • auth / proxy / composition

所以这篇文章的重点不是介绍怎么安装 fastmcp，而是回答三个更关键的问题：

  1. 这个项目的目录结构是怎么组织的
  2. 它到底帮开发者封装了哪些能力
  3. 它底层是怎样把 Python 函数变成 MCP 能力的

一、先给 FastMCP 一个定位

如果只用一句话概括：

FastMCP 是一个面向 Python 开发者的高层 MCP 框架，用来降低开发 MCP server 和 MCP client 的复杂度。

这句话里最重要的是“高层框架”。

也就是说，它不是在和 MCP 协议竞争，而是在 MCP 协议之上提供一层更适合 Python 开发者的抽象。

它主要做了几件事：

  • 把协议注册过程变成 Python 装饰器
  • 把参数 schema 生成变成类型标注推导
  • 把上下文能力变成 ctx
  • 把 transport、server、client、proxy 等能力收敛进统一接口

所以从学习视角看：

  • 如果你想先快速建立“怎么写 MCP”直觉，先看 fastmcp
  • 如果你想理解官方协议边界，再回头看官方 python-sdk

二、从目录结构理解这个项目

读这类框架仓库，最忌讳一上来就平铺看所有文件。

更高效的方式，是先按职责给目录分层。

2.2 先看仓库根目录各自承担什么职责

README.md

这是项目入口。

一般会承担这些职责：

  • 介绍框架定位
  • 给最小示例
  • 说明安装方式
  • 引导你进入文档或 examples

它适合拿来建立第一印象，但不适合替代源码阅读。

pyproject.toml

这是 Python 项目的工程入口之一。

它通常会暴露很多对读源码有帮助的信息，例如：

  • 包名
  • Python 版本要求
  • 核心依赖
  • 可选依赖
  • CLI 入口

很多人读源码会忽略这个文件，但它其实很适合用来快速判断：

  • 项目依赖哪些底层库
  • 是否支持多种运行形态
  • 包结构大概怎样组织

examples/

这是最适合从“使用者视角”切入的目录。

它告诉你的不是底层细节，而是：

  • 框架希望你怎么写代码
  • 最常见的能力组合是什么
  • 哪些 API 是作者主推的

tests/

这是非常值得看的目录。

因为测试最能暴露作者真正关心的行为边界，例如：

  • tool 注册是否正确
  • schema 生成是否稳定
  • transport 行为是否一致
  • context 注入是否符合预期

很多时候，测试比文档更接近真实设计意图。

src/fastmcp/

这是最核心的源码目录。

如果你只想抓主干，绝大多数时间都应该放在这里。

2.3 再看 src/fastmcp/ 里的核心模块分工

这一层可以把它理解成“框架内核”。

server/

这是最核心的目录之一。

它通常负责：

  • 定义 FastMCP 或 server 主对象
  • 维护注册表
  • 管理生命周期
  • 对接 transport
  • 把请求路由到具体能力

如果你只想回答“FastMCP 到底是什么对象”，先看这里。

client/

这一层通常负责：

  • 连接远端或本地 MCP server
  • 发送请求
  • 接收响应
  • 封装 Python 侧 client 调用体验

这说明 fastmcp 不是只想帮你写 server，它也在构建 client 侧抽象。

tools/

这一层主要负责 tool 相关能力。

通常可以期待在这里看到：

  • tool 定义
  • tool 注册
  • 参数提取
  • 调用包装
  • 返回值处理

如果你最关心 @mcp.tool() 背后做了什么，这一层最值得看。

resources/

这里负责 resource 相关抽象。

重点通常包括：

  • resource 注册
  • resource URI 或标识组织
  • resource 读取逻辑
  • resource 内容封装

这一层特别适合理解 MCP 里的上下文供给。

prompts/

这里负责 prompt 模板能力。

如果项目把 prompts 单独拆出来，说明作者已经明确把它当成和 tools、resources 并列的一等能力，而不是随手附加的功能。

context/

这是很有框架味道的一层。

它通常负责：

  • 运行时上下文对象
  • 日志、进度、资源访问等辅助能力
  • tool 执行时的上下文注入

如果你想知道 ctx 为什么能存在、能做什么，就重点看这里。

transport/

这里一般负责通信层。

常见职责包括：

  • stdio 适配
  • HTTP 或 streamable HTTP 适配
  • 输入输出消息传递
  • 协议消息与底层连接解耦

这部分更接近“运行时基础设施”。

auth/

这部分负责认证、鉴权或安全相关封装。

它说明项目并没有把自己局限在“本地 demo 工具”层面，而是在考虑更真实的服务接入场景。

proxy/

这一层通常负责 server 间转发或代理能力。

这在复杂系统里很常见，比如：

  • 一个上层 server 代理多个下层 server
  • 把已有 MCP server 再次包装

composition/

这一层通常负责组合多个能力源。

它适合处理：

  • 多 server 聚合
  • 多模块拼装
  • 统一对外暴露能力

utilities / models / schema

这些目录名可能会因版本略有不同，但职责通常比较稳定：

  • 工具函数
  • 内部数据模型
  • schema 转换
  • 类型辅助

这部分通常不是最先读的，但它们往往支撑着上面所有高层 API。

2.4 第一层：examples

这是最适合入门的目录。

它通常承担两个作用：

  • 展示最小可运行示例
  • 展示特定能力的组合用法

如果你第一次读 fastmcp，建议先看这里，而不是直接扎进底层实现。

因为 examples 能快速回答几个问题：

  • 一个最小 server 长什么样
  • 一个 tool 是怎样暴露的
  • resource / prompt / context 是怎么被使用的

2.5 第二层：核心 server 抽象

这一层通常是整个项目最重要的部分。

你要重点关注：

  • FastMCP(...) 是在哪里定义的
  • server 对象初始化时收集了哪些能力
  • run() 最后做了哪些事情

这一层回答的是：

一个 Python MCP server 在框架里到底被抽象成了什么对象。

2.6 第三层：tool / resource / prompt 的注册逻辑

这部分是 MCP 开发体验的核心。

因为开发者最常写的就是：

  • @mcp.tool()
  • @mcp.resource()
  • @mcp.prompt()

所以你要重点看：

  • 装饰器是怎样把函数注册到 server 里的
  • 函数元信息怎样被提取
  • docstring 和类型标注怎样变成工具描述

这一层是把“Python 语法”翻译成“协议能力”的关键桥梁。

2.7 第四层：schema 与数据模型

这里要重点看两类东西：

  • 输入参数 schema 怎么生成
  • 返回结果怎样被转成模型或客户端可理解的结构

MCP 场景下，schema 非常重要，因为：

  • 模型依赖 schema 决定怎么调用工具
  • host 依赖 schema 校验参数
  • server 依赖 schema 约束输入

所以对 fastmcp 来说，schema 不是附属功能，而是核心能力。

2.8 第五层：transport 与 runtime

这一层回答的是：

  • server 最终怎么和 client 通信
  • 支持哪些传输模式
  • 消息是怎样被送进 server，再被路由到具体能力上的

一般来说，这部分会涉及：

  • stdio
  • HTTP / streamable HTTP
  • 长连接或事件流相关适配

这层对业务开发者未必是最先要看的，但对理解底层实现非常重要。

2.9 第六层：auth / proxy / composition

这是 fastmcp 比较有框架味道的地方。

它不只是帮你写一个最小 server，还考虑了更复杂的工程场景，例如：

  • 认证
  • 代理
  • server 组合
  • 多能力拼装

这一层说明它的目标不是 demo，而是尽量把 MCP 的真实工程问题也纳入框架能力。

三、FastMCP 的核心功能到底有哪些

3.1 最核心能力：把 Python 函数变成 MCP 工具

这是整个项目最直观的能力。

例如开发者写：

1
2
3
4
5
6
7
8
9

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo")


@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b

框架要帮你做的，不只是“记住这个函数”，而是要进一步完成：

  • 注册 tool 名称
  • 提取 tool 描述
  • 推导输入参数 schema
  • 推导返回值结构
  • 在运行时把调用请求路由到这个函数

所以 @mcp.tool() 的本质不是语法糖，而是一整个注册流程的入口。

3.2 第二个核心能力：暴露 resource

resource 和 tool 的区别在于：

  • tool 偏“动作执行”
  • resource 偏“上下文读取”

fastmcp 通过 @mcp.resource() 这类抽象，让开发者可以把：

  • 文件
  • 配置
  • 某类可查询对象
  • 动态生成的内容

作为标准资源暴露出去。

这对代码助手、知识库助手、企业内部助手都很重要。

3.3 第三个核心能力：暴露 prompt

这部分很多人容易忽略，但它非常能体现 MCP 的完整性。

通过 @mcp.prompt()，框架不仅能暴露“能执行什么”，还能暴露“该怎么组织任务提示”。

这意味着 server 不只是一个工具盒子，也可以成为一组任务模板的提供方。

3.4 第四个核心能力：context 注入

这是 fastmcp 一个很值得学习的点。

在简单示例里，tool 看起来像普通函数。

但实际工程里，tool 往往需要额外能力，比如：

  • 读其他 resource
  • 报告进度
  • 写日志
  • 获取请求上下文
  • 调宿主提供的能力

所以框架需要一个统一上下文对象，这就是 ctx 这一类抽象存在的意义。

这部分的重要性在于：

它让工具函数从“静态函数”变成“运行时参与者”。

3.5 第五个核心能力：client / proxy / composition

这是为什么 fastmcp 不只是一个 server helper。

它还会进一步考虑：

  • MCP client 怎样封装
  • 不同 server 之间怎样代理
  • 多个能力怎样组合

这对复杂 agent 系统很有用。

因为在真实项目里，你常常不是写一个孤立 server，而是要处理：

  • 多个 server
  • 多个能力域
  • 多层转发
  • 多种 transport

四、从使用体验反推底层实现

框架源码最适合用“从表及里”的方式看。

也就是说，先看开发者怎么用，再反推底层做了什么。

4.1 FastMCP(...) 背后做了什么

当你创建：

1

mcp = FastMCP("demo")

底层通常至少要准备这些事情：

  • 创建 server 容器对象
  • 初始化 registry
  • 初始化 tool / resource / prompt 集合
  • 初始化 transport / runtime 配置
  • 记录 server 元信息

所以这一步表面看很简单，实际上是在搭一个协议运行壳。

4.2 @mcp.tool() 背后做了什么

这个装饰器背后通常会经历：

  1. 拿到函数对象
  2. 读取函数名
  3. 读取类型标注
  4. 读取 docstring
  5. 生成 tool 描述和 schema
  6. 把函数注册到工具表
  7. 生成运行时 handler

这里最有技术含量的地方通常是：

  • Python 类型系统和 schema 的映射
  • docstring 提取
  • 参数绑定与校验

因为如果这些地方处理得不好，工具虽然“能跑”，但模型并不好用。

4.3 为什么自动 schema 生成很重要

因为 MCP 的工具不是给人手写 CLI 用的，而是要被模型理解。

模型能否稳定使用工具，很大程度取决于：

  • 参数名字是否清楚
  • 类型是否准确
  • 必填项是否明确
  • 描述是否可读

所以 fastmcp 的自动 schema 生成，不只是提升开发效率，更是在提升模型调用稳定性。

4.4 runtime 路由链路大致是什么

当 client 发来一次工具调用时，框架内部大致要经历：

  1. 收到 MCP 请求
  2. 解析请求类型
  3. 找到目标 tool
  4. 校验参数
  5. 构造上下文对象
  6. 调用 Python 函数
  7. 处理返回值
  8. 封装为 MCP 响应

这条链路说明一个关键点：

框架的本质工作，不是“帮你写函数”，而是“把函数接进协议运行时”。

五、读 FastMCP 源码时最值得抓的几条线

5.1 第一条线：入口和 server 生命周期

重点问题：

  • server 是怎么创建的
  • registry 是怎么初始化的
  • run() 到底做了什么
  • 什么时候开始真正监听或处理请求

这条线帮你建立全局骨架。

5.2 第二条线：装饰器注册链

重点问题：

  • tool / resource / prompt 分别怎么注册
  • 注册时保留了哪些元信息
  • 这些元信息最后怎样被暴露给 client

这条线直接决定开发体验。

5.3 第三条线：类型系统到 schema 的映射

重点问题：

  • int、str、list[str]、dict 这类类型怎样变成 schema
  • optional / default value 怎样表示
  • 返回值是怎样被包装的

这条线是理解“为什么 Python 写法能自动变成 MCP 能力”的关键。

5.4 第四条线：context 注入机制

重点问题：

  • ctx 是什么时候创建的
  • ctx 里有哪些能力
  • 为什么某些工具函数能读 resource、报进度或写日志

如果这条线读明白了，你对 fastmcp 的理解会明显比“只会写装饰器”更深。

5.5 第五条线：transport 与协议边界

重点问题：

  • stdio 与 HTTP 入口有什么差异
  • 哪部分是 FastMCP 的高级封装
  • 哪部分已经接近 MCP 协议原语

这条线很适合和官方 python-sdk 对照着看。

六、FastMCP 对开发者最大的价值是什么

我觉得主要有四点。

6.1 开发体验非常顺

对 Python 开发者来说，装饰器 + 类型标注的组合非常自然。

6.2 把样板代码压得很低

你不需要一开始就手写大量协议注册和 schema 定义代码。

6.3 便于逐步进阶

可以先从最小 server 开始，再逐步接触：

  • resource
  • prompt
  • context
  • transport
  • auth
  • proxy

6.4 特别适合做学习入口

很多人如果一上来就只读底层协议实现，很容易“知道很多术语，但不会写 server”。

而 fastmcp 的优势在于：

你可以先把 server 写出来，再回头理解协议分层。

七、FastMCP 的局限和阅读时要注意的点

7.1 它是高层框架，不等于协议本身

读这个项目时要始终记住：

  • FastMCP 是开发框架
  • MCP 是协议标准

不要把框架 API 误认为协议原语。

7.2 开发体验好，意味着抽象会更厚

抽象越友好，越要主动去问：

  • 这些便利背后做了什么
  • 哪些能力是框架帮我补的
  • 如果不用框架，协议层应该怎么表达

7.3 真实生产环境还会有更多问题

例如：

  • 认证与鉴权
  • 多租户
  • 超时控制
  • 观测性
  • 灰度发布

这些不一定能只靠框架默认能力完全解决。

八、建议怎样读这个仓库

一个比较稳的顺序是：

  1. 先看 examples
  2. 再看 FastMCP(...) 的定义和入口
  3. 再看 tool / resource / prompt 注册逻辑
  4. 再看 context 与 schema 生成
  5. 最后再看 transport、proxy、composition

如果你是为了写自己的 Python MCP server，这个顺序通常会比较顺手。

小结

如果只用一句话总结：

FastMCP 最值得学习的地方，不只是它让你“更快写出一个 MCP server”，而是它很好地展示了“如何把 Python 开发体验和 MCP 协议能力连接起来”。

所以它非常适合作为：

  • Python MCP 入门源码
  • 高层框架设计案例
  • “函数如何变成协议能力”的学习样本
