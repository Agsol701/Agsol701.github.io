什么是 Skills：概念、使用方式、开发方法、底层原理与常见面试题

Jun 11, 2026

写在前面

最近在使用 Claude Code、Cursor、Ducc 这类命令行 / IDE 研发 Agent 时，“Skills"这个词出现得越来越频繁。

很多人第一次接触 Skills，会把它和：

  • Prompt 模板
  • System Prompt
  • MCP（Model Context Protocol）
  • Tools / Function Calling
  • Agent / Subagent
  • Slash Command
  • Plugin

混为一谈。

但 Skills 实际上是一个有明确边界的概念。

如果用一句话先做总定义：

Skills 是一种按需加载、可被模型自主发现并使用的"任务方法包”，它把"做某一类任务的方法、流程、约束、参考资料"封装成一组文件，让 Agent 在合适的时机自动取用。

它解决的核心问题是：

  • 怎么把"经验和方法"喂给模型，而不是每次都靠用户在 prompt 里反复说
  • 怎么避免一次性把所有方法塞进 system prompt，把上下文撑爆
  • 怎么让"团队最佳实践"和"工具能力"一起被 Agent 复用

下面分十个部分，把 Skills 从概念到落地讲清楚。本文使用 Claude Code 的 Skills 实现作为例子，因为它是目前 Skills 形态最完整、最具代表性的实现。

文中术语首次出现时给出全称，后续直接使用缩写。常见缩写包括 LLM、SOP、MCP、IDE、CLI、YAML、MD、DSL、SDK、SP（System Prompt）。

1. Skills 是什么

1.1 一句话定义

Skills 是 Agent 用的"按需加载的方法书"。

每一个 Skill 都是一组文件（通常以一个 SKILL.md 为入口），里面写清楚了：

  • 这个 Skill 是干什么的
  • 什么时候该用它
  • 用它的时候要按什么步骤做
  • 有哪些约束和注意事项
  • 可以参考哪些脚本、模板、示例文件

模型在执行任务时，会先读 Skill 的"摘要信息"，判断当前任务是否需要它；只有需要时，才会加载完整内容。这就是 Skills 最核心的设计点：渐进式披露（Progressive Disclosure）。

1.2 它本质上是什么

从工程视角看，Skills 本质上是：

一组结构化的、带元信息的、可被 Agent 检索和加载的 Markdown 文档（外加可选的辅助文件）。

它不是：

  • 一段预先固定写进 system prompt、整段会话始终在线的提示词
  • 一个注册到模型的工具
  • 一段 Python 代码
  • 一个独立运行的服务

它更像是：

  • 一本"工作手册"
  • 一份"作业指导书（SOP）"
  • 一个"领域 Wiki 的入口页"

只不过这本手册的读者不是人，而是 Agent。

1.3 它在 Agent 体系里的位置

重要前提：在当前的 Claude Code 实现里（截至 2026 年 6 月），“Slash Command” 和 “Skill” 已经合并为同一个概念。官方文档原文：

“Custom commands have been merged into skills. A file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and work the same way.”

也就是说，它们不是不同的层 —— 同一个 Skill 既能被模型自动触发（看 description），也能被用户用 /skill-name 显式触发，还能用 disable-model-invocation / user-invocable 控制只允许其中一种。所以下面这张层次图把它们归为同一层。

一个研发 Agent 从收到用户输入到最终给出结果，中间会经过若干层。从靠近用户意图到靠近模型/系统，自上而下排列：

层次（自上而下） 作用 例子
① Skills（含 Slash Command） 方法/策略层：这类任务该按什么流程做。模型自动触发或用户用 /skill-name 显式触发 write-pr-description、code-review、/deploy
② Subagent 任务调度层：是否拆出独立子上下文执行（可由 Skill 通过 context: fork 触发） general-purpose、Explore、Plan
③ MCP 协议层：把外部能力按标准方式接进来 MCP Server / Client
④ Tools 能力执行层：模型实际调用的原子动作 Read、Bash、Edit
⑤ 模型 底层推理引擎 Claude Opus、Sonnet、Haiku

用户输入会大致按 ①→②→③→④→⑤ 的方向被解释和下沉，结果再反向上浮回到用户。

此外有两个横切关注点，不在这条主路径上：

横切 作用 例子
Plugin 把上面任意几层（Skills、MCP Server、subagent、hooks 等）打包分发 一个企业内部研发插件包
CLAUDE.md 项目记忆：会话开始就永久加载的"事实型"指令（与 Skills 互补，详见 1.4 节） 项目架构、命名约定、强制规范

Skills 处在第 ① 层 —— 它比 Tools/MCP 更靠近用户意图（关心"这类任务怎么做"），又比模型本身更具结构（不是泛泛的提示词，而是一个有元信息、可被检索、可触发独立子上下文的实体），是夹在"用户意图"和"执行链路"之间的方法层。

由此也能推出 Skills 与三个最容易混淆概念的相对关系：

  • 它比 Tools 更宏观：Tools 关心"调一次能做什么"，Skill 关心"一类任务怎么完成"
  • 它比 system prompt / CLAUDE.md 更动态：SP 和 CLAUDE.md 是会话开始就固定加载的，Skills 是按需注入的
  • 它和 Subagent 可以组合：Skill 通过 context: fork 可以让自己跑在独立 subagent 上下文里，反过来 subagent 也可以预加载若干 Skill

1.4 Skills 与 CLAUDE.md 的边界

这是初学者最容易踩进去的混淆区：“我想要一份跟随整个项目生命周期、永远生效的指令，是不是应该写成一个 always-on 的 Skill？”

答案是：不应该。那个东西不是 Skill，是 CLAUDE.md（项目记忆）。两者是分工关系，不是同一种东西的两种模式。

1.4.1 一张表看清差异

对比维度 CLAUDE.md（项目记忆） Skills
加载时机 会话开始就永久加载 按需注入
占用上下文 全程占用 命中时才占用
关心什么 “这个项目的固定事实和规范”（架构、目录、命名、约束） “做某一类任务的方法”（写 PR、code review）
写多了的代价 直接吃掉 context window 几乎零成本（仅占元信息）
维护粒度 一份大文件 多个独立小文件

判断口诀：

永远要遵守的 → 写进 CLAUDE.md；某类任务才用得上的 → 写成 Skill。

举例：

  • “本项目数据库统一用 PostgreSQL，禁用 MySQL 特有语法” → CLAUDE.md（永远成立）
  • “写 PR 描述时按 5 段式来” → Skill（只在写 PR 时用）
  • “本项目 Python 入口都在 app/main.py” → CLAUDE.md
  • “做 SQL review 时按三维度走” → Skill

1.4.2 Skills 里其实也有"始终在线"的部分 —— 是元信息

Skills 整体是按需加载的，但每个 Skill 的 name + description会被 Agent 启动时一次性扫进上下文，因为模型必须看得见这份"目录"才知道有哪些 Skill 可调。

1.4.3 一个工程细节：Skill 命中后会"粘"在当前会话

官方文档对这件事有非常精确的定义（Skill content lifecycle）：

“When you or Claude invoke a skill, the rendered SKILL.md content enters the conversation as a single message and stays there for the rest of the session. Claude Code does not re-read the skill file on later turns…”

“Auto-compaction… re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens.”

翻译成大白话：

  • 同一会话内：Skill 一旦被加载，它的内容就以一条消息的形式留在上下文里，直到会话结束。Claude Code 不会重复读 SKILL.md 文件，所以请把"全程要遵守的"内容写成常驻指令而不是一次性步骤。
  • 上下文压缩后：当上下文被自动压缩，每个 Skill 的最近一次调用会保留前 5,000 tokens，所有 Skill 的"压缩后保留"共享一个 25,000 tokens 的总预算，按"最近调用优先"分配。如果一个会话里调用过很多 Skill，老的可能会在压缩时被整个丢掉。
  • 新会话：上下文清空，Skill 又回到"只有 metadata 在线、正文不在线"的状态。

所以从用户视角看，Skill 在单次会话内是"半永久"的，但跨会话不是。这正是 Skills 的设计意图：每次会话都是一次"按当前任务现拉方法"，避免历史方法污染下一次任务。

工程提示：如果你发现某个 Skill 在长会话后期"不起作用"了，要么是被压缩时挤掉了（重新触发一次即可），要么是模型选了别的方法（这时该考虑加强 description 或用 hooks 做硬约束）。

1.4.4 那"近似全生命周期"的 Skill 该怎么实现

如果确实有"跨会话也始终在线"的诉求，有几种近似做法，但严格意义上都不是 Skill 的原生形态：

  1. 写进 CLAUDE.md（推荐） 把"必须永远遵守"的内容直接放进 CLAUDE.md，不要硬塞进 Skill。这就是 CLAUDE.md 的本职工作。

  2. System Prompt / 平台级指令 团队/平台层面写死，用户无法关闭。代价是吃 context。

  3. Slash Command 强制触发 写一个项目专属命令，进入工作流先打一下把对应 Skill 显式拉进来。这是"按需的强一致"，不是"全生命周期"。

  4. disable-model-invocation: true 强制手动触发 Claude Code 支持在 frontmatter 里加 disable-model-invocation: true，让 Skill 只能由用户用 /skill-name 显式触发，不会被模型自动加载。这适合 /deploy、/commit 这种"必须用户主动确认"的场景，但它不是"始终在线"，反而是"更严格的按需"。

1.4.5 一句话记住

Skills 故意设计成不长命。如果你想要"整个项目跟随生命周期"的东西，请用 CLAUDE.md / 项目记忆，那才是为这个目的而生的工具。把两者混用，最后一定会把 Skills 写成"另一份永远在线的 system prompt"，把它"按需、不挤占 context"的全部价值都浪费掉。

2. Skills 解决了什么问题

为什么需要 Skills？因为 Prompt 工程发展到今天，遇到了几个绕不开的问题。

2.1 问题一：System Prompt 越塞越胖

最早的做法是把所有规范、经验、流程一股脑写进 system prompt：

  • 项目编码规范
  • Git 提交规则
  • 各种特殊场景的处理方法
  • 部门内部的特殊术语

结果就是：

  • system prompt 动辄几千上万 token
  • 大量内容这次任务根本用不上
  • 上下文窗口被白白占用，影响真正的任务推理

Skills 的做法是：用不上的东西就别加载。

2.2 问题二：经验难以复用

每个研发都有自己一套"老中医经验"：

  • 我每次写 Dockerfile 都会顺手加 --no-cache-dir
  • 我每次改数据库迁移都会先 dry-run
  • 我团队的 PR 模板有一套固定写法

这些经验不写下来，模型每次都重新摸索；写下来塞进 SP，又会触发问题一。

Skills 的做法是：经验写一次，按需调用。

2.3 问题三：能力分发难

如果你想把"写 K8s YAML 的最佳实践"分享给团队 20 个人用：

  • 让每个人都改自己的 SP？维护成本极高
  • 做成 MCP Server？过重，纯文档型经验犯不着开服务
  • 写成 Wiki？人能看，模型不会主动查

Skills 的做法是：做成一个目录、一个仓库，就能分发。

2.4 问题四：Agent 自主性与可控性的平衡

我们既希望 Agent 聪明地自主决定怎么做事，又希望它在关键流程上严格按规矩来。

  • 全靠 Agent 自由发挥 → 不稳定
  • 全靠硬编码 workflow → 不灵活

Skills 的做法是：该松的地方让模型自由发挥，该紧的地方写进 SKILL.md。

# 写 PR 描述的方法

## 基本流程

1. 先用 `git diff origin/main...HEAD` 看完整改动
2. 按以下结构组织描述：
   - **Summary**：一句话说清楚这个 PR 做了什么
   - **Why**：为什么要做（关联 issue / 业务背景）
   - **How**：实现思路，重点说清楚关键设计决策
   - **Test**：测试覆盖了哪些场景
   - **Risk**：可能的风险点

## 不要做的事

- 不要写"修复了一些 bug"这种没信息量的话
- 不要把 commit message 直接复制进来
- 不要超过 200 行；超过说明 PR 应该拆分

4. Skills 怎么使用

4.1 Skills 的存放位置

Claude Code 官方文档明确列出 4 级作用域，优先级从上到下依次降低（同名 Skill 高优先级覆盖低优先级）：

层级 路径 作用域 谁负责放
Enterprise 通过 managed settings 部署 整个组织所有用户 组织管理员
Personal ~/.claude/skills/<skill-name>/SKILL.md 当前用户所有项目 你自己
Project <project>/.claude/skills/<skill-name>/SKILL.md 仅当前项目（随仓库走，团队共享） 项目仓库
Plugin <plugin>/skills/<skill-name>/SKILL.md 启用了该 plugin 的地方 插件作者

几个关键事实（来自官方文档）：

  • 覆盖规则：enterprise 覆盖 personal，personal 覆盖 project。Plugin Skills 用 plugin-name:skill-name 命名空间，不会和其他级别冲突。
  • 自动发现：personal、project、plugin 三级会被自动扫描，无需手动注册。Project Skills 还会沿目录树往上找 —— 在子目录启动 Claude Code，仍能加载到仓库根目录的 .claude/skills/。
  • 额外目录：用 --add-dir 或 /add-dir 加入的目录里的 .claude/skills/ 也会被自动加载（这是 additionalDirectories 设置默认不加载配置的一个例外）。
  • 实时生效：Claude Code 监听这些目录，添加/编辑/删除 Skill 不用重启就能生效。但新建一个之前不存在的顶层 skills/ 目录需要重启 Claude Code 才能开始监听。
  • 优先级冲突：如果同名既有 .claude/commands/<name>.md 又有 .claude/skills/<name>/SKILL.md，Skill 优先。

这里说的"Skills 存放位置"是 Claude Code 专属的。Claude API 上的 Skills 通过 /v1/skills 端点上传到 workspace，claude.ai 上的通过 Settings → Features 上传 zip 文件，两者都不是文件系统路径。

4.2 两种触发方式

Skills 有两种触发方式，理解这一点非常重要：

方式一：模型自主触发（隐式）

模型在执行任务时，会扫描当前可见的所有 Skill 的 name + description，判断当前任务是否匹配某个 Skill，匹配则加载它的完整内容。

例子：

  • 用户说"帮我写个 PR 描述"
  • 模型扫描到一个 write-pr-description Skill，description 写着"当用户要写或改 PR 描述时使用"
  • 模型判断匹配，加载 SKILL.md 全文
  • 按 SKILL.md 里写的方法去写

整个过程用户不需要知道 Skill 的存在。

方式二：用户显式调用

用户直接以 /skill-name 的方式触发。例如：

1

/write-pr-description

这种方式下：

  • Skill 一定会被加载
  • 不依赖模型对 description 的匹配
  • 适合"我明确知道要用哪个方法"的场景

5.7.3 几个容易踩坑的点

SKILL.md 里的代码块不会自动执行

新手常误以为"我在 SKILL.md 里写一段 bash，模型就会跑它"。不会。SKILL.md 只是改变模型的行为方式，真正的执行必须经过 Tools。

正确写法是明确引导：

  • ✅ “运行 git diff 查看改动” —— 模型会去调 bash Tool 跑
  • ❌ 直接贴一段 bash 代码块然后什么都不说 —— 模型可能以为这只是示例

路径必须用相对路径

SKILL.md 里引用辅助文件要用相对于 SKILL.md 自身的相对路径：

  • ✅ 见 scripts/check.sh
  • ✅ 见 reference/index-rules.md
  • ❌ 见 ~/.claude/skills/pdf-processing/scripts/fill_form.py（绝对路径跨机器会失效）
  • ❌ 见 ./scripts/check.sh（没必要的 ./）

脚本要做到"自包含"

如果 Skill 要分发给团队（甚至打成 Plugin），脚本不能依赖：

  • 固定的绝对路径
  • 必须本地预先安装的私有依赖
  • 用户机器上的特定环境

要么脚本自己处理依赖，要么 SKILL.md 的"前置条件"一节明确写清楚。

涉及凭证 / Token 的代码不要硬编码

如果脚本要调外部 API：

  • ❌ 把 Token 写进脚本
  • ✅ 从环境变量读，SKILL.md 里写明该 export 什么

Skill 是要进 git 的，硬编码凭证 = 凭证泄露。

5.7.4 Skill 脚本和 Tool 的边界

这是 5.7 节最容易踩进去的概念混淆：当 Skill 里塞了一个 scripts/foo.py，它和 Tool 是不是同一个东西？

直觉上很多人会说"是" —— 既然脚本能干活、有输入有输出，那它不就是个工具吗？但在 Anthropic 的 API 与 Claude Code 的语境里，二者根本不在同一个层级。

一句话先定调

Skill 里 bundled 的脚本（scripts/foo.py）从来都不是 Tool。它只是一个普通文件，由 Bash 这个 Tool 去执行它。

模型跑一个 Skill 脚本时，真实的调用链是：

1
2
3
4
5
6
7

模型决定要跑 scripts/check.py
    ↓
模型发出一次 tool_use，调用的是 Bash 这个 Tool
    ↓
Bash Tool 执行命令 `python scripts/check.py`
    ↓
脚本 stdout 作为 tool_result 回到模型

整条链路里只有一个 Tool 参与（Bash）。脚本只是 Bash 的"参数"，不是和 Bash 平级的另一个 Tool。

严格对比：Tool vs Skill 里的脚本
维度 Tool Skill 的 bundled 脚本
本质 模型可见的、有 JSON schema 的原子能力 文件系统上的普通可执行文件
声明位置 API 请求里的 tools 数组 / Claude Code 内置 / MCP server Skill 目录里的 .py/.sh 文件
模型怎么调用 发出 tool_use 块，带结构化参数 让 Bash Tool 执行一行命令
模型怎么知道它存在 启动时 schema 注入 system prompt（永久占用 token） 加载 SKILL.md 时由文档告知（Skill 命中时才占用）
接口约束 JSON schema（强类型） 命令行参数 + stdout 文本（弱类型）
基线 token 成本 每个 Tool ~50–200 tokens 永久在线 0 —— 脚本代码永远不进上下文，只有 stdout 进
权限 / 审批 /permissions 全局规则 通过 Bash 的权限规则间接管 + Skill 的 allowed-tools 可预授权
状态 可能跨多次调用持有状态（如 code execution VM 的连接池） 默认无状态、一次性
分发 内置 / MCP / 客户端实现 git push 一个文件
可见性 模型从一开始就看见 模型读了 SKILL.md 才知道有它
选"做成 Tool 还是写成 Skill 脚本"的 5 个判断维度
判断 倾向 Tool 倾向 Skill 脚本
使用频率 几乎每个任务都要用 只在某一类任务里用
跨 Skill 共享 多个 Skill 都需要它 只这一个 Skill 需要
接口稳定性 输入输出已成熟、不太变 还在迭代、专属业务逻辑
复杂状态 需要会话级状态（连接池、缓存） 一次性、stateless
实现成本 一个 MCP server 不算重 一个 50 行脚本，犯不着包成 Tool

举几个具体例子：

需求 选 Tool 还是 Skill 脚本？理由
读文件 / 写文件 Tool（Read / Write），任何任务都要用
跑 SQL 查询 Tool（MCP），多个 Skill 会用，且需要会话级连接池
把一段 SQL 格式化成可读形式 Skill 脚本（scripts/format-sql.sh），只在 sql-review Skill 里用
调用 GitHub API 创建 issue Tool（MCP），可被 pr-description、issue-triage 等多个 Skill 共用
把 sql-review 的输出 diff 一下两个版本 Skill 脚本，只服务 sql-review
跑公司内部 lint 单项目 → Skill 脚本；多项目共用 → 包成 MCP

判断口诀：

凡是"全局通用 + 多 Skill 共享 + 接口稳定" → Tool；凡是"专门为这个 Skill 服务 + 接口随业务变" → Skill 脚本。

一个常见误会

“我在 Skill 里写了 scripts/deploy.sh，是不是等于给模型加了个 deploy tool？”

不是。

  • 模型的 tools 列表里没多任何一个 Tool
  • 模型仍然只能通过 Bash Tool 执行 bash scripts/deploy.sh
  • 是 Bash Tool 的权限规则决定能不能跑这条命令（不是 deploy.sh 自己的规则）
  • 在另一个会话、没加载这个 Skill 时，模型根本不知道有这个脚本

如果你希望 deploy 真的成为模型平等可调用的"动作"（带 schema、在任何会话里都可见、有独立权限），应该写一个 MCP server 或 自定义 Tool，而不是塞个脚本进 Skill。

一句话记住

Skill 脚本是 Bash 的参数，Tool 是 Bash 的同事。 写 Skill 时把这两件事分清楚，权限边界、token 成本、可复用性都会变得清晰。

5.7.5 Skill 脚本的运行环境（vs Tool）

5.7.4 节回答了"Tool 和 Skill 脚本是不是同一个东西"。这一节回答更进一步的问题：它们各自跑在哪？

先纠正一个常见误解：Tool 不一定都跑在 MCP server 里

在 agent 开发的语境里，Tool 是个宽泛概念 —— 任何模型可发起调用的"能力单元"都算。按运行位置可分 5 类：

Tool 形态 运行位置 谁实现
Local function tool（OpenAI / LangChain 经典做法） Agent 框架进程内，作为函数被调用 你的代码
HTTP / API tool 远程 API 服务器 第三方或你的后端
MCP tool MCP server 进程（独立进程，可本地可远程） MCP server 实现方
Built-in tool（Claude Code 的 Bash/Read/Edit） Claude Code CLI 自己的进程 Anthropic
Code execution tool 托管沙箱 VM（Anthropic / OpenAI / E2B 等） 平台方

每种 Tool 的共同点是：它是一个有独立"运行实体"的能力，模型通过 tool_use → tool_result 协议跟它交互，这个运行实体的生命周期跟 Skill 无关。

Skill 代码的运行位置：它没有独立运行实体

这是 Skill 和 Tool 在"运行模型"上的根本差异：

Skill 不是一个运行实体。Skill 里的代码，是被某个 Tool（在 Claude Code 里通常是 Bash，在 API/claude.ai 里是 code execution tool）当作"参数"去执行的脚本。

具体到不同 surface：

Surface 触发 Skill 脚本的 Tool 脚本实际跑在哪 网络访问 包安装
Claude Code Bash Tool 你本机的 shell（Claude Code 进程的子进程） 全开 不建议全局，本地 ok
Claude API code execution tool Anthropic 托管的沙箱 VM 无网络 不可 runtime install
claude.ai code execution tool Anthropic 托管的沙箱 VM 视配置（可能允许 npm/PyPI） 部分配置允许

简单说：

  • 在 Claude Code 里：“Skill 脚本跑在哪” = “Bash 跑在哪” = 你的开发机
  • 在 Claude API / claude.ai 里：“Skill 脚本跑在哪” = “code execution tool 跑在哪” = Anthropic 沙箱

为什么这个区分在 agent 开发里很重要

1. 决定了 Skill 能不能跨 surface

如果你的 Skill 脚本依赖：

  • 网络访问
  • 第三方包
  • 内网服务
  • 特定本地路径

在 Claude Code 上能跑（用你本机环境），搬到 Claude API 上可能直接死（沙箱无网络、无 runtime install、没有你本地路径）。

很多人的 Skill 在自己电脑跑得好好的，发到团队就出问题，常常就是这个原因。写跨 surface 的 Skill 时，要假设运行环境是受限沙箱。

2. 决定了"该写 Tool 还是 Skill 脚本"

  • 能力有独立运行需求（持续运行 / 维持状态 / 需要专用网络）→ 写成 Tool（local function / HTTP API / MCP server）
  • 能力只是"在某个任务流程里跑一段代码" → 写成 Skill 脚本

3. 决定了部署模型

  • Tool（尤其 MCP / HTTP API）是服务，需要部署、监控、运维
  • Skill 是文件，git push 就完事
一句话记住

Tool 是"运行实体"，自己有进程或服务；Skill 没有运行实体，它的代码寄生在某个 Tool 的执行上下文里跑。 跨 surface 时，记得这个"上下文"会换，写代码时要按受限沙箱的假设来写。

5.7.6 一句话总结

Skills 不只是"写给模型看的方法书"，它完全可以带可执行代码。把代码当成 Skill 的有机组成部分（参考片段 / 辅助脚本 / 完整工具），是让 Skill 真正落地的关键 —— 否则它就只是一份华丽的文档。

# PDF Processing

## Quick start

Use pdfplumber to extract text from PDFs:

```python
import pdfplumber

with pdfplumber.open("document.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

## Advanced features

**Form filling**: See [FORMS.md](FORMS.md) for the complete workflow
**API reference**: See [REFERENCE.md](REFERENCE.md) for all methods
**Examples**: See [EXAMPLES.md](EXAMPLES.md) for common patterns

## Form filling workflow

For form-filling tasks, use the bundled scripts in this exact order:

1. **Analyze the form** — extract all form fields:
   ```bash
   python scripts/analyze_form.py input.pdf > fields.json
   ```
2. **Edit `fields.json`** to add the values for each field.
3. **Validate the mapping** — catch errors before applying:
   ```bash
   python scripts/validate.py fields.json
   ```
   Fix any reported issues before continuing.
4. **Fill the form**:
   ```bash
   python scripts/fill_form.py input.pdf fields.json output.pdf
   ```
5. **Verify the output** by opening `output.pdf` and confirming all fields are filled.

## Don'ts

- **Don't** skip the `validate.py` step — it catches non-existent field names early.
- **Don't** edit `output.pdf` directly. If something is wrong, fix `fields.json` and re-run `fill_form.py`.
- **Don't** assume packages are installed. If `pdfplumber` is missing, run:
  ```bash
  pip install pdfplumber
  ```

  • 没有 tags / version / author 字段 —— 官方不支持，写了也会被忽略
  • Quick start 在最前，先给最常用的 5 行代码
  • 链接全部一层深：SKILL.md → FORMS.md ✓，避免 SKILL.md → FORMS.md → DETAILS.md（best practices “Avoid deeply nested references”）
  • Form filling 流程用编号 + 代码块，每一步要么是检查动作要么是脚本调用，模型可以照着复制 checklist
  • Don’ts 写得具体：不是泛泛"小心使用"，而是逐条说明"哪一步不能省、为什么、错了怎么补"

#!/usr/bin/env python3
"""Extract form fields from a PDF file.

Usage:
    python scripts/analyze_form.py <input.pdf>

Outputs JSON to stdout: each field is a key with type/x/y info.
"""
import json
import sys
from pathlib import Path

try:
    import pypdf
except ImportError:
    print("pypdf is required: pip install pypdf", file=sys.stderr)
    sys.exit(3)


def extract_fields(pdf_path: Path) -> dict:
    reader = pypdf.PdfReader(str(pdf_path))
    fields = reader.get_fields() or {}
    result = {}
    for name, field in fields.items():
        result[name] = {
            "type": field.field_type or "text",
            "value": field.value or "",
        }
    return result


def main() -> int:
    if len(sys.argv) < 2:
        print("Usage: analyze_form.py <input.pdf>", file=sys.stderr)
        return 2
    fields = extract_fields(Path(sys.argv[1]))
    print(json.dumps(fields, indent=2, ensure_ascii=False))
    return 0


if __name__ == "__main__":
    sys.exit(main())

#!/usr/bin/env python3
"""Validate a fields.json before filling a form.

Usage:
    python scripts/validate.py <fields.json>

Exits 0 on success, non-zero with specific error messages on failure.
"""
import json
import sys
from pathlib import Path


def validate(data: dict) -> list[str]:
    errors = []
    for name, info in data.items():
        if not isinstance(info, dict):
            errors.append(f"Field {name!r}: value must be an object")
            continue
        if "value" not in info:
            errors.append(f"Field {name!r}: missing 'value'")
        if info.get("type") not in (None, "text", "checkbox", "sig", "choice"):
            errors.append(
                f"Field {name!r}: unknown type {info.get('type')!r}"
            )
    return errors


def main() -> int:
    if len(sys.argv) < 2:
        print("Usage: validate.py <fields.json>", file=sys.stderr)
        return 2
    data = json.loads(Path(sys.argv[1]).read_text())
    errors = validate(data)
    if errors:
        for e in errors:
            print(f"ERROR: {e}", file=sys.stderr)
        return 1
    print("OK")
    return 0


if __name__ == "__main__":
    sys.exit(main())

#!/usr/bin/env python3
"""Fill a PDF form using values from fields.json.

Usage:
    python scripts/fill_form.py <input.pdf> <fields.json> <output.pdf>
"""
import json
import sys
from pathlib import Path

try:
    import pypdf
except ImportError:
    print("pypdf is required: pip install pypdf", file=sys.stderr)
    sys.exit(3)


def fill(input_pdf: Path, fields: dict, output_pdf: Path) -> None:
    reader = pypdf.PdfReader(str(input_pdf))
    writer = pypdf.PdfWriter(clone_from=reader)
    values = {name: info["value"] for name, info in fields.items()}
    for page in writer.pages:
        writer.update_page_form_field_values(page, values)
    with open(output_pdf, "wb") as f:
        writer.write(f)


def main() -> int:
    if len(sys.argv) < 4:
        print(
            "Usage: fill_form.py <input.pdf> <fields.json> <output.pdf>",
            file=sys.stderr,
        )
        return 2
    fields = json.loads(Path(sys.argv[2]).read_text())
    fill(Path(sys.argv[1]), fields, Path(sys.argv[3]))
    print(f"Wrote {sys.argv[3]}")
    return 0


if __name__ == "__main__":
    sys.exit(main())

6. Skills 的底层原理

6.1 渐进式披露（Progressive Disclosure）

Skills 最核心的设计就是"按需加载"。官方 overview 把这个机制定义为三层 token 成本不同的加载层次：

层 何时加载 Token 成本 内容
Level 1: Metadata 启动时永久加载 ~100 tokens / Skill YAML frontmatter 里的 name + description
Level 2: Instructions Skill 被触发时通过 bash 读取 < 5,000 tokens SKILL.md 正文
Level 3: Resources 按需访问或脚本被执行 几乎不限 引用文件、辅助脚本（脚本通过 bash 执行，代码本身不进入上下文，只有输出占用 tokens）

引用官方原文：

“Progressive disclosure ensures only relevant content occupies the context window at any given time.”

三层加载是怎么发生的

  1. Level 1 / 元信息扫描：Claude Code 启动时把所有可见 Skill 的 name + description 拼进 system prompt。这一步是永久在线的，单个 Skill 大约消耗 100 tokens。所以你可以"装很多 Skill 但代价极小"。
  2. Level 2 / 触发与读取：当用户的请求匹配某个 Skill 的 description（或用户用 /skill-name 显式触发），Claude 用 bash 工具去读 SKILL.md 文件，把内容作为一条消息加入上下文。这才是真正"载入"的时刻。注意：这里不是模型先做语义检索再决定 —— 模型一直能看见所有 description，是基于这些 description 自主选择的。
  3. Level 3 / 按需展开：如果 SKILL.md 里链接了 reference.md 或要求执行 scripts/check.sh，Claude 才会再用 bash 读那些文件或跑那些脚本。未被引用的文件永远不进入上下文。脚本代码也不进入上下文，只有 stdout 输出会进。

这套机制带来的工程含义

  • 可扩展性：你可以装 100+ 个 Skill，每个 Skill 只占 ~100 tokens 的 metadata。所有 metadata 加起来如果撑满了 listing 预算（默认是模型上下文窗口的 1%），可以在 settings 里调 skillListingBudgetFraction。
  • description 是 100 tokens 的命脉：因为它是永远在线的，写得越精准检索越准；写得越冗余越浪费。
  • 大文件零成本：在 Skill 目录里塞 100KB 的 reference 文档没有任何代价，只要它没被读到。
  • 脚本远比"模型现写代码"高效：validate_form.py 这种确定性脚本，跑一次只占输出的 tokens，远比让模型每次重写一遍代码省。

注意：Skills 在 Claude Code 里跑在一个有 bash 和文件系统访问的 VM/code execution 环境里 —— “模型用 bash 读 SKILL.md” 不是隐喻，而是真实发生的事情。

6.2 常见误解：全量写入 vs 渐进式披露

在讨论 Skills 底层原理时，网上有一种流传较广的说法：

“把所有 Skill 的 name + description 一次性写入 System Prompt 是初级做法，生产级系统应该用 embedding 检索 + 动态注入。”

这种说法有一定道理但过于绝对，需要厘清。

6.2.1 现状：Claude Code 确实是全量写入

Claude Code（以及 OpenAI Function Calling、ChatGPT Plugins）确实把所有已安装 Skill 的 name + description 一次性写入 system prompt。模型在每一轮对话中，基于注意力机制从这份列表里"挑选"要使用的 Skill。

这不是 demo 做法，而是生产系统的实际实现。

6.2.2 “Lost-in-the-Middle” 问题被夸大了

常被引用的"Lost-in-the-Middle"论文针对的是大量同质化文档的检索任务，不是结构化的 tool/skill 列表。现代模型（Claude、GPT-4o）经过专门的 tool-use fine-tuning，对结构化列表的注意力远好于自由文本段落。

实测数据：

  • OpenAI 单次调用支持 128 个 functions
  • Claude Code 生产环境常驻 10-15 个 Skills 毫无问题
  • 30-50 个 well-described tools 在主流模型上表现良好

“超过 15 个就必须换方案"这种说法过于武断。

6.2.3 “每轮 embedding 检索 + 动态注入"不是银弹

网上推崇的"两阶段动态注入"方案（先用 embedding 检索 Top-3 Skill，再动态插入本轮请求）有其适用场景，但也引入了自身的代价：

代价 说明
Router 误召回 如果前置分类器漏掉了正确的 Skill，模型根本看不到它，比"看到但没选"更严重
额外延迟 每轮多一次 embedding 计算 + 向量检索
系统复杂度 多了一个需要维护、调参、监控的组件
级联失败 Router 挂了 = 所有 Skill 都不可用

6.2.4 实际的工程权衡

这不是"初级 vs 生产级"的二元对立，而是根据规模选择合适策略：

场景 合理方案
Skills < 30，description 清晰 全量写入即可（Claude Code、ChatGPT Plugins 的做法）
Skills 30-100 分类分组 + 按类别动态挂载
Skills 100+ 前置 embedding 检索 + 动态注入

Claude Code 的 skillListingBudgetFraction（默认 1% context window）+ 对低频 Skill 的 trim 机制，本质上就是在全量写入的基础上做了轻量级优先级排序，不需要引入外部 Router。

6.2.4a Skills 30–100：分类分组 + 按类别动态挂载

核心思路：不是一次性把所有 Skill 的 metadata 写入 system prompt，而是先按领域/功能分组，每轮根据用户意图只挂载相关分组的 metadata。

  • 分类粒度需要仔细设计：太粗（一个 category 50 个 Skills）等于没分；太细（一个 category 2 个 Skills）维护成本高且容易漏挂。

6.2.4b Skills 100+：前置 embedding 检索 + 动态注入

核心思路：把所有 Skill 的 name + description 离线建立向量索引，每轮对话用用户的请求做 embedding 检索，只把 Top-K 个最相关的 Skill metadata 动态注入当轮 system prompt。

实现步骤

  1. 离线建索引：对每个 Skill 的 name + description 做 embedding，存入向量数据库（Pinecone、Weaviate、pgvector 等）。Skill 更新时重建对应向量。

  2. 每轮检索：用户请求到来时，先对请求文本做 embedding，在向量库里检索 Top-K（通常 5–15）个相似 Skill。

  3. 动态注入：将检索出的 Skill metadata 拼成列表，注入当轮的 system prompt 或第一条 user message 之前。后续流程与全量写入完全相同——模型从这份缩减列表里决策是否触发某个 Skill。

关键工程细节

  • K 的选取：K 太小会漏掉相关 Skill；K 太大等于没检索。经验值：先检索 Top-20，再用模型做一轮 rerank 取 Top-5 注入。
  • 冷启动问题：用户第一句话往往很短，embedding 质量差。可以用对话前几轮的消息拼接作为检索 query，而不是只用当轮输入。
  • 缓存：相似请求的检索结果可以缓存（TTL 5–10 分钟），减少向量检索的延迟和费用。
  • 兜底策略：始终把"高频通用 Skills”（使用频率 Top-5）加入每轮注入列表，不经过检索，防止漏召回。

代价汇总

代价 说明
Router 误召回 漏掉的 Skill 模型完全看不到，比"看到没选"更严重
额外延迟 每轮多一次 embedding 计算 + 向量检索（通常 50–200ms）
系统复杂度 多了索引构建、向量库维护、检索服务三个组件
级联失败 检索服务挂了 = 只剩兜底的通用 Skills

适合场景：Skills 数量确实超过 100 且有明显的长尾分布（大部分 Skills 只在特定垂类被使用），或者上下文窗口成本极其敏感的场景。如果 100 个 Skills 的 description 都很常用，全量写入仍然更可靠。

应对策略与 Skills 规模方案完全对应：

  • tool < 30：全量传入
  • tool 30–100：按子任务分组，每次只传该任务相关的 tool subset
  • tool 100+：前置分类器/embedding 检索，动态选 Top-K 注入

Skills 的渐进式披露机制，本质上就是把 tool 的"完整 schema"延迟到真正需要时才加载，只让 metadata（name + description）常驻——这是对 tool calling 上下文膨胀问题的一种工程封装。

ReAct vs Plan & Execute 在 tool 多时的差异

两种 Agent 范式给模型传的 tool 数据格式相同，区别在调用节奏：

  • ReAct：每一步（Thought → Action → Observation）都是一次完整 API 调用，每次都携带全量 tool 列表，tool 多时每轮重复消耗这部分 tokens。
  • Plan & Execute：Plan 阶段只让模型做推理分解，可以不传或少传 tools；Execute 阶段每个子任务单独调用，只传该子任务需要的 tools，而不是全量。

所以 Plan & Execute 天然更适合 tool 数量多的场景——execute 阶段按子任务做 tool 裁剪，每次注入的列表更短，选择更准确。

6.2.6 渐进式披露是 ReAct 循环里的一个子行为

渐进式披露不是独立的 Agent 范式，而是ReAct 循环里的一个子行为。

模型在 ReAct 的 Thought 阶段判断需要某个 Skill，然后在 Action 阶段用 bash 读取 SKILL.md——“读文件"本身就是一次 tool call，文件内容作为 Observation 返回，模型再基于这份内容决定下一步：

换句话说：渐进式披露 = 把"获取完整工具说明"本身也作为 ReAct 循环里的一个 Action，而不是把所有说明预先塞进 system prompt。它是在 ReAct 框架内做的上下文管理优化，而不是一种新的 Agent 模式。

6.2.7 一个关键澄清：“多轮循环中挑选"的表述

严格来说，Skill 的选择发生在每一轮独立决策，而非"跨多轮演进”：

  • 第 1 轮用户说"查天气” → 模型扫描列表，选 get_weather
  • 第 2 轮用户说"翻译文章" → 模型重新扫描列表，选 translate，不受上一轮影响

所以它是"每轮静态全量扫描"，不是"多轮动态演进"。这个表述是准确的。

6.2.8 一句话记住

全量写入不是反模式，它是在工具数量合理（< 50）时成本最低、可靠性最高的方案。只有当工具规模真正爆炸（100+）时，才值得引入前置 Router 的额外复杂度。

6.3 Skills 与 system prompt 的关系

可以把 Skills 看作是"延迟加载的 system prompt 片段"。

  • system prompt 是永远在线的指令
  • Skills 是按需在线的指令

被加载后的 Skill，作用上等价于把 SKILL.md 内容拼接到了 system prompt 后面。所以 Skill 的指令优先级、措辞方式，应该和写好的 system prompt 是一致的。

6.3 Skills 与 Tools 的关系

Tools 是模型的"手脚"，Skill 是模型的"作业指导书"。

举例：

  • read_file、bash、edit_file 是 Tools
  • “写 PR 描述时按这五步走” 是 Skill

执行时的协作关系：

Skill 告诉模型该按什么流程做，Tools 让模型把流程一步步执行下去。

Skill 自己不会"执行"任何东西，它只是改变模型的行为方式。

7. Skills 与 MCP、Tools、Subagent 的区别

重要前提：Slash Command 不在这张对比表里。

在当前的 Claude Code 实现里，“Slash Command” 已经合并进 Skills（详见 1.3 节 的引用）—— 你写一个 .claude/skills/deploy/SKILL.md 就自动产生了 /deploy 命令；老的 .claude/commands/deploy.md 也是同一个东西的简化形式。所以这一节剩下的就是 Skills 与 Tools / MCP / Subagent 三者的区别。

这四个概念最容易搞混，下面统一对比一遍。

7.1 一句话区分

概念 一句话定义
Tools 模型可调用的原子能力
MCP 一种把 Tools/Resources/Prompts 标准化暴露给模型宿主的协议
Skills 按需加载的任务方法包（同时也是 Slash Command 的实现）
Subagent 在独立上下文里执行子任务的执行体

7.2 它们各自回答的问题

概念 回答的问题
Tools “我能做什么动作”
MCP “怎么把能力标准化接进来”
Skills “这类任务该怎么做”
Subagent “这个子任务交给谁、用什么独立上下文做”

7.3 一个综合对比表

维度 Tools MCP Skills Subagent
本质 函数/动作 协议 方法书 + Slash Command 执行体
是否执行能力 是 否（只接入） 否（只注入方法） 是

7.4 一个综合协作场景

假设场景：“用户让 Agent 帮忙做一个数据库性能优化”：

  1. 用户输入"帮我优化下这个 SQL"，模型自动加载 sql-review Skill（按方法做 review）
  2. Skill 里写明要查表结构，模型调用 read_db_schema Tool 拉表结构
  3. 这个 Tool 是通过一个 PostgreSQL MCP Server 提供的
  4. Review 中发现需要做大规模历史查询统计，Skill 用 context: fork 在一个 Subagent 里跑慢查询日志分析（独立上下文，不污染主对话）
  5. 之后用户想再做同样的事，直接打 /sql-review —— 同一个 Skill 被显式触发，不靠模型自动判断

四个概念在一个工作流里清晰各司其职。/sql-review 不是独立的"Slash Command"，它就是 sql-review 这个 Skill 的另一个触发入口。

8. Skills 的最佳实践

下面是写过和用过若干 Skill 之后总结出的若干经验。

8.1 description 是 Skill 的命脉

description 不要写：

  • “我是一个 SQL 助手”
  • “用于代码相关的任务”

要写成：

  • “当用户给一段 SQL 并询问性能或正确性时使用”
  • “当用户要写或改 PR description 时使用”

写法上的关键词是"当…时"。模型靠这一句话决定要不要加载你，含糊一点都会出问题。

8.2 SKILL.md 不要太长

官方 best-practices 文档给的明确指引是：

“Keep SKILL.md body under 500 lines for optimal performance.”

所以经验值：

  • 目标：SKILL.md 正文 ≤ 500 行
  • 接近这个上限就该把内容拆出去
  • 拆到平铺的 .md 文件（如 reference.md、examples.md、FORMS.md）或子目录（reference/、examples/、scripts/），从 SKILL.md 用相对路径链接

记住：SKILL.md 是"按需加载"，但一旦加载就是整个文件。一旦超过 5,000 tokens（约 ≈ 500 行），就开始侵占其他上下文预算。同时官方明确只展开一层引用：模型从 SKILL.md 跳到 reference.md 是稳的，但 reference.md 再跳到 details.md，模型可能只读个开头，所以所有辅助文件都要从 SKILL.md 直接链接，不要嵌套引用。

8.3 写"不要做的事"比写"要做的事"更重要

模型本来就会做大多数对的事，但很容易掉进若干常见坑。

每个 SKILL.md 里都加一节 ## 不要做的事，效果立竿见影。

8.4 给好例子和坏例子

模型对"格式"非常敏感。

  • 给一个完美的输出例子
  • 给一个反面例子并标注"这是错的，原因是…"

效果远好过用文字描述格式。

8.5 每个 Skill 只解决一类问题

不要写一个"万能 Skill"。

  • ❌ dev-helper：什么都管
  • ✅ git-commit + pr-description + code-review：每个专精一个

小而清晰的 Skill 更容易被正确触发，也更容易维护。

8.6 用 Skill 互引代替复制粘贴

如果 pr-description Skill 也需要遵守"写英文要用现在时"，不要复制规则进去，而是写：

措辞规则与 git-commit Skill 一致，详见该 Skill。

让 Skills 形成网络，而不是孤岛。

8.7 把 Skills 当代码维护

  • 进版本控制
  • 写 CHANGELOG
  • 经验更新就改 Skill，而不是新写一个
  • 团队 review

Skill 是会被全员复用的"团队记忆"，值得当代码一样认真对待。

8.8 Skills 的安全模型

这一节官方有专门一章 (Security considerations)，强烈建议在团队推广 Skills 前读一遍。下面只是把要点摘出来。

Skill 不是无害的文档 —— 它能让模型 直接执行代码、调用工具。从这个角度看，安装一个 Skill 等同于安装一段会被 Claude 自动执行的程序。官方原话：

“Use Skills only from trusted sources: those you created yourself or obtained from Anthropic. … a malicious Skill can direct Claude to invoke tools or execute code in ways that don’t match the Skill’s stated purpose.”

8.8.1 几个真实风险

  • 工具滥用：恶意 SKILL.md 可以指挥 Claude 滥用 Bash、Edit、Read 等工具（甚至 allowed-tools 已经预授权）
  • 数据外泄：能读取代码、能执行 bash，就能把代码或环境变量打到外部 endpoint
  • 外部源被污染：用 !`curl <url>` 拉远程内容的 Skill，远程 endpoint 被攻破后等于植入了 prompt injection
  • allowed-tools 滥用：作者写 allowed-tools: Bash(*) 等同于"对这个 Skill 永久免确认"，意味着你 trust 这个仓库等于 trust 这段授权

8.8.2 落地实践

场景 建议
用第三方 Skill 先审计 SKILL.md + 所有 bundled 文件、所有脚本，确认 allowed-tools 范围合理
项目级 Skill 进 git PR review 时把 .claude/skills/ 当代码 review，重点看 allowed-tools、!(命令注入)

9. Skills 常见高频面试题

下面整理 10 道有代表性的题目，覆盖面试和实际答辩中常见的问法。

9.1 Skills 和 system prompt 有什么本质区别？

答：

最大的区别在加载时机：

  • system prompt 是始终加载，每次请求都占用上下文
  • Skills 是按需加载，只在模型判断需要时才占用上下文

其次是作用域：

  • system prompt 一般是平台级或会话级的全局指令
  • Skills 是任务方法级的局部指令

第三是可分发性：

  • system prompt 改起来要碰到底层配置
  • Skills 是文件，能进 git，能跨人复用

9.2 模型怎么知道该不该加载某个 Skill？

答：

机制是两阶段检索：

  1. 启动/初始化阶段，模型只看到所有 Skill 的 name + description
  2. 任务来临时，模型基于当前对话内容，对这些 description 做语义匹配
  3. 命中的 Skill 才会把 SKILL.md 完整加载

所以 description 写得是否到位，直接决定 Skill 能否被正确触发。

9.3 Skills 和 MCP 有什么区别？

答：

不在一个层面：

  • MCP 是协议，回答"能力怎么标准化暴露给模型宿主"
  • Skills 是方法包，回答"这类任务该怎么做"

MCP 暴露出来的更多是 Tools 和 Resources（工具与数据），而 Skills 是文档化的方法论。

一个能力可以同时存在两种形态：通过 MCP Server 暴露具体 tool 调用，再通过一个 Skill 告诉模型"这个 tool 在什么场景下、按什么流程用"。

9.4 Skills 和 Subagent 有什么区别？

答：

  • Subagent 是执行体：它有自己的独立上下文，能跑完整任务
  • Skill 是方法书：它没有自己的上下文，只是注入到主 Agent 当前上下文里

适用场景：

  • 任务需要大量上下文且不希望污染主上下文 → Subagent
  • 想让主 Agent 在某类任务上表现得更专业 → Skill

它们也可以组合：Subagent 自己也可以读取并使用 Skills。

9.5 Skills 会不会让模型变得"机械"？

答：

理论上有这个风险，但实际中可控：

  • 写 Skill 时鼓励"在 X 场景下应该 Y，否则交给模型自己判断"
  • 不要把所有分支都用规则写死
  • 只在需要"稳定输出"的地方做强约束

一个好 Skill 的标志是：把"必须这样"的部分写死，把"看情况"的部分留给模型。

9.6 一个项目里 Skill 多到一定程度，会不会拖慢响应？

答：

主要成本是 metadata 占用上下文，不是加载本身。每个 Skill 的 name + description 占大约 100 tokens，永久在线。Claude Code 给 metadata listing 一个上限，默认是模型上下文窗口的 1%（可以用 skillListingBudgetFraction 调整）。超出预算时，最少被调用的 Skill 的 description 会被先截断，所以"装很多但不用"的 Skill 会先被牺牲。

经验上：

  • 几十个 Skill：几乎无感
  • 上百个：开始触发预算 trim，但你常用的那些不受影响
  • 上千个：建议分作用域（personal/project/plugin）、分 namespace（plugin 自带 plugin-name:skill-name）、用 skillOverrides 把不常用的设为 "name-only" 或 "off"

可以通过几种方式优化：

  • 用 paths: 让 Skill 只在编辑匹配文件时自动触发
  • 用 skillOverrides 在用户 settings 里关闭长期不用的 Skill
  • 不囤 Skill，用不上的删掉

9.7 Skills 能调用 Tools 吗？能调用别的 Skill 吗？

答：

  • Tools：Skill 不直接调用 Tool，但它会指挥模型调用。SKILL.md 里可以写"用 git diff 查改动"，模型读完后就会去调 Bash Tool。Skill 还能用 allowed-tools 字段预授权工具，避免每次确认。
  • 别的 Skill：通过普通 markdown 相对路径链接（如 [code-review](../code-review/SKILL.md)）引用。模型读到链接后，会通过 bash 工具按需读取被引用的文件。Claude Code 官方文档没有 [[wiki-link]] 这种特殊语法。

9.8 Skills 和 Slash Command 是不是同一个东西？

答：

在当前的 Claude Code 实现里，是同一个东西。官方文档原话：

“Custom commands have been merged into skills. A file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and work the same way.”

也就是说：

  • 你写一个 .claude/skills/code-review/SKILL.md，自动就有 /code-review 命令
  • 同一个 Skill 既能被模型自动触发（看 description），也能被用户用 /code-review 显式触发
  • 用 frontmatter 字段可以限制只允许其中一种：disable-model-invocation: true → 只能手动触发；user-invocable: false → 只能模型自动触发

老的 .claude/commands/<name>.md 仍然能用，本质是一个简化版 Skill（只有 SKILL.md 内容、没有附属文件）。如果同名的 Skill 和 Command 都存在，Skill 优先。

9.9 怎么测试一个 Skill 是不是写得好？

答：

至少做四类测试：

  1. 正向触发：用 Skill 适用的典型 prompt 测，看是否被加载并按方法执行
  2. 负向触发：用相似但不该触发的 prompt 测，看是否被错误加载
  3. 稳定性：同一类输入跑多次，输出格式是否稳定
  4. 越界：故意给一个不太相关的输入，看 Skill 会不会强行套用

只要有一类不过关，回去改 description 或 SKILL.md。

9.10 Skills 的未来会怎么发展？

答：

可以预见的几个方向：

  • Skill Marketplace：类似插件市场，可下载、安装、订阅 Skill
  • Skill 组合 / 编排：多个 Skill 形成更高阶的"工作流模板"
  • 可执行 Skill：Skill 里不止是 Markdown，还能挂脚本（Claude Code 里部分形态已支持）
  • 跨 Agent 互通：通过类似 MCP 的协议，让 Skill 可以被不同 Agent 通用读取
  • 自动生成 Skill：根据团队的对话历史和最佳实践自动萃取出 Skill

整体趋势：Skills 会成为 Agent 的"个性"和"团队记忆"的主要载体。

10.3 一个最精简的总结

如果让我用三句话总结 Skills：

  • Skills 不是工具，而是按需加载的方法书（也是 Slash Command 的实现）
  • 核心机制是三层渐进披露：metadata 永久在线（~100 tokens / Skill）→ 命中时读 SKILL.md（< 5k tokens）→ 按需读引用文件 / 跑脚本（不限）
  • 命脉是 description 写得准不准（最长 1024 字符，listing 总预算 1536 字符，关键场景写在最前）

把这三点想清楚，就能开始动手写出一个能被团队真正用起来的 Skill。
