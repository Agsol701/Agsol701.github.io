流式返回协议对比

概述

流式返回（Streaming Response）是指服务端将数据分块逐步发送给客户端，而不是等待全部处理完成后一次性返回。这种方式特别适合长耗时任务、实时数据推送等场景。

常见流式协议

1. SSE (Server-Sent Events)

基本信息

  • 协议类型：基于 HTTP 的单向推送协议
  • 标准：W3C HTML5 标准
  • 数据格式：纯文本，每行以 data: 开头
  • 传输方式：长连接

请求示例

Host: example.com
Accept: text/event-stream
Cache-Control: no-cache

Cache-Control: no-cache
Connection: keep-alive

data: {"message": "Hello"}
data: {"message": "World"}
data: {"message": "!"}

特点

特性 说明
方向 服务端 → 客户端（单向）
重连 自动重连，支持 Last-Event-ID
编码 UTF-8 纯文本
事件类型 支持自定义事件类型 event:
浏览器支持 原生支持（除 IE）

优点

  • 实现简单，基于标准 HTTP
  • 浏览器原生支持，无需额外库
  • 自动重连机制
  • 文本格式，易于调试

缺点

  • 单向通信，客户端无法主动发送数据
  • 只支持文本，二进制数据需编码
  • 请求大小限制（GET 请求）

适用场景

  • 实时通知、消息推送
  • 聊天应用（服务端推送）
  • 实时数据更新（股票、日志）
  • AI 对话流式输出

2. WebSocket

基本信息

  • 协议类型：全双工通信协议
  • 标准：RFC 6455
  • 数据格式：二进制或文本
  • 传输方式：TCP 长连接

特点

特性 说明
方向 双向全双工
连接 单一 TCP 连接
开销 低（头部仅 2-14 字节）
数据类型 文本/二进制
子协议 支持 STOMP、MQTT 等

优点

  • 双向实时通信
  • 低延迟、低开销
  • 支持二进制数据
  • 可扩展子协议

缺点

  • 需要维护连接状态
  • 需要处理心跳和重连
  • 代理服务器可能不支持
  • 实现相对复杂

适用场景

  • 实时聊天应用
  • 在线协作（多人编辑）
  • 实时游戏
  • 股票/交易行情推送

3. HTTP Chunked Transfer Encoding

基本信息

  • 协议类型：HTTP/1.1 传输编码
  • 标准：RFC 7230
  • 数据格式：分块传输
  • 传输方式：HTTP 长连接

特点

特性 说明
方向 服务端 → 客户端
分块 每块前标注大小（十六进制）
结束 0 长度块表示结束
兼容性 HTTP/1.1 标准

优点

  • 标准协议，广泛支持
  • 无需预先知道内容长度
  • 可用于大文件传输

缺点

  • 单向传输
  • 客户端断开后服务端可能继续处理
  • 格式相对复杂

适用场景

  • 大文件下载
  • 动态生成内容
  • API 流式响应（如 OpenAI API）

4. gRPC Streaming

基本信息

  • 协议类型：基于 HTTP/2 的 RPC 框架
  • 标准：gRPC Protocol
  • 数据格式：Protocol Buffers
  • 传输方式：HTTP/2 多路复用

Proto 定义

service ChatService {
  // 客户端流式
  rpc SendMessage (stream Message) returns (Response);

  // 服务端流式
  rpc GetMessages (Request) returns (stream Message);

  // 双向流式
  rpc Chat (stream Message) returns (stream Message);
}

特点

特性 说明
方向 单向/双向流式
协议 HTTP/2
序列化 Protocol Buffers
多路复用 单连接多流

优点

  • 高性能（二进制、HTTP/2）
  • 强类型（IDL 定义）
  • 支持多种流式模式
  • 内置负载均衡、认证

缺点

  • 学习曲线较陡
  • 需要代码生成
  • 调试相对困难
  • 浏览器支持需 gRPC-Web

适用场景

  • 微服务间通信
  • 高性能 API
  • 需要强类型的流式接口
  • 多语言环境

5. MQTT

基本信息

  • 协议类型：发布/订阅消息协议
  • 标准：ISO/IEC 20922 (MQTT 3.1.1)
  • 数据格式：二进制
  • 传输方式：TCP

消息格式 

Fixed Header (1-2 bytes)
  └─ Message Type + Flags
Variable Header (0-4 bytes)
  └─ Topic Name / Packet Identifier
Payload (0 bytes or more)
  └─ Application Data

特点

特性 说明
模式 发布/订阅
QoS 3 级（0/1/2）
开销 极小（最小 2 字节）
连接 持久会话

优点

  • 超低开销
  • QoS 保证
  • 离线消息支持
  • 适合 IoT 场景

缺点

  • 非标准 HTTP
  • 需要代理服务器
  • 不适合浏览器直接使用

适用场景

  • IoT 设备通信
  • 传感器数据采集
  • 实时监控
  • 消息队列

app = Flask(__name__)

@app.route('/stream')
def stream():
    def generate():
        for i in range(10):
            yield f"data: {i}\n\n"
            time.sleep(1)
    return Response(generate(), mimetype='text/event-stream')

客户端断开行为对比

协议 客户端断开后服务端行为 检测时机
SSE 立即终止（下次 yield 失败） 写入时
WebSocket 立即终止（连接关闭） 写入/读取时

gRPC 立即终止（流关闭） 写入/读取时
MQTT 会话保留，离线消息存储 连接断开时

核心概念解释

长连接 vs 短连接

短连接（Short Connection）

定义：每次通信都需要建立新的连接，通信完成后立即关闭连接。

工作流程：

客户端              服务端
  │                   │
  │ ── TCP 握手 ────→ │  建立连接
  │                   │
  │ ── 发送请求 ────→ │
  │ ←── 返回响应 ──── │
  │                   │
  │ ── 关闭连接 ────→ │  连接断开
  │                   │
  │ ── TCP 握手 ────→ │  下次请求重新建立
  │ ── 发送请求 ────→ │
  │ ←── 返回响应 ──── │
  │ ── 关闭连接 ────→ │

特点：

  • 每次请求都需要完整的 TCP 三次握手
  • 请求完成后立即断开连接
  • 服务端不需要维护连接状态
  • 并发连接数可能较多

优点：

  • 实现简单
  • 无需维护连接状态
  • 服务器资源占用可控

缺点：

  • 频繁建立/断开连接，开销大
  • 无法实现实时推送
  • 性能较差（每次都有握手延迟）

适用场景：

  • 传统 HTTP/1.0 请求
  • 请求频率低的应用
  • 不需要实时性的场景

长连接（Long Connection / Keep-Alive）

定义：建立连接后，保持连接状态，可以多次发送请求和接收响应。

工作流程：

客户端              服务端
  │                   │
  │ ── TCP 握手 ────→ │  建立连接（只一次）
  │                   │
  │ ── 发送请求1 ───→ │
  │ ←── 返回响应1 ─── │
  │                   │
  │ ── 发送请求2 ───→ │  复用同一连接
  │ ←── 返回响应2 ─── │
  │                   │
  │ ── 发送请求3 ───→ │
  │ ←── 返回响应3 ─── │
  │                   │
  │ ── 关闭连接 ────→ │  连接断开

特点：

  • 一次建立连接，多次复用
  • 通过 Connection: keep-alive 头部标识
  • 可以设置超时时间
  • 减少握手开销

优点：

  • 减少握手开销，性能更好
  • 降低延迟
  • 支持实时推送
  • 节省服务器资源

缺点：

  • 需要维护连接状态
  • 可能占用较多服务器连接资源
  • 需要处理连接超时和重连

适用场景：

  • HTTP/1.1 Keep-Alive
  • WebSocket 连接
  • SSE 流式推送
  • 数据库连接池

对比表

特性 短连接 长连接
连接建立 每次请求都建立 一次建立，多次复用
连接关闭 每次响应后关闭 超时或主动关闭
握手开销 高（每次都有） 低（只需一次）
延迟 高（每次握手） 低
服务器压力 并发连接数多 连接数少，但占用时间长
实时性 差 好
状态管理 无状态 需维护连接状态
典型协议 HTTP/1.0 HTTP/1.1、WebSocket、SSE

全双工 vs 半双工 vs 单工

单工（Simplex）

定义：数据只能沿一个方向传输，不能反向传输。

示意图：

发送端 ───────────────→ 接收端

特点：

  • 单向通信
  • 发送方只能发送，接收方只能接收
  • 类似于广播电台

例子：

  • 广播电台
  • 电视信号传输
  • 键盘到计算机

半双工（Half-Duplex）

定义：数据可以双向传输，但不能同时进行，同一时间只能有一个方向。

示意图：

发送端 ←──────────────→ 接收端
   (同一时间只能单向)

特点：

  • 双向通信
  • 但不能同时收发
  • 需要切换方向
  • 类似于对讲机

例子：

  • 对讲机
  • 早期以太网（共享介质）
  • 无线电通信

全双工（Full-Duplex）

定义：数据可以同时双向传输。

示意图：

发送端 ←──────────────→ 接收端
   (可以同时双向传输)

特点：

  • 双向同时通信
  • 无需切换方向
  • 效率最高
  • 类似于电话

例子：

  • 电话通话
  • 现代以太网
  • WebSocket
  • gRPC

对比表

特性 单工 半双工 全双工
传输方向 单向 双向（分时） 双向（同时）
同时收发 ❌ ❌ ✅
效率 低 中 高
复杂度 低 中 高
典型应用 广播、电视 对讲机 电话、WebSocket

协议特性对照

协议 连接类型 通信模式 说明
HTTP/1.0 短连接 单工 每次请求新连接
HTTP/1.1 长连接（Keep-Alive） 单工 复用连接，但仍是请求-响应模式
SSE 长连接 单工 服务端持续推送
WebSocket 长连接 全双工 双向实时通信
gRPC 长连接 全双工 基于 HTTP/2 的双向流
MQTT 长连接 半双工 发布/订阅模式

实际应用示例

场景 1：传统网页浏览（短连接 + 单工） 

浏览器 ──[请求]──→ 服务器
浏览器 ←──[响应]─── 服务器
连接关闭

场景 2：在线聊天（长连接 + 全双工） 

客户端 ←──[消息1]─── 服务器
客户端 ──[消息2]──→ 服务器
客户端 ←──[消息3]─── 服务器
客户端 ──[消息4]──→ 服务器
连接保持...

场景 3：AI 对话流式输出（长连接 + 单工） 

客户端 ──[请求]──→ 服务器
客户端 ←──[token1]── 服务器
客户端 ←──[token2]── 服务器
客户端 ←──[token3]── 服务器
...
连接关闭

总结

  • 长连接 vs 短连接：关注连接的复用方式和生命周期
  • 全双工 vs 半双工 vs 单工：关注数据传输的方向和并发性

流式协议通常使用长连接来保持持续的传输通道，而是否支持全双工则取决于协议的设计需求（如 WebSocket 支持全双工，SSE 只支持单向推送）。
