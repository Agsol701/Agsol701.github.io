AI Agent Planning 深度解析：原理、实现机制、工程实践与高频面试题

source: agent-planning
May 16, 2026

写在前面

当任务变复杂时，Agent 不能只靠"下一步做什么"的局部判断——它需要先把目标拆成可执行步骤，再根据工具结果动态调整计划。这就是 Planning（规划） 能力。

本文将从底层原理到工程实现，结合 LangChain 1.3+ / LangGraph 1.2+ 源码，深入剖析 Agent Planning 的核心机制。

一、Planning 解决什么问题

1.1 复杂任务需要拆解 

1

帮我分析这份需求，查公司已有接口规范，设计 Application Programming Interface（API，应用程序编程接口），并给出测试用例。

这个任务至少包含：理解需求 → 检索规范 → 设计接口 → 生成测试用例 → 检查风险。每个步骤之间存在依赖关系和上下文传递。

1.2 没有 Planning 的 Agent 会怎样

问题 表现
漏步骤 跳过"检索规范"直接设计接口
顺序错误 先写测试用例再设计接口
工具调用混乱 反复调用同一工具
无法解释进度 用户不知道当前在做什么
失败不可恢复 一步出错整个任务崩溃

1.3 Planning 的本质定义

Planning 是 Agent 在执行前/执行中对"做什么、按什么顺序做、如何应对变化"进行结构化决策的过程。

从控制论角度看，Planning 是一个 前馈控制(Feedforward Control) + 反馈控制(Feedback Control) 的混合系统：

┌─────────────────────────────────────────────────────────┐
│                    Planning System                        │
│                                                          │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐           │
│  │ 目标分解  │───▶│ 步骤排序  │───▶│ 资源分配  │  前馈控制  │
│  └──────────┘    └──────────┘    └──────────┘           │
│       ▲                                  │               │
│       │          ┌──────────┐            ▼               │
│       └──────────│ 计划修正  │◀────── 执行反馈   反馈控制  │
│                  └──────────┘                            │
└─────────────────────────────────────────────────────────┘

二、Planning 的学术基础与范式演进

2.1 从 CoT 到 Planning 的演进路径 

Chain-of-Thought（CoT，链式思维）
   │  线性推理，不可回溯
   ▼
ReAct（Reasoning + Acting）
   │  推理与行动交替，有外部反馈
   ▼
PS/PS+（Plan-and-Solve / Plan-and-Solve Plus）
   │  先规划后执行，两阶段分离
   ▼
Tree of Thoughts（ToT，思维树）
   │  多路径搜索，可回溯
   ▼
LATS（Language Agent Tree Search）
      结合 Monte Carlo Tree Search（MCTS，蒙特卡洛树搜索），规划+行动+推理统一

2.2 CoT：线性推理的起点

核心思想：通过在 Prompt 中加入 “Let’s think step by step”，引导 Large Language Model（LLM，大语言模型）生成中间推理步骤，而非直接输出最终答案。

示例对比：

# 标准 Prompting（直接回答）
Q: 一个商店苹果5元，买3个打9折，多少钱？
A: 13.5元

# CoT Prompting（逐步推理）
Q: 一个商店苹果5元，买3个打9折，多少钱？
A: 先计算原价：5 × 3 = 15元
   再打9折：15 × 0.9 = 13.5元
   答案是 13.5元

CoT 的两种形态：

Few-shot CoT

做法：在 Prompt 中手动编写若干带推理过程的示例（exemplars），让 LLM 通过 in-context learning 模仿这种"边想边答"的模式。

# Prompt 中提供的示例（人工编写）
Q: Roger 有5个网球，他又买了2罐，每罐3个，他现在有多少个？
A: Roger 一开始有5个球。2罐每罐3个，共 2×3=6 个。5+6=11。答案是11。

Q: 食堂有23个苹果，用掉20个做午餐，又买了6个，还剩多少？
A: 原来23个，用了20个剩 23-20=3 个。又买6个，3+6=9。答案是9。

# 然后给出实际问题，LLM 会模仿上面的推理风格作答
Q: ...
A: (LLM 生成带推理链的回答)

关键特点：

  • 需要人工精心设计示例，示例质量直接影响推理效果
  • 示例中的推理路径起到"教学"作用，告诉模型该如何分步思考
  • 对不同任务需要不同的示例（迁移性差）
  • 在数学推理任务（GSM8K）上，将 PaLM-540B 的准确率从 18% 提升到 57%

Zero-shot CoT

做法：不提供任何示例，仅在问题后追加一句触发语 “Let’s think step by step”，即可激发 LLM 的逐步推理能力。

Q: 一个商店苹果5元，买3个打9折，多少钱？

# 只需追加这一句触发语：
A: Let's think step by step.
   首先，3个苹果的原价是 5×3 = 15元。
   然后，打9折后价格为 15×0.9 = 13.5元。
   所以答案是 13.5元。

关键特点：

  • 零成本：不需要编写任何示例，通用于所有任务
  • 本质是一个"元提示"（meta-prompt），激活了 LLM 预训练时学到的逐步推理模式
  • 效果通常弱于 Few-shot CoT，因为没有任务特定的示例引导
  • 但在某些任务上已经足够，且极其简单易用

两者对比

维度 Few-shot CoT Zero-shot CoT
示例需求 需要 2-8 个人工编写的示例 不需要任何示例
准备成本 高（需人工设计推理过程） 几乎为零
推理质量 更高（有示例引导） 较低（纯靠模型自身能力）
任务迁移性 差（每个任务需要新示例） 好（同一句触发语通用）
Token 开销 高（示例占用上下文） 低（仅多一句话）
典型触发方式 精心设计的 Q-A 示例对 “Let’s think step by step”
后续发展 → Self-Consistency（多次采样投票） → Plan-and-Solve（替换为更结构化的触发语）

CoT 的局限性（也是后续方法改进的方向）：

  1. 单路径：只生成一条推理链，无法回溯纠错
  2. 无外部反馈：纯内部推理，不与环境交互，易产生幻觉
  3. 无显式计划：推理方向隐式决定，不可控
  4. 串行思考：不支持并行探索多种可能

这些局限催生了 ReAct（引入外部行动）、Plan-and-Solve（引入显式规划）、ToT 等后续工作。

2.3 ReAct：推理与行动的交替

核心思想：LLM 交替生成推理轨迹(Thought)和任务动作(Action)，每次行动后获得观测(Observation)反馈。

Thought 1: 我需要查找公司的接口规范文档
Action 1:  search_docs("接口规范")
Obs 1:     找到《RESTful API 设计规范 v2.3》
Thought 2: 规范要求使用 JavaScript Object Notation（JSON，JS 对象表示法）Schema，我需要先确认鉴权方式
Action 2:  search_docs("鉴权方式")
Obs 2:     规范要求使用 OAuth 2.0
Thought 3: 现在可以设计 API 了...

ReAct 的局限：本质是贪心搜索（Greedy Search），每一步只考虑当前最优动作，没有全局计划。

2.4 Plan-and-Solve：两阶段分离

核心创新：将零样本 CoT 的 “Let’s think step by step” 替换为显式的两阶段指令。

变体 Prompt 模板 改进点
PS “Let’s first devise a plan, then solve step by step” 显式规划阶段
PS+ PS + “extract relevant variables” + “calculate intermediate results” 减少计算错误和语义遗漏

关键洞察：仅通过 prompt 引导 LLM 在回答前先生成计划，就能显著提升推理质量。

2.5 Tree of Thoughts：多路径搜索

核心机制：将推理过程组织为树结构，每个节点是一个"想法"(Thought)，允许多个分支并行探索并回溯。

                      [目标]
                    /    |    \
              [方案A]  [方案B]  [方案C]
              /    \      |       ✗ (剪枝)
         [A.1]  [A.2]  [B.1]
           ✓      ✗      ✓

与 CoT 的对比：

维度 CoT ToT
搜索策略 单路径，贪心 多路径，BFS/DFS
可回溯性 不可回溯 可回溯
评估机制 无中间评估 每步自评估
适用场景 简单推理 需要探索的复杂决策

为什么 CoT 不可回溯而 ToT 可以？——底层机制差异：

根本原因在于 谁控制推理流程：

CoT：LLM 自回归生成控制流程（模型内部）
ToT：外部程序控制流程，LLM 只负责生成和评估（模型外部）

具体来说：

CoT 不可回溯的原因：

LLM 本质是一个自回归模型（Autoregressive Model），token 逐个从左到右生成。一旦某个 token 被输出，它就成为后续生成的固定上下文——模型没有"撤销已生成内容"的机制。

LLM 生成过程（不可逆）：

  token_1 → token_2 → token_3 → ... → token_n
     ↓         ↓         ↓
  固定上下文，无法修改，只能继续往右生成

# CoT 就是一次完整的自回归生成：
"Step 1: 7×4=28 → Step 2: 28-2=26 → Step 3: ..."
  ──────────── 这是一次连续生成，无法回到 Step 1 重新选择 ──────────

ToT 可以回溯的原因：

ToT 将控制权从 LLM 内部转移到外部程序。每个"Thought"是一次独立的 LLM 调用，由外部代码维护树结构、决定扩展哪个节点、丢弃哪个分支。

外部程序控制（可回溯）：

  ┌─ 调用LLM生成 Thought A ──▶ 调用LLM评估 ──▶ 得分 0.3（差）──▶ 丢弃
  │
  ├─ 调用LLM生成 Thought B ──▶ 调用LLM评估 ──▶ 得分 0.8（好）──▶ 继续扩展
  │                                                                    │
  │                                              ┌─ 调用LLM生成 B.1 ──▶ ...
  │                                              └─ 调用LLM生成 B.2 ──▶ ...
  │
  └─ 调用LLM生成 Thought C ──▶ 调用LLM评估 ──▶ 得分 0.5（中）──▶ 暂存

  # "回溯" = 外部程序选择从另一个节点重新开始调用LLM，而非LLM自己退回

类比理解：

CoT ToT
类比 用笔在纸上写字，写错了无法擦除 用便利贴，每个想法写一张，贴在白板上，随时撕掉重来
控制者 LLM 自己（单次生成） 外部程序（多次独立调用 LLM）
状态管理 模型内部隐式状态（KV Cache） 外部显式数据结构（树/队列）
LLM 角色 既是思考者也是决策者 只是"思考生成器"和"评估打分器"
代价 1 次 LLM 调用 N 次 LLM 调用（生成×节点数 + 评估×节点数）

简言之：CoT 的"推理"发生在一次 LLM 调用内部，无法回退；ToT 的"推理"发生在多次独立 LLM 调用之间，由外部代码自由编排，自然支持回溯。

Game of 24 实验：

Game of 24 是一个经典数学推理游戏——给定 4 个数字（1-13），通过加减乘除和括号运算，使结果恰好等于 24。例如给定 [4, 9, 10, 13]，一个合法解是 (10 - 4) × (13 - 9) = 24。

这个任务对 LLM 极具挑战性，因为：

  • 搜索空间大：4 个数字的全排列 × 运算符组合 × 括号位置
  • 需要试错回溯：大部分路径走不通，必须换方向
  • 早期选择影响全局：第一步选错数字/运算符，后面无论如何组合都无法得到 24
# 示例：给定数字 [1, 2, 4, 7]

# CoT 方式（线性尝试，一条路走到底）：
Step 1: 7 × 4 = 28, 太大了... 
Step 2: 28 - 2 = 26, 不行...
Step 3: 放弃这条路，但 CoT 无法回溯 → 失败

# ToT 方式（多路径并行探索 + 回溯）：
分支A: 7 × 4 = 28 → 评估：需要减4，但只剩1和2 → 剪枝
分支B: 7 × 2 = 14 → 评估：需要再得到10 → 继续探索
分支C: 4 × (7 - 1) = 24 ✓ → 成功！

实验结果：GPT-4 + CoT 成功率仅 4%，GPT-4 + ToT 成功率达到 74%——提升 18.5 倍。这证明了在需要搜索和回溯的任务中，多路径探索远胜于线性推理。

2.6 LATS：统一规划-行动-推理

什么是蒙特卡洛树搜索（MCTS）

MCTS 是一种用于决策问题的搜索算法，最著名的应用是 AlphaGo。它的核心思想是：不穷举所有可能，而是通过随机模拟来估计每条路径的价值，优先探索最有前途的方向。

现实类比：

假设你要在一座陌生城市找最好的餐厅：

  • 穷举法：吃遍所有餐厅（不现实）
  • 贪心法：去评分最高的那家（可能被刷好评）
  • MCTS 法：先随机试几家 → 记住哪个区域好吃 → 在好吃的区域多试几家 → 逐步缩小范围

MCTS 的四个步骤：

              ┌─────────────────────────────────────────────────┐
              │         MCTS 单次迭代（不断重复）                  │
              │                                                  │
              │  ┌────────────┐     从根节点沿"最有前途"的路径     │
Step 1        │  │  Selection │     向下走，直到到达叶节点         │
(选择)        │  │  (选择)     │     使用 UCB 公式平衡探索/利用    │
              │  └─────┬──────┘                                  │
              │        ▼                                         │
              │  ┌────────────┐     在叶节点生成一个或多个         │
Step 2        │  │  Expansion │     新的子节点（候选动作）         │
(扩展)        │  │  (扩展)     │                                  │
              │  └─────┬──────┘                                  │
              │        ▼                                         │
              │  ┌────────────┐     从新节点出发，随机模拟到       │
Step 3        │  │ Simulation │     终局，得到一个胜/负结果        │
(模拟)        │  │  (模拟)     │     （或用评估函数直接打分）       │
              │  └─────┬──────┘                                  │
              │        ▼                                         │
              │  ┌────────────┐     将模拟结果沿路径回传给         │
Step 4        │  │Backpropagation│  所有祖先节点，更新其统计信息   │
(回传)        │  │  (回传)     │     （访问次数、胜率）            │
              │  └─────────────┘                                  │
              └─────────────────────────────────────────────────┘

UCB（Upper Confidence Bound，置信上界）公式（Selection 阶段用于选节点）：

UCB = 胜率/平均价值 + C × √(ln(父节点访问次数) / 本节点访问次数)
      ─────────────   ──────────────────────────────────────────
         利用项                       探索项
      (选价值高的)              (选访问少的，避免遗漏)
  • 利用项高 → 这条路看起来好，继续走
  • 探索项高 → 这条路还没怎么试过，去看看
  • C 是平衡系数，控制"冒险程度"

为什么 MCTS 适合与 LLM 结合：

MCTS 需要的能力 LLM 可以提供
生成候选动作（Expansion） LLM 天然擅长生成多种方案
评估局面好坏（Simulation） LLM 可以自评估/打分
需要领域知识引导搜索 LLM 的预训练知识天然提供先验

LATS 如何将 MCTS 与 LLM Agent 结合

LATS 的创新是将 MCTS 的四步映射到 Agent 场景：

┌───────────────────────────────────────────────────────────┐
│           LATS = MCTS + LLM Agent                          │
│                                                            │
│  MCTS 步骤        LATS 中的实现                             │
│  ─────────        ──────────────                           │
│  Selection   ──▶  UCB 公式选择最值得探索的动作路径           │
│                                                            │
│  Expansion   ──▶  LLM 生成多个候选动作（如调用不同工具）     │
│                                                            │
│  Simulation  ──▶  LLM 自评估 + 实际执行动作获得环境反馈      │

│                                                            │
│  Backprop    ──▶  将环境反馈的价值回传给祖先节点             │

└───────────────────────────────────────────────────────────┘

LATS vs ToT 的区别：

维度 ToT LATS
评估方式 LLM 纯自评估（可能幻觉） LLM 评估 + 环境真实反馈
是否有动作 否（纯推理空间） 是（与工具/环境交互）
节点选择策略 简单 BFS（Breadth-First Search，广度优先搜索）/DFS（Depth-First Search，深度优先搜索） UCB 公式（有数学保证）
历史利用 不利用失败经验 失败路径通过 Backprop 降低权重
适用场景 推理类任务（24点、写作） 需要交互的 Agent 任务（编程、网页操作）

三、ReAct 实现机制：Agent 如何边想边做（源码解析）

ReAct 是 Agent 最基础的执行模式。理解它是理解后续 Plan-and-Execute 的前提——Plan-and-Execute 本质上是在 ReAct 之上加了一个"全局规划层"。

3.1 ReAct 的核心思想

ReAct = 每步都让 LLM 决定"现在做什么"，做完拿到反馈，再决定下一步。没有预先计划，靠逐步反应推进任务。

┌───────────────────────────────────────────────────────┐
│              ReAct 执行循环                              │
│                                                        │
│  用户输入 ──▶ [LLM 思考+决定动作]                        │
│                      │                                 │
│              有 tool_calls?                             │
│              /           \                             │
│           是              否                            │
│            │               │                           │
│      [执行工具]         [返回最终回答]                    │
│            │                                           │
│      [工具结果追加到消息]                                 │
│            │                                           │
│            └──────▶ [LLM 再次思考] ──▶ ...（循环）      │
└───────────────────────────────────────────────────────┘

一句话总结：ReAct 是"走一步看一步"，每一步的决策质量完全依赖 LLM 对当前上下文的判断。

3.3 ReAct 的局限——为什么需要 Planning

局限 表现 后果
无全局视图 每步只看当前消息决策 容易遗漏步骤或做无用功

class TodoListMiddleware(AgentMiddleware):
    """不改变图结构，通过注入工具+prompt 让 Agent 自发规划"""

    def wrap_model_call(self, request, handler):
        # 在 system message 中追加 "如何使用 write_todos" 的引导

    def after_model(self, state, runtime):
        # 防止 Agent 并行调用多次 write_todos（全量替换会冲突）
        write_todos_calls = [tc for tc in last_ai_msg.tool_calls if tc["name"] == "write_todos"]
        if len(write_todos_calls) > 1:
            return {"messages": [error_messages]}
        return None

四、Plan-and-Execute：先规划再执行（显式 Planning）

当 ReAct 的"走一步看一步"不够用时，就需要 Plan-and-Execute——先让一个 Planner 生成全局计划，再让 Executor 按步骤执行，执行中根据反馈动态调整计划。

4.2 与 ReAct 的核心区别

维度 ReAct（第三章） Plan-and-Execute
决策视野 局部（每步决策） 全局（先规划再执行）
有无显式计划 无（LLM 隐式决定方向） 有（结构化 JSON/列表）

调整机制 每步可切换方向（但无记录） Replanning 节点显式修改计划

from langchain_core.messages import AnyMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

# 1. 定义 State：比 ReAct 多了 plan/current_step/results 字段
class PlanExecuteState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    plan: list[str]           # 计划步骤列表
    current_step: str | None  # 当前正在执行的步骤
    results: dict[str, str]   # 每步执行结果
    response: str | None      # 最终响应

# 2. 定义三个独立节点
async def planner_node(state: PlanExecuteState) -> dict:
    """Planner: 根据用户目标生成全局计划"""
    plan = await planner_llm.ainvoke(state["messages"])
    return {"plan": plan.steps, "current_step": plan.steps[0]}

async def executor_node(state: PlanExecuteState) -> dict:
    """Executor: 只关注当前步骤，调用工具完成它"""
    step = state["current_step"]
    result = await executor_chain.ainvoke({"step": step, "context": state["results"]})
    results = state["results"].copy()
    results[step] = result
    return {"results": results}

async def replanner_node(state: PlanExecuteState) -> dict:
    """Replanner: 根据执行结果决定——继续/调整计划/结束"""
    remaining = [s for s in state["plan"] if s not in state["results"]]
    if not remaining:
        return {"response": synthesize(state["results"]), "current_step": None}
    revised_plan = await replanner_llm.ainvoke({
        "original_plan": state["plan"],
        "completed": state["results"],
        "remaining": remaining,
    })
    return {"plan": revised_plan.steps, "current_step": revised_plan.steps[0]}

# 3. 构建图
def should_continue(state: PlanExecuteState) -> str:
    if state.get("response"):
        return END
    return "executor"

workflow = StateGraph(PlanExecuteState)
workflow.add_node("planner", planner_node)
workflow.add_node("executor", executor_node)
workflow.add_node("replanner", replanner_node)

workflow.add_edge(START, "planner")
workflow.add_edge("planner", "executor")
workflow.add_edge("executor", "replanner")
workflow.add_conditional_edges("replanner", should_continue, {END: END, "executor": "executor"})

app = workflow.compile()

五、动态调整计划（Replanning）

5.1 Replanning 的本质：计划层面的 ReAct

Replanning 不是某个框架独有的 API，而是一类控制策略：在执行过程中观察中间结果，再判断原计划是否仍然适用。

它和 ReAct 都属于"观察 → 决策 → 行动"的反馈循环，但两者的决策粒度不同：

ReAct（动作级反馈）:
  观察工具结果 → 决定下一个工具调用 → 执行工具 → 继续观察

Replanning（计划级反馈）:
  观察步骤结果 → 判断计划是否仍成立 → 继续/修订/终止 → 执行后续步骤

所以，更准确的说法是：Replanning 可以被实现成计划层面的 ReAct 式循环，但它本身不等同于 ReAct。

┌─────────────────────────────────────────────────────────────┐
│  计划层循环（Plan / Execute / Replan）                         │
│                                                              │
│   观察: 已完成步骤、失败信息、用户新输入                         │
│   决策: 继续原计划 / 修改后续步骤 / 直接结束                     │
│   输出: 更新后的 plan、当前 step 或最终 response                 │
│                                                              │
│   ┌───────────────────────────────────────────────────────┐  │
│   │  执行层循环（可选：ReAct Agent）                         │  │
│   │                                                        │  │
│   │   观察: 当前步骤 + 相关上下文                            │  │
│   │   决策: 调用哪个工具、传什么参数                          │  │
│   │   输出: 当前步骤的执行结果                               │  │
│   └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘

关键区别：

维度 ReAct（动作级） Replanning（计划级）
决策对象 下一个工具调用或动作 后续计划是否需要调整
操作粒度 单个 action / tool call 一组 step 的增删改排
信息输入 当前消息和工具返回 已完成步骤、剩余步骤、失败信息、用户变更
典型输出 Action 或最终回答 Continue / Replan / Finish
失败影响 单步失败，可重试或换工具 计划假设失效，后续步骤可能整体需要重排

为什么不能只依赖一层 ReAct？

理论上，强模型可以通过连续 ReAct 完成较长任务；但工程实践中，显式计划层能降低三类风险：

  • 长上下文中目标和约束被稀释，后续 action 容易偏离任务主线
  • 没有显式剩余步骤，难以判断任务进度和遗漏项
  • 发现前置假设错误时，只靠下一次 action 很难系统性重排后续工作

因此，Plan-and-Execute 通常把职责拆开：计划层决定做什么以及是否改计划，执行层决定怎么完成当前步骤。

两种常见实现方式

Replanning 和 ReAct 的关系不能简单说成"谁包含谁"，更准确地说，它们可以组合成两种工程形态。

方式 A：把 Replanning 当作普通 Agent 的一个能力

单循环 Agent:
  Thought → Action(执行/查询/写入计划) → Observation → Thought → ...

# 计划更新只是 Agent 可选择的一类动作
# 例如通过 todo / plan 工具维护任务列表，由 Agent 自主决定何时更新

这种方式下：

  • ReAct 或类似 agent loop 负责整体循环
  • Replanning 体现为"更新任务列表/修改后续步骤"的能力
  • 优点是实现简单，缺点是是否及时重规划依赖模型自觉性和提示词约束

方式 B：把 Replanning 建成独立图节点

显式 Plan-and-Execute:
  Planner → Executor → Replanner → Executor → ... → END

# Replanner 是独立节点，读取状态并返回结构化决策

这种方式下：

  • Replanner 通常有单独 Prompt 和结构化输出 Schema

适用场景 中等复杂度任务、交互式协作 长任务、强审计、强可控流程

本文的立场：两种方式都合理。中等任务可以让 Agent 在同一循环里维护计划；复杂任务更适合把 Replanner 显式建模为节点。后续代码示例采用方式 B 的写法，但它是工程模板，不是 LangGraph 内置的唯一标准实现。

5.2 为什么必须支持动态调整

计划不是一次生成就永远正确。实际执行中的常见变化包括：

触发场景 应对策略
工具返回可恢复错误 重试、换参数或替换工具
信息不足 插入新的信息收集步骤
用户补充或改变需求 合并新约束，重排后续步骤
前置假设不成立 废弃受影响步骤，重新规划
已经足够回答 提前结束，避免无意义执行
发现更优路径 替换或合并后续步骤

这里要区分两类调整：

  • 局部恢复：只影响当前步骤，例如工具超时后重试一次
  • 全局重规划：影响后续路径，例如发现需求理解错了，需要重写剩余计划

不是每个异常都要触发完整 Replanning。工程上通常会先做局部恢复，只有当失败改变了计划假设、目标约束或步骤依赖时，才进入计划级重规划。

七、LangGraph 底层执行机制

前面章节展示了如何用 LangGraph 构建 Planning Agent。本章深入底层——理解 LangGraph 的执行引擎如何驱动这些图的运行，以及 State/Channel/Checkpoint 机制的实现原理。

7.1 Pregel 模型：图计算的底层范式

LangGraph 的执行引擎基于 Google Pregel 论文（2010）的图计算模型。理解 Pregel 是理解 LangGraph 所有行为的基础。

Pregel 的核心思想

传统编程是"顺序执行指令"，Pregel 是"图节点并行计算，通过消息通信"：

┌───────────────────────────────────────────────────────────────┐
│               Pregel 执行模型（Superstep 驱动）                  │
│                                                                │
│  Superstep 0:  输入写入 Channel                                │
│       │                                                        │
│       ▼                                                        │
│  Superstep 1:  所有被触发的 Node 并行执行                       │
│       │        每个 Node: 读取 Channel → 计算 → 写入 Channel    │
│       ▼                                                        │
│  Superstep 2:  Channel 更新触发了新的 Node                      │
│       │        被触发的 Node 并行执行                            │
│       ▼                                                        │
│  Superstep N:  没有新的 Node 被触发 → 终止                      │
│       │                                                        │
│       ▼                                                        │
│     输出                                                        │
└───────────────────────────────────────────────────────────────┘

概念映射到 Agent 场景

Pregel 概念 LangGraph 实现 Agent 场景含义
Node（节点） workflow.add_node("planner", fn) Agent 的一个处理步骤
Channel（通道） State 中的每个字段 节点间传递数据的管道
Superstep（超步） 一次 tick（读→执行→写） 一轮节点执行
Message（消息） 节点返回的 dict（State 更新） 节点的输出
Termination（终止） 没有节点被触发 / 到达 END Agent 任务完成

为什么选择 Pregel 而非普通 DAG

普通 DAG 执行器（如 Airflow）是"预先确定全部执行顺序"，而 Pregel 是"动态决定下一步执行谁"：

DAG 执行器:
  编译时确定: A → B → C → D（固定拓扑）
  运行时无法改变执行路径

Pregel 执行器:
  每个 Superstep 动态判断: 哪些 Channel 被更新了？哪些 Node 被触发？
  运行时可以根据 State 选择不同路径（条件边）

这正是 Agent 需要的——根据 LLM 的输出动态决定下一步是"调用工具"还是"结束"。

class BinaryOperatorAggregate(BaseChannel):
    def update(self, values: Sequence[Value]) -> bool:
        """核心方法：接收本轮所有写入值，用 operator 逐个合并"""
        if not values:
            return False
        if self.value is MISSING:
            self.value = values[0]
            values = values[1:]
        for value in values:
            # 检测 Overwrite 标记（强制覆盖而非合并）
            is_overwrite, overwrite_value = _get_overwrite(value)
            if is_overwrite:
                self.value = overwrite_value
            else:
                # 调用 reducer: self.value = operator(self.value, value)
                self.value = self.operator(self.value, value)
        return True

class LastValue(BaseChannel):
    def update(self, values: Sequence[Value]) -> bool:
        if len(values) == 0:
            return False
        if len(values) != 1:
            # 同一 Superstep 内多个节点写入同一个 LastValue Channel → 报错
            raise InvalidUpdateError(
                "At key '{key}': Can receive only one value per step. "
                "Use an Annotated key to handle multiple values."

        self.value = values[0]
        return True

# 简化后的 PregelLoop 核心执行逻辑:
class PregelLoop:
    step: int       # 当前 Superstep 编号
    stop: int       # 最大 Superstep 数（recursion_limit）
    channels: dict  # 所有 Channel 实例
    checkpoint: Checkpoint  # 当前检查点

    def tick(self) -> bool:
        """执行一个 Superstep，返回是否还需要继续"""

        # 1. 确定本轮要执行哪些 Task（Node）
        #    根据哪些 Channel 在上一轮被更新，触发对应的 Node
        tasks = prepare_next_tasks(self.checkpoint, self.channels, ...)

        if not tasks:
            return False  # 没有任务要执行 → 图终止

        # 2. 并行执行所有 Task
        #    每个 Task 读取 Channel → 执行 Node 函数 → 产生 writes
        for task in tasks:
            task.writes = execute_node(task.node_fn, read_channels(...))

        # 3. 将所有 writes 应用到 Channel
        #    调用每个 Channel 的 update/reducer
        updated_channels = apply_writes(
            self.checkpoint, self.channels, tasks, ...
        )

        # 4. 保存 Checkpoint（如果配置了 Checkpointer）
        if self.checkpointer:
            save_checkpoint(self.checkpoint, self.channels)

        # 5. 检查中断条件
        if should_interrupt(tasks, self.interrupt_after):
            return False  # 用户请求中断

        self.step += 1
        return self.step < self.stop  # 未超过最大步数则继续

def apply_writes(checkpoint, channels, tasks, get_next_version, trigger_to_nodes):
    """将一组 Task 的写入应用到 Channel，返回被更新的 Channel 集合"""

    # 1. 按路径排序，确保确定性顺序
    tasks = sorted(tasks, key=lambda t: task_path_str(t.path[:3]))

    # 2. 更新 versions_seen（记录每个 Node 看到过哪些 Channel 版本）
    for task in tasks:
        checkpoint["versions_seen"][task.name].update(...)

    # 3. 消费已读取的 Channel（某些 Channel 读取后清空，如 EphemeralValue）
    for chan in triggered_channels:
        channels[chan].consume()

    # 4. 按 Channel 分组写入
    pending_writes_by_channel = defaultdict(list)
    for task in tasks:
        for chan, val in task.writes:
            pending_writes_by_channel[chan].append(val)

    # 5. 调用每个 Channel 的 update（触发 Reducer）
    updated_channels = set()
    for chan, vals in pending_writes_by_channel.items():
        if channels[chan].update(vals):       # ← Reducer 在这里被调用
            updated_channels.add(chan)

    # 6. 判断是否应该终止
    #    如果没有 Channel 更新能触发新的 Node → 图自然终止
    if updated_channels.isdisjoint(trigger_to_nodes):
        # 通知所有 Channel 执行 finish()
        for chan in channels:
            channels[chan].finish()

    return updated_channels

关键洞察：图的终止条件是"没有 Channel 的更新能触发任何 Node"——这是一个自然终止条件，不需要显式设置。条件边（add_conditional_edges）通过控制"写入哪个 Channel"来控制"触发哪个 Node"。

┌────────────────────────────────────────────────────────────────┐
│  Send 的执行流程                                                │
│                                                                 │
│  条件边返回 [Send("tools", data1), Send("tools", data2)]        │
│       │                                                         │

# 判断 Node 是否应该在下一个 Superstep 执行:
def should_node_execute(node_name, triggers, checkpoint):
    """Node 的某个触发 Channel 有了新版本（Node 还没看到过）"""
    for trigger_channel in triggers:
        channel_version = checkpoint["channel_versions"].get(trigger_channel)

    return False

def get_next_executable_steps(plan: list[PlanStep], results: dict) -> list[PlanStep]:
    """正确处理依赖关系的步骤调度"""
    executable = []
    failed_steps = {s["id"] for s in plan if s["status"] == "failed"}

    for step in plan:
        if step["status"] != "pending":
            continue
        # 检查所有依赖是否已完成
        deps_met = all(
            dep in results and dep not in failed_steps
            for dep in step["depends_on"]
        )
        # 如果依赖失败，标记为 blocked
        deps_failed = any(dep in failed_steps for dep in step["depends_on"])
        if deps_failed:
            step["status"] = "blocked"
        elif deps_met:
            executable.append(step)

    return executable

"""
完整的 Plan-and-Execute Agent 实现
基于 LangChain 1.3+ / LangGraph 1.2+
"""
from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, SystemMessage
from langchain_core.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from pydantic import BaseModel


# ========== 1. 定义工具 ==========
@tool
def search_docs(query: str) -> str:
    """搜索内部文档"""
    return f"搜索结果：找到关于'{query}'的3篇文档..."

@tool
def write_code(spec: str) -> str:
    """根据规格生成代码"""
    return f"已根据规格生成代码：{spec[:50]}..."

@tool
def run_tests(code: str) -> str:
    """运行测试"""
    return "所有测试通过 (12/12)"


# ========== 2. 定义 State ==========
class PlanStep(BaseModel):
    name: str
    description: str

class PlanOutput(BaseModel):
    steps: list[PlanStep]
    reasoning: str

class ReplanDecision(BaseModel):
    action: str  # "continue" | "replan" | "finish"
    new_steps: list[PlanStep] | None = None
    final_answer: str | None = None

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    plan: list[str]
    current_step: str | None
    results: dict[str, str]
    response: str | None
    step_count: int


# ========== 3. 定义节点 ==========
async def plan_node(state: AgentState) -> dict:
    """生成初始计划"""
    planner = model.with_structured_output(PlanOutput)
    user_goal = state["messages"][-1].content
    result = await planner.ainvoke([
        SystemMessage("将用户目标分解为3-8个可执行步骤。"),
        HumanMessage(user_goal)
    ])
    steps = [s.name for s in result.steps]
    return {
        "plan": steps,
        "current_step": steps[0],
        "results": {},
        "step_count": 0
    }

async def execute_node(state: AgentState) -> dict:
    """执行当前步骤"""
    executor = model.bind_tools([search_docs, write_code, run_tests])
    context = "\n".join(f"- {k}: {v}" for k, v in state["results"].items())
    result = await executor.ainvoke([
        SystemMessage(f"执行以下步骤。前序结果:\n{context}"),
        HumanMessage(f"请执行: {state['current_step']}")
    ])
    # 简化处理：直接记录结果
    return {
        "results": {**state["results"], state["current_step"]: result.content},
        "step_count": state["step_count"] + 1
    }

async def replan_node(state: AgentState) -> dict:
    """决定下一步：继续/重新规划/结束"""
    remaining = [s for s in state["plan"] if s not in state["results"]]
    if not remaining:
        return {"response": "所有步骤已完成。" + str(state["results"]), "current_step": None}
    return {"current_step": remaining[0]}


# ========== 4. 定义路由 ==========
def route_after_replan(state: AgentState) -> str:
    if state.get("response"):
        return END
    if state["step_count"] >= 15:  # 安全阀
        return "force_end"
    return "execute"


# ========== 5. 组装图 ==========
workflow = StateGraph(AgentState)
workflow.add_node("plan", plan_node)
workflow.add_node("execute", execute_node)
workflow.add_node("replan", replan_node)

workflow.add_edge(START, "plan")
workflow.add_edge("plan", "execute")
workflow.add_edge("execute", "replan")
workflow.add_conditional_edges("replan", route_after_replan, {END: END, "execute": "execute"})

app = workflow.compile(checkpointer=InMemorySaver())

十一、高频面试题

Q1: Agent 为什么需要 Planning？和直接用 ReAct 有什么区别？

答：

  • 必要性：复杂任务（5步以上）包含多个子目标和依赖关系。没有计划，Agent 容易漏步骤、顺序错误、重复执行。
  • 与 ReAct 的区别：
    • ReAct 是逐步决策（Greedy），每步只看当前状态决定下一步动作，没有全局视图。
    • Plan-and-Execute 是先全局规划再逐步执行，有显式计划可以追踪和修改。
    • ReAct 适合 3-5 步的简单任务；Plan-and-Execute 适合 5-20+ 步的复杂任务。
    • Plan-and-Execute 的 Token 效率更高，因为 Executor 只需关注当前步骤的上下文。

Q2: Plan-and-Solve Prompting 的核心思想是什么？

答：

  • 将零样本 CoT 的 “Let’s think step by step” 替换为两阶段指令：先 Plan（制定方案）再 Solve（逐步执行）。
  • PS+ 在此基础上追加细化指令（提取变量、计算中间结果），减少计算错误和语义遗漏。
  • 核心洞察：仅通过 Prompt Engineering 让 LLM 显式生成计划，就能大幅提升复杂推理质量。

Q3: Tree of Thoughts 和普通 CoT 的本质区别？

答：

维度 CoT ToT
搜索方式 单路径、贪心 多路径、BFS/DFS
可否回溯 不可 可以
中间评估 无 有（LLM 自评估）
计算成本 O(1)路径 O(b^d)路径
适用场景 线性推理 需要探索的决策问题

Game of 24 任务中，CoT 成功率 4%，ToT 成功率 74%。

Q4: Replanning 如何避免无限循环？

答：

工程中必须设置多重终止条件：

  1. 最大重规划次数：超过 N 次 Replanning 强制结束
  2. 最大总步骤数：执行超过 M 步强制结束
  3. Token 预算：总 Token 消耗超过阈值时停止
  4. LLM 指令：在 Replanner 的 Prompt 中明确要求"如果信息足够就生成最终答案"
  5. 递减信心：每次 Replan 降低"需要继续"的概率

Q5: LangGraph 中如何实现 Plan-and-Execute？

答：

核心组件：

  1. StateGraph 定义图结构，State 中包含 plan、current_step、results 字段
  2. planner_node：调用 LLM + with_structured_output 生成结构化计划
  3. executor_node：调用 LLM + tools 执行当前步骤
  4. replanner_node：判断继续/修改计划/结束
  5. add_conditional_edges：根据 Replanner 输出路由到不同节点
  6. Checkpointer：持久化中间状态，支持中断恢复

Q6: 如何解决 Planning 中的 Token 消耗问题？

答：

  1. Planner 和 Executor 分离：Executor 只需当前步骤上下文，不需全局历史
  2. 结果摘要：只传递最近 N 步的结果摘要给 Replanner，不传全量
  3. SummarizationMiddleware：LangChain 1.3 内置的消息压缩中间件
  4. 分层 Planning：大任务拆成子任务，每个子任务独立上下文
  5. Structured Output：用 with_structured_output 让 LLM 输出精简结构，避免冗余文本

Q7: Planning 和 Workflow 有什么区别？什么时候用哪个？

答：

维度 Planning Workflow
定义时机 运行时动态生成 开发时预先定义
灵活性 高（可处理开放域任务） 低（固定流程）
可靠性 较低（依赖 LLM） 高（确定性执行）
Token 成本 高（需要 LLM 规划） 低（无规划开销）
适用场景 开放域/未知任务 业务流程/确定性任务

最佳实践：用 Workflow 定义骨架（确定性部分），用 Planning 处理动态部分（开放域子任务）。

Q8: LangChain 1.3 的 Middleware 机制如何支撑 Planning？

答：

Middleware 采用洋葱模型（类似 Express/Koa）：

  • wrap_model_call：拦截 LLM 调用前后，注入 Planning 相关的 System Prompt
  • after_model：LLM 返回后检查（如 TodoListMiddleware 检查是否并行调用了 write_todos）
  • wrap_tool_call：拦截工具调用，可实现工具级别的计划验证

TodoListMiddleware 通过注入 write_todos 工具和引导 Prompt，让 Agent 自动维护任务列表。关键设计：用 Command(update={...}) 直接更新 State，避免序列化问题。

Q9: 如何设计计划的粒度？

答：

黄金法则：每个步骤应能被 1 次 LLM 调用 + 1-2 次工具调用完成。

判断依据：

  • 太细：步骤内容是单个 API 参数级别（“设置 Content-Type 为 application/json”）
  • 合适：步骤内容是一个完整动作（“设计用户注册 API，包含输入验证和错误处理”）
  • 太粗：步骤内容无法直接执行（“完成后端开发”）

经验值：一个 10 分钟的人类任务，拆成 3-8 步通常合适。

Q10: LATS 相比 ToT 有什么改进？为什么说它统一了规划、行动和推理？

答：

改进点：

  • ToT 只在"纯推理"空间搜索（不与环境交互），LATS 将搜索扩展到"行动空间"（与工具/环境交互）
  • LATS 用 MCTS 的 UCB 公式平衡探索(Exploration)与利用(Exploitation)
  • LATS 的 Backpropagation 步骤用环境反馈更新节点价值，而非纯 LLM 自评估

统一性：

  • 推理 = LLM 生成 Thought（节点展开时的推理）
  • 行动 = LLM 选择 Action 并与环境交互（节点展开时的动作）
  • 规划 = MCTS 的 Selection + Backpropagation（树搜索本身就是规划）

这三者在 LATS 的每个 Superstep 中自然发生，不需要人为划分阶段。

Q11: 生产环境中 Agent Planning 最容易踩的坑是什么？

答（按严重程度排序）：

  1. Replanning 死循环：没有设置终止条件，Agent 无限修改计划
  2. Token 爆炸：每步都传完整历史，复杂任务几轮就超出上下文窗口
  3. 格式不稳定：LLM 生成的计划格式时对时错，导致解析失败
  4. 状态冲突：并行工具执行时 State 写入互相覆盖
  5. 恢复不一致：从 Checkpoint 恢复后外部环境已变，基于旧状态做决策
  6. 粒度不当：太细导致成本高、太粗导致执行质量低
  7. 依赖处理错误：前置步骤失败后，依赖步骤仍被执行

每个问题在本文第八章都有对应的解决方案。
