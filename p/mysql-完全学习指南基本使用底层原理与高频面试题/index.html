1. MySQL 基础概念

1.1 什么是 MySQL？

MySQL 是开源的关系型数据库管理系统（RDBMS，Relational Database Management System），最早由 MySQL AB 开发，2008 年被 Sun Microsystems 收购，现归 Oracle 所有。它使用 SQL 作为查询语言，是互联网业务最常见的 OLTP 数据库选型之一。

核心定位：

  • 互联网业务 OLTP 主流选型
  • 成熟的主从复制和分库分表生态
  • 中小规模数据系统的默认数据库

1.2 MySQL 的主要特点

特性 说明
开源免费 社区版采用 GPL 协议，企业版商用授权
多存储引擎 默认 InnoDB，另有 MyISAM、Memory、Archive 等
ACID 事务 InnoDB 引擎支持完整 ACID 事务
主从复制 基于 binlog 的成熟复制机制，支持异步、半同步、MGR
行级锁 InnoDB 行级锁 + MVCC，并发性能好
生态成熟 工具链、运维经验、中间件、培训资源丰富

2. MySQL 基础语法

2.1 SQL 语言分类

SQL 语言按功能分为五大类：

分类 全称 作用 核心语句

DML Data Manipulation Language（数据操作语言） 操作表中数据 INSERT、UPDATE、DELETE
DQL Data Query Language（数据查询语言） 查询数据 SELECT
DCL Data Control Language（数据控制语言） 权限管理 GRANT、REVOKE
TCL Transaction Control Language（事务控制语言） 事务管理 COMMIT、ROLLBACK、SAVEPOINT

简单记忆：DDL 管结构，DML 管数据，DQL 管查询，DCL 管权限，TCL 管事务。

2.3 库表字段设计

良好的库表字段设计可以减少后续改表成本，也能提升查询性能和数据一致性。设计时重点关注：命名、主键、字段类型、约束、索引和扩展性。

数据库设计原则 

1

3
4

-- 推荐：明确字符集和排序规则
CREATE DATABASE shop
    DEFAULT CHARACTER SET utf8mb4
    DEFAULT COLLATE utf8mb4_unicode_ci;

建议：

  • 使用 utf8mb4，支持 emoji 和完整 Unicode 字符
  • 库名、表名、字段名统一使用小写和下划线，如 user_order
  • 避免使用 MySQL 保留字，如 order、group、desc
  • 不同业务模块可以用表名前缀区分，如 user_profile、order_item

CREATE TABLE user_order (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id BIGINT UNSIGNED NOT NULL,
    order_no VARCHAR(64) NOT NULL,
    status TINYINT UNSIGNED NOT NULL DEFAULT 0,
    amount DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    remark VARCHAR(255) DEFAULT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    KEY idx_user_id_created_at (user_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

建议：

  • 每张表都显式定义主键，InnoDB 推荐使用 BIGINT UNSIGNED AUTO_INCREMENT
  • 业务唯一字段使用唯一索引约束，如订单号 order_no
  • 高频查询条件提前规划索引，但不要给每个字段都建索引
  • 建议保留 created_at、updated_at，方便审计和排查问题
  • 大字段如正文、扩展 JSON（JavaScript Object Notation，JavaScript 对象表示法）、图片地址列表等可以考虑拆到扩展表

字段类型选择

场景 推荐类型 说明
主键ID BIGINT UNSIGNED 容量大，适合作为内部主键
状态/类型 TINYINT UNSIGNED 比 VARCHAR 更省空间，适合枚举值
金额 DECIMAL(10,2) 避免 FLOAT/DOUBLE 精度问题
短文本 VARCHAR(n) 根据实际长度设置，不要盲目给很大
长文本 TEXT 不适合频繁排序和过滤
时间 DATETIME / TIMESTAMP 业务时间常用 DATETIME，记录更新时间可用自动更新
是否标记 TINYINT(1) MySQL 没有真正的布尔存储类型，常用 0/1

NULL 与默认值

建议：

  • 能明确必填的字段使用 NOT NULL
  • 给状态、计数、金额等字段设置合理默认值
  • 允许未知或暂时不存在的值时，再使用 NULL
  • 注意普通比较遇到 NULL 会返回 NULL，判断空值要用 IS NULL

status TINYINT UNSIGNED NOT NULL DEFAULT 0,

-- 可选信息允许为空

主键与业务ID

不建议直接使用随机 UUID（Universally Unique Identifier，通用唯一标识符）作为 InnoDB 主键，因为随机写入容易导致页分裂和索引碎片。

更推荐：

1
2
3
4

id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
public_id CHAR(36) NOT NULL,
PRIMARY KEY (id),
UNIQUE KEY uk_public_id (public_id)

含义：

  • id：内部主键，用于聚簇索引、表关联和高效查询
  • public_id：外部业务标识，用于接口暴露、防枚举和链路追踪

常见设计误区

  • 用 VARCHAR 存金额，导致计算和排序困难
  • 用 FLOAT/DOUBLE 存金额，导致精度误差
  • 主键使用随机 UUID，导致插入性能下降和索引碎片
  • 字段全部允许 NULL，增加查询和判断复杂度
  • 单表字段过多，把低频大字段和高频字段混在一起
  • 索引过多，写入、更新和删除都要维护大量索引

常见坑

坑1：LEFT JOIN + WHERE 条件变成 INNER JOIN

1
2
3
4
5
6
7
8
9

-- ❌ 错误：WHERE过滤掉了右表为NULL的行，等价于INNER JOIN
SELECT u.name, o.amount
FROM users u LEFT JOIN orders o ON u.id = o.user_id
WHERE o.amount > 100;
-- 李四和王五的o.amount是NULL，NULL > 100 为false，被过滤掉了

-- ✅ 正确：条件放在ON中，保留左表全部行
SELECT u.name, o.amount
FROM users u LEFT JOIN orders o ON u.id = o.user_id AND o.amount > 100;
  • ON：决定右表哪些行"有资格"与左表匹配。不满足条件的右表行视为"未匹配"，左表行仍保留，右侧填 NULL。
  • WHERE：对连接完成后的整个结果集做过滤，不满足的行直接丢弃（包括 NULL 行）。

SELECT u.name, SUM(o.amount) as total

SELECT u.name, t.total_amount
FROM users u
LEFT JOIN (SELECT user_id, SUM(amount) as total_amount FROM orders GROUP BY user_id) t
ON u.id = t.user_id;

3.4 降序索引

MySQL 一直支持升序索引，并且默认就是升序索引：

1
2
3

CREATE INDEX idx_created_at ON orders(created_at);
-- 等价于
CREATE INDEX idx_created_at ON orders(created_at ASC);

MySQL 8.0 之前不真正支持降序索引。即使语法中写了 DESC，通常也会被忽略，索引实际仍按升序存储：

1
2

-- MySQL 8.0 之前，DESC 基本只是语法兼容
CREATE INDEX idx_created_at_desc ON orders(created_at DESC);

但这不代表 8.0 之前不能做降序排序。单列降序排序可以通过反向扫描升序索引完成：

1
2
3

SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20;

MySQL 8.0 开始真正支持降序索引，索引可以按 DESC 顺序存储：

1

CREATE INDEX idx_created_at_desc ON orders(created_at DESC);

降序索引在联合索引混合排序中更有价值，例如：

1
2
3
4
5
6

CREATE INDEX idx_user_created ON orders(user_id ASC, created_at DESC);

SELECT * FROM orders
WHERE user_id = 100
ORDER BY created_at DESC
LIMIT 20;

这里索引先按 user_id 升序组织，同一个 user_id 内再按 created_at 降序排列，可以减少额外 filesort。

总结：

  • 升序索引：一直支持，默认就是 ASC
  • 降序排序：8.0 之前也支持，可以反向扫描升序索引
  • 降序索引：MySQL 8.0 才真正支持，尤其适合联合索引中的 ASC/DESC 混合排序

4.3 索引原理详解

一、为什么需要索引？

没有索引时的查询：

  • 全表扫描（时间复杂度O(n)）
  • 数据量大时性能极差

有索引后的查询：

  • 使用B+树快速定位（时间复杂度O(log n)）
  • 千万级数据只需3-4次磁盘IO

二、B+树原理深入

1. B+树结构图解

  • 叶子节点：存储键值和完整数据（聚簇索引）或主键值（二级索引）

为什么B+树更适合数据库索引：

  1. 磁盘IO更少：非叶子节点不存数据，一页能存更多索引项，树更矮
  2. 范围查询高效：叶子节点链表连接，适合 BETWEEN、>、< 等范围查询
  3. 查询性能稳定：所有查询都要走到叶子节点，时间复杂度稳定

4. 超大数据行如何存储（行溢出）

InnoDB 一个数据页默认 16KB，并要求每页至少能容纳两行数据（否则 B+ 树会退化），所以单行最大长度大约是 8KB。当一行数据超过这个限制时，InnoDB 通过**行溢出（Row Overflow）**机制处理。

行格式决定溢出策略：

行格式 溢出策略 页内保留
COMPACT 部分溢出 前 768 字节 + 20 字节指针
REDUNDANT 部分溢出 前 768 字节 + 20 字节指针
DYNAMIC（5.7+ 默认） 完全溢出 仅 20 字节指针
COMPRESSED 完全溢出 + 压缩 仅 20 字节指针

  • 每个溢出页只属于一行的一个列，不会被多行共享
  • 聚簇索引行里只留 20 字节指针（DYNAMIC），结构是 space_id(4) + page_no(4) + offset(4) + length(8)

DYNAMIC vs COMPACT 的实际差异：

假设一个 TEXT 字段存了 10KB：

  • COMPACT：前 768B 留在数据页内 + 剩余 ~9KB 在溢出页。数据页很容易被"撑爆"，能放下的行数变少，扫描效率下降
  • DYNAMIC：整个 10KB 全部去溢出页，数据页里只有 20B 指针。数据页保持紧凑，B+ 树更高效；只有真正访问该列时才会去读溢出页

这就是 MySQL 5.7+ 默认改成 DYNAMIC 的原因。

实践建议：

  1. 不需要的字段不要 SELECT *：访问溢出列需要额外随机 IO
  2. 冷热分离：把超大 BLOB/JSON 拆到单独的扩展表，主表只放热字段
  3. 页大小可调：innodb_page_size 可设为 4K/8K/16K/32K/64K（需要初始化时指定）
  4. VARCHAR(N) 的 N 不是越大越无害：虽然不影响实际占用，但会影响优化器的内存预估
  5. 压缩：ROW_FORMAT=COMPRESSED 配合 KEY_BLOCK_SIZE 可压缩溢出页，适合大量重复文本

一句话总结：InnoDB 通过"聚簇索引行内只放 20 字节指针 + 数据存到溢出页链表“的方式来承载超大行；DYNAMIC 行格式下大字段几乎完全外置，从而保证一个叶子节点至少能放下两行索引数据，B+ 树结构不被破坏。

特点：

为什么二级索引存"主键"而不是"行指针"：

MyISAM 的二级索引叶子存的是物理地址（行指针），InnoDB 存的是主键值。原因：

  • InnoDB 是索引组织表，行数据本身就在主键 B+ 树里，物理位置会因页分裂而变动
  • 如果二级索引存物理地址，每次行迁移都要更新所有二级索引；存主键则不需要，主键是逻辑稳定的
  • 代价就是查询要"回表"，多一次 B+ 树查找

这也是为什么 InnoDB 强烈建议主键短小（比如自增 BIGINT 而不是长字符串）—— 主键值会被复制到每一个二级索引的每一个叶子节点里，主键越大，二级索引越臃肿。

3. 覆盖索引（Covering Index）

回表详解

什么是回表：当通过二级索引（非聚簇索引）查询时，如果所需数据不在索引中，需要拿着主键回到聚簇索引再查一次，这个过程叫"回表"。

为什么 age 有索引还会回表：

idx_age(age) 是二级索引，叶子节点只保存 age 和主键 id：

1
2

[age=25 | id=7]
[age=25 | id=12]

它只能定位到哪些主键满足 age = 25，不能直接返回 name、email 等其他列。

所以 SELECT * FROM users WHERE age = 25 虽然能使用 idx_age 过滤条件，但 SELECT * 需要完整行数据，必须再拿主键 id 回到聚簇索引查询完整记录，这就触发了回表。

如果查询字段都在二级索引中，就不需要回表：

1
2

-- idx_age(age) 的叶子节点包含 age 和主键 id
SELECT id, age FROM users WHERE age = 25;

结论：用了索引不代表不回表；只有查询字段都能从当前索引中拿到，才不需要回表。

联合索引原理

最左前缀原则：联合索引只能从最左列开始连续匹配，不能跳过中间列。

原因：B+树按定义顺序排序（先a，a相同按b，b相同按c），跳过中间列后续列就是无序的。

命中规则速查表（索引 (a, b, c)）：

查询条件 能用到的索引列 原因
WHERE a=1 a ✅ 最左列
WHERE a=1 AND b=2 a, b ✅ 连续匹配
WHERE a=1 AND b=2 AND c=3 a, b, c ✅ 全部命中
WHERE a=1 AND c=3 只有 a ⚠️ 跳过了b，c在b不确定时无序
WHERE b=2 无 ❌ 没有最左列a
WHERE b=2 AND c=3 无 ❌ 没有最左列a
WHERE a=1 AND b>5 AND c=3 a, b ⚠️ 范围查询截断索引，c无法利用有序性

关键点：范围查询会"截断"索引——范围列之后的列无法继续利用索引有序性。

FROM users;

例如：

1

1

扫描 idx_age + 大量随机回表

不如：

1

全表扫描 + filesort 排序

因此可能不会使用 idx_age。

七、索引使用建议总结

✅ 适合创建索引的场景
  1. WHERE子句的列
  2. JOIN关联的列
  3. ORDER BY / GROUP BY的列
  4. DISTINCT的列
  5. 高选择性列（唯一值多，区分度高）
❌ 不适合创建索引的场景
  1. 频繁更新的列（索引维护成本高）
  2. 数据量小的表（<1000行，全表扫描更快）
  3. 选择性低的列（性别、状态等只有几个值）
  4. TEXT、BLOB大字段
  5. 很少使用的查询列
🔧 索引设计原则
  1. 列顺序：区分度高的列放前面
  2. 列数量：单表索引不超过5个，单个索引不超过5列
  3. 前缀索引：长字符串使用前缀索引
  4. 覆盖索引：避免回表
  5. 定期维护：删除重复/未使用的索引

4.4 事务与锁机制

ACID特性

  • Atomicity（原子性）：事务是不可分割的最小单位（undo log保证）
  • Consistency（一致性）：事务前后数据完整性约束不变
  • Isolation（隔离性）：并发事务之间互不干扰（锁 + MVCC，Multi-Version Concurrency Control，多版本并发控制保证）
  • Durability（持久性）：事务提交后永久保存（redo log保证）

事务隔离级别详解

一、并发事务带来的问题

在深入理解隔离级别之前，先了解并发事务可能导致的三种问题：

1. 脏读（Dirty Read）

  • 定义：一个事务读到了另一个事务未提交的数据
  • 问题：如果另一个事务回滚，读到的数据就是无效的
1

Next-Key Lock 的实现方式：

Next-Key Lock 是 Record Lock + Gap Lock，锁的是索引范围。它既锁住已有索引记录，也锁住索引记录之间的空隙，目的是防止其他事务修改范围内已有记录，或者插入新的幻影记录。

假设 age 上有索引，当前索引值为：

1

10, 20, 30, 40

执行：

1

SELECT * FROM users WHERE age BETWEEN 20 AND 30 FOR UPDATE;

InnoDB 在 RR 隔离级别下会加 Next-Key Lock，可以理解为：

1
2

(10, 20]  锁住 20 这条记录，以及 10 到 20 的间隙
(20, 30]  锁住 30 这条记录，以及 20 到 30 的间隙

这样其他事务就不能插入：

1

INSERT INTO users(name, age) VALUES('赵六', 25); -- 被阻塞

因为 25 落在 (20, 30) 这个间隙中。

三种锁可以这样区分：

1
2
3

Record Lock：只锁索引记录本身，例如 [20]
Gap Lock：只锁索引记录之间的间隙，例如 (20, 30)
Next-Key Lock：锁间隙 + 索引记录，例如 (20, 30]

注意点：

  • Gap Lock 主要阻止 INSERT，防止范围内出现新记录
  • Next-Key Lock 依赖索引；如果查询条件没有走索引，可能扩大锁范围
  • 普通快照读 SELECT 不加 Next-Key Lock，SELECT ... FOR UPDATE、UPDATE、DELETE 这类当前读才会加锁
  • 唯一索引等值命中已有记录时，通常退化为 Record Lock，不需要锁间隙

等值查询 age = 20 的加锁前提：

对于下面这个 SQL：

1

SELECT * FROM users WHERE age = 20;

是否加锁、加什么锁，取决于查询类型和索引类型。

1. 普通 SELECT：快照读，不加锁

1

SELECT * FROM users WHERE age = 20;

这是普通快照读，依赖 MVCC 读取可见版本，不会加 Record Lock、Gap Lock 或 Next-Key Lock。

2. FOR UPDATE：当前读，会加锁

1

SELECT * FROM users WHERE age = 20 FOR UPDATE;

FOR UPDATE 表示查询并加排他锁，常用于“先查再改”的场景。它需要放在事务中使用，锁会持续到事务提交或回滚。

3. age 是普通非唯一索引

假设 age 索引中有：

1

10, 20, 20, 30

执行：

1

SELECT * FROM users WHERE age = 20 FOR UPDATE;

InnoDB 在 RR 隔离级别下通常会加 Next-Key Lock，锁住：

1
2

age=20 的索引记录
age=20 前后的相关索引间隙

作用是防止其他事务修改已有的 age=20 记录，也防止插入新的 age=20 幻影记录。

4. age 是唯一索引且命中已有记录

如果 age 是唯一索引，并且 age=20 这条记录存在：

1

SELECT * FROM users WHERE age = 20 FOR UPDATE;

通常只加 Record Lock，锁住 age=20 这条索引记录，不需要 Gap Lock。因为唯一索引等值查询已经能确定最多只有一条记录，不需要锁间隙防止重复插入。

5. age 没有索引

如果 age 没有索引，InnoDB 无法精准定位 age=20 的索引范围，可能扫描并锁住更多记录，锁范围会扩大，并发性能较差。

总结：

1
2
3
4

普通 SELECT age=20：快照读，不加锁
SELECT ... FOR UPDATE + 普通索引：当前读，可能加 Next-Key Lock
SELECT ... FOR UPDATE + 唯一索引命中：通常只加 Record Lock
SELECT ... FOR UPDATE + 无索引：可能扩大锁范围

    • 完全避免所有并发问题
    • 性能最差，并发能力极低
  • 应用场景：数据一致性要求极高的场景（金融核心系统）

六、常见面试问题

Q: 为什么MySQL默认使用RR而不是RC？

A:

  1. 数据一致性更强：基于事务级快照避免不可重复读
  2. 主从复制：早期基于 binlog 的 STATEMENT 格式需要 RR 配合 Gap Lock 保证主从一致；现在 ROW 格式下这一约束已不强
  3. 间隙锁：通过 Next-Key Lock 防止当前读出现幻读
  4. 历史延续：从早期版本沿用至今，多数业务代码已隐含依赖此默认

A: 不是完全解决，而是部分解决：

  • 快照读：通过MVCC避免幻读
  • 当前读：通过 Next-Key Lock 防止幻读
  • 例外情况：

锁机制

锁类型：

  • 共享锁（S锁）：读锁，允许其他事务加S锁，不能加X锁
  • 排他锁（X锁）：写锁，不允许其他事务加任何锁

行锁算法：

  • Record Lock：锁单条索引记录，例如 [20]
  • Gap Lock：锁索引记录之间的间隙，例如 (20, 30)，用于阻止范围内插入新记录
  • Next-Key Lock：Record Lock + Gap Lock，例如 (20, 30]，既锁间隙也锁记录

4.5 MVCC（多版本并发控制）

MVCC让读操作不加锁，提升并发性能。

核心组件

  2. Undo Log：

    • 存储数据的历史版本
    • 支持事务回滚和MVCC读

  3. Read View：

    • 记录当前活跃事务列表
    • 判断哪个版本对当前事务可见

4.6 日志系统

Redo Log（重做日志）

  • 作用：保证持久性，崩溃恢复
  • 特点：
    • 物理日志，记录"数据页的修改"
    • 循环写，空间固定
    • WAL（Write-Ahead Logging，预写日志）机制：先写日志，再写磁盘
  • 流程： 
    1

    修改数据 → 写入Buffer Pool → 写入Redo Log Buffer → 刷盘到Redo Log → 后台异步刷脏页

Undo Log（回滚日志）

  • 作用：保证原子性，事务回滚，MVCC
  • 特点：
    • 逻辑日志，记录"反向SQL"
    • 随事务提交持久化

Bin Log（归档日志）

  • 作用：主从复制，数据备份
  • 特点：
    • Server层日志，所有引擎通用
    • 逻辑日志，记录SQL语句（Statement模式）或行数据变更（Row模式）
    • 追加写，不覆盖

哪些操作会写入 Binlog：

Binlog 记录的是已提交、会改变数据库状态的操作。

会写入 Binlog：

  • DDL：CREATE TABLE、ALTER TABLE、DROP TABLE
  • DML：INSERT、UPDATE、DELETE
  • DCL：GRANT、REVOKE、CREATE USER 等权限或用户变更
  • 带写入效果的查询：CREATE TABLE ... AS SELECT、INSERT ... SELECT

不会写入 Binlog：

  • 普通 DQL：SELECT * FROM users，只查询数据，不改变数据库状态
  • 回滚事务中的变更：事务最终 ROLLBACK，不会作为有效变更同步

TCL 本身不是核心变更，关键看事务是否提交：事务中有写操作并 COMMIT，写操作会进入 Binlog；如果 ROLLBACK，则不会记录为有效变更。

两阶段提交：保证Redo Log和Bin Log一致性

1. 写入Redo Log（prepare状态）
2. 写入Bin Log
3. 提交事务，Redo Log改为commit状态

4.7 高可用与多副本复制

MySQL 高可用的目标是：当主库故障时，业务能够尽快切换到可用节点，同时尽量减少数据丢失和服务不可用时间。

主从复制基础 

1
2
3
4
5
6
7

Master                           Slave
  │                               │
  ├─ Binlog                       │
  │                               │
  │  ──────── 复制 ────────→      ├─ Relay Log
  │                               │
  │                               ├─ SQL Thread 重放

核心流程：

  1. 主库事务提交后写入 binlog
  2. 从库 I/O 线程拉取主库 binlog，写入本地 relay log
  3. 从库 SQL 线程重放 relay log，完成数据同步

复制模式

模式 特点 优点 风险
异步复制 主库不等待从库确认 性能最好 主库宕机可能丢失未同步数据
半同步复制 主库等待至少一个从库确认收到日志 降低数据丢失风险 延迟比异步复制高
组复制 MGR（MySQL Group Replication） 多节点协同确认事务 自动故障检测和切换 架构和运维复杂度更高

异步复制：

主库提交事务后，只要自己写完 binlog 就返回成功，从库之后再异步拉取和重放日志。

1
2
3

客户端写入 → 主库提交成功 → 返回客户端
                         ↓
                   从库异步同步

优点是性能最好，主库不用等待从库；风险是主库刚提交但日志还没同步到从库时宕机，从库提升为新主库后可能丢失这部分数据。

半同步复制：

主库提交事务时，需要等待至少一个从库确认“已经收到 binlog”，然后才返回客户端成功。

1

客户端写入 → 主库写 binlog → 至少一个从库收到 binlog → 返回客户端

注意：从库确认的是收到日志，不一定已经执行完成。半同步复制比异步复制更安全，但主库需要等待从库 ACK，延迟会更高。

组复制 MGR：

MGR 是多个 MySQL 节点组成一个复制组，事务提交前需要组内多个节点参与确认。

1
2
3

Node1  Node2  Node3
  \      |     /
   组复制协议

MGR 支持单主模式和多主模式，能自动检测节点故障并进行切换，一致性比普通主从复制更强，但架构和运维复杂度也更高。

简单总结：

  • 异步复制：最快，但主库宕机时可能丢数据
  • 半同步复制：安全性更高，但提交延迟更高
  • MGR：一致性和自动切换能力更强，但架构更复杂

常见解决方案：

  • 写后短时间内强制读主库，保证“读己之写”
  • 对一致性要求高的接口直接读主库
  • 监控主从延迟，延迟过大时暂停读从库
  • 使用半同步复制降低主从数据差异风险

需要关注：

  • RTO（Recovery Time Objective，恢复时间目标）：故障后多久恢复服务
  • RPO（Recovery Point Objective，恢复点目标）：最多可能丢失多少数据
  • 脑裂：旧主库未真正下线，新主库又被提升，导致双主写入
  • 数据一致性：切换前要确认新主库是否拥有最新日志

常见高可用方案

  1. 主从复制 + 手动切换

    • 简单易理解
    • 主库故障时需要人工切换，恢复时间较长

  2. MHA（Master High Availability）

    • 自动检测主库故障并提升从库
    • 可以尝试保存故障主库未同步的 binlog
    • 常见于传统 MySQL 主从架构

  3. MGR（MySQL Group Replication）

    • MySQL 官方组复制方案
    • 支持单主或多主模式
    • 通过组内一致性协议减少故障切换复杂度

  4. MySQL InnoDB Cluster

    • 由 MGR + MySQL Router + MySQL Shell 组成
    • 是 MySQL 官方推荐的高可用集群方案

分布式场景补充

MySQL 原生更偏向单机与主从复制，分布式能力通常依赖业务架构、中间件或云数据库产品。

常见问题：

  • 全局 ID：分库分表后自增 ID 不再天然全局唯一，可用雪花算法、号段模式、UUIDv7/ULID
  • 分布式事务：跨库事务可用 XA、TCC、可靠消息、最终一致性等方案
  • 数据路由：根据分片键定位库表，避免跨库 JOIN 和跨库分页
  • 多副本一致性：根据业务选择强一致、最终一致或读己之写

6. MySQL 高频面试题

6.1 为什么MySQL使用B+树而不是B树或Hash索引？

深入原理见 B+树原理深入

答案：

  1. vs B树：

    • B+树非叶子节点不存数据，一页能存更多索引项，树更矮（3层可存2000万数据）
    • B+树叶子节点用指针连接，范围查询只需遍历链表（B树需要中序遍历）

  2. vs Hash索引：

    • Hash索引不支持范围查询、排序、最左前缀匹配
    • Hash冲突时性能不稳定
    • 只有Memory引擎支持（InnoDB有自适应Hash，自动优化热点查询）

6.2 什么是回表？如何避免？

深入原理见 回表详解、覆盖索引

答案：

  • 回表：二级索引叶子节点存储主键值，查询完整数据需要先查二级索引，再回主键索引查询
  • 避免方法：
    1. 使用覆盖索引：查询列都在索引中
    2. 尽量使用主键查询
    3. 合理设计复合索引

示例：

-- 索引: INDEX idx_age_email (age, email)

-- 需要回表
SELECT * FROM users WHERE age = 25;

-- 覆盖索引，无需回表
SELECT id, age, email FROM users WHERE age = 25;

6.3 什么是索引下推（ICP）？

答案：

  • 作用：在索引遍历过程中就执行where条件过滤，减少回表次数
  • 示例：

-- 有ICP：存储引擎直接在索引中过滤name和age → 减少回表次数

6.4 什么是幻读？MySQL如何解决？

深入原理见 事务隔离级别详解 中的幻读与间隙锁部分

答案：

  • 幻读：一个事务两次查询，结果集数量不一致（其他事务插入/删除了数据）
  • 解决方式：快照读靠 MVCC，当前读靠 Next-Key Lock

SELECT * FROM users WHERE age BETWEEN 20 AND 30;  -- 返回6条（幻读）

-- 解决：Next-Key Lock锁住(20, 30)间隙，事务B无法插入

6.5 char和varchar的区别？

答案：

类型 存储方式 最大长度 适用场景
char 定长，不足补空格，读取时去除尾部空格 255 字符 长度固定（手机号、MD5、地区码）
varchar 变长，需 1-2 字节存长度 65535 字节（受行限制） 长度变化（用户名、邮箱）

注意：

  • CHAR(M) 和 VARCHAR(M) 的 M 是字符数，不是字节数（utf8mb4 一个字符最多 4 字节）
  • VARCHAR 的 65535 是整行的字节上限（含其他列与变长开销），单列最大 ≈ 65532 字节
  • 长度 > 255 字符时 VARCHAR 用 2 字节存长度，否则 1 字节

6.6 MySQL主从复制原理？

深入原理见 高可用与多副本复制

答案：

  1. 主库提交事务后写入 binlog
  2. 从库 I/O 线程拉取 binlog 并写入 relay log
  3. 从库 SQL 线程重放 relay log，完成数据同步

复制模式：

  • 异步复制：主库不等待从库确认，性能好但可能丢数据
  • 半同步复制：主库等待至少一个从库确认，降低丢数据风险
  • MGR 组复制：多节点协同确认事务，支持自动故障检测和切换

6.8 什么是MVCC？解决了什么问题？

深入原理见 MVCC（多版本并发控制）

答案：

  • 解决问题：
    • 读操作不加锁，读写不冲突
    • 实现读已提交、可重复读隔离级别
  • 实现：隐藏字段 + Undo Log + Read View

6.9 count(1)、count(*)、count(字段)的区别？

答案：

  • count(*)：统计总行数（推荐，InnoDB优化过，不区分NULL）
  • count(1)：类似count(*)，性能相同
  • count(字段)：
    • 不统计NULL值
    • 需要扫描该字段，性能较差
  • count(主键)：扫描主键索引

注意：count是全表扫描，大表建议：

  1. 维护计数表
  2. 使用缓存（Redis）
  3. information_schema.TABLES.TABLE_ROWS 统计（不精确，仅参考量级）

6.10 分库分表的策略和问题？

答案：

策略：

  1. 垂直分库：按业务拆分（用户库、订单库）
  2. 垂直分表：按列拆分（大字段单独表）
  3. 水平分库：按规则路由到不同实例
  4. 水平分表：同一实例内按规则拆分多表

分片键选择：

  • 常用查询字段（user_id、order_id）
  • 数据分布均匀
  • 避免跨分片查询

常见问题：

  1. 跨分片join：数据冗余、全局表、应用层组装
  2. 分布式事务：两阶段提交、TCC、最终一致性
  3. 全局唯一ID：snowflake、号段模式、UUID
  4. 分页排序：各分片排序后归并

中间件：ShardingSphere、MyCat

6.12 什么是MySQL的高可用架构？

深入原理见 高可用与多副本复制

答案：

  • 目标：主库故障时快速恢复服务，尽量降低数据丢失和不可用时间
  • 核心指标：RTO 表示恢复时间，RPO 表示可接受的数据丢失量
  • 基础方案：主从复制 + 读写分离，但要处理复制延迟和主库单点问题
  • 自动切换：可使用 MHA、MGR、MySQL InnoDB Cluster 等方案
  • 关键风险：主从延迟、故障切换丢数据、脑裂、业务连接切换
