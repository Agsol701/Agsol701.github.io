Eventlet vs Gevent 在 Celery 中的差异分析

Mar 20, 2026

Eventlet vs Gevent 在 Celery 中的差异分析

问题现象

在使用 Celery 的 green pool（协程并发池）时，比较常见的一类现象是：

  • 使用 eventlet 时，worker 进程看起来是正常的
  • 进程没有退出，心跳有时也还在
  • 但是消费者就是“不再消费”或者消费明显卡住
  • 将启动参数从 eventlet 改成 gevent 后，现象消失

这个问题很容易让人误以为是 Celery 的 consumer 逻辑有 bug，但从源码链路来看，更多时候问题并不在 Celery 的“消费逻辑本身”，而是在 green pool 的运行时、monkey patch 时机、事件循环实现、以及第三方库兼容性 上。

先说结论

先给结论，再展开源码：

  • eventlet 和 gevent 在 Celery 里都属于 green pool，本质都是单进程内跑大量 greenlet
  • Celery 对两者的封装其实很薄，主要差异不在 Celery 自己，而在 eventlet / gevent 运行时
  • eventlet 对 monkey patch 的时机更敏感，兼容性问题也更多
  • gevent 的底层事件循环更成熟，默认运行表现通常更稳定
  • “进程正常但不消费”这类现象，通常意味着 worker 没挂，但某个关键 I/O 或 hub 调度被阻塞了
  • 如果切到 gevent 后恢复正常，通常说明问题更接近于 eventlet 的运行时行为，而不是任务代码或 broker 协议本身

Celery Pool 类型概览

Celery 支持多种并发池（Pool）实现，通过 -P 参数指定：

Pool 类型 并发模型 适用场景 启动命令示例
prefork (默认) 多进程 CPU 密集型任务，无需处理大量并发连接 celery -A task worker -c 4
eventlet 协程 (greenlet) I/O 密集型，大量并发网络请求 celery -A task worker -P eventlet -c 100
gevent 协程 (greenlet) 类似 eventlet，API 更友好，稳定性更好 celery -A task worker -P gevent -c 100
solo 单线程 开发调试、任务量小 celery -A task worker -P solo
threads 多线程 轻量级 I/O 任务 celery -A task worker -P threads -c 10

默认行为

如果不指定 -P 参数，Celery 默认使用 prefork（多进程模式）：

1
2
3

# 这两个命令等价
celery -A task worker -Q celery -l debug -c 4
celery -A task worker -Q celery -l debug -P prefork -c 4

选择建议

场景 推荐的 Pool 原因
CPU 密集型计算 prefork 多进程充分利用多核，避免 GIL 限制
大量 HTTP 请求、数据库查询 gevent 协程高效处理并发 I/O
开发调试 solo 简单可控，便于排查问题
已有 eventlet 代码且运行稳定 eventlet 保持兼容，但新项目建议用 gevent

CPU 密集型 vs I/O 密集型

选择 Pool 类型的关键在于理解任务的特性：

特征 CPU 密集型 I/O 密集型

CPU 利用率 高，持续占用 低，大部分时间在等待
主要操作 数学计算、数据处理、加密解密 网络请求、磁盘读写、数据库查询

CPU 密集型任务（用 prefork）：
┌─────────────────────────────────────┐
│ 进程1: ████████████████████████████ │  ← CPU 满载
│ 进程2: ████████████████████████████ │
│ 进程3: ████████████████████████████ │
│ 进程4: ████████████████████████████ │
└─────────────────────────────────────┘
→ 多进程并行，充分利用多核 CPU

I/O 密集型任务（用 gevent/eventlet）：
┌─────────────────────────────────────┐
│ 协程1: ██░░░░░░░░░░░░██░░░░░░░░░░██ │  ← 大部分时间在等待
│ 协程2: ░░██░░░░░░░░░░░░██░░░░░░░░░░ │
│ 协程3: ░░░░██░░░░░░░░░░░░██░░░░░░░░ │
│ 协程4: ░░░░░░██░░░░░░░░░░░░██░░░░░░ │
└─────────────────────────────────────┘
██ = CPU 工作  ░░ = 等待 I/O
→ 单进程多协程，等待时自动切换执行其他协程

简单判断方法

任务是在"算"还是在"等"？

  • 算得多 → CPU 密集型 → 用 prefork
  • 等得多 → I/O 密集型 → 用 gevent

重要提示：eventlet 和 gevent 都属于 green pool，需要确保任务代码中不包含阻塞调用（如未 patch 的 socket、time.sleep 等），否则会阻塞整个事件循环。

Celery 中两者怎么用

正确的启动方式 

1
2

celery -A proj worker -P gevent -c 500 -l info
celery -A proj worker -P eventlet -c 500 -l info

这里最重要的一点不是命令本身，而是 用 -P 在进程启动的尽可能早期选择 pool。

Celery 在 celery/worker/components.py 里明确写了这样一条告警语义：

1
2
3

The worker_pool setting shouldn't be used to select the eventlet/gevent
pools, instead you must use the -P argument so that patches are applied
as early as possible.

这句话非常关键，因为它其实已经直接点出了 green pool 最容易出问题的地方：

  • 不是“有没有配置成功”
  • 而是“补丁是不是足够早地打上了”

不推荐的方式

不建议依赖配置文件里的 worker_pool = 'eventlet' 或 worker_pool = 'gevent' 来切换 green pool，尤其是 eventlet。

原因不是 Celery 不支持，而是 太晚了。一旦 socket、ssl、threading、某些 broker 相关模块已经按标准阻塞实现被导入，再去 patch，行为就可能变得不一致。

DISABLE_MONKEY_PATCH=true 的作用

这里要先说明一个边界：DISABLE_MONKEY_PATCH 不是 Celery 官方统一定义的标准配置项，它通常是项目自己的启动开关，用来控制是否执行类似下面这种代码：

1
2
3
4
5
6

from gevent import monkey
monkey.patch_all()

# 或
import eventlet
eventlet.monkey_patch()

如果项目里约定了：

1

DISABLE_MONKEY_PATCH=true

那它的含义通常就是：禁止 eventlet/gevent 在 Celery worker 进程启动时对 Python 标准库做 monkey patch。

monkey patch 会把一些标准库模块替换成协程友好的版本，例如：

  • socket
  • ssl
  • select
  • threading
  • time
  • subprocess

这对 -P gevent / -P eventlet 这类 green pool 很关键，因为它们依赖 cooperative I/O。如果不 patch，很多网络 I/O、sleep、锁等待仍然是原生阻塞行为。

对 Celery green pool 的影响

如果 worker 使用的是：

1
2
3

celery -A app worker -P gevent
# 或
celery -A app worker -P eventlet

正常情况下应该尽早完成 monkey patch。否则即使 gevent/eventlet pool 启动成功，任务里的很多调用仍然可能阻塞整个 worker 所在的 OS 线程。

也就是说，设置：

1

DISABLE_MONKEY_PATCH=true

之后，表面上看 worker 仍然可能是 green pool，但实际效果会变成：

  • 协程并发能力下降
  • 某些 I/O 调用不会自动让出执行权
  • 一个阻塞调用可能拖住整个事件循环
  • “worker 进程还活着，但不消费或消费变慢”的风险上升

所以，如果你明确使用 -P gevent 或 -P eventlet，一般不建议打开这个开关，除非你非常确定任务链路里没有依赖 monkey patch 的阻塞 I/O。

为什么有些项目会禁用 monkey patch

禁用 monkey patch 并不是完全没有价值。它的主要好处是避免全局改写标准库行为。

monkey patch 是进程级、全局性的，一旦执行，会影响整个 worker 进程里的所有库。某些库对标准库行为比较敏感，比如：

  • HTTP 客户端：requests、urllib3
  • 数据库驱动：pymysql、部分 PostgreSQL/MySQL client
  • broker / 缓存客户端：redis、Kafka client
  • RPC / 网络库：grpc
  • 线程、锁、子进程、日志相关代码

如果这些库和 eventlet/gevent 的 green 版本不兼容，禁用 monkey patch 可以让运行时更接近原生 Python 行为，减少“被悄悄改写”的副作用。

和 prefork / threads 的关系

如果 worker 使用的是默认 prefork：

1

celery -A app worker -P prefork

或者 threads / solo：

1
2

celery -A app worker -P threads
celery -A app worker -P solo

通常并不需要 eventlet/gevent 的 monkey patch。此时设置 DISABLE_MONKEY_PATCH=true 更像是一个保护开关，用来防止某些公共启动代码在非 green pool 场景下意外执行 monkey patch。

简单判断：

Celery pool 是否建议禁用 monkey patch 原因
gevent 通常不建议 green pool 依赖协程化 I/O
eventlet 通常不建议 eventlet 对 patch 时机更敏感
prefork 可以禁用 多进程模型不依赖 green patch
threads 通常可以禁用 使用原生线程并发
solo 可以禁用 单线程调试模型不需要 green patch

一句话总结：

DISABLE_MONKEY_PATCH=true 的作用是关闭 eventlet/gevent 对标准库的全局 monkey patch；这会降低 green pool 的协程化 I/O 能力，但能换取更接近原生 Python 的运行时行为。

先看 Celery 自己的源码封装

从 Celery 视角看，eventlet 和 gevent 都是并发池实现，分别在：

  • celery/concurrency/eventlet.py
  • celery/concurrency/gevent.py

Eventlet pool 的实现

celery/concurrency/eventlet.py 里，TaskPool 初始化时会绑定：

  • eventlet.greenpool.GreenPool
  • eventlet.greenthread.getcurrent
  • greenthread.spawn_n

核心逻辑可以概括为：

1
2
3
4
5
6
7

from eventlet.greenpool import GreenPool
from eventlet import greenthread

self.Pool = GreenPool
self.getcurrent = greenthread.getcurrent
self.getpid = lambda: id(greenthread.getcurrent())
self.spawn_n = greenthread.spawn_n

启动时创建 green pool：

1
2

self._pool = self.Pool(self.limit)
self._quick_put = self._pool.spawn

提交任务时，本质上是把 Celery 的 apply_target(...) 扔进 eventlet 的 greenlet 池里执行。

也就是说，Celery 在这里做的事情并不复杂：

  • 创建一个 GreenPool
  • 用 spawn 提交任务
  • 用一个映射表跟踪 greenlet
  • 必要时 kill 某个 greenlet

Gevent pool 的实现

celery/concurrency/gevent.py 的结构与之非常像，不过底层换成了：

  • gevent.pool.Pool
  • gevent.getcurrent
  • gevent.spawn_raw

核心逻辑可以概括为：

1
2
3
4
5
6
7

from gevent import getcurrent, spawn_raw
from gevent.pool import Pool

self.Pool = Pool
self.getcurrent = getcurrent
self.getpid = lambda: id(getcurrent())
self.spawn_n = spawn_raw

启动时也是：

1
2

self._pool = self.Pool(self.limit)
self._quick_put = self._pool.spawn

提交任务时，gevent 版本还会额外经过 apply_timeout(...) 包装，在设置了超时时可以用 gevent.Timeout 控制任务。

这一点说明：Celery 对 gevent 的整合稍微完整一点，至少在超时控制上是直接接进去的。

一个非常关键的源码差异：eventlet 会主动检查 patch 时机

celery/concurrency/eventlet.py 里有一段很值得注意的逻辑：它会扫描 sys.modules，看 billiard、celery、kombu 等模块是不是已经导入，并尝试对 thread、threading、socket 相关情况发出告警。

其核心意图可以概括为：

1
2
3

RACE_MODS = ('billiard.', 'celery.', 'kombu.')
# 如果这些模块已经导入，说明 eventlet patch 可能太晚了
warnings.warn(...)

这说明 Celery 官方在 eventlet 适配层里，明确意识到了一个问题：

eventlet 很容易出现“补丁打得太晚”的竞态问题。

而这类问题最麻烦的地方在于：

  • 进程不一定会崩
  • worker 也不一定会报明显异常
  • 但某些 socket、DNS、SSL、线程同步对象仍然是“阻塞版”
  • 一旦这些对象出现在消费链路里，就可能把整个 hub 卡住

这正是“进程正常，但不消费”的典型成因之一。

Worker 启动时，Hub 和 Pool 是怎么挂起来的

Celery 的 worker bootstep 在 celery/worker/components.py。

这里有两个关键点。

1. Hub bootstep

Hub bootstep 会根据 worker 是否启用事件循环来创建 kombu 的 event loop：

  • w.hub = get_event_loop()
  • 如果没有，就 set_event_loop(...)

也就是说，Celery worker 自己有一层基于 kombu 的 hub/event loop，负责 broker I/O、定时器、consumer 等协作。

2. Pool bootstep

Pool bootstep 会创建 w.pool，然后 consumer 在初始化时会拿到：

  • pool=w.pool
  • timer=w.timer
  • hub=w.hub

也就是说，从结构上看，消费链路并不是“池子自己单独跑”，而是：

  • kombu hub 负责消息侧事件循环
  • pool 负责任务执行并发
  • 两者要协同工作

这意味着一旦 green runtime 对 socket、定时器、DNS、信号、线程原语的兼容性出现问题，表面看上去就可能是“consumer 不消费了”，但根因其实是 event loop / cooperative I/O 某处失去协作。

gevent 的 libev 到底用在了哪里

libev 不在 Celery 里直接使用，而是在 gevent 运行时里使用。

也就是说：

  • Celery 只知道自己在用 celery/concurrency/gevent.py
  • gevent.py 再去调用 gevent 的 Pool、getcurrent、spawn_raw
  • gevent 自己内部的 hub / loop 再落到 libev 或 libuv

根据 gevent 官方文档，gevent 是建立在 libev 或 libuv event loop 之上的；在非 Windows 环境下，长期默认实现通常是 libev。

文档位置：

  • https://www.gevent.org/
  • https://www.gevent.org/loop_impls.html
  • https://www.gevent.org/api/gevent.hub.html

从 gevent 的设计上看，可以把调用链理解为：

1
2
3
4
5
6

Celery worker
  -> celery/concurrency/gevent.py
  -> gevent.pool.Pool / gevent Hub
  -> gevent loop implementation
  -> libev/libuv
  -> epoll/kqueue/select 等 OS I/O 多路复用能力

所以你在 Celery 源码里看不到 libev 很正常，因为它属于 gevent 的底层实现，不是 Celery 的直接依赖层。

如果是“第一天正常，第二天不消费”，应该优先怀疑什么

如果你的现象不是“启动后马上不消费”，而是：

  • eventlet worker 刚启动时完全正常
  • 可以连续跑很久，比如一天
  • 过了一段时间后，进程还在，但突然不再继续消费
  • 重启 worker 后又恢复

那我会优先判断成：

不是任务代码跑一天后自己坏了，而是 worker 在运行一段时间后，遇到了一次 broker 连接抖动、重连、心跳、取消消费或恢复消费相关事件，之后 consumer 没有完全恢复到继续拉消息的状态。

这个判断并不是拍脑袋，因为 Kombu / Celery 历史记录里确实长期有这类问题痕迹。

1. Kombu 的 changelog 里就有直接相关的修复

Kombu changelog 中有两条非常值得注意：

  • Fix Redis connections after reconnect - consumer starts consuming the tasks after crash. (#2007)
  • Redis: Consumer.cancel() is now thread safe.

第二条后面还直接解释了 greenlet 场景：

  • This fixes an issue when using gevent/eventlet and a message is handled after the consumer is canceled resulting in a "message for queue without consumers" error.

这几条信息说明两件事：

  • 重连之后 consumer 恢复消费 这件事，历史上确实出过问题
  • Consumer.cancel / consumer 恢复流程 在 gevent/eventlet 这类并发模型下，确实是容易出边缘问题的地方

2. Celery issue 中也有“运行一段时间后 idle，不再消费”的案例

Celery issue #4012 中描述的现象就非常像你说的这种：

  • worker 跑了一段时间后开始 idle
  • 进程还活着，也有多个 broker 连接
  • 但就是不再继续消费
  • 手动把 RabbitMQ 连接关掉，触发重连后，又会恢复消费

这类现象很像：

  • 不是任务执行层直接崩溃
  • 而是消费循环、broker I/O、重连后的注册状态，某一步进入了“看似活着、实际上不再推进”的状态

3. “一天后才出问题”更像周期性连接事件触发

从时间特征上看，“第一天正常，第二天不消费”通常更像：

  • broker 空闲连接被回收
  • 网络短暂抖动
  • heartbeat 检测触发一次异常
  • Redis / RabbitMQ 连接发生 reconnect
  • consumer cancel / re-register 在某个边缘时序下没有完全恢复

这类问题的特征就是：

  • 不会在启动时立刻出现
  • 不会在压测的前几分钟必现
  • 往往要等到一次真正的连接生命周期事件发生后才暴露

所以，这种“跑一天后卡住”的时间特征，更像连接状态机或 hub 协作链路问题，而不是纯 CPU 打满。

4. 我会优先考虑的三类触发点

第一类：broker / 网络侧的空闲回收、断连、心跳异常

这是最符合你现象的一类。

一旦 broker 连接因为空闲、超时、网络闪断或心跳异常进入重连流程，worker 会经历：

  • 旧连接失效
  • consumer cancel
  • channel / connection cleanup
  • 新连接建立
  • queue / consumer 重新注册
  • 恢复 drain events

如果这条链路里任何一步在 greenlet 场景下没有完全收干净，就可能出现：

  • worker 进程还在
  • hub 还在跑
  • 但已经不再真正从 broker 拉取任务

第二类：eventlet 下某个 greenlet 在关键时刻阻塞了消费 loop

这类情况也很常见，尤其是任务里存在：

  • 阻塞型网络 I/O
  • DNS 查询
  • SSL 握手
  • 不可 monkey patch 的 C 扩展
  • 某些不会主动让出执行权的长阻塞调用

平时它可能不一定出问题，但一旦刚好发生在：

  • heartbeat 发送/接收
  • broker socket 重建
  • consumer 恢复订阅
  • 定时器回调执行

这些关键时刻，就可能把整个 cooperative 调度链拖住。

第三类：重连后 consumer 状态没有完全恢复

这一类和第一类非常接近，但更偏状态机残留问题。

也就是：

  • 连接已经重建了
  • worker 看起来也在线
  • 但 consumer 的某些注册、取消、恢复流程没有完全收尾
  • 导致后续 drain_events 或消费回调没有真正重新推进

Kombu changelog 里关于 Consumer.cancel() 的修复，本质上就在说明这条链路历史上并不稳定。

把“一天后不消费”落到源码链路里看

如果从源码路径去看，这类问题通常不在“任务执行函数”本身，而是在 consumer 事件循环 -> broker I/O -> 异常恢复 -> 重新注册消费 这条链路上。

1. Celery 的 consumer 主循环并不是一直傻等，而是在不断推进 event loop

在 celery/worker/loops.py 里，green pool 常走 asynloop(...)。它的主干逻辑可以概括成：

1
2
3
4
5
6
7

while blueprint.state == RUN and obj.connection:
    state.maybe_shutdown()
    if heartbeat_error is not None:
        raise heartbeat_error
    if qos.prev != qos.value:
        update_qos()
    next(loop)

这里有三个非常关键的点：

  • next(loop) 本质上是在推动 hub/event loop 往前走
  • 心跳异常会通过 heartbeat_error 抛出来
  • 只要这条循环不再继续推进，worker 就可能表现为“进程还在，但不拉消息”

也就是说，你看到的“不消费”，从源码视角更像是：

  • loop 没有继续有效推进
  • 或者推进了，但没有再拿到可读事件
  • 或者重连后没有把新的消费 fd 正确重新挂回 loop

2. 心跳检查本身就是一个可能触发异常恢复的入口

同一个文件里，_enable_amqheartbeats(...) 会周期性调用：

1

connection.heartbeat_check(rate)

一旦这里抛异常，asynloop(...) / synloop(...) 就会进入异常路径。

这和你的现象很契合，因为：

  • worker 可以先正常跑很久
  • 等到某次 heartbeat、socket timeout、连接 reset 才触发问题
  • 问题触发后不是立刻进程退出，而是转入恢复流程

所以“第一天正常、第二天不消费”，从源码上完全可以解释成：

正常消费路径一直没问题，真正出错的是某次连接生命周期事件之后的恢复路径。

3. Celery 在连接异常后，确实会走一条“关闭 + 重启 blueprint”的恢复链路

在 celery/worker/consumer/consumer.py 里，Consumer.start() 的逻辑大致是：

1
2
3
4
5
6
7

while blueprint.state not in STOP_CONDITIONS:
    try:
        blueprint.start(self)
    except recoverable_errors as exc:
        self.on_connection_error_after_connected(exc)
        self.on_close()
        blueprint.restart(self)

这里可以看到，Celery 的恢复思路不是“原地修一下就算了”，而是：

  • 记录连接异常
  • 调 on_connection_error_after_connected(...)
  • 调 on_close() 做清理
  • 再 blueprint.restart(self) 重新拉起 consumer 相关 bootsteps

也就是说，如果你跑了一天后才不消费，一个非常合理的源码级推测就是：

  • 某次 recoverable error 确实发生了
  • 但后续 on_close -> restart 这条清理/重建链路没有完全恢复干净
  • 于是 worker 还活着，但消费功能并没有彻底回来

4. Celery 在异常后的清理动作，本身就可能卡在连接收尾上

on_connection_error_after_connected(...) 里有一个值得注意的调用：

1
2
3
4

try:
    self.connection.collect()
except Exception:
    pass

这段代码的意图是做连接清理，但从排障角度看，它说明一件事：

  • Celery 在连接异常后，确实依赖底层 transport / connection 去收尾
  • 如果某个 transport 的清理动作在 greenlet/hub 场景下不彻底，恢复路径就可能留下残留状态

所以你的现象不能只盯着“异常是否发生”，还要盯着：

  • 异常后清理是否完成
  • 清理后 consumer 是否重新注册
  • hub 是否开始监听新的 fd

5. Redis transport 的源码里，确实能看到 cancel / 读事件 / 重新注册这些敏感点

如果 broker 是 Redis，kombu/transport/redis.py 里有几段非常关键。

basic_cancel() 不是立即取消，而是可能延后到“本次读取完成后”

源码逻辑大意是：

1
2
3

if connection.cycle._in_protected_read:
    return connection.cycle.after_read.add(...)
return self._basic_cancel(...)

这说明在 Redis transport 里，如果当时正处在受保护的读取阶段，取消消费并不会立刻执行，而是延迟到读取完成后处理。

这就引出了一个典型风险：

  • 如果 cancel / reconnect / read 这几个动作在时序上撞在一起
  • 某些延后动作没有被完整执行
  • 就可能留下“看起来 consumer 在，实际上没真正订阅成功”的状态

on_readable() / poller / fd 注册决定了能不能继续拉到消息

Redis transport 的 MultiChannelPoller 会：

  • 在 get(...) 中调用 poller.poll(timeout)
  • 在 on_readable(fileno) 时读取 broker 数据
  • 在 register_with_event_loop(...) 时，把 fd 重新挂到 event loop

逻辑链可以概括成：

1
2
3

events = self.poller.poll(timeout)
for fileno, event in events:
    self.handle_event(fileno, event)

以及：

1
2
3

def register_with_event_loop(self, connection, loop):
    ...
    [add_reader(fd, on_readable, fd) for fd in cycle.fds]

所以如果重连之后出现以下任何一种情况：

  • 老 fd 没清掉
  • 新 fd 没重新 add_reader
  • cycle.fds 没恢复正确
  • poller 还盯着旧连接

那表现出来就会非常像你说的这种：

  • worker 在线
  • hub 在跑
  • 但 broker 消息不再进入消费回调

6. 为什么这类问题会“很久以后才触发”

把上面几段源码串起来，时间特征就很好理解了。

启动后的正常阶段走的是：

  • consumer.consume()
  • next(loop)
  • poller.poll(...)
  • on_readable(...)
  • create_task_handler()

这一整条路径在第一天可能一直正常。

但只要某个时刻发生：

  • heartbeat_check() 失败
  • socket reset / timeout
  • broker reconnect
  • basic_cancel() 延迟执行
  • register_with_event_loop() 未完全恢复

问题就会从“正常消费路径”切换到“异常恢复路径”。

而很多线上问题恰恰不是出在前者，而是出在后者。

7. 结合源码，我会把高概率怀疑点收敛到哪里

如果结合 Celery 和 Kombu 这几处源码，我会把“eventlet 跑一天后不消费”的高概率怀疑点收敛到下面三处：

  • celery/worker/loops.py：event loop 仍在，但 heartbeat / loop 推进已经异常
  • celery/worker/consumer/consumer.py：recoverable error 之后的 on_close + blueprint.restart 没完全恢复
  • kombu/transport/redis.py：cancel、protected read、fd 重新注册、poller 状态之间留下了残留

如果 broker 不是 Redis，而是 RabbitMQ，这个结论也仍然成立，只是具体 transport 文件不同，核心仍然是：

  • 旧连接断开
  • event loop 收到异常
  • transport 清理旧 fd / channel
  • 重新建连并重新注册 consumer
  • 恢复 drain_events / readable callback

只要其中某一步没有完全回到一致状态，就会出现“活着，但不消费”。

为什么 eventlet 更容易把这种问题暴露出来

这里要先强调一件事：

不能把这个现象简单归因成一个单一 bug。

更准确的说法是，eventlet 更容易触发这类问题，常见原因有以下几类。

1. monkey patch 时机过晚

这是最经典的一类。

如果 worker 启动前，某些关键模块已经被普通阻塞版本导入，比如：

  • socket
  • ssl
  • threading
  • 某些数据库驱动
  • 某些 HTTP 客户端
  • broker transport 依赖链上的模块

那么即使后面用了 eventlet，也可能只是“部分变绿”。

这种状态下，worker 仍然能：

  • 启动成功
  • 打印 ready
  • 维持进程存活

但当消费链路进入某个阻塞调用点时，整个协作调度就可能卡住，表现出来就是：

  • 队列里有消息
  • worker 在线
  • 就是不拉取或不继续处理

2. eventlet 的兼容性更脆弱

eventlet 和 gevent 都依赖 monkey patch，但实际项目里常见的兼容性体验通常是：

  • eventlet 更容易踩库兼容问题
  • gevent 更容易维持“整体可运行”

这不是因为 Celery 对 gevent 做了大量特殊优化，而是因为 gevent 的底层事件循环和生态维护更成熟。

另外，eventlet 官方文档现在已经明确给出警告：新项目使用 eventlet 已经被 heavily discouraged，并说明项目进入以稳定性和 bug fix 为主的维护模式，不再接受新的通用特性，长期目标是推动用户迁移。

这意味着什么？意味着当你遇到这种“跑了一天后才卡住”的边缘时序问题时：

  • 它未必没有人遇到过
  • 但后续生态层面的修复速度和覆盖范围，通常会比 gevent 弱
  • 你需要自己承担更多运行时兼容性验证成本

Celery 官方文档在 gevent 页面里也直接描述 gevent 是建立在 libev/libuv 上的高性能 event loop；同时，Celery 社区对 eventlet 的维护风险也有明确讨论。

3. DNS / SSL / socket 这类 I/O 更容易放大 eventlet 的问题

这类问题往往不会在最简单的 demo 中暴露，但在真实业务环境里常见：

  • 任务里发 HTTP 请求
  • 连接 Redis / RabbitMQ / 数据库
  • 进行 DNS 解析
  • 使用 SSL/TLS

green runtime 只要有一处没 patch 好，或者第三方库内部偷偷走了阻塞调用，就可能把整个线程卡住。

对 green pool 来说，最可怕的不是“报错退出”，而是 主 greenlet 还活着，但调度停滞。

4. Celery 对 eventlet 的封装更强调“能跑”，不是“替你兜底所有兼容性”

从 celery/concurrency/eventlet.py 的实现可以看出来，Celery 的做法主要是：

  • 包一层 GreenPool
  • 把任务提交进去
  • 做一点生命周期管理
  • 提供若干 signals
  • 在模块导入阶段提醒 patch 竞态

它并不会替你修复：

  • 第三方库是否 cooperative
  • DNS 解析是否走绿色实现
  • 某个驱动是否混用了线程锁和阻塞 socket
  • 某个 import 是否发生得太早

因此，一旦运行时组合复杂起来，eventlet 很容易比 gevent 更早暴露出“不消费”这类症状。

为什么 gevent 通常更稳

注意，这里说的是“通常更稳”，不是“绝对不会出问题”。

1. gevent 的底层 loop 更成熟

gevent 的核心优势不在 Celery 适配层，而在运行时底层：

  • 事件循环实现成熟
  • I/O watcher 体系更稳定
  • 与高并发网络场景长期磨合更多

这也是为什么你在表面上看到的只是把：

1

-P eventlet

换成：

1

-P gevent

结果消费就恢复了。

真正变化的不是 Celery consumer 逻辑，而是 整个 green runtime 的稳定性基础。

2. gevent 在 Celery 中的集成更直接

从 celery/concurrency/gevent.py 可以看到：

  • pool 就是 gevent.pool.Pool
  • 提交就是 spawn
  • 超时控制直接接 gevent.Timeout

这条路径比较直接，运行期语义也相对清晰。

3. gevent 的文档和运行时观测能力更好

gevent 对 loop、watcher、DNS、signal 的文档化程度更高，遇到问题时通常更容易定位。

这里有哪些重复或容易冲突的认知

结合前面文章里的内容，最容易冲突的点主要有这几个。

1. eventlet 和 prefork 不是一回事

之前如果把“eventlet 问题”和“prefork fork 子进程状态丢失”直接绑在一起，会造成概念冲突。

因为当你用：

1

celery -A proj worker -P eventlet

时，使用的是 eventlet green pool，而不是 prefork。

所以“eventlet 不消费”的根因，不应该简单解释成“prefork fork 之后状态没继承”。这两条分析链路要分开。

2. libev 不在 Celery 里直接出现

如果文章一边说“gevent 使用 libev”，一边又让读者在 Celery 代码里找 libev，就容易造成困惑。

更准确的表述应该是：

  • Celery 集成的是 gevent pool
  • gevent 的底层 loop 才是 libev/libuv
  • 所以 libev 的使用点在 gevent 运行时，不在 Celery 业务层

3. worker_pool 配置和 -P 启动参数不是等价建议

从 celery/worker/components.py 的提示可以看出，对 green pool 来说，-P 比配置文件切换更关键，因为它关系到 patch 是否足够早。

因此这两种方式不能无差别并列成“都一样的推荐用法”。

更合理的结论

如果你的现象是：

  • eventlet 下 worker 进程正常但不消费
  • 改成 gevent 后恢复正常

那么更合理的解释是：

  1. Celery 的消费主链路本身大概率没问题
  2. eventlet 运行时更容易在 patch 时机或库兼容性上出问题
  3. 某个 I/O 调用阻塞了 cooperative 调度，导致看起来像“consumer 不工作”
  4. 换成 gevent 后，底层 loop 和兼容性更稳，所以症状消失

换句话说，这更像是：

相同的 Celery 上层逻辑，落在了两个稳定性不同的 green runtime 上。

实践建议

如果你遇到的是“运行一天后不消费”

建议优先从“连接生命周期”角度排查，而不是只盯任务代码：

  • 检查 broker 是否存在空闲连接回收、heartbeat timeout、连接被 server 主动关闭
  • 拉 worker 日志，重点看不消费前后是否出现 reconnect、consumer cancel、heartbeat、socket reset 相关日志
  • 如果是 Redis，重点关注 reconnect 后是否重新恢复消费
  • 如果是 RabbitMQ，重点观察 heartbeat、channel close、connection reset 后 worker 是否真正恢复 drain_events
  • 尝试人工断开 broker 连接，看 worker 是会自动恢复，还是会进入“进程存活但不再消费”的状态
  • 记录恢复手段：是 broker 重连能恢复，还是必须重启 worker 才恢复

如果“断开连接后能自动恢复”与“跑一天后自然卡住”表现不同，那么问题通常就在 异常重连路径，而不是正常消费路径。

如果继续用 gevent

建议：

  • 用 -P gevent 启动，而不是晚期配置切换
  • 明确把任务限定为 I/O 密集型
  • 检查任务中是否存在长时间阻塞调用
  • 配合 -c 做压力测试，而不是只看单次运行
  • 确认 greenlet 版本与 Python 版本匹配

如果必须继续用 eventlet

建议优先排查：

  • 是否通过 -P eventlet 启动
  • 是否有过早 import 导致 patch 太晚
  • 是否存在 DNS / SSL / socket 阻塞点
  • 是否用了不适合 greenlet 的第三方库
  • 是否存在某些任务根本没有主动让出控制权

对于 eventlet，实战里经常还会加：

1

EVENTLET_NO_GREENDNS=yes

这不是万能药，但在 DNS 相关问题上经常值得一试。

总结

从源码上看，Celery 对 eventlet 和 gevent 的适配层其实都不厚，核心区别主要来自两者底层运行时：

  • eventlet：更依赖 monkey patch 时机，兼容性更脆弱
  • gevent：底层 loop 更成熟，通常更稳定

因此，“eventlet 进程正常但不消费，而 gevent 正常”的现象，更像是 运行时协作调度失效，而不是 Celery 消费代码本身失效。

如果只用一句话总结：

Celery 上层逻辑没变，变的是 green runtime 的稳定性。
