AI Agent Prompt Engineering：指令分层、输出约束、任务拆解、反幻觉与高频面试题

source: agent-prompt-engineering
May 12, 2026

写在前面

Agent 不是靠一个神奇 prompt 就能稳定运行，但 prompt 仍然是 Agent 行为控制的重要接口。

好的 prompt 不是写得长，而是把目标、边界、输入、输出和失败处理说清楚。

本文在讲解 Agent Prompt 核心概念的同时，结合 LangChain 源码分析 prompt 模板系统的设计实现，帮助理解"工程化的 prompt 管理"是如何落地的。

一、Agent Prompt 的目标

1.1 不是让模型更会聊天

Agent prompt 的目标通常是：

  • 明确任务目标
  • 限定工具使用边界
  • 约束输出格式
  • 说明失败时如何处理
  • 让模型遵守业务规则

1.2 Prompt 与 Skills 的区别

在 Agent 体系中，prompt 和 skills（工具/技能）经常被混淆，但它们是两个不同层面的东西：

维度 Prompt Skills
本质 文本指令，告诉模型"你是谁、怎么做" 可执行的能力单元，包含代码逻辑
形态 字符串（系统消息、模板） 函数/工具/子流程（有输入输出接口）
作用时机 推理前注入，影响模型行为 运行时被调用，执行具体操作
谁在执行 Large Language Model（LLM，大语言模型）自身理解并遵循 程序代码执行，LLM 只负责决定何时调用
可靠性 软约束（模型可能不遵守） 硬执行（代码逻辑确定性高）
举例 “你是知识库Agent，不可编造内容” search_docs(query) 检索函数

简单类比：

  • Prompt = 给员工的岗位说明书（你该做什么、不该做什么）
  • Skills = 员工手上的工具箱（搜索引擎、计算器、数据库客户端）

两者配合工作：prompt 告诉模型"什么时候用什么 skill"，skill 提供实际执行能力。单有 prompt 模型只能说话，单有 skills 模型不知道何时该调用。

在 LangChain 中的对应：

  • Prompt → ChatPromptTemplate（指令模板）
  • Skills → Tools（工具定义 + 实现函数）

1.3 Prompt 是行为接口

可以把 prompt 理解成模型和系统之间的接口文档。

接口文档不清楚，调用方就容易误用；prompt 不清楚，模型就容易偏离预期。

                                /      |       \
                               /       |        \
              SystemMessage    HumanMessage    MessagesPlaceholder

关键属性：
  BasePromptTemplate
    ├── input_variables: List[str]
    ├── format(**kwargs) → str
    └── format_messages(**kwargs) → List[BaseMessage]

  ChatPromptTemplate
    ├── messages: List[MessageLikeRepresentation]
    └── from_messages(messages) → ChatPromptTemplate

  MessagesPlaceholder
    └── variable_name: str  (运行时注入的变量名)

设计思想：

  • PromptTemplate 用于补全类模型（单字符串输入）
  • ChatPromptTemplate 用于对话类模型（消息列表输入），这是 Agent 场景的主力
  • MessagesPlaceholder 是实现"动态注入"的关键——agent 的历史对话、工具调用记录都通过它插入

class ChatPromptTemplate(BasePromptTemplate):
    messages: List[MessageLikeRepresentation]

    @classmethod
    def from_messages(cls, messages):
        """从 (role, template) 元组列表构建模板"""
        _messages = [_convert_to_message(m) for m in messages]
        input_vars = set()
        for m in _messages:
            input_vars.update(m.input_variables)
        return cls(messages=_messages, input_variables=sorted(input_vars))

    def format_messages(self, **kwargs):
        """将模板 + 变量渲染为最终的消息列表"""
        result = []
        for message_template in self.messages:
            if isinstance(message_template, MessagesPlaceholder):
                # 动态注入：直接展开变量中的消息列表
                result.extend(kwargs[message_template.variable_name])
            else:
                result.append(message_template.format(**kwargs))
        return result

flowchart TD
    A[实际发给 LLM 的消息列表]
    A --> B[SystemMessage: system_prompt 内容]
    A --> C[历史消息: messages 列表中的所有历史消息]
    C --> C1[HumanMessage / AIMessage / ToolMessage 按时序排列]
    A --> D[工具定义: 通过 bind_tools 自动注入到 API 请求中]
    D --> D1[tools: name / description / parameters]

与旧版的对比：

维度 旧版（ChatPromptTemplate + agent_scratchpad） 当前版本（create_agent）
工具描述 手动渲染为文本，partial 填入 prompt 框架自动通过 bind_tools 注入
历史状态 intermediate_steps → agent_scratchpad 文本 messages 列表直接传入
用户输入 {input} 变量替换 HumanMessage 消息
Prompt 模板 需要手动定义 ChatPromptTemplate 只需提供 system_prompt 字符串

  • 历史推理链路就是 messages 本身，不需要额外的 agent_scratchpad 格式转换
  • 每一步 AIMessage + ToolMessage 配对形成证据链

三、输出约束

3.1 自然语言输出

自然语言适合最终面向用户的回答。

要求应该明确：

  • 使用中文
  • 先结论后解释
  • 不确定时说明原因
  • 引用资料时保留来源

3.2 JSON 输出

内部决策更适合 JavaScript Object Notation（JSON，JS 对象表示法）。

1

3
4

{
  "action": "search_docs",
  "query": "报销发票要求",
  "reason": "用户问题依赖公司制度"

3.3 常见问题

常见问题包括：

  • 字段缺失
  • 多输出了自然语言
  • 枚举值不稳定
  • JSON 被截断
  • 类型不一致

解决方式是用 schema、低温度、短字段和失败重试。

3.4 LangChain 源码：格式指令注入机制

LangChain 通过 OutputParser 体系将格式约束注入 prompt，形成"告诉模型怎么输出 → 解析模型输出"的闭环。

核心流程：

sequenceDiagram
    participant O as OutputParser
    participant P as Prompt
    participant L as LLM
    participant A as 应用代码
    O->>P: get_format_instructions()
    P->>L: 包含格式约束的完整 prompt
    L-->>O: 原始文本输出
    O->>A: parse() 返回结构化对象
    O-->>A: 解析失败时 retry 或抛异常

class PydanticOutputParser(BaseOutputParser[T]):
    pydantic_object: Type[T]

    def get_format_instructions(self) -> str:
        """生成 JSON schema 描述，注入到 prompt 中"""
        schema = self.pydantic_object.model_json_schema()
        reduced_schema = {k: v for k, v in schema.items()
                         if k not in ("title", "type")}
        return (
            "输出必须是如下 JSON schema 的合法 JSON：\n"
            f"```json\n{json.dumps(reduced_schema)}\n```"
        )

    def parse(self, text: str) -> T:
        """从 LLM 输出中提取 JSON 并验证"""
        json_str = extract_json(text)
        return self.pydantic_object.model_validate_json(json_str)

from pydantic import BaseModel, Field

class ActionDecision(BaseModel):
    action: str = Field(description="要执行的工具名称")
    query: str = Field(description="工具参数")
    reason: str = Field(description="选择此工具的原因")

parser = PydanticOutputParser(pydantic_object=ActionDecision)

prompt = PromptTemplate(
    template="根据用户问题决定下一步行动。\n{format_instructions}\n问题：{question}",
    input_variables=["question"],
    partial_variables={"format_instructions": parser.get_format_instructions()}
)

这个设计的好处：

  • 格式约束自动从 Pydantic model 生成，不需要手写 JSON schema 描述
  • 类型验证在 parse 阶段强制执行，输出不合法直接报错
  • partial_variables 让格式指令在模板创建时就注入，调用时只需传业务参数

2. 步骤二

    tools=[search_docs, query_db, create_ticket],

设计要点：

  • 规划指令强调"不要跳步"、“不要多余步骤”——这是对模型行为的边界约束
  • 要求最终回答基于工具结果——确保有收敛且有证据支撑
  • 可以将 Planner 和 Executor 分为两个 Agent，也可以在单个 Agent 的 prompt 中融入规划思维

五、反幻觉设计

5.1 让模型承认不知道

Agent prompt 中应该明确：

1

如果上下文或工具结果不足以支持结论，请回答无法确认，并说明缺少什么信息。

这比让模型"尽量回答"更可靠。

5.2 要求证据绑定

在 RAG + Agent 中，建议让答案绑定证据：

结论 证据来源 置信度
报销需提供发票 财务制度第 3 条 高
超过 5000 元需主管审批 报销流程说明 中

5.3 工具结果优先

如果工具结果和模型常识冲突，应该优先相信工具结果，除非工具结果明显错误或过期。

5.4 langchain 1.0+：Messages 作为证据链

在当前版本中，不再需要单独的 agent_scratchpad 格式转换机制。Agent 的推理历史就是 messages 列表本身——每一轮工具调用的 AIMessage 和 ToolMessage 配对自动形成证据链：

Scratchpad 的累积过程：

flowchart LR
    subgraph R1[第1轮]
        A[用户问题] --> B[LLM 决定调用 search_docs]
        B --> C[工具返回结果]
    end
    subgraph R2[第2轮]
        D[messages 已包含<br/>AI 调用 search_docs + ToolMessage 结果] --> E[LLM 基于结果<br/>生成回答或继续调用工具]
    end
    subgraph R3[第3轮: 如需要]
        F[messages 继续累积] --> G[LLM 综合所有证据<br/>生成最终回答]
    end
    C --> D
    E --> F

messages 列表的实际结构：

# 每轮循环后 messages 自动累积
messages = [
    SystemMessage("你是企业知识库 Agent..."),
    HumanMessage("差旅报销有什么限制？"),

    # 第1轮：LLM 决定调用工具
    AIMessage(content="", tool_calls=[{
        "name": "search_docs",
        "args": {"query": "差旅报销限制"},
        "id": "call_001"
    }]),
    # 第1轮：工具真实返回结果
    ToolMessage(
        content='{"snippet": "单次报销上限5000元，需提供发票"}',
        tool_call_id="call_001"
    ),

    # 第2轮：LLM 基于真实证据生成回答
    AIMessage(content="根据公司制度，差旅报销单次上限5000元，需要提供有效发票。"),
]

为什么这能降低幻觉：

  • 模型看到的是真实的工具返回结果（ToolMessage），而非自己编造的中间答案
  • 每一步推理都有对应的证据（AIMessage.tool_calls + ToolMessage 配对），形成可追溯的证据链
  • 如果工具没返回某个信息，模型在 messages 中找不到依据，更倾向于说"无法确认"
  • 不再需要 format_to_openai_tool_messages() 等格式转换函数，messages 天然就是证据链

六、Prompt 版本管理

6.1 为什么要版本管理

Prompt 改动会影响 Agent 行为。

需要记录：

  • prompt_version
  • 生效时间
  • 适用 Agent
  • 变更原因
  • 回归测试结果

6.2 不要在线上随手改 Prompt

线上 prompt 应该像代码一样管理，至少要有测试集和回滚方式。

七、常见面试题

7.1 Agent Prompt 和普通聊天 Prompt 有什么区别？

Agent Prompt 更关注行为边界、工具使用、输出结构、失败处理和安全约束，不只是让模型回答得自然。

7.2 为什么要做指令分层？

指令分层可以区分全局安全规则、任务规则、工具规则和用户输入，减少用户输入覆盖系统约束的风险。在 LangChain 中，ChatPromptTemplate.from_messages() 将每一层映射为不同类型的消息（SystemMessage、HumanMessage、MessagesPlaceholder），物理上保证了层级隔离。

7.3 如何降低 Agent 幻觉？

可以通过证据绑定、工具结果优先、不确定时拒答、结构化输出、检索日志和评估集来降低幻觉。langchain 1.0+ 中，messages 列表本身就是证据链——每一轮 AIMessage(tool_calls) + ToolMessage 配对将工具调用结果显式保留在上下文中，让模型基于真实证据推理。

7.4 为什么 Prompt 需要版本管理？

Prompt 改动会改变 Agent 行为。版本管理可以支持回归测试、灰度发布和问题回溯。

7.5 Few-shot 示例什么时候有用？

当任务格式复杂、边界不易描述或输出风格要求稳定时，few-shot 示例很有用。

7.6 LangChain 中 ChatPromptTemplate 和 PromptTemplate 有什么区别？

PromptTemplate 输出单个字符串，适用于补全类模型。ChatPromptTemplate 输出消息列表（List[BaseMessage]），适用于对话类模型。Agent 场景几乎只用 ChatPromptTemplate，因为它能天然支持 system/human/ai 的角色分层和 MessagesPlaceholder 的动态注入。

7.7 messages 列表在 Agent 中起什么作用？

在 langchain 1.0+ 中，AgentState.messages: list[AnyMessage] 是 Agent 的核心状态。它同时承载两类内容：

  1. chat_history：多轮对话记忆（HumanMessage / AIMessage 交替）
  2. 推理证据链：工具调用历史（AIMessage.tool_calls + ToolMessage 配对）

不再需要旧版中单独的 agent_scratchpad 和 chat_history 分离设计。

它让模板结构保持稳定，而运行时内容可以动态变化。

7.8 如何在 Prompt 中注入输出格式约束？

LangChain 的做法是通过 OutputParser.get_format_instructions() 自动生成格式描述文本，用 partial_variables 注入到 prompt 模板中。好处是格式约束从数据模型（如 Pydantic class）自动派生，不需要手动维护 prompt 中的 JSON schema 描述。
