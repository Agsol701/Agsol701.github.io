RAG 召回详解：检索策略、核心算法、工程实现与适用场景

May 06, 2026

写在前面

在 RAG（Retrieval-Augmented Generation，检索增强生成）系统里，很多人会把注意力放在大模型、prompt、向量数据库上。

但真正决定效果上限的，往往是召回。

因为 RAG 的基本链路是：

flowchart TD
  A["用户问题"] --> B["检索外部知识"]
  B --> C["把检索结果放进上下文"]
  C --> D["让大模型生成答案"]

如果召回阶段没有把正确证据找出来，后面的模型再强，也很难凭空答对。

所以这篇文章只聚焦一个问题：

RAG 里到底有哪些召回策略，它们背后的算法是什么，工程上怎么实现，分别适合什么场景？

这篇会覆盖：

  1. 召回在 RAG 链路里的位置
  2. BM25（Best Matching 25）关键词召回
  3. 向量语义召回
  4. 混合召回
  5. 多路召回
  6. 查询改写与查询扩展
  7. metadata filter
  8. Parent-Child Retrieval（父子检索）
  9. Summary Index（摘要索引）
  10. Graph Retrieval（图检索）
  11. rerank 和召回的关系
  12. 召回评估与调优

一、先理解召回的目标

1.1 召回不是最终排序

在 RAG 里，召回的职责不是直接选出最终答案，而是：

从大量知识片段中，找出一批“可能相关”的候选证据。

它和排序的职责不同。

召回关注：

  • 正确证据有没有进入候选集
  • 候选集覆盖是否足够
  • 是否漏掉关键文档
  • 是否覆盖不同表达方式

排序关注：

  • 哪些候选更相关
  • 正确候选是否排在前面
  • 噪声是否被压下去
  • 最终放进 prompt 的内容是否干净

所以召回阶段更重视 Recall，排序阶段更重视 Precision。

1.2 召回失败是 RAG 最致命的问题

RAG 常见失败可以分成三种：

  1. 没召回正确证据
  2. 召回了但排序靠后
  3. 证据在上下文里，但模型没用好

其中第一种最致命。

如果正确证据根本没有进入候选集，后面的 rerank、prompt、LLM 基本都救不回来。

所以排查 RAG 效果时，第一件事应该是：

对失败问题查看召回 top-k 结果里有没有正确 chunk。

如果没有，就先不要改 prompt。

二、RAG 召回的基础对象

2.1 检索对象通常是 chunk

RAG 不是直接检索整篇文档，而是检索切分后的 chunk。

例如一篇产品手册可能被切成下面几段。这里的 API（Application Programming Interface，应用程序编程接口）指系统对外提供的接口能力。

1
2
3
4

doc_001_chunk_001: 登录流程
doc_001_chunk_002: 密码重置
doc_001_chunk_003: 权限申请
doc_001_chunk_004: API 调用限制

用户问：

1

接口调用次数有限制吗？

系统应该召回 doc_001_chunk_004，而不是整篇产品手册。

所以召回质量和 chunk 质量强相关。

如果 chunk 切得太碎，正确证据可能不完整。

如果 chunk 切得太大，召回结果噪声会很多。

2.2 一个索引记录通常包含什么

一个可检索的 chunk 通常不只包含正文。

更完整的结构类似：

  • section_path 可以增强语义
  • metadata 用于过滤和排序
  • chunk_id 用于评估和引用

生产系统里不要只存一段裸文本。

三、BM25 关键词召回

3.1 BM25 解决什么问题

BM25 是传统搜索系统里非常经典的关键词检索算法。

它适合处理：

  • 错误码
  • API 名称
  • 类名函数名
  • 版本号
  • 法条编号
  • 商品型号
  • 人名地名
  • 精确术语

例如用户问：

1

ERR_CONN_RESET 是什么原因？

这类问题的核心不是语义相似，而是文本里有没有精确出现 ERR_CONN_RESET。

向量检索可能会把它理解成“连接错误”，召回一堆泛泛的网络故障文档。

BM25 则更容易命中包含这个错误码的片段。

3.2 BM25 的核心思想

BM25 主要考虑三件事：

  1. 查询词是否出现在文档里
  2. 查询词在文档里出现多少次
  3. 查询词在整个语料库里是否稀有

一个词越稀有，它越有区分度。

例如在技术文档里：

  • “接口”这个词很常见，区分度低
  • OrderService.create() 很少见，区分度高

BM25 会更重视后者。

3.3 BM25 的简化公式

BM25 的常见形式可以简化理解为：

1

score(D, Q) = sum( IDF(qi) * TF(qi, D) 的饱和函数 * 文档长度归一化因子 )

其中：

  • Q 是用户查询
  • D 是文档或 chunk
  • qi 是查询里的词
  • sum(...) 表示对 query 中每个词 qi 的整项得分求和
  • TF 表示词在当前文档中出现的频率
  • IDF 表示这个词在全库中的稀有程度
  • 文档长度归一化用于避免长文档天然占优

更接近实际的公式是：

1
2
3
4
5

score(D, Q) =
sum(
  IDF(qi) * ( f(qi, D) * (k1 + 1) )
  / ( f(qi, D) + k1 * (1 - b + b * |D| / avgdl) )
)

参数含义：

  • f(qi, D)：词 qi 在文档 D 中出现的次数
  • |D|：当前文档长度
  • avgdl：平均文档长度
  • k1：控制词频增长的饱和速度
  • b：控制文档长度归一化强度

不需要死记公式，但要理解两个关键点：

  • 稀有词更重要
  • 词频增加会提高分数，但不是无限线性提高

工程上通常不会自己手写 BM25，而是使用搜索引擎。

常见选择：

  • Elasticsearch
  • OpenSearch
  • Lucene

  • SQLite FTS

3.5 如果 embedding 已经放进向量数据库，BM25 怎么做

这里要明确一个点：

embedding 放进向量数据库，并不等于 BM25 也在向量数据库里完成。

向量检索依赖的是 embedding。

BM25 依赖的是原始文本的倒排索引。

所以同一个 chunk 通常会同时保留两类数据：

1
2
3
4

chunk_id
content
metadata
embedding

其中：

  • embedding 给向量检索用
  • content 给 BM25 / 全文检索用
  • metadata 给过滤和权限控制用
  • chunk_id 给多路召回结果合并去重用

方式一：向量数据库和搜索引擎双写

这是生产里很常见、也很稳的方案。

同一份 chunk 写入两套索引：

1
2

chunk 文本 + metadata + embedding -> 向量数据库
chunk 文本 + metadata            -> Elasticsearch / OpenSearch / Lucene

查询时并行执行：

flowchart TD
  A["用户 query"] --> B["向量数据库：向量召回 top 50"]
  A --> C["搜索引擎：BM25 召回 top 50"]
  B --> D["按 chunk_id 合并去重"]
  C --> D
  D --> E["RRF 或加权融合"]
  E --> F["rerank"]
  F --> G["最终 top-k"]

关键是两边必须使用同一个 chunk_id。

例如向量库里有：

  "metadata": {
    "product": "billing",
    "region": "cn"

搜索引擎里也应该有同一个 chunk_id：

这样两路召回结果才能合并。

方式二：使用同时支持全文检索和向量检索的系统

有些系统可以同时做 BM25 和向量检索。

例如：

  • Elasticsearch：BM25 + dense_vector
  • OpenSearch：BM25 + k-NN
  • PostgreSQL：full-text search + pgvector
  • Weaviate：BM25 + vector search

这种方式的好处是系统数量少。

但也要注意：

  • 不同系统的 hybrid search 实现不一样
  • 分数融合方式不一定透明
  • 过滤条件和排序逻辑要仔细验证

以 PostgreSQL 为例，可以同时保存：

  chunk_id text PRIMARY KEY,
  content text,

方式三：使用向量数据库自带的 hybrid 能力

有些向量数据库支持 sparse vector、keyword search 或 hybrid search。

这时可以在同一个系统里完成：

1

dense vector search + sparse / keyword search

但要确认它具体支持的是什么：

  • 标准 BM25
  • sparse vector
  • token match
  • 自定义 hybrid score

这些能力名字相似，但算法和效果可能不同。

所以工程上不要只看“支持 hybrid search”，还要看：

  • 是否支持中文分词
  • 是否支持字段权重
  • 是否支持 metadata filter
  • 是否能解释 BM25 分数
  • 是否能独立查看每一路召回结果

如果系统不透明，排查召回问题会比较困难。

3.6 BM25 的优点和缺点

优点：

  • 对精确词匹配非常强
  • 可解释性好
  • 成本低
  • 查询速度快
  • 适合错误码、编号、术语、代码

缺点：

  • 对同义表达不敏感
  • 用户换一种说法可能召回不到
  • 依赖分词质量
  • 对自然语言语义理解弱

例如：

1
2

用户问：忘记密码怎么办？
文档写：用户可重置登录凭证。

如果关键词重合少，BM25 可能召回不好。

3.7 BM25 适用场景

BM25 适合：

  • 技术文档搜索
  • API 文档问答
  • 日志错误码问答
  • 法律条款问答
  • 规章制度检索
  • 电商 SKU 或商品型号检索
  • 代码仓库问答

如果知识库里有大量专有名词，不建议只做向量检索。

四、向量语义召回

4.1 向量召回解决什么问题

向量召回解决的是：

用户表达和文档表达不一样，但语义相近。

例如：

1
2

用户问：怎么找回账号？
文档写：用户可以通过安全中心重置登录凭证。

这两个句子没有太多关键词重合，但意思接近。

BM25 可能不稳，向量检索更适合。

4.2 embedding 是什么

embedding 会把文本转换成一个高维向量。

可以把它理解为：

1

"忘记密码怎么办" -> [0.12, -0.08, 0.44, ...]

语义相近的文本，在向量空间里的距离通常更近。

所以向量召回的基本流程是：

1
2
3
4
5

离线阶段：
chunk 文本 -> embedding 模型 -> chunk 向量 -> 向量索引

在线阶段：
用户 query -> embedding 模型 -> query 向量 -> 近邻搜索 -> top-k chunk

4.3 相似度算法

向量检索常见相似度包括三种。

Cosine Similarity

余弦相似度看两个向量的夹角。

1

cosine(a, b) = a · b / (|a| * |b|)

它关注方向是否接近，不太关注向量长度。

很多文本 embedding 检索会使用它。

Dot Product

点积直接计算：

1

dot(a, b) = sum(ai * bi)

如果向量已经归一化，点积和余弦相似度排序结果通常等价。

Euclidean Distance

欧氏距离看两个向量在空间中的直线距离。

1

distance(a, b) = sqrt(sum((ai - bi)^2))

距离越小越相似。

实际使用哪种，要看 embedding 模型和向量数据库的推荐配置。

不要随便混用。

4.4 ANN（Approximate Nearest Neighbor，近似最近邻）搜索

如果数据量很小，可以暴力计算 query 向量和所有 chunk 向量的相似度。

但真实系统里可能有：

  • 10 万 chunk
  • 100 万 chunk
  • 1 亿 chunk

逐个计算会很慢。

所以向量数据库通常使用 ANN，也就是 Approximate Nearest Neighbor，近似最近邻搜索。

它牺牲一点点精确性，换取大幅查询速度提升。

常见索引算法包括：

  • HNSW
  • IVF
  • PQ
  • ScaNN

4.5 HNSW 的基本思想

HNSW 是 Hierarchical Navigable Small World。

可以把它理解成一张多层图。

底层图连接很多近邻点，上层图更稀疏，用于快速跳转。

查询过程类似：

flowchart TD
  A["从最高层入口点开始"] --> B["找到当前层更接近 query 的节点"]
  B --> C["逐层向下"]
  C --> D["在底层做更细的近邻搜索"]

它的特点：

  • 查询速度快
  • 召回质量高
  • 适合在线检索
  • 内存占用相对较高

常见参数：

  • M：每个节点连接的邻居数量
  • efConstruction：建索引时搜索范围，越大质量越高但构建越慢
  • efSearch：查询时搜索范围，越大召回越好但查询越慢

调参方向：

1
2
3
4

召回不够：提高 efSearch
查询太慢：降低 efSearch 或优化过滤范围
索引质量差：提高 efConstruction
内存太高：降低 M

4.6 IVF 的基本思想

IVF 是 Inverted File Index。

它会先把向量空间聚类成多个中心。

离线阶段：

1

所有向量 -> 聚类 -> 分配到不同 cluster

在线阶段：

1

query 向量 -> 找最近的几个 cluster -> 只在这些 cluster 里搜索

它的特点：

  • 适合大规模向量
  • 查询速度快
  • 需要训练聚类中心
  • 如果只查太少 cluster，可能漏召回

常见参数：

  • nlist：聚类中心数量
  • nprobe：查询时探测多少个 cluster

调参方向：

1
2
3

召回不够：提高 nprobe
查询太慢：降低 nprobe
数据规模变大：适当增加 nlist

4.7 PQ 的基本思想

PQ 是 Product Quantization，乘积量化。

它的目标是压缩向量，降低内存和存储成本。

基本思路是：

flowchart TD
  A["原始高维向量"] --> B["拆成多个子向量"]
  B --> C["每个子向量用码本近似表示"]
  C --> D["用较短编码代替原始向量"]

优点：

  • 节省内存
  • 支持更大规模索引
  • 查询成本更低

缺点：

  • 有精度损失
  • 召回可能下降
  • 调参复杂度更高

在 RAG 场景里，如果数据量不是特别大，通常先用 HNSW 更简单。

当数据量和成本压力上来，再考虑 IVF、PQ 等压缩方案。

五、混合召回

5.1 为什么需要混合召回

BM25 和向量召回各有盲区。

BM25 擅长精确匹配，但不懂同义表达。

向量召回擅长语义相似，但对精确术语不稳定。

所以生产 RAG 里很常见的做法是：

BM25 + 向量召回 + 结果融合 + rerank。

5.2 典型混合召回流程 

flowchart TD
  A["用户 query"] --> B["并行执行 BM25 召回 top 50"]
  A --> C["并行执行向量召回 top 50"]
  B --> D["合并结果"]
  C --> D
  D --> E["去重"]
  E --> F["分数融合"]
  F --> G["rerank"]
  G --> H["取 top 5 到 top 10 进入上下文"]

这个流程的目标是：

  • BM25 兜住精确匹配
  • 向量召回兜住语义表达
  • rerank 提升最终前排质量

5.3 分数归一化

  • rank-based fusion

5.4 RRF 融合算法

RRF 是 Reciprocal Rank Fusion。

它不关心原始分数，只关心排名。

公式是：

1

RRF(d) = sum( 1 / (k + rank_i(d)) )

其中：

  • d 是某个候选文档
  • sum(...) 表示对所有召回通道里的排名得分求和
  • rank_i(d) 是它在第 i 路召回里的排名
  • k 是平滑常数，常见取 60

例如一个 chunk：

  • 在 BM25 里排第 2
  • 在向量检索里排第 10

它的 RRF 分数是：

1

1 / (60 + 2) + 1 / (60 + 10)

RRF 的优点：

  • 实现简单
  • 不依赖不同检索器的分数尺度
  • 对多路召回很友好
  • 工程上稳定

def reciprocal_rank_fusion(result_lists, k=60):
    scores = {}
    docs = {}

    for results in result_lists:
        for rank, doc in enumerate(results, start=1):
            doc_id = doc["chunk_id"]
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
            docs[doc_id] = doc

    return sorted(
        docs.values(),
        key=lambda doc: scores[doc["chunk_id"]],
        reverse=True,
    )

5.5 加权融合

另一种方式是分数归一化后加权：

1

final_score = alpha * vector_score + beta * bm25_score

例如：

1

它的好处是可控。

缺点是：

  • 需要归一化
  • 参数要调
  • 不同问题类型可能需要不同权重

例如：

  • 概念解释类问题：向量权重更高
  • 错误码类问题：BM25 权重更高

5.6 混合召回适用场景

混合召回几乎是生产 RAG 的默认推荐方案。

尤其适合：

  • 企业知识库
  • 技术文档
  • API 文档
  • 客服问答
  • 法律制度
  • 代码问答
  • 产品手册

如果只能选一个通用方案，通常从混合召回开始。

六、多路召回

6.1 多路召回是什么

多路召回确实和混合召回很像，因为它们都会出现：

flowchart TD
  A["多种检索结果"] --> B["合并"]
  B --> C["去重"]
  C --> D["融合或重排"]

但它们关注的层次不一样。

一句话区分：

混合召回关注“用哪些检索算法互补”，多路召回关注“从哪些检索通道找候选”。

更具体地说：

对比项 混合召回 多路召回
关注点 检索算法互补 检索通道编排
典型组合 BM25 + 向量 原始 query、改写 query、扩展 query、标题索引、摘要索引、图关系等
解决问题 语义召回和关键词召回互补 单一路径容易漏召回
粒度 偏检索器层面 偏策略和流程层面
常见结果处理 分数融合、RRF、rerank 多路合并、去重、融合、rerank

所以可以这样理解：

混合召回通常是多路召回的一种基础形态，但多路召回不只等于 BM25 + 向量。

6.2 混合召回和多路召回的关系

最简单的混合召回是：

通道 2：Vector("v2.3.17 导出接口 403")

这已经可以叫混合召回，也可以看成两路召回。

但真实系统里的多路召回可能是：

通道 2：Vector(原始 query)

这里不仅混合了 BM25 和向量，还混合了：

  • 不同 query 版本
  • 不同索引字段
  • 不同索引粒度
  • 不同数据结构
  • 不同业务规则

所以多路召回更像一个召回编排框架。

混合召回只是这个框架里最常见的一组基础通道。

6.3 为什么有了混合召回，还需要多路召回

因为 BM25 + 向量只能解决一部分问题。

它主要解决的是：

1

关键词匹配能力 + 语义相似能力

但真实 RAG 还会遇到其他问题。

问题一：用户 query 本身不好检索

例如用户问：

1

这个接口怎么又没权限了？

即使你同时用 BM25 和向量检索，效果也可能不好。

因为问题里的“这个接口”没有被消解，“没权限”也没有变成文档里常见的 403 Forbidden、权限配置、角色授权。

这时需要 query rewrite。

也就是新增一路：

1

Vector(导出接口返回 403 Forbidden 的原因和权限配置说明)

问题二：一个问题有多种可能说法

例如用户问：

1

怎么开通 VPN？

知识库里可能写的是：

  • 远程办公权限申请
  • VPN 账号配置
  • 网络访问白名单
  • 员工入职 IT 权限

这时只做原始 query 的 BM25 + 向量仍然可能漏。

需要 query expansion，扩展出多路检索。

问题三：答案在长文档里，需要先定位章节

例如用户问：

1

数据权限模型是怎么设计的？

直接查细粒度 chunk，可能只召回局部字段说明。

更好的做法是增加 summary index 召回：

flowchart TD
  A["Summary Vector(数据权限模型是怎么设计的)"] --> B["先找到“权限模型设计”章节"]
  B --> C["再在这个章节下检索原文 chunk"]

问题四：问题依赖实体关系

例如：

1

订单服务创建订单时会影响哪些表？

这不是单纯文本相似问题。

它可能需要：

1

OrderService -> create_order -> writes -> orders

这时需要图召回或符号索引，而不是只靠 BM25 + 向量。

多路召回可以进一步做：

你会发现，多路召回不是简单地“多加几个 top-k”。

它是在从不同角度补召回：

  • 版本号走 metadata 或 BM25
  • 错误码走 BM25
  • 语义原因走向量
  • 标题命中走 title 字段
  • 接口实体走图或结构化索引
  • 口语化表达走 query rewrite

6.5 多路召回的代价

多路召回能提高覆盖率，但不是越多越好。

它会带来：

  • 延迟增加
  • 成本增加
  • 候选噪声增加
  • 融合逻辑复杂
  • 排查问题更困难

所以多路召回应有明确目的。

不要为了“看起来高级”加很多路。

更合理的做法是：

flowchart TD
  A["先做基础混合召回"] --> B["看失败样本漏在哪里"]
  B --> C["针对性增加一路召回"]
  C --> D["用评估集验证 Recall@k 是否提升"]

例如：

  • 错误码漏召回：加强 BM25 或字段权重
  • 指代问题漏召回：增加 query rewrite
  • 长文档宏观问题漏召回：增加 summary index
  • 多跳实体问题漏召回：增加 graph retrieval
  • 标题强相关但正文噪声多：增加 title 字段召回

  • 一个问题可能对应多个文档说法

6.10 HyDE 召回

HyDE 是 Hypothetical Document Embeddings。

它的思路是：

先让模型根据问题生成一个“假想答案”或“假想文档”，再用这个假想文档去做向量检索。

例如用户问：

1

什么情况下订单不能退款？

模型先生成一个假想文档：

1

订单不能退款的情况通常包括虚拟商品已发货、超过退款期限、企业合同订单另有约定等。

然后对这段假想文档做 embedding，用它去检索。

为什么可能有效？

因为用户问题有时很短，而假想文档更接近知识库里的答案表述。

简化流程：

flowchart TD
  A["question"] --> B["LLM 生成 hypothetical document"]
  B --> C["embedding hypothetical document"]
  C --> D["vector search"]

适合：

  • 用户问题很短
  • 抽象问题
  • 概念解释
  • 文档表达偏答案式

不适合：

  • 精确事实
  • 错误码
  • 金额、日期、版本号
  • 高风险场景

因为 HyDE 生成的假想文档可能带入错误假设。

工程上最好把 HyDE 作为一路辅助召回，而不是唯一召回。

7.2 为什么 metadata filter 很重要

  • 美国区文档
  • 旧版文档
  • 新版文档

用户问：

如果不加 metadata filter，系统可能召回：

  • 美国区发票规则
  • 旧版发票流程
  • 内部财务操作文档
  • 用户无权限查看的文档

这些内容语义上都相关，但业务上不该用。

metadata filter 最好在召回阶段就生效。

不要把越权内容召回后再交给 LLM 判断。

因为一旦越权内容进入 prompt，就已经有泄露风险。

7.4 metadata filter 的风险

metadata filter 也可能造成漏召回。

例如：

  • 文档 metadata 标错
  • 用户所属权限组不同步
  • 新文档没有写 doc_status
  • 地区字段不规范
  • 时间字段格式混乱

所以 metadata 不是附属信息，而是 RAG 数据治理的一部分。

7.5 适用场景

metadata filter 适合：

  • 多租户系统
  • 企业内部知识库
  • 多产品线文档
  • 多地区政策
  • 多版本文档
  • 权限敏感场景
  • 时效性强的制度文档

八、Parent-Child Retrieval

8.1 它解决什么问题

RAG 里有一个经典矛盾：

  • chunk 小，检索更准，但上下文不完整
  • chunk 大，上下文完整，但检索噪声多

Parent-child retrieval 就是为了解这个矛盾。

8.2 基本思想

索引时保存两种粒度：

1
2

parent chunk：较大的段落或章节
child chunk：较小的检索片段

检索时：

flowchart TD
  A["用 child chunk 做精准召回"] --> B["找到 child 所属 parent"]
  B --> C["把 parent 或相邻片段交给 LLM"]

企业合同订单以合同条款为准。
退款到账时间通常为 3 到 5 个工作日。

child chunk 可以是：

1

虚拟商品一经发货不支持退款。

parent chunk 是完整小节：

1

检索命中 child 后，把 parent 带给模型，模型就能同时看到规则、例外和上下文。

九、Summary Index 召回

9.1 它解决什么问题

当文档很多、单篇文档很长时，直接 chunk 检索可能不稳定。

用户问一个宏观问题：

1

9.2 基本思想

为文档或章节生成摘要，并对摘要建立索引。

2

第一步：查 summary index，找到相关文档或章节
第二步：在这些文档或章节内查原文 chunk

  • 摘要可能遗漏细节
  • 不适合非常精确的字段查询

9.5 适用场景

适合：

  • 研究报告
  • 架构设计文档

  • 政策文件
  • 会议纪要
  • 多章节知识库

十一、Rerank 和召回的关系

11.1 rerank 不是召回，但通常紧跟召回

召回负责找候选。

rerank 负责把候选重新排序。

常见流程：

flowchart TD
  A["多路召回 top 100"] --> B["去重"]
  B --> C["rerank"]
  C --> D["取 top 5 到 top 10"]
  D --> E["上下文组装"]

11.2 Cross-Encoder Rerank

向量召回通常是双塔结构：

1
2
3

query -> embedding
chunk -> embedding
计算相似度

query 和 chunk 是分别编码的。

Cross-encoder rerank 则把 query 和 chunk 放在一起编码：

1

[query, chunk] -> relevance score

它更慢，但判断更精细。

适合对召回候选做二次排序。

11.3 LLM Rerank

也可以让大模型判断相关性。

例如给模型：

1
2
3
4

问题：Pro 套餐 API 调用上限是多少？
候选片段：Pro 套餐每月包含 100 万次 API 调用。

请判断候选片段是否能回答问题，输出 0 到 3 分。

优点：

  • 灵活
  • 可解释
  • 能处理复杂问题

缺点：

  • 成本高
  • 延迟高
  • 一致性不如专用 reranker

生产上更常见的是专用 rerank 模型。

11.4 rerank 适用场景

适合：

  • 召回结果多
  • 混合召回后噪声多
  • top-k 排名不稳定
  • 问题需要精细语义判断

不适合替代召回。

如果正确 chunk 没进入候选集，rerank 无法发挥作用。

十三、召回评估

13.1 召回评估看什么

召回评估不看最终答案，只看检索结果。

核心问题是：

正确证据有没有被找出来，排名是否足够靠前？

常见指标：

  • Recall@k（前 k 个结果的召回率）
  • Precision@k（前 k 个结果的精确率）
  • MRR（Mean Reciprocal Rank，平均倒数排名）
  • NDCG（Normalized Discounted Cumulative Gain，归一化折损累计增益）

13.2 Recall@k

Recall@k 看正确 chunk 是否出现在前 k 个结果里。

例如：

1
2

100 个问题里，有 82 个问题的正确 chunk 出现在 top 10
Recall@10 = 0.82

RAG 里非常关注这个指标。

如果 Recall@50 很低，说明召回链路有问题。

13.3 Precision@k

Precision@k 看前 k 个结果里有多少是相关结果。

例如：

1
2

top 10 结果里，有 6 个结果是相关 chunk
Precision@10 = 0.6

它衡量的是召回结果的干净程度。

在 RAG 里，Precision@k 太低通常意味着候选里噪声太多，后续 rerank 和上下文组装压力会变大。

13.4 MRR

MRR 看第一个正确结果排在第几位。

例如：

1
2
3

问题 A：正确结果排第 1，得分 1
问题 B：正确结果排第 2，得分 1/2
问题 C：正确结果排第 5，得分 1/5

MRR 越高，说明正确结果越靠前。

13.5 NDCG

如果一个问题有多个相关 chunk，而且相关程度不同，可以用 NDCG。

例如：

  • 完全相关：3 分
  • 部分相关：2 分
  • 弱相关：1 分
  • 不相关：0 分

NDCG 能衡量高相关结果是否排在前面。

13.7 召回失败排查

当一个问题没有召回正确 chunk，可以按这个顺序排查：

  1. 原始文档里有没有正确内容？
  2. 文档解析后内容是否丢失？
  3. chunk 是否把答案切完整？
  4. chunk 是否进入索引？
  5. query 是否表达了正确意图？
  6. BM25 是否能召回？
  7. 向量检索是否能召回？
  8. metadata filter 是否误过滤？
  9. top-k 是否太小？
  10. 多路融合是否把正确结果压低？

这个顺序可以快速定位问题在哪一层。

十四、常见调优建议

14.1 不要只调 top-k

很多人召回不好，第一反应是把 top-k 调大。

这能提高候选覆盖，但也会带来：

  • 噪声增加
  • rerank 成本增加
  • 延迟增加
  • 上下文组装压力增加

如果 top-k=100 仍然找不到正确结果，问题通常不在 top-k，而在：

  • chunk
  • query
  • embedding
  • BM25
  • metadata
  • 索引字段

14.2 不要只依赖向量检索

只做向量检索是很多 RAG demo 的默认方案，但生产中风险很高。

只要知识库里有：

  • 编号
  • 术语
  • 代码
  • 配置项
  • 错误码
  • 版本号

就应该考虑 BM25 或其他精确检索。

14.3 title 和 section_path 很重要

不要只把正文送去索引。

更好的索引文本通常是：

1
2
3

标题：计费系统说明
章节：套餐规则 > Pro 套餐 > API 调用限制
正文：Pro 套餐每月包含 100 万次 API 调用，超出部分按量计费。

标题和章节路径能显著增强召回信号。

14.4 权限过滤要前置

权限过滤不能只靠 prompt。

错误做法：

1
2

先召回所有内容
再告诉模型不要使用无权限内容

正确做法：

1

召回阶段就只搜索当前用户有权限的内容

权限是系统约束，不是生成建议。

14.5 线上失败样本要回流

召回优化不能只靠离线假问题。

最有价值的数据来自：

  • 用户点踩
  • 用户追问
  • 客服转人工
  • 搜索无结果
  • 答案引用不匹配
  • 用户重新换词搜索

这些样本应该进入评估集。

十五、高频面试题

15.1 RAG 里的召回是什么？它和生成有什么关系？

召回是从知识库里找候选证据。

生成是大模型基于这些证据组织答案。

在 RAG 链路里，召回通常发生在生成之前：

flowchart TD
  A["用户问题"] --> B["召回候选 chunk"]
  B --> C["rerank 排序"]
  C --> D["上下文组装"]
  D --> E["LLM 生成答案"]

召回质量决定答案上限。

如果正确证据没有被召回，后面的 rerank、prompt、LLM 通常很难补救。

15.2 召回和排序有什么区别？

召回关注的是：

正确证据有没有进入候选集。

排序关注的是：

正确证据能不能排在更靠前的位置。

所以召回更看重 Recall，排序更看重 Precision 和前排质量。

例如：

1

召回 top-50 里有正确 chunk，但排在第 40 位

这说明召回没有完全失败，但排序或 rerank 需要优化。

如果：

1

召回 top-100 里都没有正确 chunk

那就是更严重的召回问题。

15.3 为什么 RAG 不能只用向量召回？

向量召回擅长语义相似。

例如：

1
2
3

退款流程是什么？
订单能不能退？
如何申请售后退款？

这些表达不同，但语义接近，适合向量检索。

但向量召回不擅长所有问题。

例如：

  • 错误码
  • API 名称
  • 函数名
  • 版本号
  • 法条编号
  • 合同编号
  • 配置项

这些内容差一个字符，业务含义可能完全不同。

所以生产 RAG 通常会组合：

1

向量召回 + BM25 关键词召回 + metadata filter + rerank

15.4 BM25 和向量召回的区别是什么？

BM25 是关键词召回。

它主要看查询词是否出现在文档里，以及这些词有多重要。

适合：

  • 精确词
  • 编号
  • 错误码
  • API 名称
  • 专有名词

向量召回是语义召回。

它主要看 query 和 chunk 的 embedding 是否接近。

适合：

  • 同义表达
  • 自然语言问题
  • 概念相近内容
  • 用户说法和文档说法不同的场景

一句话：

BM25 擅长“字面匹配”，向量召回擅长“语义匹配”。

15.5 BM25 和倒排索引是什么关系？

倒排索引是数据结构。

BM25 是基于倒排索引做相关性打分的排序算法。

倒排索引负责找到候选：

1

词项 -> 出现在哪些 chunk 里

BM25 负责给候选打分：

1

这个 chunk 和 query 有多相关？

完整流程可以理解为：

flowchart TD
  A["query 分词"] --> B["查倒排索引找到候选 chunk"]
  B --> C["用 BM25 计算相关性分数"]
  C --> D["返回 top-k"]

所以：

倒排索引解决“去哪找”，BM25 解决“谁排前面”。

15.6 什么是混合召回？

混合召回通常指同时使用多种检索方式。

最常见的是：

1

BM25 召回 + 向量召回

例如：

flowchart TD
  A["query"] --> B["BM25 top-k"]
  A --> C["向量 top-k"]
  B --> D["去重"]
  C --> D
  D --> E["融合排序"]
  E --> F["rerank"]

它的价值在于互补。

BM25 可以抓住精确词。

向量检索可以抓住语义相似。

两者结合，比单一路召回更稳。

15.7 混合召回和多路召回有什么区别？

混合召回通常强调不同检索算法的组合。

例如：

1

BM25 + 向量检索

多路召回范围更广。

它可以包括：

  • 原始 query 召回
  • query rewrite 召回
  • query expansion 召回
  • HyDE 召回
  • 字段级召回
  • parent-child retrieval
  • summary index 召回
  • graph retrieval

所以可以理解为：

混合召回是多路召回的一种常见形式，但多路召回不只包含 BM25 和向量检索。

15.8 RRF 是什么？为什么混合召回常用它？

RRF 是 Reciprocal Rank Fusion，倒数排序融合。

它不直接比较不同召回通道的原始分数，而是根据排名融合。

常见公式是：

1

score(d) = sum( 1 / (k + rank_i(d)) )

其中：

  • d 是候选文档或 chunk
  • rank_i(d) 是它在第 i 个召回通道中的排名
  • k 是平滑参数，常见取值如 60

RRF 适合混合召回，因为不同通道的分数不可直接比较。

例如 BM25 分数和向量 cosine 分数不在同一个尺度上。

RRF 用排名融合，可以减少分数归一化带来的麻烦。

15.9 metadata filter 为什么重要？

metadata filter 用于限定检索范围。

例如：

  • 只查当前租户
  • 只查当前用户有权限的文档
  • 只查某个产品线
  • 只查当前版本
  • 排除废弃文档

它解决的不只是效果问题，还有安全问题。

错误做法是：

1
2

先召回全库
再让模型不要使用无权限内容

正确做法是：

1

召回阶段就只搜索用户有权限的数据

权限、租户、文档状态这类强约束，应该尽量前置过滤。

15.10 metadata filter 放在召回前还是召回后？

优先放在召回前或召回时。

也就是 pre-filter。

例如：

1
2
3

tenant_id = tenant_a
AND doc_status = active
AND permission_group IN user_groups

然后只在符合条件的 chunk 中召回。

如果先全库召回再过滤，会有几个问题：

  • 浪费 top-k 名额
  • 正确结果可能被挤掉
  • 无权限内容可能进入 rerank
  • 日志和缓存可能记录敏感内容

但如果 filter 条件不确定，例如产品线识别不准，可以考虑弱过滤或 boost，而不是强行过滤。

15.11 Parent-Child Retrieval 解决什么问题？

它解决的是：

小 chunk 适合检索，大 chunk 适合阅读。

如果 chunk 太小，检索更精准，但上下文可能不完整。

如果 chunk 太大，上下文完整，但检索容易被噪声干扰。

Parent-child retrieval 的做法是：

1
2

用 child chunk 做检索
命中后取 parent chunk 做上下文

例如：

1
2

child chunk：Pro 套餐每月包含 100 万次 API 调用。
parent chunk：整个 Pro 套餐规则小节。

这样可以同时兼顾检索精度和上下文完整性。

15.12 Summary Index 适合什么场景？

Summary Index 适合长文档粗定位。

例如：

  • 长报告
  • 白皮书
  • 合同
  • 研究论文
  • 大型产品手册

它的基本思路是：

1
2
3
4

先对文档或章节生成摘要
对摘要建索引
查询时先命中摘要
再进入对应章节找原始 chunk

它不是用摘要替代原文。

更稳妥的做法是：

summary 用来定位范围，原始 chunk 用来提供证据。

15.13 Graph Retrieval 适合什么场景？

Graph Retrieval 适合问题依赖实体关系或多跳关系的场景。

例如：

1

客户 A 当前合同对应的 SLA 是什么？

这个问题可能需要沿着关系查：

flowchart TD
  A["客户 A"] --> B["合同 B"]
  B --> C["套餐 C"]
  C --> D["SLA 条款 D"]

向量检索可能只找到语义相似文本，但不一定能正确沿关系跳转。

图召回适合：

  • 组织架构
  • 业务对象关系
  • 法规条款引用
  • 代码调用链
  • 知识图谱问答

但图召回的前提是实体和关系质量足够好。

15.14 HyDE 召回是什么？

HyDE 是 Hypothetical Document Embeddings。

它的做法是：

1
2
3

先让 LLM 根据 query 生成一个假想答案或假想文档
再对这个假想文档做 embedding
用这个 embedding 去检索真实文档

它适合 query 太短、太口语化、缺少检索词的场景。

例如用户问：

1

这个怎么收费？

直接检索可能很难。

HyDE 可以先生成一个更像文档的表达，再去检索。

但它也有风险：

  • LLM 生成内容可能带偏检索
  • 成本更高
  • 延迟更高
  • 不适合强事实约束场景直接依赖

15.15 Rerank 是召回吗？

严格说，rerank 不是召回。

召回负责从大规模知识库里找一批候选。

rerank 负责对候选重新排序。

流程通常是：

flowchart TD
  A["召回 top-50"] --> B["rerank 重排"]
  B --> C["取 top-5 进入上下文"]

rerank 不能凭空找回召回阶段漏掉的正确 chunk。

所以如果正确证据没有进入候选集，rerank 通常救不回来。

15.16 怎么评估召回效果？

常见指标包括：

  • Recall@k
  • MRR
  • NDCG
  • Hit Rate（命中率）

其中最基础的是 Recall@k。

例如：

1

Recall@10 = 正确 chunk 出现在 top-10 的问题比例

如果 Recall@10 很低，说明正确证据经常没有进入候选。

如果 Recall@50 很高，但最终答案仍然不好，可能是 rerank、上下文组装或生成阶段的问题。

15.17 召回失败应该怎么排查？

可以按链路从前往后排查：

  1. 原文里有没有答案
  2. 文档解析有没有丢内容
  3. chunk 是否切完整
  4. chunk 是否入库
  5. embedding 是否生成成功
  6. BM25 是否索引了正确字段
  7. query 是否需要改写
  8. metadata filter 是否误过滤
  9. top-k 是否太小
  10. 融合策略是否把正确 chunk 压低

排查时不要一上来就改 prompt。

先看：

召回 top-k 里有没有 golden chunk。

如果没有，优先修召回链路。

15.18 生产级召回和 demo 最大区别是什么？

demo 往往是：

flowchart TD
  A["chunk"] --> B["embedding"]
  B --> C["向量库 top-k"]
  C --> D["LLM"]

生产级召回通常还需要：

  • 文档解析质量
  • chunk 策略
  • BM25
  • 向量检索
  • 混合召回
  • 多路召回
  • metadata filter
  • 权限控制
  • rerank
  • 评估集
  • 失败样本回流
  • 索引版本管理

最大的区别是：

demo 追求能跑通，生产系统追求稳定、可控、可评估、可解释、可治理。

小结

RAG 召回不是“向量库 top-k”这么简单。

一个成熟的召回系统，通常会组合：

  • BM25 关键词召回
  • 向量语义召回
  • 混合召回
  • 多 query 召回
  • query rewrite
  • metadata filter
  • parent-child retrieval
  • summary index
  • graph retrieval
  • rerank

不同策略解决的问题不同：

  • BM25 解决精确匹配
  • 向量检索解决语义相似
  • 混合召回解决互补
  • metadata filter 解决范围和权限
  • parent-child 解决检索粒度和上下文完整性的矛盾
  • summary index 解决长文档定位
  • graph retrieval 解决实体关系和多跳问题
  • rerank 解决候选排序质量

如果只记一句话：

RAG 召回的目标不是“找几段相似文本”，而是稳定、可控、可解释地把正确证据送到模型面前。
