AI Agent Tool Calling 详解

May 13, 2026

写在前面

Tool Calling 是 Agent 从"会说话"变成"能做事"的关键。没有工具，模型只能生成文本；有了工具，Agent 才能查询数据库、检索知识库、调用业务系统。

本文以 Tool Calling 机制为主线，结合 LangChain 1.0+ 源码进行工程实践分析，帮助你理解从工具定义到执行闭环的完整链路。

一、Tool Calling 核心概念

1.1 基本定义

模型根据当前任务，选择一个工具，并生成该工具需要的结构化参数，由程序执行工具后再把结果返回给模型。

核心要点：

  • 模型负责决策：选择哪个工具、生成什么参数
  • 程序负责执行：校验参数、调用工具、返回结果
  • 模型不直接执行任何操作：它只输出结构化的"调用意图"

1.2 两种实现范式

范式指的是模型如何传递工具调用意图——Large Language Model（LLM，大语言模型）如何告诉程序"我要调用哪个工具"。

范式 代表 本质 优缺点
Prompt-based 早期 LangChain Agent 模型输出文本，程序解析文本 兼容任何模型，但格式不稳定，容易解析失败
Native Function Calling OpenAI/Claude/Gemini Application Programming Interface（API，应用程序编程接口） 模型输出结构化数据，程序直接读取 格式稳定、可并行调用多工具，是当前主流方案

注意：这里说的是通信机制，不是思维框架。 ReAct（Reasoning + Acting）是一种思维框架——让模型交替"思考→行动→观察"循环推理。 ReAct 早期用 Prompt-based 实现，现在主流用 Native Function Calling 实现，两者不是同一维度：

在 Prompt 里告诉模型"请按这个格式输出"，模型输出普通文本，程序用正则解析：

模型训练时就学会了输出结构化的工具调用字段，API 直接返回 JavaScript Object Notation（JSON，JS 对象表示法）结构：

类比：Prompt-based = 让人"把答案写在纸上，按固定格式写"（容易写错）；Function Calling = 让人"填表格，每个字段有固定位置"（不容易出错）。

二、完整流程与数据流

2.1 一次 Tool Calling 的完整时序

以用户问"北京今天天气怎么样？“为例：

sequenceDiagram
    participant U as 用户
    participant A as Agent Runtime（程序层）
    participant L as LLM（大模型）
    participant T as Tool（外部 API）
    U->>A: 北京今天天气？
    A->>L: 发送请求（System Prompt + 工具列表 + 用户消息）
    L-->>A: AIMessage(tool_calls: get_weather)
    A->>A: 校验参数 city: string
    A->>T: get_weather(city="北京")
    T-->>A: {temp: 28, condition: "晴"}
    A->>L: ToolMessage(content, tool_call_id="call_001")
    L-->>A: 北京今天晴朗，28°C
    A-->>U: 北京今天晴朗，28°C

逐步拆解：

阶段 谁在做事 做了什么 关键点
①② 决策 Agent → LLM LLM 看到工具列表后，决定调用哪个工具、传什么参数 LLM 不执行工具，只输出调用意图
③ 校验 Agent 自身 用 JSON Schema 校验 LLM 生成的参数 程序负责安全边界
④⑤ 执行 Agent → Tool 程序真正调用外部 API 获取数据 程序负责执行
⑥⑦ 总结 Agent → LLM 把工具原始数据交给 LLM 组织成自然语言 tool_call_id 关联请求和响应

LLM 只负责"想”（选工具、填参数、组织语言），程序负责"做"（校验、执行、传递）。 两者通过结构化的 tool_calls 和 ToolMessage 进行通信。

# LLM 决定调用工具时，输出包含 tool_calls 的 AIMessage
ai_msg = AIMessage(
    content="",
    tool_calls=[{
        "name": "get_weather",
        "args": {"city": "北京"},
        "id": "call_abc123"
    }]
)

# 工具执行结果通过 ToolMessage 回填，tool_call_id 关联对应请求
tool_msg = ToolMessage(
    content='{"temp": 28, "condition": "晴"}',
    tool_call_id="call_abc123",
    name="get_weather"
)

# LLM 认为信息充足时，输出不含 tool_calls 的 AIMessage → 循环结束
final_msg = AIMessage(content="北京今天晴朗，气温28°C。")
消息类型 循环中的含义
AIMessage(tool_calls=[...]) 请求调用工具，循环继续
ToolMessage(content, tool_call_id) 工具执行结果，回填给 LLM
AIMessage(content="...") 最终回答，循环结束

设计要点：

  • enum 约束：限制取值范围，减少模型幻觉
  • description 字段：每个参数都要有说明，这是模型理解参数含义的关键
  • maxLength/minimum/maximum：设置边界，防止异常输入
  • 默认值说明：在 description 中告知模型默认行为

3.4 工具集设计原则

  1. 单一职责：每个工具做一件事，不要设计"万能工具"
  2. 正交性：工具之间功能不重叠，避免 LLM 选择困难
  3. 粒度适中：太细（get_user_name, get_user_email）增加调用次数；太粗（do_everything）参数复杂
  4. 描述精确：明确说明适用场景和不适用场景
  5. 结果可预测：相同输入应产生相同格式的输出
  6. 错误友好：错误信息应帮助 LLM 自我修正

class BaseTool(RunnableSerializable[Union[str, dict, ToolCall], Any]):
    name: str                    # 工具名称，传给 LLM
    description: str             # 工具描述，LLM 据此决定是否调用
    args_schema: Optional[Type[BaseModel]] = None  # Pydantic 参数模型
    return_direct: bool = False  # True 则工具结果直接返回用户，不再经过 LLM
    handle_tool_error: Optional[Union[bool, str, Callable]] = False

    @abstractmethod
    def _run(self, *args, **kwargs) -> Any:
        """子类必须实现的同步执行方法"""

    @property
    def args(self) -> dict:
        """返回工具参数的 JSON Schema"""
        if self.args_schema:
            return self.args_schema.model_json_schema()
        return {"type": "object", "properties": {}}

BaseTool 继承自 RunnableSerializable，意味着每个工具都是 LCEL 中的一等公民，可以用 | 管道符组合、自动获得 batch/async/stream 能力。

def convert_to_openai_tool(tool: Union[BaseTool, Type[BaseModel], Callable]) -> dict:
    if isinstance(tool, BaseTool):
        return {
            "type": "function",
            "function": {
                "name": tool.name,
                "description": tool.description,
                "parameters": tool.args  # 来自 args_schema.model_json_schema()
            }
        }

class BaseChatModel:
    def bind_tools(self, tools, tool_choice=None, **kwargs) -> Runnable:
        formatted_tools = [convert_to_openai_tool(t) for t in tools]
        return self.bind(tools=formatted_tools, tool_choice=tool_choice, **kwargs)

tool_choice 参数控制模型的工具调用行为：

tool_choice 值 含义
"auto" 模型自行决定是否调用工具（默认）
"any" / "required" 必须调用至少一个工具
{"type":"function","function":{"name":"xxx"}} 强制调用指定工具
"none" 禁止调用工具

四、参数校验机制

4.1 为什么模型生成的参数不能直接信任

即使提供了严格的 JSON Schema，模型仍可能：

  • 遗漏必填字段
  • 类型错误（字符串写成数字）
  • 枚举值拼写错误
  • 注入恶意内容（Prompt Injection via Tool Args）
  • 越权访问（传入他人 ID）

4.2 多层校验策略 

flowchart TD
    A[Layer 1: JSON Schema 格式校验\n类型 / 必填 / 枚举 / 长度]
    B[Layer 2: 业务逻辑校验\n金额范围 / 日期合理性 / ID 存在性]
    C[Layer 3: 安全校验\n权限检查 / 注入检测 / 敏感操作拦截]
    D[Layer 4: 上下文校验\n参数与对话上下文是否一致 / 是否越权]
    A --> B --> C --> D

4.3 校验失败的处理策略

策略 适用场景 实现方式
让模型重试 轻微格式错误 返回 ValidationError 信息作为 ToolMessage
自动修复 可推断的错误（如类型转换） 在校验层自动 coerce
请求用户补充 缺少关键信息 Agent 生成澄清问题
拒绝执行 安全风险 返回拒绝信息 + 记录日志

# BaseTool.invoke() 中的校验逻辑（简化）
def invoke(self, input: ToolCall, config=None):
    tool_input = input["args"]
    if self.args_schema:
        try:
            validated = self.args_schema(**tool_input)
            tool_input = validated.model_dump()
        except ValidationError as e:
            if self.handle_validation_error:
                return str(e)  # 返回错误信息让 LLM 自我修正
            raise
    return self._run(**tool_input)

from langchain_core.tools import BaseTool
from pydantic import BaseModel, Field, field_validator

class QueryDBInput(BaseModel):
    sql: str = Field(description="SQL 查询语句，仅支持 SELECT")
    database: str = Field(description="目标数据库", default="main")

    @field_validator("sql")
    @classmethod
    def validate_sql(cls, v):
        if not v.strip().upper().startswith("SELECT"):
            raise ValueError("仅允许 SELECT 查询")
        dangerous = ["DROP", "DELETE", "UPDATE", "INSERT", "ALTER"]
        for keyword in dangerous:
            if keyword in v.upper():
                raise ValueError(f"禁止使用 {keyword} 语句")
        return v

class QueryDBTool(BaseTool):
    name = "query_database"
    description = "执行只读 SQL 查询。仅支持 SELECT 语句。"
    args_schema = QueryDBInput
    handle_tool_error = True

    def _run(self, sql: str, database: str = "main") -> str:
        conn = get_connection(database)
        result = conn.execute(sql)
        return json.dumps(result.fetchall())

五、Agent 执行循环

5.1 循环机制

Agent 的核心是一个"LLM 决策 → 工具执行 → 结果回填"的循环，直到 LLM 认为信息充足为止。

flowchart TD
    A[Agent / LLM] --> B{has tool_calls?}
    B -- Yes --> C[Tools execute]
    C -- ToolMessage --> A
    B -- No --> D[END]

5.2 终止条件

终止条件（满足任一即停止）：

1. LLM 不再输出 tool_calls → 它认为信息够了，直接生成文本回答
2. 达到最大调用次数限制 → 强制停止，防止无限循环
3. 工具返回终止信号 → 如 return_direct=True 的工具，结果直接返回用户

常见的无限循环场景及防御：

场景：LLM 反复调用同一个工具，每次参数略有不同
原因：工具返回的错误信息不够明确，LLM 不知道该放弃

防御：
  ├── 设置最大调用次数硬上限
  ├── 针对特定工具设置调用次数限制
  └── 错误信息要明确告诉 LLM "此操作不可行，请换个方案"

class ToolNode(RunnableCallable):
    """从 AIMessage 的 tool_calls 中提取并执行工具"""

    def __init__(self, tools: Sequence[BaseTool], handle_tool_errors: bool = True):
        self.tools_by_name = {tool.name: tool for tool in tools}

    def _func(self, input: Union[list, dict]) -> dict:
        messages = input if isinstance(input, list) else input["messages"]
        last_message = messages[-1]

        outputs = []
        for tool_call in last_message.tool_calls:
            tool = self.tools_by_name[tool_call["name"]]
            try:
                result = tool.invoke(tool_call)
            except Exception as e:
                if self.handle_tool_errors:
                    result = f"Error: {e}"
                else:
                    raise
            outputs.append(
                ToolMessage(content=result, tool_call_id=tool_call["id"])
            )
        return {"messages": outputs}

class AgentExecutor(Chain):
    agent: Runnable
    tools: Sequence[BaseTool]
    max_iterations: int = 15

    def _call(self, inputs: dict) -> dict:
        intermediate_steps = []
        iterations = 0
        while self._should_continue(iterations):
            output = self.agent.plan(intermediate_steps=intermediate_steps, **inputs)
            if isinstance(output, AgentFinish):
                return self._return(output, intermediate_steps)
            for action in [output]:
                tool = self._get_tool(action.tool)
                observation = tool.run(action.tool_input)
                intermediate_steps.append(AgentStep(action, observation))
            iterations += 1
        return self._handle_early_stopping()

7.1 错误分类与处理策略

错误类型 示例 是否可重试 处理方式

十、高频面试题

Q1: Tool Calling 和普通函数调用有什么区别？

维度 普通函数调用 Tool Calling
决策者 程序逻辑（if/else） LLM 根据语义理解
参数来源 硬编码或用户输入 LLM 从上下文推断生成
调用时机 编译时确定 运行时动态决定
错误恢复 程序员预设 LLM 可自我修正重试
组合方式 固定流程 LLM 动态编排多工具

本质区别：Tool Calling 将"调用什么"和"传什么参数"的决策权交给了 LLM，程序只负责执行和校验。

Q2: 为什么工具参数还需要程序侧校验？

LLM 的输出本质上是概率采样，不是确定性程序。即使给了完美的 Schema：

  1. 模型可能幻觉：生成不存在的枚举值
  2. 格式不稳定：偶尔输出非法 JSON
  3. 安全边界：模型不理解业务权限
  4. Prompt Injection：用户可能通过对话注入恶意参数

程序侧校验是 Agent 系统的安全边界，是防止 LLM 不确定性传导到下游系统的最后一道防线。

Q3: Prompt-based 和 Native Function Calling 的区别？ReAct 属于哪个？ 

 1

Prompt-based（通信机制）:
  本质：模型输出文本，程序用正则解析出工具名和参数
  优点：兼容任何 LLM
  缺点：依赖正则解析，格式不稳定，不支持并行调用

Native Function Calling（通信机制）:
  本质：模型输出结构化 tool_calls 字段，程序直接读取
  优点：格式稳定、支持并行调用、模型专门训练过
  缺点：依赖特定模型 API 支持

ReAct（思维框架，不是通信机制）:
  本质：让模型交替执行 Thought → Action → Observation 循环
  早期用 Prompt-based 实现
  现在用 Native Function Calling 实现
  ReAct 关注的是"怎么思考"，不是"怎么传递调用意图"

    │       → 立即停止，告知用户无权限，不重试
    │
    ├── 超时/网络错误？
    │       → 自动重试 1-2 次，仍失败则降级或告知用户
    │
    ├── 业务逻辑失败（如"订单不存在"）？
    │       → 将业务错误返回给 LLM，由其决定下一步
    │
    └── 达到最大重试次数？
            → 记录完整 trace，返回友好错误信息给用户

Q5: 如何防止 Tool Calling 中的 Prompt Injection？

六层防御：工具白名单 → 参数 Schema 校验 → 权限隔离 → 输入清洗 → Human-in-the-Loop → 审计日志。

核心思路：不信任 LLM 的任何输出，在程序层做严格的边界控制。

Q6: LangChain 中 BaseTool 为什么继承 Runnable？

Runnable 是 LangChain LCEL 的核心抽象，提供统一的 invoke/ainvoke/batch/stream 接口。工具继承 Runnable 意味着：

  • 可以用 | 管道符与其他组件组合
  • 自动获得 batch（批量执行）能力
  • 自动获得 async 支持
  • 可以被 LangGraph 的节点系统直接使用
  • 统一的 callback/tracing 机制

Q7: 如何设计一个好的工具集？

  1. 单一职责：每个工具做一件事
  2. 正交性：工具之间功能不重叠
  3. 粒度适中：太细增加调用次数，太粗参数复杂
  4. 描述精确：明确适用和不适用场景
  5. 结果可预测：相同输入产生相同格式输出
  6. 错误友好：错误信息帮助 LLM 自我修正
