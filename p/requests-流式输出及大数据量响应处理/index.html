Requests 流式输出及大数据量响应处理

source: response处理流式输出及大参数接收处理
Mar 18, 2026

问题背景

在 Workflow 向 Console 传输大数据量流式响应时，客户端使用 requests.Response.iter_lines() 逐行消费数据。数据量较小时工作正常，但数据量增大后，会出现长时间接收不到新消息、表现类似“卡住”的情况。

将其替换为自定义的增量行解析器后，流式数据可以继续正常接收，处理性能也得到改善。

需要说明的是，iter_lines() 没有固定的数据量上限。“卡住”并不等于超过了 Requests 的最大响应大小，更可能与以下因素共同相关：

  • iter_lines() 只有遇到换行符或响应结束时才会返回当前行，超长单行会长时间保存在缓冲区中。
  • 原版通过 pending + chunk 拼接未完成行，超长行会反复创建并复制 bytes 对象。
  • 默认读取分块大小及底层网络缓冲可能影响流式数据的可见延迟。
  • \r\n 恰好被拆分到两个网络 Chunk 时，原版可能将其识别成两个换行符，从而产生额外空行；如果上层协议对空行有特殊含义，可能进一步影响消息状态机。

本文记录 response.text、response.content 与流式迭代接口的区别，并给出自定义行解析器的实现及适用边界。

完整响应与流式读取的区别

response.content

response.content 返回完整响应体的 bytes。即使请求使用了 stream=True，访问该属性仍会读取剩余响应并缓存到内存中，因此它不是逐块消费接口。

1
2
3
4

import requests

response = requests.get("https://api.example.com/data", stream=True)
body = response.content  # bytes；读取完整响应体

response.text

response.text 返回完整响应体解码后的 str。它依赖完整的 response.content，同样不适合无限流、实时日志或大文件等需要边接收边处理的场景。

1
2
3
4

import requests

response = requests.get("https://api.example.com/data", stream=True)
text = response.text  # str；读取完整响应体后进行解码

iter_content() 与 iter_lines()

真正用于流式消费的是：

  • response.iter_content()：按数据块读取，适合文件下载、二进制数据和自定义协议解析。
  • response.iter_lines()：在 iter_content() 之上按行切分，适合日志流和以行为边界的文本协议。
  • response.raw：直接访问 urllib3 的底层响应对象，控制能力更强，但需要自行处理解压、异常和兼容性问题。

例如，流式下载文件时应使用 iter_content()：

1
2
3
4
5
6
7

import requests

with requests.get("https://api.example.com/file", stream=True) as response:
    response.raise_for_status()
    for chunk in response.iter_content(chunk_size=64 * 1024):
        if chunk:
            process_chunk(chunk)

因此，content 与 iter_content() 不能混为一谈：前者是完整字节响应，后者才是分块迭代接口。

pending = None

    if pending is not None:
        chunk = pending + chunk

    lines = chunk.splitlines()

    if 最后一部分不是完整行:
        pending = lines.pop()
    else:
        pending = None

    yield from lines

if pending is not None:
    yield pending

普通情况下，这种实现能够正确拼接跨 Chunk 的行。例如：

1
2

chunk1 = b"hello wor"
chunk2 = b"ld\nnext"

原版会先保存 b"hello wor"，收到下一个 Chunk 后拼接并返回 b"hello world"。

但是，数据量较大且单行很长时，下面的操作会不断创建新的不可变 bytes 对象，并复制已经积累的数据：

1

chunk = pending + chunk

这会增加 CPU 和瞬时内存开销。需要强调的是：这里是潜在性能原因，不是 Requests 规定了某个固定的数据量上限。

CRLF 跨 Chunk 的边界问题

Windows 和 HTTP 文本中常见的换行符是 \r\n。网络分块不保证按照行边界切分，因此可能出现：

1
2

chunk1 = b"hello\r"
chunk2 = b"\nworld"

原版对第一个 Chunk 调用 splitlines() 时，可能先把末尾 \r 当成一个完整换行符；处理第二个 Chunk 时，又把开头的 \n 当成另一个换行符，于是额外产生一个空行。

这通常不会直接让 iter_lines() 永久停止读取，但在 SSE 或自定义流式协议中，空行可能表示“一条事件结束”。额外空行可能导致事件被提前提交、产生空事件，或者使上层消息状态机进入异常状态，从外部看起来类似消息中断或卡住。

自定义解析器遇到缓冲区末尾的 \r 时不会立即消费，而是等待下一个 Chunk：

1
2

第一次：hello\r     → 暂不判断
第二次：hello\r\n   → 确认为一个完整的 CRLF

真正解决 CRLF 边界问题的是“保留跨 Chunk 缓冲区并延迟判断”，而不是 bytearray 类型本身。

from collections.abc import Iterator

import requests


def chunk_iter_lines(
    resp: requests.Response,
    chunk_size: int | None = None,
    decode_unicode: bool = False,
    encoding: str | None = None,
    trim_threshold: int = 5 << 20,
) -> Iterator[bytes | str]:
    """增量解析流式响应，兼容跨 Chunk 换行并减少缓冲区复制。"""
    buf = bytearray()
    line_start = 0
    search_start = 0
    enc = encoding or resp.encoding or "utf-8"

    for chunk in resp.iter_content(chunk_size=chunk_size, decode_unicode=False):
        if not chunk:
            continue

        old_length = len(buf)
        buf.extend(chunk)

        # 上一块若以 CR 结束，需要从 CR 位置重新判断；否则只扫描新增数据。
        scan_from = min(search_start, old_length)

        while True:
            nl = buf.find(b"\n", scan_from)
            cr = buf.find(b"\r", scan_from)

            if nl == -1 and cr == -1:
                search_start = len(buf)
                break

            if nl == -1:
                line_end = cr
            elif cr == -1:
                line_end = nl
            else:
                line_end = min(nl, cr)

            # CR 位于当前缓冲区末尾时，等待下一块确认是否组成 CRLF。
            if buf[line_end] == 13 and line_end == len(buf) - 1:
                search_start = line_end
                break

            if buf[line_end] == 13 and buf[line_end + 1] == 10:
                line_ending_length = 2
            else:
                line_ending_length = 1

            line = bytes(buf[line_start:line_end])
            line_start = line_end + line_ending_length
            scan_from = line_start
            search_start = line_start

            if decode_unicode:
                yield line.decode(enc, errors="replace")
            else:
                yield line

        # 仅删除已经消费的前缀，避免每解析一行都移动剩余数据。
        if line_start > trim_threshold:
            del buf[:line_start]
            search_start -= line_start
            line_start = 0

    # EOF 时，缓冲区末尾的单独 CR 应作为换行符，而不是正文。
    if line_start < len(buf) and buf[-1] == 13:
        line = bytes(buf[line_start:-1])
        if decode_unicode:
            yield line.decode(enc, errors="replace")
        else:
            yield line
    elif line_start < len(buf):
        line = bytes(buf[line_start:])
        if decode_unicode:
            yield line.decode(enc, errors="replace")
        else:
            yield line

实现要点

使用持久化缓冲区

所有 Chunk 都追加到同一个 bytearray：

1

buf.extend(chunk)

相较于反复执行 pending + chunk，这种方式减少了新建 bytes 对象和复制历史数据的次数。

只扫描新增数据

search_start 记录已经搜索过的位置。当前缓冲区没有换行符时，下一次从新增数据附近继续搜索，避免超长行每到一个 Chunk 就从行首重新扫描。

唯一需要回退的位置是缓冲区末尾的 \r，因为必须结合下一个字节确认它是否属于 \r\n。

兼容三种换行格式

解析器支持：

  • \n
  • \r\n
  • \r

当 \r 位于 Chunk 末尾时延迟判断，避免将一个跨 Chunk 的 \r\n 错误识别成两个换行符。

定期清理已消费数据

line_start 超过阈值后，统一删除已经处理过的缓冲区前缀：

1

del buf[:line_start]

这可以避免已处理数据长期占用内存。该阈值不是最大响应大小，也不是最大行长度。

为什么修改后不再“卡住”

结合实现差异，替换后恢复正常可能来自以下改进：

  1. 通过 bytearray 增量追加，减少超长行场景下反复拼接不可变 bytes 的开销。
  2. 使用搜索游标跳过已经检查过的数据，避免对超长未完成行重复全量扫描。
  3. 正确处理跨 Chunk 的 \r\n，避免额外空行干扰上层消息协议。
  4. chunk_size=None 改变了底层分块交付方式，在当前链路中可能降低等待固定大小数据块带来的延迟。

第 4 点的实际行为会受到服务端传输方式、urllib3 版本、代理缓冲和网络环境影响。因此，应将“不再卡住”作为当前业务链路中的实际结果，而不应推广成所有 Requests 场景下的必然结论。

文本解码注意事项

不要对任意网络 Chunk 直接执行：

1

text = chunk.decode("utf-8")

UTF-8 中文字符可能被拆分到两个 Chunk，从而触发 UnicodeDecodeError。本文的自定义解析器先在字节层面拼接出完整行，再对整行进行解码，因此适用于 UTF-8 等以单字节 \r、\n 表示换行的 ASCII 兼容编码。

如果需要处理不以单字节表示换行的编码，或者需要直接解码任意数据块，应使用增量解码器。

使用边界

该实现仍然不是固定内存算法。如果服务端持续发送一个没有任何换行符的超大单行，为了保持 iter_lines() 的语义，解析器必须保留整行内容，缓冲区仍会持续增长。

生产环境可以根据协议增加最大单行长度限制：

1
2

if len(buf) - line_start > max_line_size:
    raise ValueError("流式响应单行超过允许的最大长度")

另外，流式接口还应结合连接超时、读取超时、服务端及时 flush、反向代理缓冲配置以及断线重试机制综合排查。

总结

  • response.content 和 response.text 都会读取完整响应，不是流式消费接口。
  • 流式响应应使用 iter_content()、iter_lines() 或经过审慎封装的底层响应流。
  • iter_lines() 没有固定数据量上限，但超长单行、重复拼接、读取缓冲和上层协议状态可能造成明显卡顿。
  • 自定义实现通过持久化 bytearray、增量扫描、跨 Chunk CRLF 判断和已消费前缀裁剪，改善了当前大数据量流式响应链路的稳定性与处理性能。
  • 没有换行符的无限长单行仍可能持续占用内存，必要时应设置最大单行长度。
