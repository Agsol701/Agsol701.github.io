什么是 RAG：完整流程、常见实现、底层原理、常见坑与高频面试题

May 04, 2026

写在前面

这两年 RAG 基本已经成了大模型落地里出现频率最高的词之一。

很多人会把它简单理解成：

  • 向量数据库
  • 知识库问答
  • embedding 检索
  • 给模型外挂记忆

这些理解都不算完全错，但都不够完整。

如果先用一句话做一个总定义：

RAG，即 Retrieval-Augmented Generation，是一种“先检索外部知识，再基于检索结果生成答案”的系统方法。

这里最关键的是两点：

  • RAG 不是单纯的检索系统
  • RAG 也不是单纯的生成系统

它本质上是一套把“知识供给”与“语言生成”组合起来的应用架构。

所以这篇文章不只回答“RAG 是什么”，还会系统整理这些问题：

  1. 一个完整的 RAG 到底分几步
  2. 常见实现方式有哪些
  3. 它底层为什么能工作
  4. 工程上最容易踩哪些坑
  5. 面试里最常被问什么
  6. 除了搭建，还应该怎么评估和优化

一、RAG 到底是什么

1.1 最直白的理解

可以先把 RAG 理解成：

让模型在回答前，先去知识库里“查资料”。

例如用户问：

“公司的报销流程是什么？”

如果只靠模型参数记忆，它很可能不知道你们公司的内部制度。

但如果系统先去：

  • 内部文档库
  • Wiki
  • 产品手册
  • 数据库说明

里找出最相关的资料，再把这些资料和问题一起交给大模型，那么模型就可以基于这些真实内容来回答。

这就是 RAG 的核心思路。

1.2 它解决的核心问题是什么

RAG 主要解决的是：

模型知识不够新、不够专、不够私有时，如何把外部知识动态提供给模型。

这背后通常对应四类痛点。

第一类：模型不知道私有知识

比如：

  • 企业内部制度
  • 项目源码
  • 私有 API 文档
  • 合同、报告、会议纪要

这些内容通常不会出现在模型训练数据里。

第二类：模型知识过期

即使模型很强，它参数里的知识也不是实时更新的。

所以：

  • 最新政策
  • 新版本文档
  • 刚上线的产品能力
  • 当天生成的业务数据

都更适合通过检索动态注入。

第三类：模型容易幻觉

如果没有可靠依据，模型很可能“看起来像在回答，实际上是在猜”。

RAG 的一个重要价值，就是尽量让回答建立在可追溯资料之上。

第四类：纯微调成本高且不灵活

如果每次知识更新都靠微调：

  • 成本高
  • 反馈慢
  • 数据准备重
  • 难以处理高频变更

而 RAG 更适合处理“知识频繁变化”的场景。

二、RAG 的完整流程

很多人以为 RAG 只有“切块 + 向量库 + 检索 + 生成”。

这其实只说到了主干，没有把工程链路讲完整。

一个相对完整的 RAG，通常可以拆成下面几个阶段。

2.1 数据接入

先把知识源接进系统。

常见来源包括：

  • PDF
  • Word
  • Markdown
  • 网页
  • FAQ
  • 数据库
  • 代码仓库
  • 工单与聊天记录

这一阶段的关键，不是“存进去”，而是先解决：

  • 数据从哪里来
  • 更新频率如何
  • 权限怎么处理
  • 原始格式怎么统一

2.2 文档解析

原始文档往往不能直接拿去检索。

例如 PDF 里可能有：

  • 页眉页脚
  • 表格
  • 图片
  • 双栏排版
  • OCR 错误

所以通常要先做解析，把它转成更适合处理的文本结构。

这一步常见操作包括：

  • 提取正文
  • 去噪
  • 保留标题层级
  • 识别表格和代码块
  • 保留文档元数据

2.3 文本切分

解析后的长文档，通常还要切成多个 chunk。

这是因为：

  • embedding 模型有长度限制
  • 检索粒度不能太粗
  • LLM 上下文窗口有限

切分时常见策略包括：

  • 固定长度切分
  • 滑动窗口切分
  • 按标题层级切分
  • 按段落语义切分
  • 针对代码、表格、问答做定制切分

chunk 设计直接影响后面的召回质量，是 RAG 里最关键的环节之一。

2.4 向量化与索引构建

切好块之后，通常要把每个 chunk 转成向量。

这一步就是 embedding。

向量化之后，系统会把这些内容连同元数据存进索引中，常见形式包括：

  • 向量索引
  • 倒排索引
  • 混合索引
  • 图结构索引

这里的元数据通常包括：

  • 文档标题
  • 来源 URL
  • 时间
  • 权限标签
  • 部门
  • 产品线
  • 章节路径

2.5 查询理解

用户问题并不总是适合直接拿去检索。

例如用户问：

“这个东西最近权限改了吗？”

这里的“这个东西”如果没有上下文，检索很难命中。

所以很多系统在检索前会先做查询理解，例如：

  • query rewrite
  • query expansion
  • 指代消解
  • 多轮上下文拼接
  • 把模糊问题改写成可检索问题

2.6 召回

这一步是从索引中找出最相关的候选内容。

常见召回方式包括：

  • 向量相似度召回
  • BM25 关键词召回
  • 混合召回
  • 多路召回

召回阶段重点关注的是：

  • 尽量别漏掉真正相关内容
  • 给后续排序保留足够候选集

也就是说，这一阶段更偏“高召回率”。

2.7 重排

召回出来的结果不一定顺序最好，所以通常还会有 rerank。

重排的作用是：

在候选集合里，把真正最相关的内容排到前面。

常见方式包括：

  • cross-encoder rerank
  • 基于大模型打分
  • 结合 metadata 规则重排
  • 基于时间、权限、来源可信度重排

很多线上系统的实际效果提升，往往就来自“召回后再排一次”。

2.8 上下文组装

不是把召回结果一股脑塞给模型就行。

还要解决：

  • 选哪几段
  • 按什么顺序放
  • 是否去重
  • 是否合并相邻片段
  • 是否附带来源信息

这一阶段本质上是在做：

context packing

也就是在有限 token 预算里，把最有价值的信息装进去。

2.9 生成答案

把用户问题和检索结果一起交给大模型，让模型生成最终回答。

这一阶段常见设计包括：

  • 严格基于资料回答
  • 回答时附上引用
  • 资料不足时明确说不知道
  • 区分“原文摘录”和“模型总结”

2.10 后处理与反馈闭环

一个成熟系统通常还有最后几步：

  • 答案引用对齐
  • 敏感信息过滤
  • 结果缓存
  • 用户反馈收集
  • 失败样本回流

这部分决定系统能不能持续优化，而不是只跑通一次 demo。

三、RAG 的常见实现方式

RAG 并不是只有一种形态。

3.1 Naive RAG

最基础的做法是：

  1. 文档切块
  2. embedding
  3. 向量检索 top-k
  4. 把结果塞给 LLM

这是很多教程里的起点。

优点是简单、容易落地。

缺点也很明显：

  • 对 query 表达很敏感
  • 容易召回不准
  • chunk 粗糙时效果差
  • 缺少 rerank 和多路检索时上限较低

3.2 Advanced RAG

这是最常见的工程升级形态。

典型增强点包括：

  • 更合理的 chunk 策略
  • query rewrite
  • hybrid search
  • rerank
  • metadata filter
  • 引用输出
  • 缓存和评估

很多企业里的“生产级 RAG”，本质上都属于这一类。

3.3 Hybrid RAG

也就是混合检索。

它通常把：

  • 稠密检索
  • 稀疏检索

结合起来。

原因是：

  • 向量检索擅长语义相近
  • 关键词检索擅长精确术语、缩写、版本号、错误码

例如：

  • API 名称
  • 订单号
  • 类名函数名
  • 法条编号

这类内容，单靠向量检索往往不稳定。

3.4 Graph RAG

当知识之间存在明显关系结构时，会有人引入图。

例如：

  • 实体关系
  • 组织架构
  • 系统依赖关系
  • 代码调用关系

它的思路不是只检索文本相似度，而是利用实体和关系做扩展检索与推理。

适合：

  • 多跳问答
  • 复杂实体关系问题
  • 依赖路径分析

3.5 Agentic RAG

在更复杂的系统里，检索不一定只发生一次。

模型可能会：

  1. 先理解问题
  2. 决定检索哪类资料
  3. 看第一次结果够不够
  4. 不够就继续改写 query 或继续查
  5. 最后再生成答案

这类做法通常会和 agent、tool use、workflow 编排结合起来。

它的特点是更灵活，但系统复杂度也更高。

3.6 Long-Context RAG

随着上下文窗口变大，一些团队会减少复杂检索层，更多依赖“大上下文直接读”。

但这不等于 RAG 失效。

更准确地说，是 RAG 的重点会从“强压缩检索”转向：

  • 更好的筛选
  • 更好的排序
  • 更好的上下文组织

长上下文不是 RAG 的替代品，而是改变了 RAG 的工程权衡。

四、RAG 的底层原理

这部分是面试里最容易被问到，也最容易回答空泛的地方。

4.1 embedding 为什么能检索相似内容

embedding 的核心作用，是把文本映射成高维向量。

在这个向量空间里，语义相近的文本，通常距离更近。

例如：

  • “怎么重置密码”
  • “忘记密码怎么办”

虽然字面不完全一样，但 embedding 后可能距离较近。

检索时，系统会把用户 query 也转成向量，然后在向量库里找“距离最近”的若干个 chunk。

常见相似度计算方式包括：

  • cosine similarity
  • dot product
  • euclidean distance

4.2 为什么还需要关键词检索

因为“语义相近”不等于“字面精确”。

例如：

  • ERR_CONN_RESET
  • v2.3.17
  • OrderService.create()

这类符号、编号、专有名词，BM25 或倒排索引往往更稳定。

所以真实系统里，通常不会只依赖单一路径。

4.3 chunk 为什么会影响效果

因为检索命中的对象不是整篇文档，而是 chunk。

如果 chunk 太大：

  • 噪声多
  • 主题混杂
  • 命中后塞进上下文的成本高

如果 chunk 太小：

  • 语义不完整
  • 容易丢上下文
  • 答案依据被切散

所以 RAG 很多问题，不是模型不行，而是 chunk 粒度设计得不对。

4.4 rerank 为什么有效

召回阶段通常追求“别漏”，所以候选结果里常常混入一些“差不多相关”的内容。

而 rerank 更像第二道筛选：

它不要求扫全库，只要求在较小候选集里做更精细的相关性判断。

因此它通常能显著改善 top 几条结果的质量。

4.5 RAG 为什么能降低幻觉

因为模型不再只靠参数记忆，而是能参考外部证据。

但要注意：

RAG 只能降低幻觉，不能彻底消灭幻觉。

因为即使检索到了正确内容，也仍然可能出现：

  • 模型误读资料
  • 引用错段落
  • 过度总结
  • 把多个来源拼错

所以 RAG 本质上是“提升证据供给质量”，不是“自动保证真相”。

五、RAG 中最容易遇到的坑

真正做 RAG，问题通常不在“能不能跑起来”，而在“为什么效果总是不稳定”。

5.1 只关注模型，不关注数据质量

这是最常见的问题。

如果源文档本身：

  • 过期
  • 冲突
  • OCR 错误严重
  • 标题层级混乱

那后面检索和生成做得再漂亮，结果也不会稳定。

5.2 chunk 切分太机械

很多 demo 会直接按固定字数切。

这在真实场景里经常导致：

  • 表格被截断
  • 问答对被拆开
  • 标题和正文分离
  • 代码片段不完整

结果就是看起来检索到了，实际上证据不完整。

5.3 只做向量检索

纯向量检索对很多术语型问题并不稳。

特别是这些场景：

  • 版本号
  • 接口名
  • 错误码
  • SKU
  • 人名、地名、法条编号

如果没有关键词或混合检索，经常会漏召回。

5.4 top-k 拿得过多或过少

top-k 太小，容易漏关键依据。

top-k 太大，又会导致：

  • 噪声增加
  • token 浪费
  • 模型注意力分散

这不是固定参数能一劳永逸解决的问题，通常要结合数据集调优。

5.5 没有做 metadata 过滤

如果知识库跨多个部门、产品线、地区、租户，缺少 metadata filter 会让检索结果非常脏。

例如本来应该查：

  • 某个业务线
  • 某个语言版本
  • 某个时间区间

结果系统把不相关范围的文档也拿进来了。

5.6 把“答案质量问题”误判成“检索问题”

有时候检索结果其实是对的，但生成阶段 prompt 不好，导致：

  • 回答不够保守
  • 没按引用回答
  • 总结过度
  • 没区分事实和推断

所以 RAG 调优一定要拆开看：

  • 是没召回
  • 是排序不对
  • 还是生成没用好证据

5.7 缺少评估体系

很多团队调 RAG 靠“手感”。

今天换个 embedding，明天改个 prompt，最后却说不清到底哪里变好了。

如果没有最基本的评估集和指标，优化会非常低效。

5.8 忽略权限与安全

企业 RAG 很容易踩这个坑。

例如：

  • 检索结果越权
  • 敏感字段被带进上下文
  • 缓存污染不同用户结果
  • 日志里泄露原文

所以生产级 RAG 不只是算法问题，还是治理问题。

六、RAG 的常见技术栈与实现路径

如果从工程实现看，常见链路大概是这样：

6.1 数据处理层

  • 文档解析：OCR、PDF parser、HTML parser
  • 清洗与标准化：去噪、结构抽取、元数据补充
  • 切分：固定窗口、语义切分、结构化切分

6.2 索引层

  • 稠密向量库：Milvus、FAISS、pgvector、Weaviate、Qdrant
  • 稀疏检索：Elasticsearch、OpenSearch、Lucene、BM25
  • 混合检索：向量 + 倒排

6.3 检索增强层

  • query rewrite
  • multi-query retrieval
  • rerank
  • metadata filtering
  • parent-child retrieval
  • summary index

6.4 生成层

  • LLM answer synthesis
  • citation grounding
  • refusal when insufficient evidence

6.5 编排层

  • LangChain
  • LlamaIndex
  • Haystack
  • 自研 workflow
  • agent runtime

这里要注意：

框架不是 RAG 的本质，数据、检索和评估才是 RAG 的核心。

七、除了搭建，还要怎么评估和优化

这是很多文章会漏掉，但实际工作里非常重要的一部分。

7.1 至少拆成两层评估

第一层是检索评估。

常见关注点：

  • 是否召回了正确文档
  • 正确 chunk 排名是否靠前
  • 有没有明显漏召回

第二层是答案评估。

常见关注点：

  • 是否基于证据回答
  • 是否答到了问题
  • 是否有幻觉
  • 是否引用正确

7.2 常见评估指标

检索侧常见指标：

  • Recall@k
  • Precision@k
  • MRR
  • NDCG

生成侧常见指标：

  • faithfulness
  • answer relevancy
  • groundedness
  • citation accuracy

当然，很多业务场景最终还是要落回人工标注与业务指标。

7.3 优化时的正确顺序

如果效果不好，一个更稳妥的排查顺序通常是：

  1. 先看数据源是否干净、完整、最新
  2. 再看 chunk 是否合理
  3. 再看召回是否漏
  4. 再看 rerank 是否有效
  5. 最后才看 prompt 和模型

因为很多问题，根本不是“模型不够强”，而是前面的知识供给链路出了问题。

八、RAG 与微调、长上下文、Agent 的关系

这也是高频讨论点。

8.1 RAG 和微调的区别

可以这样粗略区分：

  • RAG 主要解决“把外部知识提供给模型”
  • 微调 主要解决“改变模型行为模式或任务适配”

例如：

  • 产品手册更新，优先考虑 RAG
  • 模型语气、格式、任务风格不稳定，可能考虑微调

很多场景并不是二选一，而是组合使用。

8.2 RAG 和长上下文的关系

长上下文让模型一次能看更多资料，但它没有解决：

  • 哪些内容最该看
  • 怎么从海量文档中选
  • 如何控制成本

所以长上下文更多是在改变 RAG 的实现方式，而不是让 RAG 消失。

8.3 RAG 和 Agent 的关系

RAG 关注的是知识获取与注入。

Agent 关注的是：

  • 规划
  • 决策
  • 多步执行
  • 工具调用

一个 agent 完全可以把 RAG 当成自己的一个能力模块。

例如：

  • 先检索知识库
  • 再调用数据库
  • 再结合工具结果做决策

九、高频面试题

下面这些问题，在面试和技术交流里都很常见。

9.1 什么是 RAG？它解决什么问题？

回答重点：

  • 先检索、再生成
  • 解决知识时效性、私有知识、幻觉和知识注入问题
  • 本质是知识增强架构

9.2 RAG 的完整流程是什么？

回答时最好按链路说完整：

数据接入、解析、切分、向量化、索引构建、查询理解、召回、重排、上下文组装、生成、评估反馈。

9.3 为什么要切 chunk？chunk 太大或太小有什么问题？

回答重点：

  • 检索对象是 chunk，不是整篇文档
  • 太大噪声多、成本高
  • 太小语义不完整、上下文丢失
  • chunk 粒度直接影响召回和生成

9.4 向量检索和 BM25 的区别是什么？

回答重点：

  • 向量检索偏语义相似
  • BM25 偏关键词匹配
  • 术语、编号、错误码这类内容 BM25 往往更稳
  • 线上常见做法是 hybrid search

9.5 为什么需要 rerank？

回答重点：

  • 召回重覆盖，重排重精度
  • 候选集里会混入“差不多相关”的内容
  • rerank 可以提升 top 几条结果的质量

9.6 RAG 为什么仍然会幻觉？

回答重点：

  • 检索不到
  • 检索到了但排序靠后
  • 模型误读证据
  • 多段资料拼接错误
  • prompt 没限制好

9.7 RAG 和微调怎么选？

回答重点：

  • 知识更新、私有知识，优先 RAG
  • 行为模式、格式风格、专任务适配，优先微调
  • 二者经常组合

9.8 怎么评估 RAG 效果？

回答重点：

  • 拆成检索评估和生成评估
  • 看 Recall@k、MRR、NDCG
  • 看 groundedness、faithfulness、citation accuracy
  • 最终结合人工标注和业务指标

9.9 RAG 最容易踩哪些坑？

回答重点：

  • 数据脏
  • chunk 不合理
  • 只做向量检索
  • 缺少 metadata filter
  • 没有评估集
  • 权限控制缺失

9.10 生产级 RAG 和 demo 最大区别是什么？

回答重点：

  • demo 重“跑通”
  • 生产级重“稳定、可评估、可治理、可更新、可追踪”

十、一个更实用的理解框架

如果你想在工作里更稳地理解 RAG，可以记住下面这个框架：

RAG 不只是“检索 + 生成”，而是一整套“知识进入系统、被索引、被召回、被组织、被模型使用、再被评估和优化”的工程链路。

所以真正决定效果的，通常不只是模型，而是这几层是否都做对了：

  • 数据质量
  • chunk 设计
  • 检索策略
  • 排序机制
  • 上下文组织
  • 生成约束
  • 评估闭环

小结

RAG 的本质，是让模型从“只依赖参数记忆回答”，变成“基于外部知识进行回答”。

它最核心的价值，不是让系统看起来更聪明，而是让回答：

  • 更可追溯
  • 更适合私有知识
  • 更适合动态知识
  • 更容易持续优化

如果把一句话再说得更工程化一点：

RAG 是大模型应用里最重要的知识供给系统之一，而不是一个单独的检索技巧。
