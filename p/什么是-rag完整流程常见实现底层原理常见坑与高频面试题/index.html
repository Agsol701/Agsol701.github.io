什么是 RAG：完整流程、常见实现、底层原理、常见坑与高频面试题

May 04, 2026

写在前面

这两年 RAG 基本已经成了大模型落地里出现频率最高的词之一。

很多人会把它简单理解成：

  • 向量数据库
  • 知识库问答
  • embedding 检索
  • 给模型外挂记忆

这些理解都不算完全错，但都不够完整。

如果先用一句话做一个总定义：

RAG，即 Retrieval-Augmented Generation，是一种“先检索外部知识，再基于检索结果生成答案”的系统方法。

这里最关键的是两点：

  • RAG 不是单纯的检索系统
  • RAG 也不是单纯的生成系统

它本质上是一套把“知识供给”与“语言生成”组合起来的应用架构。

所以这篇文章不只回答“RAG 是什么”，还会系统整理这些问题：

  1. 一个完整的 RAG 到底分几步
  2. 常见实现方式有哪些
  3. 它底层为什么能工作
  4. 工程上最容易踩哪些坑
  5. 面试里最常被问什么
  6. 除了搭建，还应该怎么评估和优化

一、RAG 到底是什么

1.1 最直白的理解

可以先把 RAG 理解成：

让模型在回答前，先去知识库里“查资料”。

例如用户问：

“公司的报销流程是什么？”

如果只靠模型参数记忆，它很可能不知道你们公司的内部制度。

但如果系统先去：

  • 内部文档库
  • Wiki
  • 产品手册
  • 数据库说明

里找出最相关的资料，再把这些资料和问题一起交给大模型，那么模型就可以基于这些真实内容来回答。

这就是 RAG 的核心思路。

1.2 它解决的核心问题是什么

RAG 主要解决的是：

模型知识不够新、不够专、不够私有时，如何把外部知识动态提供给模型。

这背后通常对应四类痛点。

第一类：模型不知道私有知识

比如：

  • 企业内部制度
  • 项目源码
  • 私有 API 文档
  • 合同、报告、会议纪要

这些内容通常不会出现在模型训练数据里。

第二类：模型知识过期

即使模型很强，它参数里的知识也不是实时更新的。

所以：

  • 最新政策
  • 新版本文档
  • 刚上线的产品能力
  • 当天生成的业务数据

都更适合通过检索动态注入。

第三类：模型容易幻觉

如果没有可靠依据，模型很可能“看起来像在回答，实际上是在猜”。

RAG 的一个重要价值，就是尽量让回答建立在可追溯资料之上。

第四类：纯微调成本高且不灵活

如果每次知识更新都靠微调：

  • 成本高
  • 反馈慢
  • 数据准备重
  • 难以处理高频变更

而 RAG 更适合处理“知识频繁变化”的场景。

二、RAG 的完整流程

很多人以为 RAG 只有“切块 + 向量库 + 检索 + 生成”。

这其实只说到了主干，没有把工程链路讲完整。

一个相对完整的 RAG，通常可以拆成下面几个阶段。

2.1 数据接入

先把知识源接进系统。

常见来源包括：

  • PDF
  • Word
  • Markdown
  • 网页
  • FAQ
  • 数据库
  • 代码仓库
  • 工单与聊天记录

这一阶段的关键，不是“存进去”，而是先解决：

  • 数据从哪里来
  • 更新频率如何
  • 权限怎么处理
  • 原始格式怎么统一

2.2 文档解析

原始文档往往不能直接拿去检索。

例如 PDF 里可能有：

  • 页眉页脚
  • 表格
  • 图片
  • 双栏排版
  • OCR 错误

所以通常要先做解析，把它转成更适合处理的文本结构。

这一步常见操作包括：

  • 提取正文
  • 去噪
  • 保留标题层级
  • 识别表格和代码块
  • 保留文档元数据

2.3 文本切分

解析后的长文档，通常还要切成多个 chunk。

这是因为：

  • embedding 模型有长度限制
  • 检索粒度不能太粗
  • LLM 上下文窗口有限

切分时常见策略包括：

  • 固定长度切分
  • 滑动窗口切分
  • 按标题层级切分
  • 按段落语义切分
  • 针对代码、表格、问答做定制切分

chunk 设计直接影响后面的召回质量，是 RAG 里最关键的环节之一。

这里值得展开讲一下，因为很多 RAG 效果问题，本质都不是“大模型不会答”，而是“知识在进入检索系统之前就已经被切坏了”。

2.3.1 chunk 到底是什么

chunk 不是简单的一段文本，而是 RAG 系统里的最小检索单元。

也就是说，用户问题进来以后，系统不是直接在整篇文档里找答案，而是在一个个 chunk 里找最相关的片段。

所以 chunk 同时承担三个角色：

  • 检索单元：向量库或倒排索引真正召回的是它
  • 证据单元：LLM 最终看到的上下文通常也是它
  • 评估单元：我们判断有没有召回正确依据时，也经常以它为单位

这意味着：

chunk 不是越大越好，也不是越小越好，而是要让“一个 chunk 刚好能表达一个相对完整的问题答案或知识点”。

2.3.2 chunk 太大有什么问题

如果 chunk 太大，例如一口气切 2000 到 4000 个中文字符，常见问题是：

  • 一个 chunk 里混入多个主题
  • embedding 表达会被多个语义方向稀释
  • 检索命中后上下文 token 成本很高
  • 召回结果看起来相关，但真正有用的句子只占很小一部分
  • LLM 容易被同一个 chunk 里的无关信息干扰

例如一篇产品文档里同时有：

  • 登录
  • 权限
  • 计费
  • API 调用限制

如果它们被放进同一个大 chunk，当用户问“API 调用限制是多少”时，这个 chunk 虽然可能被召回，但里面大量登录、权限、计费内容都会变成噪声。

2.3.3 chunk 太小有什么问题

如果 chunk 太小，例如只按 100 到 200 个字硬切，也会有另一类问题：

  • 标题和正文分离
  • 定义和解释分离
  • 条件和结论分离
  • 表格行之间失去关系
  • 问答对被拆散
  • 代码函数被截断

例如原文是：

1
2
3
4

退款规则：
1. 订单支付后 7 天内可以申请退款。
2. 虚拟商品一经发货不支持退款。
3. 企业合同订单以合同条款为准。

如果被切成几个过小的片段，系统可能只召回“7 天内可以申请退款”，但漏掉“虚拟商品不支持退款”和“企业合同以合同为准”。最终回答就会不完整，甚至误导用户。

2.3.4 常见切分策略怎么选

可以把切分策略分成几类。

固定长度切分

这是最简单的方式，例如每 500 个 token 切一段。

优点是：

  • 实现简单
  • 速度快
  • 对任意文本都能跑

缺点是：

  • 不理解文档结构
  • 容易切断段落、表格、代码
  • 对复杂文档效果不稳定

它适合做 demo 或处理结构很差、无法可靠解析的原始文本，但生产系统里通常不建议只靠它。

带 overlap 的滑动窗口切分

滑动窗口是在固定长度基础上增加重叠区。

例如：

1
2

chunk_size = 500 tokens
overlap = 80 tokens

这样第一个 chunk 的末尾 80 个 token，会出现在第二个 chunk 的开头。

它的好处是减少“关键信息刚好被切在边界上”的问题。

但 overlap 也不是越大越好：

  • overlap 太小，边界问题仍然明显
  • overlap 太大，索引膨胀，重复召回增加
  • 重复内容过多，会浪费上下文窗口

一般可以把 overlap 理解成一种“边界保险”，而不是主要切分方法。

按结构切分

更推荐的方式，是优先利用文档结构。

例如 Markdown、HTML、Word、PDF 解析后，通常可以拿到：

  • 一级标题
  • 二级标题
  • 段落
  • 列表
  • 表格
  • 代码块

这时可以按结构切分：

1

标题路径 + 当前小节正文 = 一个 chunk

例如：

1
2
3

文档：支付系统说明
章节路径：退款规则 > 虚拟商品
正文：虚拟商品一经发货不支持退款，除非商品未完成交付。

这样做的好处是：

  • chunk 语义更完整
  • 标题能增强检索信号
  • 召回结果更容易解释
  • 引用来源更清晰

语义切分

语义切分不是按固定长度，而是根据语义边界切。

例如把同一主题的几段放在一起，主题变化时再切开。

这种方式适合：

  • 长报告
  • 研究文章
  • 会议纪要
  • 客服知识库

但它也有成本：

  • 实现复杂
  • 需要额外模型或规则
  • 不同领域的边界判断不一样

所以工程上常见做法不是纯语义切分，而是：

先按文档结构粗切，再在过长的小节里做语义或长度二次切分。

2.3.5 不同内容类型要用不同切分方式

真实知识库里，最怕“一刀切”。

不同内容应该有不同策略。

FAQ

FAQ 最好保持“一问一答”为一个 chunk。

不要把问题和答案拆开，也不要把多个无关 FAQ 混在一起。

较好的结构是：

1
2
3

问题：如何申请退款？
答案：用户可以在订单支付后 7 天内申请退款，虚拟商品除外。
标签：售后、退款

表格

表格不能只按纯文本硬切。

因为表格的含义通常依赖表头。

例如：

套餐 月费 API 调用次数
Basic 99 10 万
Pro 299 100 万

如果只召回一行：

1

Pro 299 100 万

模型未必知道每一列代表什么。

更好的 chunk 应该保留表头：

1
2

套餐价格表：
套餐=Pro，月费=299，API 调用次数=100 万。

代码

代码知识库要避免把函数、类、注释、调用关系切散。

常见方式是按：

  • 文件
  • 类
  • 函数
  • 方法
  • docstring

来切分。

同时保留元数据：

  • repo
  • branch
  • file_path
  • symbol_name
  • language

否则用户问 OrderService.create() 的行为时，只召回半截函数体，效果会很差。

法律、制度、合同

这类文档最重要的是条款编号、适用条件和例外情况。

切分时要尽量保留：

  • 条款编号
  • 上下位条款关系
  • 生效时间
  • 适用范围
  • 例外说明

否则模型很容易只看到结论，看不到限制条件。

2.3.6 一个实用的 chunk 设计原则

可以用下面几个问题检查 chunk 是否合理：

  1. 单独看这个 chunk，是否能理解它在讲什么？
  2. 它是否包含回答一个具体问题所需的最小上下文？
  3. 标题、正文、表头、代码注释有没有被拆散？
  4. 里面是否混入太多不相关主题？
  5. 如果它被召回给模型，模型能不能据此回答而不用猜？

工程上可以先从一个保守配置开始：

  • 普通中文文档：300 到 800 中文字左右
  • 技术文档：按标题层级切分，过长小节再二次切
  • FAQ：一问一答一个 chunk
  • 表格：表头和行内容一起结构化
  • 代码：按函数、类、文件结构切
  • overlap：一般 10% 到 20% 起步，再根据评估调

这些不是固定标准，而是调参起点。

真正的判断标准只有一个：

看它能不能稳定召回“足够完整、足够少噪声、可以支撑回答”的证据。

2.4 向量化与索引构建

切好块之后，通常要把每个 chunk 转成向量。

这一步就是 embedding。

向量化之后，系统会把这些内容连同元数据存进索引中，常见形式包括：

  • 向量索引
  • 倒排索引
  • 混合索引
  • 图结构索引

这里的元数据通常包括：

  • 文档标题
  • 来源 URL
  • 时间
  • 权限标签
  • 部门
  • 产品线
  • 章节路径

2.5 查询理解

用户问题并不总是适合直接拿去检索。

例如用户问：

“这个东西最近权限改了吗？”

这里的“这个东西”如果没有上下文，检索很难命中。

所以很多系统在检索前会先做查询理解，例如：

  • query rewrite
  • query expansion
  • 指代消解
  • 多轮上下文拼接
  • 把模糊问题改写成可检索问题

2.6 召回

这一步是从索引中找出最相关的候选内容。

常见召回方式包括：

  • 向量相似度召回
  • BM25 关键词召回
  • 混合召回
  • 多路召回

召回阶段重点关注的是：

  • 尽量别漏掉真正相关内容
  • 给后续排序保留足够候选集

也就是说，这一阶段更偏“高召回率”。

召回是 RAG 里第二个非常关键的环节。切分决定“知识以什么颗粒度进入系统”，召回决定“用户问题来了以后，系统能不能把正确证据找出来”。

2.6.1 召回不是排序，召回的第一目标是别漏

很多人会把召回和排序混在一起。

但在检索系统里，它们的职责不同：

  • 召回：从海量知识里找出一批可能相关的候选
  • 排序：在候选里把最相关的放到前面

召回阶段最怕的是：

正确答案根本没有进入候选集。

如果正确 chunk 没有被召回，后面的 rerank、prompt、模型再强也很难补救。

所以召回阶段一般更关注：

  • Recall@k
  • 候选覆盖率
  • 多路召回互补
  • 是否漏掉精确术语
  • 是否被权限、时间、产品线等过滤条件误伤

2.6.2 向量召回适合什么

向量召回擅长处理“意思相近但字面不同”的问题。

例如：

1
2

用户问：忘记密码怎么办？
文档写：用户可通过账号安全页重置登录凭证。

这两个句子字面重合不多，但语义接近，embedding 检索可能命中。

向量召回适合：

  • 自然语言问答
  • 概念解释
  • 同义表达
  • 模糊描述
  • 用户不知道准确术语的场景

但它不擅长：

  • 错误码
  • 版本号
  • 文件路径
  • API 名称
  • 订单号
  • 法条编号
  • 很短的关键词查询

因为这些内容的核心不是“语义相近”，而是“字面必须精确”。

2.6.3 BM25 关键词召回适合什么

BM25 代表的是传统信息检索里的稀疏检索思路。

它更关注：

  • 词有没有出现
  • 出现了几次
  • 这个词在语料里是否稀有
  • 文档长度是否影响匹配强度

BM25 对下面这些场景非常有效：

  • ERR_CONN_RESET
  • OrderService.create
  • v1.8.2
  • GB/T 35273
  • user_id
  • 401 Unauthorized

这些查询如果只走向量检索，结果可能很飘。

所以一个经验是：

只要你的知识库里有大量专有名词、编号、代码、错误码、商品型号，就不要只做向量召回。

2.6.4 混合召回为什么常见

混合召回就是把多种召回方式结合起来。

最常见的是：

1
2
3
4
5
6

向量召回 top 50
BM25 召回 top 50
metadata 过滤
结果合并去重
rerank 重排
取最终 top 5 到 top 10

它的价值在于互补：

  • 向量召回补语义
  • BM25 补精确匹配
  • metadata filter 补范围约束
  • rerank 补精细相关性判断

例如用户问：

1

v2.3.17 版本的导出接口为什么返回 403？

这里同时包含：

  • 版本号：适合关键词
  • 接口问题：适合关键词和结构化 metadata
  • 403 原因：适合语义检索

如果只走一路，很容易漏。

2.6.5 多路召回有哪些常见路径

生产系统里经常不止两路召回。

常见路径包括：

原始 query 召回

直接用用户问题检索。

这是基础路径，适合问题表达清楚的情况。

改写 query 召回

先把用户问题改写成更适合检索的形式。

例如：

1
2

原问题：这个接口怎么老是没权限？
改写后：导出接口返回 403 Forbidden 的原因和权限配置说明

它适合口语化、上下文依赖强的问题。

多 query 召回

一个问题生成多个检索 query。

例如用户问：

1

新员工怎么开通 VPN？

可以扩展成：

1
2
3

新员工 VPN 开通流程
VPN 权限申请
远程办公账号配置

这样能提高覆盖率，但也会增加噪声和成本。

metadata 召回或过滤

有些问题必须先确定范围。

例如：

  • 只查 2026 年之后的制度
  • 只查中国区文档
  • 只查某个产品线
  • 只查当前用户有权限看的内容

这类条件不应该完全交给向量相似度，而应该通过 metadata filter 明确控制。

Parent-child 召回

这是一种很实用的策略。

索引时保存两层内容：

  • child chunk：较小，用于精准检索
  • parent chunk：较大，用于提供完整上下文

检索时先命中小 chunk，再把它所属的父级片段带给模型。

它解决的问题是：

  • 小 chunk 检索准
  • 大 chunk 上下文完整

这对长文档、制度文档、技术文档都很有用。

Summary index 召回

对于特别长的文档，可以先为章节或整篇文档生成摘要索引。

检索时先命中摘要，判断可能相关的文档或章节，再进入原文 chunk 做二次检索。

它适合：

  • 文档数量巨大
  • 单篇文档很长
  • 用户问题比较宏观

例如：

1

问：我们系统的数据权限模型是怎么设计的？

这种问题可能需要先找到“权限设计文档”，再进入具体章节。

2.6.6 召回参数怎么理解

召回里常见几个参数。

top-k

top-k 表示取前多少个候选。

如果 top-k 太小：

  • 召回容易漏
  • rerank 没有足够候选
  • 答案依据可能不完整

如果 top-k 太大：

  • 噪声变多
  • 成本上升
  • rerank 变慢
  • 后续上下文组装压力变大

实际系统里常见做法是：

1
2
3

召回阶段取 top 30 到 top 100
rerank 后取 top 5 到 top 10
最终进 prompt 的可能只有 3 到 8 段

具体值要靠评估集调。

score threshold

有些系统会设置相似度阈值，低于阈值的结果不返回。

它可以减少明显不相关内容，但也可能误伤。

尤其不同 embedding 模型、不同向量库、不同相似度算法下，分数分布不一样，不能照搬阈值。

更稳的方式是基于评估集观察：

  • 正确召回通常分数在哪个范围
  • 错误召回通常分数在哪个范围
  • 两者是否有明显分界

metadata filter

metadata filter 的作用是先限定搜索范围。

例如：

1
2
3
4

product = "billing"
region = "cn"
doc_status = "active"
permission_group in current_user.groups

这类过滤通常应该发生在召回阶段，而不是等 LLM 自己判断。

因为一旦越权内容进入 prompt，就已经产生安全风险。

2.6.7 召回失败怎么排查

当用户说“RAG 没答对”时，不要一上来就改 prompt。

可以按下面顺序排查召回：

  1. 正确答案是否存在于原始知识库？
  2. 文档解析后，正确内容是否还在？
  3. chunk 是否把正确内容切完整？
  4. query 是否表达了正确意图？
  5. 向量召回 top-k 里有没有正确 chunk？
  6. BM25 召回 top-k 里有没有正确 chunk？
  7. metadata filter 是否把正确文档过滤掉？
  8. rerank 是否把正确 chunk 排低了？
  9. context packing 是否把正确 chunk 丢掉了？

这条链路能帮助你定位问题属于哪一层。

一个很重要的判断是：

如果正确 chunk 没进入召回候选，这是召回问题；如果进入候选但没进最终上下文，可能是重排或上下文组装问题；如果进入上下文但回答仍然错，才重点看 prompt 和生成模型。

2.7 重排

召回出来的结果不一定顺序最好，所以通常还会有 rerank。

重排的作用是：

在候选集合里，把真正最相关的内容排到前面。

常见方式包括：

  • cross-encoder rerank
  • 基于大模型打分
  • 结合 metadata 规则重排
  • 基于时间、权限、来源可信度重排

很多线上系统的实际效果提升，往往就来自“召回后再排一次”。

2.8 上下文组装

不是把召回结果一股脑塞给模型就行。

还要解决：

  • 选哪几段
  • 按什么顺序放
  • 是否去重
  • 是否合并相邻片段
  • 是否附带来源信息

这一阶段本质上是在做：

context packing

也就是在有限 token 预算里，把最有价值的信息装进去。

2.9 生成答案

把用户问题和检索结果一起交给大模型，让模型生成最终回答。

这一阶段常见设计包括：

  • 严格基于资料回答
  • 回答时附上引用
  • 资料不足时明确说不知道
  • 区分“原文摘录”和“模型总结”

2.10 后处理与反馈闭环

一个成熟系统通常还有最后几步：

  • 答案引用对齐
  • 敏感信息过滤
  • 结果缓存
  • 用户反馈收集
  • 失败样本回流

这部分决定系统能不能持续优化，而不是只跑通一次 demo。

三、RAG 的常见实现方式

RAG 并不是只有一种形态。

3.1 Naive RAG

最基础的做法是：

  1. 文档切块
  2. embedding
  3. 向量检索 top-k
  4. 把结果塞给 LLM

这是很多教程里的起点。

优点是简单、容易落地。

缺点也很明显：

  • 对 query 表达很敏感
  • 容易召回不准
  • chunk 粗糙时效果差
  • 缺少 rerank 和多路检索时上限较低

3.2 Advanced RAG

这是最常见的工程升级形态。

典型增强点包括：

  • 更合理的 chunk 策略
  • query rewrite
  • hybrid search
  • rerank
  • metadata filter
  • 引用输出
  • 缓存和评估

很多企业里的“生产级 RAG”，本质上都属于这一类。

3.3 Hybrid RAG

也就是混合检索。

它通常把：

  • 稠密检索
  • 稀疏检索

结合起来。

原因是：

  • 向量检索擅长语义相近
  • 关键词检索擅长精确术语、缩写、版本号、错误码

例如：

  • API 名称
  • 订单号
  • 类名函数名
  • 法条编号

这类内容，单靠向量检索往往不稳定。

3.4 Graph RAG

当知识之间存在明显关系结构时，会有人引入图。

例如：

  • 实体关系
  • 组织架构
  • 系统依赖关系
  • 代码调用关系

它的思路不是只检索文本相似度，而是利用实体和关系做扩展检索与推理。

适合：

  • 多跳问答
  • 复杂实体关系问题
  • 依赖路径分析

3.5 Agentic RAG

在更复杂的系统里，检索不一定只发生一次。

模型可能会：

  1. 先理解问题
  2. 决定检索哪类资料
  3. 看第一次结果够不够
  4. 不够就继续改写 query 或继续查
  5. 最后再生成答案

这类做法通常会和 agent、tool use、workflow 编排结合起来。

它的特点是更灵活，但系统复杂度也更高。

3.6 Long-Context RAG

随着上下文窗口变大，一些团队会减少复杂检索层，更多依赖“大上下文直接读”。

但这不等于 RAG 失效。

更准确地说，是 RAG 的重点会从“强压缩检索”转向：

  • 更好的筛选
  • 更好的排序
  • 更好的上下文组织

长上下文不是 RAG 的替代品，而是改变了 RAG 的工程权衡。

四、RAG 的底层原理

这部分是面试里最容易被问到，也最容易回答空泛的地方。

4.1 embedding 为什么能检索相似内容

embedding 的核心作用，是把文本映射成高维向量。

在这个向量空间里，语义相近的文本，通常距离更近。

例如：

  • “怎么重置密码”
  • “忘记密码怎么办”

虽然字面不完全一样，但 embedding 后可能距离较近。

检索时，系统会把用户 query 也转成向量，然后在向量库里找“距离最近”的若干个 chunk。

常见相似度计算方式包括：

  • cosine similarity
  • dot product
  • euclidean distance

4.2 为什么还需要关键词检索

因为“语义相近”不等于“字面精确”。

例如：

  • ERR_CONN_RESET
  • v2.3.17
  • OrderService.create()

这类符号、编号、专有名词，BM25 或倒排索引往往更稳定。

所以真实系统里，通常不会只依赖单一路径。

4.3 chunk 为什么会影响效果

因为检索命中的对象不是整篇文档，而是 chunk。

如果 chunk 太大：

  • 噪声多
  • 主题混杂
  • 命中后塞进上下文的成本高

如果 chunk 太小：

  • 语义不完整
  • 容易丢上下文
  • 答案依据被切散

所以 RAG 很多问题，不是模型不行，而是 chunk 粒度设计得不对。

4.4 rerank 为什么有效

召回阶段通常追求“别漏”，所以候选结果里常常混入一些“差不多相关”的内容。

而 rerank 更像第二道筛选：

它不要求扫全库，只要求在较小候选集里做更精细的相关性判断。

因此它通常能显著改善 top 几条结果的质量。

4.5 RAG 为什么能降低幻觉

因为模型不再只靠参数记忆，而是能参考外部证据。

但要注意：

RAG 只能降低幻觉，不能彻底消灭幻觉。

因为即使检索到了正确内容，也仍然可能出现：

  • 模型误读资料
  • 引用错段落
  • 过度总结
  • 把多个来源拼错

所以 RAG 本质上是“提升证据供给质量”，不是“自动保证真相”。

五、RAG 中最容易遇到的坑

真正做 RAG，问题通常不在“能不能跑起来”，而在“为什么效果总是不稳定”。

5.1 只关注模型，不关注数据质量

这是最常见的问题。

如果源文档本身：

  • 过期
  • 冲突
  • OCR 错误严重
  • 标题层级混乱

那后面检索和生成做得再漂亮，结果也不会稳定。

5.2 chunk 切分太机械

很多 demo 会直接按固定字数切。

这在真实场景里经常导致：

  • 表格被截断
  • 问答对被拆开
  • 标题和正文分离
  • 代码片段不完整

结果就是看起来检索到了，实际上证据不完整。

5.3 只做向量检索

纯向量检索对很多术语型问题并不稳。

特别是这些场景：

  • 版本号
  • 接口名
  • 错误码
  • SKU
  • 人名、地名、法条编号

如果没有关键词或混合检索，经常会漏召回。

5.4 top-k 拿得过多或过少

top-k 太小，容易漏关键依据。

top-k 太大，又会导致：

  • 噪声增加
  • token 浪费
  • 模型注意力分散

这不是固定参数能一劳永逸解决的问题，通常要结合数据集调优。

5.5 没有做 metadata 过滤

如果知识库跨多个部门、产品线、地区、租户，缺少 metadata filter 会让检索结果非常脏。

例如本来应该查：

  • 某个业务线
  • 某个语言版本
  • 某个时间区间

结果系统把不相关范围的文档也拿进来了。

5.6 把“答案质量问题”误判成“检索问题”

有时候检索结果其实是对的，但生成阶段 prompt 不好，导致：

  • 回答不够保守
  • 没按引用回答
  • 总结过度
  • 没区分事实和推断

所以 RAG 调优一定要拆开看：

  • 是没召回
  • 是排序不对
  • 还是生成没用好证据

5.7 缺少评估体系

很多团队调 RAG 靠“手感”。

今天换个 embedding，明天改个 prompt，最后却说不清到底哪里变好了。

如果没有最基本的评估集和指标，优化会非常低效。

5.8 忽略权限与安全

企业 RAG 很容易踩这个坑。

例如：

  • 检索结果越权
  • 敏感字段被带进上下文
  • 缓存污染不同用户结果
  • 日志里泄露原文

所以生产级 RAG 不只是算法问题，还是治理问题。

六、RAG 的常见技术栈与实现路径

如果从工程实现看，常见链路大概是这样：

6.1 数据处理层

  • 文档解析：OCR、PDF parser、HTML parser
  • 清洗与标准化：去噪、结构抽取、元数据补充
  • 切分：固定窗口、语义切分、结构化切分

6.2 索引层

  • 稠密向量库：Milvus、FAISS、pgvector、Weaviate、Qdrant
  • 稀疏检索：Elasticsearch、OpenSearch、Lucene、BM25
  • 混合检索：向量 + 倒排

6.3 检索增强层

  • query rewrite
  • multi-query retrieval
  • rerank
  • metadata filtering
  • parent-child retrieval
  • summary index

6.4 生成层

  • LLM answer synthesis
  • citation grounding
  • refusal when insufficient evidence

6.5 编排层

  • LangChain
  • LlamaIndex
  • Haystack
  • 自研 workflow
  • agent runtime

这里要注意：

框架不是 RAG 的本质，数据、检索和评估才是 RAG 的核心。

七、除了搭建，还要怎么评估和优化

这是很多文章会漏掉，但实际工作里非常重要的一部分。

很多 RAG 项目一开始能跑通，但后面会进入一种很低效的状态：

  • 用户说效果不好
  • 工程师改 chunk
  • 再换 embedding
  • 再改 prompt
  • 再调 top-k
  • 最后不知道到底哪个改动有效

这就是缺少评估体系的典型表现。

评估的目的不是为了做漂亮报表，而是为了回答三个问题：

  1. 系统现在到底差在哪里？
  2. 某次改动到底有没有变好？
  3. 线上失败样本应该回流到哪一层优化？

7.1 至少拆成四层评估

最简单的说法是“检索评估 + 答案评估”，但真实排查时，最好拆得更细一点。

第一层：数据评估

先看知识库本身有没有问题。

常见关注点：

  • 原始文档是否完整
  • 文档是否过期
  • 是否存在多版本冲突
  • PDF、OCR、表格解析是否正确
  • 标题层级和元数据是否保留
  • 权限标签是否准确

如果数据源错了，后面的检索和生成只会更稳定地犯错。

第二层：切分评估

切分评估关注的是：

正确知识有没有以合适的颗粒度进入索引。

常见检查点：

  • 一个 chunk 是否语义完整
  • 是否包含标题路径
  • 表格是否保留表头
  • FAQ 是否保持问答一体
  • 代码是否保留函数或类边界
  • chunk 是否混入太多主题
  • overlap 是否造成大量重复

这一层通常要抽样人工看，因为 chunk 好坏很难只靠一个指标判断。

第三层：检索评估

常见关注点：

  • 是否召回了正确文档
  • 正确 chunk 排名是否靠前
  • 有没有明显漏召回
  • 是否误召回了大量相似但不相关内容
  • metadata filter 是否正确生效
  • 不同召回路径是否互补

检索评估的核心是：

在不看 LLM 生成的情况下，只看系统有没有把正确证据找出来。

第四层：答案评估

常见关注点：

  • 是否基于证据回答
  • 是否答到了问题
  • 是否有幻觉
  • 是否引用正确
  • 是否在证据不足时拒答
  • 是否把条件、例外、时间范围说清楚
  • 是否把多个来源错误拼接

这层才是最终用户感知到的效果。

但要注意：答案错不代表一定是模型错。它可能是数据错、切分错、召回错、排序错，也可能才是生成错。

7.2 评估集怎么构建

没有评估集，就很难系统优化 RAG。

一个最小可用的评估集，通常至少包含：

  • 用户问题
  • 标准答案或答案要点
  • 应该命中的文档或 chunk
  • 问题类型
  • 权限或业务范围
  • 难度标签

可以设计成这样：

字段 示例
question Pro 套餐每月 API 调用上限是多少？
expected_answer Pro 套餐每月 API 调用上限是 100 万次
golden_chunk_id pricing_doc_chunk_003
category 产品价格
query_type 精确事实
metadata_scope product=billing, region=cn

7.2.1 问题从哪里来

评估问题最好不要只靠工程师自己编。

更好的来源包括：

  • 真实用户搜索日志
  • 客服问答记录
  • 工单系统
  • 产品 FAQ
  • 面试或验收问题
  • 线上失败样本
  • 高价值业务场景手工补充

其中最有价值的是线上失败样本。

因为它代表的不是“理论上可能会问什么”，而是“用户真的问了，并且系统真的没答好”。

7.2.2 评估集要覆盖哪些问题类型

RAG 的问题类型不一样，优化方向也不一样。

建议至少覆盖这些类型：

  • 精确事实：某个字段、金额、日期、配置值是什么
  • 术语解释：某个概念是什么意思
  • 流程类：某件事应该怎么操作
  • 条件判断：什么情况下可以或不可以
  • 对比类：A 和 B 有什么区别
  • 多跳问题：需要跨多个片段组合回答
  • 时效问题：只允许使用最新版本或指定时间范围
  • 权限问题：不同用户能看到的答案不同
  • 无答案问题：知识库里没有，系统应该拒答

尤其要放入“无答案问题”。

否则系统可能只学会回答，不学会克制。

7.3 常见评估指标怎么理解

指标不要只背名字，要理解它们分别回答什么问题。

7.3.1 检索侧指标

Recall@k

Recall@k 看的是：

正确 chunk 有没有出现在前 k 个召回结果里。

例如 Recall@10 = 0.85，意思是 85% 的问题，其正确依据能在前 10 个召回结果里找到。

这个指标非常重要，因为如果正确依据没进候选，后面基本没法补救。

Precision@k

Precision@k 看的是：

前 k 个结果里，有多少是真相关。

它关心结果纯度。

但在 RAG 里，召回阶段通常更重视 Recall，最终进入 prompt 前才更重视 Precision。

MRR

MRR 是 Mean Reciprocal Rank。

它关注第一个正确结果排在第几位。

例如：

  • 正确结果排第 1，得分是 1
  • 正确结果排第 2，得分是 1/2
  • 正确结果排第 5，得分是 1/5

它适合衡量：

正确答案是不是足够靠前。

NDCG

NDCG 适合有多级相关性标注的场景。

例如：

  • 3 分：完全相关
  • 2 分：部分相关
  • 1 分：弱相关
  • 0 分：不相关

它不仅看有没有相关结果，也看高相关结果是不是排在前面。

7.3.2 生成侧指标

生成侧常见指标：

  • faithfulness
  • answer relevancy
  • groundedness
  • citation accuracy

这些指标可以这样理解。

Faithfulness

看答案是否忠实于给定证据。

如果上下文里只说“企业合同订单以合同条款为准”，模型却回答“所有订单都可以 7 天无理由退款”，这就是 faithfulness 问题。

Answer relevancy

看答案是否真正回答了用户问题。

有时模型没有幻觉，但答偏了。

例如用户问“怎么关闭自动续费”，模型回答了一大段“自动续费是什么”，这就是相关性问题。

Groundedness

看答案中的关键结论是否能在证据里找到支撑。

它和 faithfulness 很接近，但更强调“每个重要说法是否有依据”。

Citation accuracy

看引用是否准确。

常见错误包括：

  • 引用了不支持该结论的 chunk
  • 引用段落和答案内容不匹配
  • 引用过期文档
  • 引用被权限过滤后不该展示的来源

引用不是装饰，它是 RAG 可追溯性的核心。

7.4 人工评估怎么做

自动指标有用，但 RAG 很难完全靠自动评估。

一个实用的人工评分表可以包括：

维度 评分说明
正确性 答案事实是否正确
完整性 是否覆盖关键条件、例外、步骤
证据一致性 是否严格基于召回内容
引用准确性 引用是否支撑答案
简洁性 是否啰嗦或夹杂无关内容
安全性 是否泄露敏感或越权信息

评分时最好把问题拆成两步：

  1. 先只看召回结果，不看模型答案
  2. 再看模型答案和引用

这样能避免把所有问题都归咎于模型。

7.5 RAG 错误怎么归因

评估的真正价值，是能把错误归因到具体链路。

可以按下面这张表排查：

现象 更可能的问题
正确内容不在知识库 数据接入问题
原文有，解析后没有 文档解析问题
解析后有，但 chunk 不完整 切分问题
chunk 存在，但召回不到 召回问题
召回到了，但排名很低 rerank 或相似度问题
排名靠前，但没放进 prompt 上下文组装问题
prompt 里有证据，但答错 生成或提示词问题
答案对，但引用错 citation 对齐问题
不该看到的内容被召回 权限过滤问题

这个归因表很实用。

因为不同问题的解决方式完全不同：

  • 数据问题靠清洗和治理
  • 切分问题靠 chunk 策略
  • 召回问题靠 embedding、BM25、hybrid、多 query
  • 排序问题靠 rerank
  • 生成问题靠 prompt、模型和上下文组织
  • 权限问题靠 metadata 和系统设计

7.6 优化时的正确顺序

如果效果不好，一个更稳妥的排查顺序通常是：

  1. 先看数据源是否干净、完整、最新
  2. 再看 chunk 是否合理
  3. 再看召回是否漏
  4. 再看 rerank 是否有效
  5. 最后才看 prompt 和模型

因为很多问题，根本不是“模型不够强”，而是前面的知识供给链路出了问题。

更具体一点，可以按这个闭环做：

第一步：建立 baseline

先固定一套最小系统：

  • 当前文档集
  • 当前 chunk 策略
  • 当前 embedding
  • 当前召回方式
  • 当前 rerank 方式
  • 当前 prompt

然后在评估集上跑出基础结果。

没有 baseline，就无法判断后续改动是提升还是退化。

第二步：一次只改一个关键变量

例如这次只改 chunk：

  • 从固定长度切分改成按标题切分
  • 其他召回、rerank、prompt 都先不动

这样才能判断变化来自哪里。

如果同时换 embedding、改 chunk、加 rerank、改 prompt，最后很难归因。

第三步：先优化召回上限

先看 Recall@k。

如果 Recall@50 都很低，说明正确证据没有进入候选集，这时优化 prompt 没意义。

应该优先看：

  • 文档是否进入索引
  • chunk 是否合理
  • query 是否需要 rewrite
  • 是否需要 BM25
  • 是否需要 hybrid search
  • metadata filter 是否过窄

第四步：再优化 top 结果质量

如果 Recall@50 不错，但最终答案仍然差，说明候选里有正确结果，但前排质量不好。

这时重点看：

  • rerank
  • score 融合
  • 去重
  • parent-child retrieval
  • 上下文排序
  • 相邻 chunk 合并

第五步：最后优化生成

当正确证据已经进入 prompt，但答案仍然不好，再优化生成。

常见方向包括：

  • 要求只基于证据回答
  • 证据不足时明确拒答
  • 要求列出引用
  • 要求区分事实和推断
  • 控制答案结构
  • 限制模型不要补充未提供信息

7.8 评估里最容易忽略的几件事

不要只看平均分

平均分会掩盖关键问题。

例如整体准确率 85%，但权限类问题准确率只有 40%，这在企业场景里可能是严重风险。

所以要按问题类型分桶看：

  • FAQ
  • 表格
  • 代码
  • 权限
  • 流程
  • 多跳
  • 无答案
  • 最新政策

不要只评估有答案的问题

RAG 系统必须知道什么时候“不知道”。

如果评估集全是有答案问题，系统可能会倾向于强行回答。

因此要专门放一批：

  • 知识库没有的问题
  • 权限不允许的问题
  • 问题太模糊的问题
  • 文档证据互相冲突的问题

不要只在开发集上调参

如果一直对同一批问题调参，很容易过拟合。

更好的做法是至少拆成：

  • dev set：用于调参
  • test set：用于最终比较
  • online set：来自线上持续回流

不要忽略成本和延迟

RAG 评估不只看答案质量。

还要看：

  • 检索耗时
  • rerank 耗时
  • LLM token 成本
  • 索引更新成本
  • p95 / p99 延迟
  • 缓存命中率

一个质量稍高但延迟翻倍的方案，不一定适合线上。

八、RAG 与微调、长上下文、Agent 的关系

这也是高频讨论点。

8.1 RAG 和微调的区别

可以这样粗略区分：

  • RAG 主要解决“把外部知识提供给模型”
  • 微调 主要解决“改变模型行为模式或任务适配”

例如：

  • 产品手册更新，优先考虑 RAG
  • 模型语气、格式、任务风格不稳定，可能考虑微调

很多场景并不是二选一，而是组合使用。

8.2 RAG 和长上下文的关系

长上下文让模型一次能看更多资料，但它没有解决：

  • 哪些内容最该看
  • 怎么从海量文档中选
  • 如何控制成本

所以长上下文更多是在改变 RAG 的实现方式，而不是让 RAG 消失。

8.3 RAG 和 Agent 的关系

RAG 关注的是知识获取与注入。

Agent 关注的是：

  • 规划
  • 决策
  • 多步执行
  • 工具调用

一个 agent 完全可以把 RAG 当成自己的一个能力模块。

例如：

  • 先检索知识库
  • 再调用数据库
  • 再结合工具结果做决策

九、高频面试题

下面这些问题，在面试和技术交流里都很常见。

9.1 什么是 RAG？它解决什么问题？

回答重点：

  • 先检索、再生成
  • 解决知识时效性、私有知识、幻觉和知识注入问题
  • 本质是知识增强架构

9.2 RAG 的完整流程是什么？

回答时最好按链路说完整：

数据接入、解析、切分、向量化、索引构建、查询理解、召回、重排、上下文组装、生成、评估反馈。

9.3 为什么要切 chunk？chunk 太大或太小有什么问题？

回答重点：

  • 检索对象是 chunk，不是整篇文档
  • 太大噪声多、成本高
  • 太小语义不完整、上下文丢失
  • chunk 粒度直接影响召回和生成

9.4 向量检索和 BM25 的区别是什么？

回答重点：

  • 向量检索偏语义相似
  • BM25 偏关键词匹配
  • 术语、编号、错误码这类内容 BM25 往往更稳
  • 线上常见做法是 hybrid search

9.5 为什么需要 rerank？

回答重点：

  • 召回重覆盖，重排重精度
  • 候选集里会混入“差不多相关”的内容
  • rerank 可以提升 top 几条结果的质量

9.6 RAG 为什么仍然会幻觉？

回答重点：

  • 检索不到
  • 检索到了但排序靠后
  • 模型误读证据
  • 多段资料拼接错误
  • prompt 没限制好

9.7 RAG 和微调怎么选？

回答重点：

  • 知识更新、私有知识，优先 RAG
  • 行为模式、格式风格、专任务适配，优先微调
  • 二者经常组合

9.8 怎么评估 RAG 效果？

回答重点：

  • 拆成检索评估和生成评估
  • 看 Recall@k、MRR、NDCG
  • 看 groundedness、faithfulness、citation accuracy
  • 最终结合人工标注和业务指标

9.9 RAG 最容易踩哪些坑？

回答重点：

  • 数据脏
  • chunk 不合理
  • 只做向量检索
  • 缺少 metadata filter
  • 没有评估集
  • 权限控制缺失

9.10 生产级 RAG 和 demo 最大区别是什么？

回答重点：

  • demo 重“跑通”
  • 生产级重“稳定、可评估、可治理、可更新、可追踪”

十、一个更实用的理解框架

如果你想在工作里更稳地理解 RAG，可以记住下面这个框架：

RAG 不只是“检索 + 生成”，而是一整套“知识进入系统、被索引、被召回、被组织、被模型使用、再被评估和优化”的工程链路。

所以真正决定效果的，通常不只是模型，而是这几层是否都做对了：

  • 数据质量
  • chunk 设计
  • 检索策略
  • 排序机制
  • 上下文组织
  • 生成约束
  • 评估闭环

小结

RAG 的本质，是让模型从“只依赖参数记忆回答”，变成“基于外部知识进行回答”。

它最核心的价值，不是让系统看起来更聪明，而是让回答：

  • 更可追溯
  • 更适合私有知识
  • 更适合动态知识
  • 更容易持续优化

如果把一句话再说得更工程化一点：

RAG 是大模型应用里最重要的知识供给系统之一，而不是一个单独的检索技巧。
