Python SDK 源码解析：官方 MCP Python SDK 的目录结构、能力模型与底层实现

May 03, 2026

写在前面

如果说 PrefectHQ/fastmcp 更适合帮你快速建立开发直觉，那么 modelcontextprotocol/python-sdk 更适合帮你建立“官方视角”。

这点非常重要。

因为很多人学 MCP 时会遇到一个典型问题：

  • 会写框架代码
  • 但分不清哪些是框架抽象，哪些是协议能力

而官方 Python SDK 的价值就在这里：

它能帮你把“开发体验”和“协议边界”对齐起来。

所以这篇文章会重点拆三件事：

  1. 官方 Python SDK 的目录结构怎么理解
  2. 它暴露了哪些能力模型
  3. 它底层是怎样把 MCP 协议落到 Python 里的

一、先给官方 Python SDK 一个定位

如果用一句话概括：

modelcontextprotocol/python-sdk 是 MCP 官方维护的 Python SDK，用来在 Python 生态中实现 MCP server、client 以及相关协议能力。

和高层框架相比，它更值得学习的地方在于：

  • 更贴近官方能力模型
  • 更容易看到协议原语
  • 示例覆盖面很完整
  • 适合从最小能力一直读到进阶 transport

所以这个仓库的价值，不只是“可以用”，更是“可以作为学习协议的标准参照物”。

├── README.md
├── examples/
│   └── snippets/
│       └── servers/

│       ├── utilities / shared helpers
│       └── high-level API related modules
├── tests/

同样地，这里的重点不是每个目录名绝对一模一样，而是先抓住这个仓库的骨架：

  • examples：展示官方推荐用法
  • src/mcp：协议和 SDK 的核心实现
  • tests：验证能力边界
  • pyproject.toml：展示工程配置和依赖边界

2.2 先看根目录各自的职责

README.md

这是官方 SDK 的总入口。

它最重要的作用通常是：

  • 说明项目定位
  • 给最小示例
  • 给学习路径
  • 指向 examples 和文档

pyproject.toml

这类文件虽然不显眼，但很适合拿来快速判断：

  • SDK 的包结构
  • 依赖关系
  • Python 版本要求
  • 命令行入口或构建方式

对于读源码的人来说，这个文件能帮你先建立“工程边界感”。

examples/

这是整个仓库最适合先看的地方之一。

它的价值在于：

  • 把抽象能力转成最小可运行代码
  • 展示官方希望用户怎样使用 SDK
  • 给出从基础到进阶的样例路径

tests/

测试目录通常最能体现官方 SDK 认为什么行为是关键契约。

例如：

  • 工具注册的正确性
  • transport 行为的一致性
  • notifications 的协议语义
  • 结构化输出的稳定性

src/mcp/

这是最核心的源码目录。

它承载的不是单纯“一个 server helper”，而是官方 Python 版 MCP 能力模型本身。

2.3 再看 src/mcp/ 内部主要模块做什么

server/

这里通常是 server 侧实现核心。

主要职责通常包括：

  • server 生命周期
  • 能力注册
  • 请求分发
  • 和 transport 的对接

如果你想知道“一个 MCP server 在官方 SDK 里是怎样被建模的”，这里是第一优先级。

client/

这里是 client 侧抽象。

主要职责通常包括：

  • 建立连接
  • 发起请求
  • 接收响应
  • 处理通知

它能帮助你理解 MCP 不只是 server 框架，而是完整 client/server 交互模型。

types/ 或协议模型目录

这一层非常关键。

因为它通常负责：

  • 请求对象
  • 响应对象
  • 通知对象
  • schema 或协议数据模型

如果你想真正理解“协议长什么样”，这层比高层示例更重要。

transport/

这里负责协议消息的承载方式。

通常会覆盖：

  • stdio
  • HTTP 相关 transport
  • streamable HTTP

这层说明官方 SDK 并不只是一个“本地工具包装库”，而是在认真处理协议通信。

auth/

这部分一般负责认证或授权相关能力。

尤其在 OAuth 示例存在时，这部分就更值得关注，因为它能帮助你理解官方 SDK 如何进入更真实的服务场景。

utilities / shared helpers

这部分通常负责：

  • 公共工具函数
  • 共享转换逻辑
  • 内部辅助封装

虽然它不是第一优先级，但很多高层能力最后都会落回这里。

高层 API 相关模块

这一层负责把低层协议能力包装成更易用的 Python 接口。

如果你在示例里看到的代码非常简洁，那么大量“简洁体验”通常就来自这里。

2.4 第一层：README 与 examples

这是读官方 SDK 最好的起点。

因为你最先需要知道的不是内部实现细节，而是：

  • 官方推荐怎么写最小 server
  • 官方示例怎么组织
  • 哪些功能是 SDK 直接支持的

这个仓库里非常适合学习的目录是：

  • examples/snippets/servers

这里的示例基本覆盖了从基础到进阶的关键能力：

  • basic_tool
  • basic_resource
  • structured_output
  • notifications
  • oauth_server
  • streamable_http
  • lowlevel

2.5 第二层：高层 API

如果你从示例往回追，通常会先看到高层 API。

这一层主要回答：

  • 怎样快速创建 server
  • 怎样注册 tool / resource / prompt
  • 怎样用更 Pythonic 的方式编写 MCP 能力

这一层和 FastMCP 比较接近，但更值得关注的是：

它和官方能力模型之间的映射会更直接。

2.6 第三层：低层 server / client 抽象

这部分是理解官方 SDK 的关键。

因为一旦往下走，你会逐渐看到：

  • 请求和响应是怎样建模的
  • server 和 client 之间怎样通信
  • 哪些能力属于高层封装
  • 哪些能力已经接近协议原语

如果说 examples 帮你看“怎么用”，那么这一层是在回答“协议是怎么落地的”。

2.7 第四层：transport

官方 SDK 很值得看的一个地方，就是它不会只停留在“最小 demo”层。

它还会通过示例和实现展示：

  • stdio
  • streamable HTTP
  • notification 机制
  • OAuth 相关能力

也就是说，这个仓库既能帮你写 toy project，也能帮你理解真实工程里会遇到的通信问题。

2.8 第五层：类型与 schema

MCP 在 Python 里落地时，绕不开的一层就是：

  • Python 类型
  • schema 描述
  • 结构化输出

这也是为什么 structured_output 这个示例特别值得看。

因为它直接对应一个现实问题：

工具结果不仅要“能返回”，还要“能被宿主和模型稳定理解”。

三、这个 SDK 的能力模型可以怎么理解

3.1 tools

这是最直观的能力。

官方 SDK 会帮助你把 Python 里的可调用能力暴露成 MCP tool。

这一层重点不只是“调用函数”，而是：

  • 工具元信息
  • 参数约束
  • 结构化返回
  • 与 host 的对接方式

3.2 resources

这部分非常适合拿来理解为什么 MCP 叫 Model Context Protocol。

因为 resource 的价值在于：

  • 不是执行动作
  • 而是供模型读取上下文

这也是为什么 basic_resource 这类示例值得单独看。

3.3 prompts

prompts 往往不是初学者最先关注的能力，但它其实是 MCP 体系完整性的体现。

它说明 server 不只是一个执行层，还可以是任务模板的提供层。

3.4 notifications

这是官方 SDK 很值得学的部分之一。

传统的“请求-响应”视角，很容易让人以为 MCP 只是 RPC。

但 notifications 说明它不只是同步调用协议，还会涉及：

  • 状态变化通知
  • 进度反馈
  • 能力变化广播

这对复杂工具调用和长任务执行都很重要。

3.5 streamable HTTP

这部分对应的是更真实的远程服务场景。

如果你只看 stdio，会很容易把 MCP 理解成“本地 CLI 工具协议”。

但 streamable_http 会提醒你：

MCP 也可以被部署成更标准的远程服务形态。

3.6 lowlevel

这一部分尤其适合进阶学习。

因为它能帮助你区分：

  • 哪些是 SDK 提供的便利层
  • 哪些是协议本身的低层表达

如果这部分读懂了，你对 MCP 的理解就会更扎实。

四、从示例反推底层实现

官方 SDK 最适合的读法，不是先看底层实现，而是先抓几个示例，再反推底层。

4.1 从 basic_tool 看最小工具链路

这一类示例最适合回答：

  • 一个最小 server 怎么启动
  • 一个最小 tool 怎么注册
  • 一次调用怎样从输入走到输出

如果把这条线读清楚，你就能建立一个最小心智模型：

  1. server 暴露工具
  2. client 发现工具
  3. host 把工具描述交给模型
  4. 模型产生调用意图
  5. host 调用 server
  6. server 返回结果

4.2 从 basic_resource 看上下文供给

这一类示例会帮助你理解：

  • resource 和 tool 的职责区别
  • resource 为什么适合做上下文注入
  • 为什么 MCP 不只是“执行动作”

这部分对于写代码助手、文档助手特别重要。

4.3 从 structured_output 看结构化结果

很多初学者只关注输入参数 schema，却忽略了输出结构也同样重要。

structured_output 会直接告诉你：

  • 结果怎么组织更稳
  • 为什么结构化输出比一大段自由文本更适合工具调用链
  • 模型后续推理为什么会受返回结构影响

4.4 从 notifications 看协议不只是 RPC

这是官方 SDK 很适合拿来拉开理解层次的地方。

如果你只看到“tool call”，很容易把 MCP 误认为是另一种函数调用协议。

而 notifications 这一层会告诉你，它还在处理：

  • 事件
  • 状态
  • 进度
  • 变更传播

4.5 从 streamable_http 看部署形态

这一类示例能帮助你从本地开发迈向远程服务思维。

重点要看：

  • HTTP transport 是怎样接入的
  • 数据流是怎样传递的
  • 远程部署和本地 stdio 有哪些心智差异

4.6 从 lowlevel 看协议原语

这一部分最适合问自己：

  • 如果没有这些高层 helper，我该怎么手工表达 MCP 能力
  • SDK 到底替我封装了多少
  • 协议层到底长什么样

五、读官方 SDK 源码时最值得抓的几条线

5.1 第一条线：能力注册

重点看：

  • tool / resource / prompt 分别怎么注册
  • 注册时会记录哪些元数据
  • 这些元数据最后怎样暴露给 client

5.2 第二条线：类型、schema 与结构化输出

重点看：

  • 类型标注怎样映射成 schema
  • 返回结构怎样映射成可传输对象
  • 为什么某些输出更适合让模型继续推理

5.3 第三条线：请求路由

重点看：

  • 请求到达 server 后怎样分流
  • 怎样从协议消息找到具体 handler
  • 参数在什么时候被校验

这一条线是理解 runtime 的关键。

5.4 第四条线：notifications 与事件机制

重点看：

  • 哪些能力属于请求-响应
  • 哪些能力属于通知
  • 进度或状态变化如何被传递

这能帮助你避免把 MCP 过度简化成 RPC。

5.5 第五条线：transport 层

重点看：

  • stdio 与 streamable HTTP 的差异
  • transport 和业务 handler 是怎么解耦的
  • 哪些逻辑属于协议层，哪些属于通信层

5.6 第六条线：低层 API 与高层 helper 的边界

这是官方 SDK 最适合深挖的一条线。

因为它最能帮助你建立这种判断力：

  • 我现在用的是 SDK 便利层
  • 我现在看到的是协议原语

六、官方 Python SDK 最适合拿来学什么

我觉得主要有五点。

6.1 学“官方推荐写法”

这个价值非常直接。

6.2 学“协议能力全貌”

不仅是 tools，还包括：

  • resources
  • prompts
  • notifications
  • OAuth
  • streamable HTTP

6.3 学“从最小示例到进阶特性”的路径

它的 examples 体系很适合搭建系统学习路径。

6.4 学“高层封装和低层协议的边界”

这点尤其适合写博客、做技术分享或者准备面试。

6.5 学“如何把 MCP 真正落到 Python 里”

这和只看概念介绍完全不是一回事。

七、阅读这个仓库时要注意什么

7.1 不要只看 README

README 适合入门，但不够形成真正的源码理解。

7.2 不要只看最小示例

最小示例会让你以为 MCP 很简单，但它不会自然暴露：

  • notifications
  • transport 差异
  • 低层 API

7.3 不要把 SDK helper 当成协议本身

这点和读 FastMCP 时一样重要。

一定要不断追问：

  • 这是 SDK 的便利层吗
  • 这是协议本身的要求吗

八、建议怎样读这个仓库

一个比较稳的顺序是：

  1. 先看 README 的最小 server 示例
  2. 再看 examples/snippets/servers
  3. 先读 basic_tool 和 basic_resource
  4. 再读 structured_output 和 notifications
  5. 然后看 streamable_http
  6. 最后再看 lowlevel

这个顺序的好处是：

  • 先建立最小直觉
  • 再补全能力全貌
  • 最后再理解协议边界

小结

如果只用一句话总结：

官方 python-sdk 最值得学习的地方，是它能帮助你把“会写 Python MCP”进一步升级成“理解官方 MCP 能力模型和协议边界”。

所以它特别适合作为：

  • 官方参考实现
  • 示例驱动学习材料
  • Python 版 MCP 协议落地样本
