2. 底层实现原理

2.1 数据存储结构

2.1.1 SDS（Simple Dynamic String）

Redis 字符串不是 C 语言字符串，而是 SDS。

对应上层结构：

  • String：value 使用 SDS 保存字符串内容
  • 所有 Redis 数据结构：key 本身也是 SDS
  • Hash / List / Set / ZSet：内部元素、字段名等字符串内容也可能使用 SDS 表示
1
2
3
4
5

struct sdshdr {
    int len;        // 已使用长度
    int free;       // 剩余长度
    char buf[];    // 字节数组
};

优点：

  • O(1) 获取长度
  • 防止缓冲区溢出
  • 减少内存重分配（空间预分配 + 惰性释放）
  • 二进制安全

2.1.2 Linked List（双向链表）

List 的底层实现之一（还有 ZipList 和 QuickList）。

对应上层结构：

  • List：早期版本在列表元素较多或不适合压缩编码时使用双向链表
  • Redis 服务内部：也会用于保存客户端、慢查询日志等内部链表结构
1

3
4
5

8

typedef struct list {
    listNode *head;
    listNode *tail;
    unsigned long len;
    void *(*dup)(void *ptr);
    void (*free)(void *ptr);
    int (*match)(void *ptr, void *key);
} list;

特点：

  • 双向链表
  • 头尾操作 O(1)
  • 支持迭代器

2.1.3 ZipList（压缩列表）

List、Hash、ZSet 的底层实现之一。

ZipList 本质上是一块连续内存空间，Redis 会用紧凑格式把多个元素挨个存起来。它不像双向链表那样为每个节点额外保存前后指针，因此在小数据量场景下更节省内存。

简单理解：ZipList 是 Redis 为了“用更少内存存小集合”设计的紧凑型列表结构。

对应上层结构：

  • List：早期版本小列表使用 ZipList
  • Hash：字段和值都较小、数量较少时使用 ZipList
  • ZSet：成员和 score 数量较少时使用 ZipList

特点：

  • 连续内存块
  • 适合小数据量（< 512 字节）
  • 节省内存
  • 增删需要重新压缩

触发条件：

  • List: 元素 < 64 字节 且 元素数 < 512
  • Hash: 元素 < 64 字节 且 元素数 < 512
  • ZSet: 元素 < 64 字节 且 元素数 < 128

2.1.4 QuickList（快速列表）

List 的底层实现，是 LinkedList + ZipList 的组合。

QuickList 可以理解为“链表套压缩列表”：外层是双向链表，多个节点通过前后指针串起来；每个链表节点内部不是只存一个元素，而是保存一个 ZipList，用连续内存存储多个 List 元素。

这样设计的好处是：外层链表方便从头尾插入、删除，内层 ZipList 又能减少每个元素单独作为链表节点带来的指针开销，因此兼顾了链表的操作性能和压缩列表的内存优势。

  • List：Redis 3.2+ 的默认底层实现
  • List：逻辑上仍是链表，链表节点内部用压缩列表保存多个元素

  • ZSet：元素较多或较大时，使用 Dict 保存 member 到 score 的映射
  • Redis 全局键空间：key 到 redisObject 的映射也由 Dict 实现

2.1.6 SkipList（跳表）

ZSet 的底层实现。

对应上层结构：

  • ZSet：元素较多或较大时使用 SkipList 按 score 排序
  • ZSet：通常与 Dict 搭配使用，SkipList 负责范围查询和排序，Dict 负责按 member 快速定位 score

特点：

  • 多层链表
  • 查找 O(logN)
  • 插入/删除 O(logN)
  • 比平衡树实现简单

2.1.7 IntSet（整数集合）

Set 的底层实现之一（元素都是整数时）。

对应上层结构：

  • Set：当集合元素全部是整数且元素数量较少时使用 IntSet
  • Set：一旦出现非整数元素，或元素数量超过阈值，会转换为 Dict

特点：

  • 连续内存
  • 16/32/64 位整数
  • 升级策略
  • 元素不可重复

2.2 内存淘汰策略

2.2.1 过期策略

Redis 有三种过期删除策略，实际使用的是惰性删除 + 定期删除的组合。

定时删除：

  • 设置定时器，key 一过期立即删除
  • 内存友好：过期 key 立即释放
  • CPU 不友好：大量定时器占用 CPU 资源
  • Redis 不使用此方案

惰性删除：

  • 访问 key 时才检查是否过期，过期则删除
  • CPU 友好：只在访问时触发，不主动消耗 CPU
  • 内存不友好：过期 key 若未被访问，会一直堆积占用内存

定期删除：

  • Redis 每隔一段时间（默认 100ms）随机抽查一批设置了过期时间的 key
  • 发现过期的则删除，并根据过期比例动态调整下次扫描频率
  • 是内存和 CPU 的折中方案

Redis 使用：惰性删除 + 定期删除

两者组合的原因：

  • 惰性删除保证访问到的 key 一定是有效的
  • 定期删除兜底清理那些永远不会被访问的过期 key，防止内存无限膨胀

2.3 持久化机制

2.3.1 RDB（Redis Database）

原理：

  • 定时生成数据快照
  • Fork 子进程执行
  • 阻塞主进程（时间点快照）

配置：

  • 恢复快
  • Fork 子进程，不影响主进程

  • 可能丢失最近数据
  • Fork 耗时（大数据量）

Q: 布隆过滤器能删除数据吗？

不能。布隆过滤器不支持删除，因为删除可能影响其他元素（共享 bit 位）。解决方案：使用 Counting Bloom Filter 或定期重建。

Q: 如何选择布隆过滤器的参数？

1
2
3
4
5
6
7

9

n = 元素数量
p = 假阳性率

m = - (n * ln(p)) / (ln(2)^2)  # 所需 bit 数
k = (m / n) * ln(2)            # 哈希函数数量

例如：n=100000, p=0.01
m = -100000 * ln(0.01) / 0.48 ≈ 958506 bits ≈ 117 KB
k = 7

  • 不宜过长：数据恢复后等待时间长
  • 不宜过短：频繁穿透到数据库
  • 建议：30秒 ~ 5分钟，根据业务调整

def release_lock(lock_name, lock_value):
    # Lua 脚本：只有持有锁才能释放
    script = """
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
    else
        return 0
    end
    """
    return r.eval(script, 1, lock_name, lock_value)

# 使用
lock = acquire_lock('my_lock')

    try:
        # 业务逻辑
        pass
    finally:
        release_lock('my_lock', lock)

def scan_big_keys(host='localhost', port=6379, count=1000):
    r = redis.Redis(host=host, port=port)
    big_keys = []
    
    cursor = 0
    while True:
        cursor, keys = r.scan(cursor, count=count)
        
        for key in keys:
            key_type = r.type(key)
            if key_type == 'string':
                length = r.strlen(key)
                if length > 1024 * 1024:  # > 1MB
                    big_keys.append((key, 'string', length))
            elif key_type == 'hash':
                length = r.hlen(key)
                if length > 10000:
                    big_keys.append((key, 'hash', length))
            elif key_type == 'list':
                length = r.llen(key)
                if length > 10000:
                    big_keys.append((key, 'list', length))
            elif key_type == 'set':
                length = r.scard(key)
                if length > 10000:
                    big_keys.append((key, 'set', length))
            elif key_type == 'zset':
                length = r.zcard(key)
                if length > 10000:
                    big_keys.append((key, 'zset', length))
        
        if cursor == 0:
            break
    
    return big_keys

7. 面试题

基础类

Q1: Redis 为什么快？

  1. 内存存储：数据在内存中，访问 O(1)
  2. 单线程模型：无锁竞争，上下文切换少
  3. I/O 多路复用：一个线程处理多个连接
  4. 高效数据结构：SDS、跳表等
  5. Pipeline：减少网络往返

Q2: Redis 数据过期后立即删除吗？

不是，Redis 采用惰性删除 + 定期删除的组合策略：

策略 触发时机 内存 CPU
定时删除 到期立即删 友好 不友好（Redis 不用）
惰性删除 访问时检查 不友好 友好
定期删除 周期性抽查 折中 折中
  • 惰性删除：访问时才检查是否过期并删除，不消耗额外 CPU，但可能内存堆积
  • 定期删除：每 100ms 随机抽查一批 key，清理过期的，防止长期无访问的 key 占用内存

Q3: Redis 持久化方式？

  1. RDB：定时快照，恢复快，可能丢数据
  2. AOF：命令日志，数据安全，文件较大
  3. 混合持久化：4.0+，结合两者优点

Q4: Redis 和 Memcached 区别？

维度 Redis Memcached
数据结构 String/Hash/List/Set/ZSet 仅 String
持久化 支持 不支持
复制 主从 无
集群 原生支持 需要客户端实现
内存分配 自有内存管理 Slab
事务 支持 Lua 不支持

Q6: 什么是渐进式 rehash？

  2. 每次增删改查迁移一个桶
  3. 迁移期间查询两个表
  4. 迁移完成后使用新表
  5. 避免一次性迁移阻塞

Q7: Redis 6.0 多线程？

  • I/O 多线程：网络读写并发
  • 命令执行单线程：保证原子性
  • 提升网络 I/O，不提升命令执行

Q8: Pipeline 和 Lua 脚本区别？

维度 Pipeline Lua
原子性 非原子 原子
网络 多次命令一次往返 一次执行
使用场景 批量操作 复杂逻辑

Q9: 主从同步原理？

  2. Master 执行 BGSAVE 生成 RDB
  3. Master 发送 RDB 给 Slave
  4. Master 发送缓冲区命令给 Slave
  5. 之后 Master 发送写命令（命令传播）

Q10: 哨兵机制？

  • 配置提供者：提供地址

脑裂类

Q16: 什么是脑裂？如何解决？

脑裂：集群中多个节点同时认为自己是主节点

解决方案：

  • 最小副本数：min-replicas-to-write
  • 合理超时：down-after-milliseconds 不宜过短
  • Sentinel 奇数个
  • 网络隔离

Q17: Sentinel 选举机制？

  1. 多个 Sentinel 认为 Master 下线 → 客观下线
  2. 选举领头的 Sentinel（先到先得）
  3. 领头 Sentinel 从 Slave 选举新 Master
  4. 其他 Slave 改为复制新 Master

Q18: Redis Cluster 故障转移？

  1. 节点定时发送心跳
  2. 节点超时未响应 → 标记为 PFAIL
  3. 多数派确认 → 标记为 FAIL
  4. 从节点发起选举
  5. 获得多数派投票 → 升级为主节点
