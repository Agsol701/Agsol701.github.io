什么是 MCP：概念、使用方式、开发方法、底层原理与常见面试题

May 02, 2026

写在前面

最近 MCP 这个词出现得非常频繁。

很多人第一次接触它时，会把它和：

  • function calling
  • tools
  • plugins
  • agent framework
  • API 网关

混在一起。

但实际上，它们并不是一回事。

如果用一句话先做一个总定义：

MCP，通常指 Model Context Protocol，是一套让大模型宿主程序以标准方式连接外部能力与外部上下文的协议。

这里的“外部能力”可以是：

  • 文件系统操作
  • 数据库查询
  • 搜索引擎
  • 浏览器自动化
  • 企业内部 API
  • 本地脚本

这里的“外部上下文”可以是：

  • 本地文件
  • 项目源码
  • 文档知识库
  • 数据表
  • 运行时状态

所以从本质上说，MCP 不是某个具体工具，而是一套“标准连接方式”。

一、MCP 到底是什么

1.1 最直白的理解

可以先把它理解成：

大模型世界里的“标准化外设协议”。

就像电脑需要统一的 USB 协议来连接键盘、鼠标、摄像头一样，AI 宿主程序也需要一种统一方式来连接各种外部工具和数据源。

如果没有这层标准化协议，现实里就会变成这样：

  • 每个 AI 客户端都要单独对接每个工具
  • 每个工具都要为每个客户端重复开发适配层
  • 工具描述、参数格式、返回结构都不统一
  • 权限控制、错误处理、生命周期管理很难复用

而 MCP 做的事，就是把这一层对接方式标准化。

1.2 它解决的核心问题是什么

MCP 主要解决的是：

模型如何以一致、可扩展、可治理的方式，访问模型外部的能力和上下文。

这里面其实包含了四个子问题。

第一个问题：连接问题

模型本身不会直接访问你的文件、数据库或浏览器。

真正执行这些动作的，通常是宿主程序、agent runtime 或外部服务。

所以必须有一种机制，让宿主程序知道：

  • 有哪些可用能力
  • 每个能力怎么调用
  • 输入参数是什么
  • 调用结果怎么返回

第二个问题：标准化问题

如果没有标准协议，每个工具都有自己的一套：

  • 入参格式
  • 错误格式
  • 描述方式
  • 发现机制

那么接入成本会非常高。

MCP 的价值之一，就是让工具接入不再是“一次性私有对接”，而是“按协议注册”。

第三个问题：上下文问题

大模型不是只需要工具，还需要上下文。

例如：

  • 读取某个目录下的代码文件
  • 获取数据库表结构
  • 查一篇内部文档
  • 获取当前项目配置

这些不一定是“执行动作”，很多时候更像“读取可供模型理解的上下文资源”。

所以 MCP 不只是工具协议，也是一种上下文接入协议。

第四个问题：治理问题

当工具越来越多时，系统还必须考虑：

  • 权限边界
  • 可观测性
  • 超时和重试
  • 错误传播
  • 审计与追踪

MCP 本身不是完整治理平台，但它为治理提供了统一接口基础。

二、MCP 和 function calling、tools、插件、Agent 的区别

这是最容易在面试和工作里说混的一部分。

2.1 MCP 和 function calling 的区别

function calling 更像是：

模型输出一个结构化调用意图。

例如模型说：

2
3
4
5
6

{
  "name": "search_docs",
  "arguments": {
    "query": "MCP architecture"
  }
}

这说明模型“想调用”一个函数。

但它没有解决这些问题：

  • 函数从哪里发现
  • 函数如何注册
  • 宿主如何统一管理多个外部能力
  • 如何暴露资源和提示模板
  • 如何做标准生命周期管理

所以可以这样理解：

  • function calling 是模型层的调用表达
  • MCP 是系统层的能力接入协议

2.2 MCP 和 tools 的区别

tool 是能力本身，MCP 是暴露能力的协议。

也就是说：

  • tool 回答“我能做什么”
  • MCP 回答“我怎样被标准化地提供出来”

比如“读取文件”是一个工具能力；把它通过统一 schema、统一发现方式、统一调用流程提供给宿主程序，这一层就是 MCP。

2.3 MCP 和插件的区别

插件通常是某个平台定义的一种扩展包机制。

它往往带有平台绑定特征，比如：

  • 某个 IDE 的插件系统
  • 某个 SaaS 产品的插件机制
  • 某个 agent 平台的扩展规范

而 MCP 更强调跨宿主、跨工具的标准通信协议。

可以把它理解为：

  • 插件更像“产品扩展形态”
  • MCP 更像“协议层标准”

2.4 MCP 和 Agent 的区别

Agent 是一种运行范式，关注的是：

  • 推理
  • 规划
  • 执行
  • 反思
  • 多轮工具调用

而 MCP 只负责其中一个重要问题：

Agent 怎样标准化接入外部世界。

所以它们不是替代关系，而是协作关系。

三、MCP 的核心角色

理解 MCP，最重要的是先分清楚几个角色。

3.1 Host

Host 是宿主程序，也就是用户真正交互的那个应用。

例如：

  • AI 桌面客户端
  • IDE 中的 AI 助手
  • 命令行 agent
  • 企业内部智能工作台

Host 的职责通常是：

  • 管理会话
  • 管理模型调用
  • 管理 MCP server 连接
  • 决定何时把工具和资源暴露给模型
  • 承接最终用户交互

3.2 Client

Client 可以理解为宿主内部的 MCP 协议客户端。

它负责：

  • 连接 MCP server
  • 发送协议请求
  • 获取 server 暴露的能力
  • 发起工具调用
  • 拉取资源内容

很多时候，client 是 host 的一部分实现，而不是一个独立产品。

3.3 Server

Server 是能力提供方。

它把某些外部能力或上下文，通过 MCP 标准暴露出来。

比如一个 server 可以提供：

  • 文件读写工具
  • Git 操作工具
  • 数据库查询工具
  • 浏览器控制工具
  • 企业知识库资源

3.4 Model

严格来说，模型本身不是 MCP 协议参与方。

真正参与协议通信的，一般是 host 和 server。

模型通常只会：

  • 看到被 host 注入的工具描述
  • 选择是否调用某个工具
  • 根据返回结果继续推理

所以一个非常关键的理解是：

MCP 连接的是“宿主程序”和“外部能力”，不是“模型自己直接联网去调用工具”。

四、MCP 里通常有哪些能力类型

虽然不同实现会有细节差异，但从理解上，最常见的可以先抓住三类。

4.1 Tools

tools 是可执行动作。

例如：

  • 运行 SQL
  • 读取文件
  • 写入文件
  • 调浏览器打开网页
  • 调企业 API 创建工单

它强调“执行”。

4.2 Resources

resources 更像可读取的上下文资源。

例如：

  • 某个文件
  • 某段源码
  • 某份文档
  • 某个数据对象

它强调“供模型理解的上下文输入”。

4.3 Prompts

有些实现里还会暴露 prompts。

它可以理解为：

由 server 提供的一组可复用提示模板或任务模板。

这类能力不是必须，但对复杂业务场景很有帮助，比如：

  • 代码审查模板
  • 故障排查模板
  • 报表分析模板

五、MCP 怎么使用

如果你是使用者，而不是协议开发者，可以按下面这个心智模型理解。

5.1 第一步：在宿主程序里配置 MCP server

一般来说，你会在某个 AI 宿主程序中配置一组 MCP server。

配置内容通常包含：

  • server 名称
  • 启动命令
  • 参数
  • 环境变量
  • 工作目录

一个常见的本地 stdio 方式配置，大致会像这样：

{
  "mcpServers": {
    "filesystem": {
      "command": "python",
      "args": ["server.py"],
      "cwd": "/path/to/project"
    }
  }
}

它的意思是：

  • 宿主程序启动一个本地进程
  • 这个进程实现了 MCP server
  • 双方通过标准输入输出进行协议通信

5.2 第二步：宿主发现 server 暴露的能力

连接建立后，宿主会做几件事：

  • 初始化连接
  • 协商能力
  • 获取工具列表
  • 获取资源列表
  • 获取提示模板列表

这样宿主才能知道：

  • 这个 server 能干什么
  • 哪些能力适合暴露给模型

5.3 第三步：宿主把能力描述提供给模型

模型通常不会直接看到整个协议过程。

它只会看到宿主整理后的内容，例如：

  • 工具名称
  • 工具说明
  • 参数 schema

然后模型根据当前任务决定是否调用。

5.4 第四步：模型产生调用意图

例如用户说：

帮我统计这个目录下有多少个 Markdown 文件。

如果宿主已经把文件系统工具提供给模型，模型就可能选择调用：

  • 列目录
  • 查找文件
  • 统计数量

5.5 第五步：宿主执行 MCP 调用并把结果回传给模型

真正的流程通常是：

  1. 模型输出调用意图
  2. 宿主把调用请求发给 MCP server
  3. server 执行真实逻辑
  4. server 返回结构化结果
  5. 宿主把结果注入模型上下文
  6. 模型基于结果继续回答用户

这就是 MCP 在实际使用中的主链路。

六、MCP 怎么开发

如果你要自己开发一个 MCP server，最重要的不是先背协议细节，而是先想清楚：

  • 你要暴露什么能力
  • 这些能力是 tool 还是 resource
  • 权限边界是什么
  • 输入输出 schema 怎么设计

6.1 开发一个 MCP server 的基本步骤

通常可以分成这几步。

1. 明确服务边界

先确定这个 server 到底负责什么。

例如：

  • 只负责本地文件读取
  • 只负责 Git 仓库分析
  • 只负责数据库只读查询
  • 只负责调用公司内部工单 API

边界越清晰，越容易控制安全性和可维护性。

2. 设计能力清单

把能力拆成几个明确的 tool 或 resource。

例如一个文档知识库 server 可能包含：

  • search_docs
  • get_doc
  • list_collections

3. 定义参数 schema

每个 tool 都应该有清晰的输入描述。

例如：

  • 必填参数有哪些
  • 每个参数类型是什么
  • 是否允许额外字段
  • 返回结果结构是什么

这一层非常重要，因为模型是否能稳定调用，很大程度取决于 schema 是否明确。

更进一步说，schema 设计时最好重点抓住下面几个原则。

第一，字段要少而明确

一个 tool 的参数不要一上来就设计成十几个字段。

字段一多，模型更容易：

  • 搞混参数含义
  • 漏填必填项
  • 把本该拆成两个工具的事情硬塞进一个工具

更稳的做法通常是：

  • 一个工具只保留完成当前动作真正必需的字段
  • 可选字段只保留高频、稳定、语义清楚的那几个

第二，字段命名要可预测

字段名最好让模型一眼就知道是什么意思。

例如：

  • path 往往比 target 更直观
  • query 往往比 input 更直观
  • limit 往往比 size 更直观

不要轻易用这类过于抽象的名字：

  • data
  • payload
  • options
  • config

因为这些名字对人来说也许“够通用”，但对模型来说往往“不够具体”。

第三，能用枚举就不要用自由文本

如果某个字段只有少数几种合法值，最好直接限制死。

例如不要写成：

  • mode: str

而更适合写成类似：

  • mode: "summary" | "full_text" | "metadata"

这样做的好处很直接：

  • 模型更不容易乱填
  • 宿主更容易校验
  • server 逻辑分支更清楚

第四，必填和可选要分清

不要把其实必须提供的信息做成“可选”。

例如一个读取文档详情的工具，如果必须知道文档 id，那就不要把它做成：

  • id: Optional[str] = None

这种写法会让模型误以为“这个字段也许可以不传”。

第五，限制额外字段

如果一个工具只接受固定参数，最好显式限制不要接受任意扩展字段。

否则很容易出现：

  • 模型多传了一个看似合理、其实无效的字段
  • server 静默忽略
  • 最后用户看到结果不对，却很难定位问题

从工程上说：

宁可让调用因为非法字段而明确报错，也不要悄悄吞掉错误参数。

第六，描述里要写“用途”，不要只写“类型”

schema 不是只给程序看的，也是在给模型看。

所以字段描述最好不仅写类型，还要写用途。

例如不要只写：

  • query: string

更好的写法是：

  • query: 要搜索的问题或关键词，用于在知识库中召回相关文档

第七，返回结构也要设计，不要只设计输入

很多人设计 schema 时只盯着入参，但 MCP 场景里，出参同样重要。

因为返回结果通常还要再喂给模型继续推理。

所以返回结果最好：

  • 结构稳定
  • 层次清楚
  • 字段名有语义
  • 既适合程序处理，也适合模型阅读

例如检索类工具返回时，通常会比“一大段拼接字符串”更适合设计成：

  • items
  • total
  • next_cursor
  • source

这样的结构。

第八，给模型留足够信息，但不要把 schema 做成文档

字段描述需要清楚，但也不要把一整篇说明都塞进 schema 里。

太长会带来两个问题：

  • 模型抓不住重点
  • 工具定义本身会变得啰嗦

更好的方式是：

  • 用一两句话说清字段用途
  • 把复杂规则放到更上层的 tool 描述里

不太好的设计：

from mcp.server.fastmcp import FastMCP
from pathlib import Path

mcp = FastMCP("demo-filesystem")
BASE_DIR = Path("/Users/guojian/dev/blog").resolve()


@mcp.tool()
def read_text_file(path: str) -> str:
    target = (BASE_DIR / path).resolve()

    if not str(target).startswith(str(BASE_DIR)):
        raise ValueError("path is outside allowed directory")

    return target.read_text(encoding="utf-8")


@mcp.tool()
def list_markdown_files(subdir: str = ".") -> list[str]:
    target = (BASE_DIR / subdir).resolve()

    if not str(target).startswith(str(BASE_DIR)):
        raise ValueError("path is outside allowed directory")

    return [
        str(p.relative_to(BASE_DIR))
        for p in target.rglob("*.md")
    ]


if __name__ == "__main__":
    mcp.run()

这个例子虽然很小，但已经体现了几个关键点：

  • server 有明确名字
  • 通过装饰器暴露工具
  • 工具有明确参数
  • 有权限边界检查
  • 返回值尽量结构化

6.3 开发时最容易踩的坑

1. 工具粒度太粗

比如设计成一个万能工具：

  • execute_anything

这种做法虽然省事，但问题很多：

  • 模型难以正确选择
  • 参数语义不清晰
  • 安全风险极高
  • 可观测性很差

更好的方式通常是：

  • 一个工具只做一类清晰动作

2. schema 太模糊

如果你把参数写得过于宽泛，比如全部都是字符串，模型很容易调用错。

好的 schema 应该：

  • 约束清楚
  • 命名明确
  • 字段少而准
  • 能枚举就枚举
  • 明确限制额外字段
  • 返回结构也一起设计

3. 返回结果不可读

如果返回一大段混乱文本，模型后续处理会变差。

更好的做法是：

  • 返回结构化 JSON
  • 或返回带标签的文本块

4. 没有权限边界

这是最危险的问题。

例如：

  • 任意路径读写
  • 任意 shell 执行
  • 任意 SQL 执行

这些如果不限制，MCP server 很容易变成一个高风险入口。

6.4 用 Python 源码视角还原一次执行流程

假设用户在宿主程序里说：

帮我调用一个 Python MCP server，读取某个资源并生成结构化结果。

如果底层接的是基于 fastmcp 或官方 python-sdk 写出来的 server，那么背后大致会发生这些事：

  1. host 把这个 server 暴露出来的工具描述提供给前置模型。
  2. 模型判断应该调用某个合适的 tool 或读取某个 resource。
  3. host 通过 MCP client 发起工具调用。
  4. Python MCP server 收到请求后，先做参数校验。
  5. server 执行真实逻辑，例如读文件、查数据、做转换或返回结构化输出。
  6. server 返回结构化结果给 client。
  7. host 再把结果喂回前置模型。
  8. 模型基于返回结果继续生成最终回答。

这个流程里同样有一个关键点：

这个 Python MCP server 不一定会再调用另一个模型，它也可能只是执行抓取、转换和整理逻辑。

当然，如果它内部又调用了摘要模型、OCR 模型或 reranker，那它就从“纯工具型 server”变成了“带智能处理的 server”。

七、MCP 的底层原理

这一部分是最适合面试拉开差距的。

7.1 从分层角度理解

从工程分层上看，MCP 大致可以拆成四层。

第一层：能力层

这是你真正要暴露的业务能力，例如：

  • 文件操作
  • 数据查询
  • 网页抓取
  • 企业系统调用

第二层：协议层

这一层负责把能力描述成标准协议对象，例如：

  • tool 定义
  • resource 定义
  • prompt 定义
  • 输入输出 schema

第三层：传输层

协议消息需要被真正传输。

常见方式包括：

  • stdio
  • 基于 HTTP 的远程通信
  • 事件流或长连接方式

无论具体传输形式怎样，核心目标都是：

  • 建立 client/server 通信
  • 发送请求
  • 返回响应
  • 传递通知事件

第四层：宿主编排层

宿主程序会在这层完成：

  • server 生命周期管理
  • 工具发现
  • 模型可见性控制
  • 调用转发
  • 结果注入
  • 日志与审计

7.2 协议通信本质上是什么

从本质上说，MCP 可以理解为：

一套围绕能力发现、能力描述、能力调用、资源读取而定义的结构化消息协议。

很多实现会采用类似 JSON-RPC 的消息风格。

也就是说，双方交换的大多是结构化 JSON 消息，比如：

  • 初始化
  • 列出工具
  • 调用工具
  • 读取资源
  • 返回错误

所以如果面试官问“底层是不是魔法”，答案当然不是。

它本质上仍然是：

  • 结构化消息
  • 标准字段
  • 请求响应模型
  • 外加通知机制

7.3 为什么它适合大模型场景

因为大模型接工具有两个特殊要求。

要求一：能力必须可描述

模型不能读源码理解所有工具，它依赖的是：

  • 名称
  • 描述
  • 参数 schema

这和传统 RPC 最大的不同之一在于：

MCP 的能力定义，不只是给程序看，也是在间接给模型看。

要求二：返回结果必须适合再推理

传统系统调用拿到结果后，通常直接给程序处理。

而大模型场景下，工具返回结果往往还要再喂给模型继续推理。

所以结果不仅要“机器可处理”，还要“模型可理解”。

7.4 MCP 的初始化过程大致是什么

一个简化版流程通常是：

  1. host 启动或连接 server
  2. client 和 server 完成初始化握手
  3. 双方声明各自支持的能力
  4. host 拉取 tools/resources/prompts 清单
  5. host 决定哪些能力暴露给模型
  6. 用户发起任务
  7. 模型选择调用某个能力
  8. host 转发请求给 server
  9. server 返回结果
  10. host 把结果注入模型上下文
  11. 模型继续生成最终答案

这个流程说明了一个关键事实：

MCP 并不是“模型直接调用工具”，而是“宿主协调模型与工具之间的调用闭环”。

7.5 为什么说 MCP 不只是工具协议，也是上下文协议

因为在很多场景里，模型真正缺的不是“执行动作”，而是“拿到正确信息”。

例如代码助手场景里，模型常常需要：

  • 读取文件
  • 获取目录树
  • 理解仓库结构
  • 查看配置文件

这些操作很多时候不是为了改动世界，而是为了补足上下文。

所以 MCP 的意义并不只是 action，更重要的是 context。

这也是 Model Context Protocol 这个名字里，Context 特别重要的原因。

八、MCP 的优点与局限

8.1 优点

1. 降低接入成本

宿主和工具提供方不必每次都私有对接。

2. 便于能力复用

一个实现良好的 MCP server，可以被多个宿主复用。

3. 便于治理

统一协议后，更容易做：

  • 权限控制
  • 日志追踪
  • 调用监控
  • 失败处理

4. 更适合复杂 agent 系统

当系统里有很多工具、很多知识源时，标准化收益会非常明显。

8.2 局限

1. 它不是万能银弹

有了 MCP，不代表模型就一定会正确选工具、正确传参数、正确理解返回结果。

2. 标准化不等于安全

协议统一了，但权限边界、数据脱敏、命令限制仍然要你自己做好。

3. 工具设计仍然是难点

很多问题不在协议，而在：

  • tool 粒度是否合理
  • 描述是否清晰
  • schema 是否稳定

4. 调用链会更复杂

引入 MCP 后，系统会多出：

  • host
  • client
  • server
  • transport
  • tool execution

这意味着调试链路也会更长。

九、什么场景适合用 MCP

比较适合的场景通常有这些。

9.1 需要接很多外部能力的 Agent 系统

例如：

  • 编码 agent
  • 运维 agent
  • 数据分析 agent
  • 办公自动化 agent

9.2 一个能力希望被多个宿主复用

比如你写了一个“企业知识库检索服务”，希望：

  • IDE 助手能用
  • 桌面助手能用
  • 命令行 agent 也能用

那么用 MCP 做统一暴露会很合适。

9.3 需要本地能力和远程能力混合接入

例如同时接：

  • 本地文件系统
  • 本地 Git 仓库
  • 远程数据库
  • 远程内部 API

9.4 需要治理和审计

如果你要做企业内部落地，往往会特别关注：

  • 谁调用了什么
  • 是否越权
  • 是否可回放
  • 是否可审计

统一协议会让这些事情更容易推进。

十、不适合或者暂时没必要上 MCP 的场景

10.1 只有一个简单工具

如果你只是做一个很小的 Demo，只有一个内部函数，直接 function calling 往往就够了。

10.2 能力完全绑定单一产品

如果这个能力只会服务某一个固定系统，而且以后也不考虑复用，私有对接可能更直接。

10.3 团队还没有想清楚工具边界

这时先上协议，往往只是把混乱标准化，并不会真的让系统变好。

很多时候更应该先做的是：

  • 拆清楚能力域
  • 梳理权限边界
  • 把输入输出设计好

十一、如何回答“请你设计一个 MCP server”

这是非常典型的面试题。

一个比较稳的回答结构可以是：

11.1 先讲目标

先说清楚这个 server 要服务什么业务。

例如：

我要设计一个面向代码库分析的 MCP server，为 AI 编码助手提供只读能力。

11.2 再讲能力边界

例如只提供：

  • list_files
  • read_file
  • search_text

不提供：

  • 任意 shell 执行
  • 任意文件写入

11.3 再讲协议设计

说明你会定义：

  • tool 名称
  • tool 描述
  • 参数 schema
  • 返回结果结构
  • 错误码或错误信息

11.4 再讲安全控制

例如：

  • 限定根目录
  • 限制文件大小
  • 限制访问后缀
  • 做超时和异常处理

11.5 再讲可观测性

例如：

  • 请求日志
  • 调用耗时
  • 错误统计
  • 审计记录

11.6 最后讲扩展性

例如以后可以再增加：

  • symbol 检索
  • Git diff 分析
  • 测试结果读取

这个回答会显得你不是只懂“怎么写一个工具”，而是懂“怎么做一个可落地的 MCP 服务”。

十二、常见面试题

下面这部分可以直接当复习提纲。

12.1 什么是 MCP

参考回答：

MCP 是 Model Context Protocol，是一套让 AI 宿主程序以标准方式连接外部工具、外部资源和提示模板的协议。它的核心价值是把模型外部能力的接入方式标准化，让不同宿主和不同能力提供方之间可以解耦。

12.2 MCP 解决了什么问题

参考回答：

它主要解决的是外部能力和外部上下文的标准化接入问题。没有它时，每个客户端都要和每个工具私有对接；有了它后，工具发现、调用、资源读取、能力描述可以统一起来，更适合复杂 agent 系统做复用和治理。

12.3 MCP 和 function calling 有什么区别

参考回答：

function calling 更偏模型输出层，强调模型如何表达“我要调用某个函数”；MCP 更偏系统接入层，强调宿主程序如何发现、描述、调用和管理外部能力。前者是调用意图表达，后者是能力接入协议。

12.4 MCP 的核心角色有哪些

参考回答：

典型会有 host、client、server 三个角色。host 是用户交互的宿主程序，client 是宿主内部的协议客户端，server 是能力提供方。模型通常不直接参与协议通信，而是由 host 把能力描述暴露给模型，再由 host 协调实际调用。

12.5 MCP 里 tool 和 resource 有什么区别

参考回答：

tool 偏动作执行，比如查数据库、写文件、调用 API；resource 偏上下文读取，比如读文档、读源码、读配置。前者强调 action，后者强调 context。

12.6 MCP 的底层原理是什么

参考回答：

本质上是基于结构化消息的 client/server 协议。它通常会定义初始化、能力发现、工具调用、资源读取、错误返回等交互模型，很多实现会采用类似 JSON-RPC 的消息格式，并运行在 stdio 或网络传输之上。

12.7 MCP 为什么适合 AI 场景

参考回答：

因为 AI 系统不仅要“调用能力”，还要“把能力描述给模型理解”。所以能力的命名、描述、参数 schema、返回结构都特别重要。MCP 正好把这一层标准化了。

12.8 开发 MCP server 时最重要的设计点有哪些

参考回答：

最重要的是能力边界、工具粒度、参数 schema、安全控制和可观测性。很多失败案例不是协议没实现，而是工具设计过粗、权限过大、返回结果不适合模型继续推理。

12.9 MCP 的安全风险有哪些

参考回答：

主要风险包括任意命令执行、任意文件访问、越权数据读取、敏感信息泄露、提示注入和返回结果污染。标准协议不会自动解决这些问题，所以需要额外做权限限制、白名单、沙箱和审计。

12.10 MCP 和传统 RPC 有什么不同

参考回答：

它们都属于结构化远程调用思路，但 MCP 更强调“给模型看的可描述性”和“给模型继续推理用的结果可读性”。所以它不是单纯面向程序员接口，也是在面向模型协作设计。

12.11 如何让模型更稳定地使用 MCP 工具

参考回答：

关键做法包括：工具命名清晰、描述具体、参数 schema 严格、返回结果结构化、工具粒度适中，并在宿主侧做好调用约束和错误处理。

12.12 什么时候应该用 MCP，什么时候不该用

参考回答：

当你有多个工具、多个知识源、多个宿主，且希望统一接入和复用时，MCP 很合适；如果只是一个小 Demo、一个固定函数、一个单体系统，直接 function calling 或私有集成可能更简单。

十三、一个适合背诵的总结

如果面试里只能用一小段话总结，可以用下面这版：

MCP 是 Model Context Protocol，本质上是一套面向 AI 宿主程序的能力接入协议。它把工具、资源和提示模板用统一方式暴露出来，让宿主程序可以标准化地发现和调用这些能力，再把结果回注给模型继续推理。它和 function calling 不同，function calling 解决的是模型表达调用意图，MCP 解决的是系统怎样标准化接入外部世界。开发 MCP server 的重点不只是协议实现，更包括工具粒度、schema 设计、安全边界和可观测性。

小结

如果只记一句话：

MCP 不是某个单独工具，而是 AI 系统连接外部能力与外部上下文的一套标准协议。

它最有价值的地方，不只是“能调工具”，而是：

  • 让能力接入标准化
  • 让上下文供给标准化
  • 让宿主和能力提供方解耦
  • 让复杂 agent 系统更容易复用、治理和扩展
