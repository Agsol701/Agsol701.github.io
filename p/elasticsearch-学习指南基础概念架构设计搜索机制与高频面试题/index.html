1. Elasticsearch 基础概念

1.1 什么是 Elasticsearch？

Elasticsearch 是一个基于 Apache Lucene 构建的分布式搜索和分析引擎。

核心定位：

  • 分布式搜索引擎
  • 实时数据分析引擎
  • 文档型数据库（NoSQL）

1.2 Elasticsearch 的主要特性

特性 说明
分布式 自动分片、自动负载均衡
近实时 数据写入后约 1 秒可搜索
高可用 支持副本、自动故障转移
RESTful API JSON 格式，易于使用
多语言支持 Java、Python、Go、JavaScript 等
强大的搜索能力 全文检索、结构化搜索、聚合分析

2.2 核心概念

Index（索引）

  • 文档的逻辑容器
  • 类似关系数据库中的"数据库"或"表"
  • 一个索引包含多个文档

Document（文档）

  • 最小数据单元
  • JSON 格式存储
  • 类似关系数据库中的"一行记录"

Type（类型）（已废弃）

  • ES 6.0 开始一个索引只能有一个类型
  • ES 7.0 完全移除类型概念
flowchart TD
    Index["Index: products"] --> Doc1["Document 1<br/>{id: 1, name: iPhone, price: 999}"]
    Index --> Doc2["Document 2<br/>{id: 2, name: MacBook, price: 1999}"]
    Index --> Doc3["Document 3<br/>{id: 3, name: iPad, price: 799}"]

Shard（分片）

  • 索引的物理分片
  • 每个分片是一个独立的 Lucene 索引
  • 分为主分片（Primary）和副本分片（Replica）
flowchart LR
    Index["Index: products<br/>3 主分片, 1 副本"]
    Index --> P0["Shard 0<br/>Primary"] --> R0["Shard 0<br/>Replica"]
    Index --> P1["Shard 1<br/>Primary"] --> R1["Shard 1<br/>Replica"]
    Index --> P2["Shard 2<br/>Primary"] --> R2["Shard 2<br/>Replica"]

Node（节点）

  • ES 集群中的单个服务器
  • 不同角色：Master、Data、Coordinating、Ingest

Cluster（集群）

  • 多个节点组成的集合
  • 通过集群名称识别

3.0.6 数据可靠性和一致性

1. ES 写入流程详解 
┌─────────────────────────────────────────────────────────────┐
│                    ES 完整写入流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  客户端 ──▶ 协调节点 ──▶ 主分片节点                             │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐    │
│  │                    主分片节点                         │   │
│  │                                                     │   │
│  │  步骤1: 写入 Translog                                 │   │
│  │    • Translog 是 WAL（Write-Ahead Log）            │   │
│  │    • 追加写入，顺序 I/O                             │   │
│  │    • 确保数据持久化                                 │   │
│  │                                                     │   │
│  │  步骤2: 写入内存缓冲区               │   │
│  │    • 文档暂存在内存中                               │   │
│  │    • 此时文档不可被搜索                             │   │
│  │                                                     │   │
│  │  步骤3: 异步 Refresh（默认1秒）                      │   │
│  │    • Buffer → 新的 Lucene 段                       │   │
│  │    • 文档可被搜索                                   │   │
│  │    • 新段写入文件系统缓存                           │   │
│  │                                                     │   │
│  │  步骤4: 定期 Flush（默认30分钟或512MB）             │   │
│  │    • 所有段写入磁盘                                 │   │
│  │    • 清空 Translog                                  │   │
│  │    • 创建新的 Translog                              │   │
│  │                                                     │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
2. Translog（预写日志）详解 
┌─────────────────────────────────────────────────────────────┐
│                    Translog 机制                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  什么是 Translog？                                         │
│    • WAL（Write-Ahead Log）预写日志                        │
│    • 记录所有写入操作                                       │
│    • 用于故障恢复                                          │
│                                                             │
│  为什么需要 Translog？                                     │
│    • Lucene 段写入磁盘较慢（需要 Flush）                   │
│    • Translog 追加写入，速度快                             │
│    • 故障恢复时重放 Translog 即可                          │
│                                                             │
│  Translog 同步策略：                                       │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  translog.durability: request                       │   │
│  │    • 每次写入请求都 fsync                           │   │
│  │    • 最安全，性能最低                               │   │
│  │    • 数据不丢失                                     │   │
│  │                                                     │   │
│  │  translog.durability: async                         │   │
│  │    • 每隔 sync_interval fsync                       │   │
│  │    • 默认值                                         │   │
│  │    • 性能高，可能丢失最后几秒数据                    │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  Translog 配置：                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  index.translog.durability: request                 │   │
│  │  index.translog.sync_interval: 5s                   │   │
│  │  index.translog.flush_threshold_size: 512mb         │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  Translog 是内存+磁盘混合：                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                                                      │   │
│  │  1. 内存部分（Translog Buffer）：                    │   │
│  │     • 写入操作先到内存 Buffer                       │   │
│  │     • 定期刷盘（默认每 5 秒）                      │   │
│  │     • 内存中的数据可能在断电时丢失                  │   │
│  │                                                      │   │
│  │  2. 磁盘部分（Translog 文件）：                     │   │
│  │     • 已刷盘的 Translog 持久化到磁盘                │   │
│  │     • 存储在 <shard>/translog/ 目录               │   │
│  │     • 故障恢复时读取                               │   │
│  │                                                      │   │
│  │  Translog 文件结构：                                │   │
│  │  ┌────────────────────────────────────────────┐    │   │
│  │  │  <index>/<shard>/translog/                │    │   │
│  │  │       ├── translog-1.ckp  (检查点)        │    │   │
│  │  │       ├── translog-1.tlog  (事务日志)      │    │   │
│  │  │       └── translog-2.tlog  (新的日志文件) │    │   │
│  │  └────────────────────────────────────────────┘    │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  断电丢数据风险：                                         │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                                                      │   │
│  │  如果使用异步刷盘（默认 async）：                   │   │
│  │    • 写入 Translog Buffer（内存）                  │   │
│  │    • 还没来得及刷盘                               │   │
│  │    • 断电了                                       │   │
│  │    • → 丢失最后几秒的数据                         │   │
│  │                                                      │   │
│  │  解决方案：                                        │   │
│  │    • translog.durability: request（同步刷盘）      │   │
│  │    • 每次写入都 fsync 到磁盘                      │   │
│  │    • 数据不丢失，但性能降低                        │   │
│  │                                                      │   │
│  │  配置对比：                                        │   │
│  │  ┌─────────────┬─────────────┬───────────────┐      │   │
│  │  │  配置        │   性能      │   数据安全    │      │   │
│  │  ├─────────────┼─────────────┼───────────────┤      │   │
│  │  │ async (默认) │    高       │  可能丢数据   │      │   │
│  │  │ request      │    低       │   不丢数据    │      │   │
│  │  └─────────────┴─────────────┴───────────────┘      │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
3. Refresh vs Flush vs Merge 
┌─────────────────────────────────────────────────────────────┐
│              Refresh vs Flush vs Merge 对比                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Refresh（刷新）：                                         │
│  ─────────────────────────────────────────────────────────  │
│    • 触发：默认每1秒 或 手动调用                           │
│    • 操作：内存 Buffer → 新的 Lucene 段                   │
│    • 效果：文档可被搜索                                    │
│    • 数据位置：文件系统缓存（Page Cache）                  │
│    • 特点：轻量级，频繁执行                                │
│                                                             │
│  Flush（刷盘）：                                           │
│  ─────────────────────────────────────────────────────────  │
│    • 触发：默认30分钟 或 Translog 达到 512MB              │
│    • 操作：所有段写入磁盘 + 清空 Translog                  │
│    • 效果：数据持久化到磁盘                                │
│    • 数据位置：磁盘文件                                    │
│    • 特点：重量级，不频繁执行                              │
│                                                             │
│  Merge（段合并）：                                         │
│  ─────────────────────────────────────────────────────────  │
│    • 触发：后台自动执行                                    │
│    • 操作：合并小的 Lucene 段 → 大的段                     │
│    • 效果：减少段数量，清理已删除文档                      │
│    • 特点：后台执行，I/O 密集                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘

什么是脑裂？

┌─────────────────────────────────────────────────────────────┐
│                    什么是脑裂？                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  脑裂 = Split-Brain = 集群分裂                            │
│                                                             │
│  定义：                                                    │
│    由于网络故障，集群分裂成多个部分                          │
│    每个部分都认为自己是主集群                               │
│    各自选举出自己的 Master                                  │
│    导致数据不一致                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘

    end

    Fault --> A
    Fault --> B
    A --> Problem["两个 Master 都能写入<br/>数据无法合并<br/>造成数据不一致或丢失"]
    B --> Problem

脑裂的危害：

┌─────────────────────────────────────────────────────────────┐
│                    脑裂的危害                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 数据不一致                                            │
│     • 两个 Master 接受不同的写入                           │
│     • 相同文档有不同的版本                                 │
│                                                             │
│  2. 数据丢失                                              │
│     • 集群恢复时不知道该信任哪个数据                       │
│     • 可能丢失部分数据                                     │
│                                                             │
│  3. 服务不稳定                                            │
│     • 客户端可能连接到不同的 Master                        │
│     • 读写操作可能冲突                                     │
│                                                             │
│  4. 难以恢复                                              │
│     • 需要人工干预                                         │
│     • 可能需要重建索引                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘

│                                                             │

│     • 5 节点：设置为 3                                     │
│                                                             │
│  3. 最佳实践：                                            │

┌─────────────────────────────────────────────────────────────┐
│                    FST 简介                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  FST = Finite State Transducer（有限状态转换器）           │
│                                                             │
│  作用：                                                    │

4.3 倒排索引何时建立

倒排索引并不是在文档"写入"时就立刻可搜索，而是经过 写入 Buffer → Refresh → Flush → Merge 四个阶段，倒排索引真正"生成"发生在 Refresh 这一步。

flowchart TD
    Write["写入 doc"] -->|立即| Buffer["Index Buffer + Translog<br/>不可搜索，无倒排索引"]
    Buffer -->|默认 1s，Refresh| Memory["In-Memory Segment<br/>倒排索引建立，可搜索"]
    Memory -->|默认 30min，Flush| Disk["磁盘 Segment<br/>倒排索引持久化"]
    Disk -->|后台异步 Merge| Merged["Merge 后的大 Segment<br/>倒排索引重组优化"]

阶段一：写入 Index Buffer（立即，无倒排索引）

┌─────────────────────────────────────────────────────────────┐
│              阶段一：写入 Index Buffer                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  发生时机：客户端写入请求到达主分片                          │
│                                                             │
│  动作：                                                     │
│    • 文档写入 Index Buffer（JVM 堆内存）                    │
│    • 同时追加 Translog（WAL，保证可靠性）                   │
│                                                             │
│  此时状态：                                                 │
│    • 倒排索引尚未建立                                       │
│    • 文档不可被搜索                                         │
│    • 即使 Translog 已落盘也搜不到                           │
│                                                             │
│  原因：                                                     │
│    Lucene 段（Segment）一旦生成就不可变，                   │
│    在 Buffer 阶段还没有"凑够"生成 Segment 的时机             │
│                                                             │
└─────────────────────────────────────────────────────────────┘

阶段二：Refresh（倒排索引真正建立 ⭐）

┌─────────────────────────────────────────────────────────────┐
│           阶段二：Refresh —— 倒排索引在这里诞生                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  触发时机：                                                 │
│    • 默认每 1 秒（index.refresh_interval = 1s）             │
│    • 手动调用 POST /index/_refresh                          │
│    • 写入时带 ?refresh=true（代价大，慎用）                 │
│                                                             │
│  动作：                                                     │
│    Index Buffer 中的文档 → 生成 In-Memory Segment            │
│    （位于 OS Cache，未落盘）                                │
│                                                             │
│  这一步具体做了什么：                                       │
│    1. 对字段执行 Analyzer（分词、归一化、小写化等）          │
│    2. 构建 Term Dictionary（有序词典）                       │
│    3. 构建 Term Index（FST 前缀索引）                        │
│    4. 构建 Posting List（文档 ID 列表 + 词频 + 位置）        │
│    5. 构建 Doc Values（列式存储，用于排序/聚合）             │
│    6. 构建 Norms、StoredFields 等辅助结构                    │
│                                                             │
│  此时状态：                                                 │
│    • 倒排索引已建立 ✅                                      │
│    • 文档可被搜索 ✅（这就是 ES 的"近实时 NRT"）             │
│    • 但 Segment 还在 OS Cache，未 fsync 到磁盘              │
│                                                             │
└─────────────────────────────────────────────────────────────┘

阶段三：Flush（倒排索引持久化）

┌─────────────────────────────────────────────────────────────┐
│              阶段三：Flush —— 持久化到磁盘                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  触发时机：                                                 │
│    • 默认 30 分钟                                           │
│    • Translog 达到 512MB（flush_threshold_size）            │
│    • 手动调用 POST /index/_flush                            │
│                                                             │
│  动作：                                                     │
│    • OS Cache 中的 Segment fsync 到磁盘                     │
│    • 清空 Translog，开启新的 Translog 文件                  │
│                                                             │
│  关键点：                                                   │
│    Flush 不会"重新建立"倒排索引                              │
│    倒排索引在 Refresh 阶段就已经建好了                       │
│    Flush 只是把它从 OS Cache 落到磁盘                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘

阶段四：Merge（倒排索引重组优化）

┌─────────────────────────────────────────────────────────────┐
│              阶段四：Merge —— 倒排索引重组                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  触发时机：后台异步执行（基于段数量、大小的策略）            │
│                                                             │
│  动作：                                                     │
│    多个小 Segment → 合并为一个大 Segment                    │
│                                                             │
│  这一步会"重写"倒排索引：                                   │
│    • 合并多个 Segment 的 Term Dictionary                    │
│    • 合并多个 Posting List（有序归并 + 重新压缩）            │
│    • 真正物理删除被标记删除的文档                           │
│    • 重建 FST、Doc Values 等                                │
│                                                             │
│  为什么 Merge 必须重写倒排索引：                             │
│    Lucene Segment 不可变 —— 删除/更新只是"标记删除"          │
│    要真正清理这些文档，必须在 Merge 时整体重写一份新 Segment │
│                                                             │
└─────────────────────────────────────────────────────────────┘

关键问答：

┌─────────────────────────────────────────────────────────────┐
│                    常见疑问澄清                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Q1：写入立即返回 200，倒排索引是不是已经建好了？           │
│    A：没有。返回 200 只代表写入了 Buffer + Translog，         │
│       倒排索引在 1 秒后的 Refresh 才生成，                    │
│       这就是为什么 ES 是"近实时(NRT)"而非实时。              │
│                                                             │
│  Q2：更新一个文档，倒排索引是修改还是新建？                 │
│    A：新建。Lucene Segment 不可变，                          │
│       update = 旧文档标记删除 + 写入新文档，                  │
│       Merge 时才真正物理清理旧文档。                         │
│                                                             │
│  Q3：想让写入立刻可搜怎么办？                                │
│    A：三种方式（按代价从小到大）：                           │
│       1. 等 1 秒（默认 refresh_interval）                    │
│       2. 调用 POST /index/_refresh（强制刷新整个索引）       │
│       3. 写入时带 ?refresh=true（代价最大，会立即创建段）    │
│       生产环境批量导入应反过来：调大 refresh_interval         │
│       甚至设为 -1，导入完再恢复，可大幅减少小 Segment。       │
│                                                             │
│  Q4：倒排索引建立的成本主要在哪？                            │
│    A：Refresh 时的 Segment 构建：分词、排序、FST 构建、       │
│       Posting List 压缩、Doc Values 列式写入。               │
│       refresh 频率越高，小 Segment 越多，                    │
│       后续 Merge 压力越大，整体写入吞吐越低。                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘

与写入流程的对应关系：

阶段 触发 数据位置 倒排索引状态 可搜索
写入 Buffer 立即 JVM 堆 + Translog 未建立 否
Refresh 默认 1s OS Cache（Segment） 建立 ⭐ 是
Flush 默认 30min 磁盘 Segment 持久化 是
Merge 后台异步 磁盘大 Segment 重组优化 是

详细的写入流程、Refresh/Flush/Merge 对比，参见 3.0.6 数据可靠性和一致性 和 3.4 写入流程。

6.4 数据恢复 

┌─────────────────────────────────────────────────────────────┐
│                    数据恢复机制                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Translog（事务日志）：                                     │
│    • 记录所有写操作                                         │
│    • 确保数据不丢失                                         │
│    • 故障恢复时重放                                         │
│                                                             │
│  Refresh（刷新）：                                          │
│    • 内存缓冲区 → 新的 Lucene 段                           │
│    • 默认 1 秒执行一次                                      │
│    • 搜索可见性                                             │
│                                                             │
│  Flush（刷盘）：                                            │
│    • 内存段 → 磁盘                                          │
│    • 清空 Translog                                          │
│    • 默认 30 分钟或 Translog 512MB                         │
│                                                             │
│  Merge（段合并）：                                          │
│    • 合并小的 Lucene 段                                     │
│    • 删除已标记删除的文档                                   │
│    • 后台自动执行                                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘

写入流程详解：

flowchart TD
    Request["1. 文档写入请求"] --> Translog["2. 写入 Translog (WAL)"]
    Translog --> Buffer["3. 写入内存缓冲区<br/>In-memory Buffer"]
    Buffer --> Refresh["4. Refresh（默认 1 秒）<br/>Buffer 生成新的 Lucene 段<br/>文档可被搜索"]
    Refresh --> Flush["5. Flush（默认 30 分钟）<br/>段写入磁盘<br/>清空 Translog"]
    Flush --> Merge["6. Merge（后台执行）<br/>合并小段<br/>清理删除文档"]

ORDER_ALIAS = 'orders-index'        # 查询别名
ORDER_WRITE_ALIAS = 'orders-write'  # 写入别名

# 2. 创建滚动索引（按天）
def create_daily_index(date_str):
    """创建每日订单索引"""
    index_name = f"{ORDER_INDEX_PREFIX}-{date_str}"
    
    # 创建索引并绑定别名
    es.indices.create(
        index=index_name,
        body={
            'settings': {
                'number_of_shards': 3,
                'number_of_replicas': 1,
                'refresh_interval': '5s'
            },
            'mappings': {
                'properties': {
                    'order_id': {'type': 'keyword'},
                    'user_id': {'type': 'keyword'},
                    'status': {'type': 'keyword'},
                    'amount': {'type': 'float'},
                    'created_at': {'type': 'date'},
                    'products': {'type': 'nested'}
                }
            },
            'aliases': {
                ORDER_ALIAS: {},  # 查询别名指向所有索引
                ORDER_WRITE_ALIAS: {'is_write_index': True}  # 写入到最新索引
            }
        }
    )

# 3. 写入订单（使用写入别名）
def create_order(order_data):
    """创建订单"""
    es.index(
        index=ORDER_WRITE_ALIAS,  # 使用别名，无需关心具体索引名
        id=order_data['order_id'],
        document=order_data
    )

# 4. 查询订单（使用查询别名）
def search_orders(query):
    """搜索订单"""
    return es.search(
        index=ORDER_ALIAS,  # 使用别名，自动搜索所有关联索引
        body=query
    )

# 5. 切换写入索引（零停机）
def rollover_write_index():
    """滚动到新的写入索引"""
    # 创建新索引
    new_date = datetime.now().strftime('%Y%m%d')
    create_daily_index(new_date)
    
    # 原子切换写入别名
    es.indices.update_aliases(body={
        'actions': [
            {
                'remove': {
                    'index': f'{ORDER_INDEX_PREFIX}-*',
                    'alias': ORDER_WRITE_ALIAS
                }
            },
            {
                'add': {
                    'index': f'{ORDER_INDEX_PREFIX}-{new_date}',
                    'alias': ORDER_WRITE_ALIAS
                }
            }
        ]
    })

9. 面试高频问题

Q1: Elasticsearch 为什么快？

参考回答：

1. 倒排索引
   - Term Index + Term Dictionary + Posting List
   - 快速定位文档

2. 分词 + 索引
   - 预先分词，无需运行时处理
   - Term Index 使用 FST 结构，内存占用小

3. 列式存储（Doc Values）
   - 聚合、排序不需要解析 JSON
   - 内存映射，高效访问

4. 分布式架构
   - 分片并行处理
   - 自动负载均衡

5. 缓存机制
   - Query Cache
   - Request Cache
   - Fielddata Cache

6. Page Cache
   - 操作系统文件缓存
   - 热数据常驻内存

Q2: ES 写入数据的流程？

参考回答：

1. 客户端发送请求到协调节点

2. 协调节点计算文档路由
   - shard = hash(routing) % primary_shards

3. 转发请求到主分片节点

4. 主分片节点：
   - 写入 Translog（确保持久化）
   - 写入内存缓冲区（In-memory Buffer）

5. 异步 Refresh（默认 1 秒）
   - Buffer → 新的 Lucene 段
   - 文档可被搜索

6. 同步到副本分片

7. 返回响应给客户端

8. 后台 Flush 和 Merge

Q3: ES 搜索数据的流程？

参考回答：

Query Then Fetch 两阶段：

Phase 1 - Query：
  1. 客户端发送请求到协调节点
  2. 协调节点将请求转发到所有相关分片
  3. 各分片执行搜索，返回文档 ID 和得分
  4. 协调节点合并排序，取 top N

Phase 2 - Fetch：
  5. 协调节点向相关分片请求完整文档
  6. 分片返回完整文档内容
  7. 协调节点组装结果返回客户端

优化：
  - 使用 routing 减少查询分片数
  - 使用 preference 控制查询节点
  - 使用 _source 过滤减少传输量

Q4: 如何解决深度分页问题？

参考回答：

问题：
  - from + size 不能超过 10000（默认）
  - 大 from 值需要排序大量数据，内存消耗大

解决方案：

1. Scroll API（适合全量导出）
   - 创建快照，适合离线处理
   - 不适合实时分页

2. search_after（适合实时分页）
   - 使用上一页最后一条的排序值
   - 只能顺序翻页，不能跳页

3. 调大 max_result_window
   - index.max_result_window = 20000
   - 不推荐，治标不治本

推荐方案：
  - 实时分页：search_after
  - 批量导出：scroll

Q5: ES 和 Solr 有什么区别？ 

┌─────────────────┬─────────────────────┬─────────────────────┐
│      对比项     │     Elasticsearch   │        Solr         │
├─────────────────┼─────────────────────┼─────────────────────┤

Q6: 如何保证 ES 数据不丢失？

   - 确保数据持久化

   - 主分片故障时，副本提升

3. 配置优化
   - translog.durability: request  # 每次请求刷盘
   - translog.sync_interval: 5s    # 同步间隔

4. 多节点部署
   - 至少 3 个节点
   - 跨机架/机房部署

5. 定期备份
   - 使用 Snapshot API
   - 备份到 S3/HDFS 等

Q7: text 和 keyword 类型的区别？

参考回答：

Text 类型：
  - 分词索引
  - 用于全文搜索
  - 使用 match 查询
  - 示例：文章内容、商品描述

Keyword 类型：
  - 不分词，整体索引
  - 用于精确匹配、排序、聚合

  - 示例：状态、标签、ID

组合使用：
  - text 类型 + fields.keyword 子字段
  - 同时支持全文搜索和精确匹配

Q9: 如何设计 ES 索引？

参考回答：

1. 分片数量
   - 单分片：10-50GB
   - 过多：资源消耗、协调开销
   - 过少：无法并行

2. 副本数量
   - 生产环境：至少 1 个
   - 高可用：2 个

3. 索引滚动
   - 按时间：logs-2024-01-01
   - 按 size：logs-000001, logs-000002

4. Mapping 设计
   - 禁用不需要的字段
   - 合理选择类型
   - 使用 keyword 替代 text（不需要分词）

5. 别名使用
   - 通过别名访问索引
   - 便于索引切换

Q10: ES 的脑裂问题是什么？如何解决？

参考回答：

问题描述：
  - 网络分区导致集群分裂
  - 多个节点认为自己是 Master
  - 数据不一致

解决方案：

1. ES 7.x+ 自动解决
   - 改进的 Raft 算法
   - 自动选举多数派 Master
   - 配置 discovery.seed_hosts

2. ES 6.x 及以下
   - 设置 minimum_master_nodes
   - 值 = master_eligible_nodes / 2 + 1

3. 网络优化
   - 节点间低延迟
   - 避免跨机房部署

4. 监控告警
   - 监控集群状态
   - 设置告警阈值

补充：常见面试追问

追问1: ES 的 Refresh 间隔为什么默认 1 秒？ 

原因：
  - 平衡实时性和性能
  - 每次 Refresh 创建新段，消耗资源
  - 太短：资源消耗大
  - 太长：搜索延迟高

调优建议：
  - 批量导入时：增大到 30s 或关闭
  - 实时搜索场景：保持 1s 或更短
  - 使用 index.refresh_interval 动态调整

追问2: ES 和传统数据库的选型？ 

选择 ES 的场景：
  ✓ 全文搜索
  ✓ 复杂聚合分析
  ✓ 日志分析
  ✓ 地理位置搜索
  ✓ 时序数据

选择传统数据库的场景：
  ✓ 事务支持
  ✓ 复杂关联查询
  ✓ 数据一致性要求高
  ✓ 数据频繁更新

常见方案：
  - MySQL + ES 双写
  - MySQL 作为主存储，ES 同步到 ES
  - 使用 Canal 等工具同步

追问3: ES 的冷热数据分离如何实现？ 

架构设计：
┌─────────────────────────────────────────────────────────────┐
│  Hot 节点（SSD）  │  Warm 节点（HDD）  │  Cold 节点（归档） │
│  - 最新数据      │  - 历史数据        │  - 冷数据归档     │
│  - 高性能        │  - 低成本          │  - 最低成本       │
│  - 高配置        │  - 中配置          │  - 低配置         │
└─────────────────────────────────────────────────────────────┘

实现方式：
1. 节点属性标记
   node.attr.data: hot/warm/cold

2. ILM 生命周期管理
   - hot phase: 高性能存储
   - warm phase: 迁移到 warm 节点
   - cold phase: 迁移到 cold 节点
   - delete phase: 删除

3. 分片分配过滤
   cluster.routing.allocation.require.data: hot
