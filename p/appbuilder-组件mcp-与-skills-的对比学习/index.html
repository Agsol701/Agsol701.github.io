AppBuilder 组件、MCP 与 Skills 的对比学习

May 02, 2026

写在前面

这篇文档里的“组件”，特指百度 AppBuilder SDK 仓库 python/core/components 目录下那类组件。

这里的组件，不是前端组件，也不是我前面误解成的“tool_eval 输入块”。这里更准确的定义应该是：

AppBuilder 中可被直接调用、可被编排、可作为工作流原子能力使用的能力组件。

比如仓库和文档里提到的这类能力：

  • 文档解析
  • 文档切分
  • 向量化
  • 检索
  • OCR
  • TTS
  • 高级问答增强组件

从这个语境看：

  • 组件 是可调用的能力单元
  • MCP 是能力接入协议
  • Skills 是任务方法和经验封装

它们三者不是同一个层面的概念。

一、AppBuilder 里的“组件”到底是什么

1.1 基本定义

在 AppBuilder 语境里，组件更接近：

一个对外暴露明确输入输出、可以直接运行、可以参与工作流编排的能力节点。

也就是说，它不是单纯的类文件集合，而是平台能力的代码化封装。

从官方仓库 README 可以看到，AppBuilder-SDK 提供了 40+ 个“源于百度生态的优质组件”，并且这些组件覆盖了构建 RAG 和 Agent 应用的多个阶段，比如文档解析、切片、向量化、召回、答案生成等。README 还明确写到 SDK 提供了 Message、Component、AgentRuntime 多级工作流抽象，用来实现工作流编排。
这说明这里的 Component 不是一个泛泛的概念，而是 SDK 的一层正式抽象。

1.2 它的关键特征

这类组件通常有几个明显特点：

  • 有明确的输入输出
  • 可以独立调用
  • 可以和其他组件串联
  • 可以被 Agent 或 Workflow 编排
  • 背后可能封装了模型能力、搜索能力或百度云服务能力

所以它更像“能力积木”，而不是“给模型看的说明块”。

1.3 可以怎么理解

如果用最直观的话说：

AppBuilder 组件，就是平台提前帮你封装好的可复用 AI 能力单元。

你不需要从零写：

  • OCR 服务调用
  • 文档解析流程
  • 向量检索逻辑
  • 某些增强问答能力

而是可以像调用 SDK 能力一样直接用这些组件。

二、这些组件一般用在什么场景

从仓库 README 展示的能力全景来看，这些组件主要用在两大类场景。

2.1 RAG 场景

这是最典型的场景。

README 中明确把组件映射到了 RAG 全流程：

  • 文档解析
  • 文档切片
  • 向量化
  • 索引构建
  • 切片召回
  • 答案生成

这说明 AppBuilder 的组件不是只给 Agent 用的，也非常适合搭建产业级 RAG 链路。

例如你可以把多个组件串起来：

  1. 先用解析组件处理文档
  2. 再用切分组件拆 chunk
  3. 再用 embedding 组件向量化
  4. 再用检索组件做召回
  5. 再交给问答或生成组件出答案

2.2 Agent 场景

README 同样提到：

  • 可以调用能力组件赋能 Agent 应用
  • 可以通过 AgentRuntime 做编排
  • 可以通过 ToolCall 联动本地组件和端云组件

这意味着这些组件也可以成为 Agent 的“可调用能力池”。

在这个语境里，组件通常扮演：

  • Agent 可直接调用的工具能力
  • 工作流中的处理节点
  • 模型能力之外的外部执行能力

三、这些组件怎么使用

3.1 直接调用

最直接的方式就是像 SDK 示例那样直接实例化组件，然后 run。

README 里给了类似下面这种模式：

  • 创建组件实例
  • 传入 Message
  • 调用 run
  • 获取结果

这说明组件的使用方式非常接近“函数化能力调用”。

3.2 作为工作流节点

README 里提到 Message、Component、AgentRuntime 多级抽象。

这意味着一个组件不只是“单次调用对象”，它还可以被放进更大的编排框架里，成为一个 workflow node。

这个视角下：

  • Message 更像数据载体
  • Component 更像能力节点
  • AgentRuntime 更像调度与执行容器

3.3 作为 Agent 工具能力

在 Agent 场景里，组件还可以被包装成模型可调用的能力。

这时模型不一定直接理解组件内部实现，但系统会告诉模型：

  • 有哪些组件能力可用
  • 哪个组件适合什么任务
  • 调用后会返回什么

所以组件也可以成为 tool-use 体系中的基础能力来源。

四、这些组件的实现原理是什么

4.1 表面上看：组件是 SDK 类

从代码结构上看，python/core/components 目录下的内容当然是代码模块和类实现。

但如果只把它理解成“一个 Python 类”，就太窄了。

4.2 本质上看：组件是平台能力的代码封装

更准确地说，它们的原理通常是：

  • 对底层模型或云服务能力做封装
  • 对输入输出做标准化
  • 对调用过程做统一接口抽象
  • 对编排场景做兼容

所以这些组件的真正价值，不在“它是一个类”，而在：

  • 它把底层能力产品化了
  • 它能被稳定复用
  • 它能参与编排

4.3 从工程上看

一个成熟组件通常会隐含这些工程特性：

  • 参数定义
  • 输入输出协议
  • 错误处理
  • 流式或非流式返回
  • 和 runtime / tracing / deployment 的兼容

这也是为什么它比“自己写一个小函数调 API”更像平台能力单元。

五、它和 MCP 有什么区别

这是最容易混淆的一点。

5.1 一句话区分

  • 组件 是可调用能力本身
  • MCP 是把能力暴露出来的一种标准协议

也就是说：

  • 组件回答“我能做什么”
  • MCP 回答“我怎么把这个能力标准化提供给外部系统”

5.2 AppBuilder 组件更像什么

AppBuilder 组件更像：

  • OCR 工具
  • 检索工具
  • 文档处理工具
  • 生成增强工具

它们是“能力实体”。

5.3 MCP 更像什么

MCP 更像：

  • 一套统一的接入规范
  • 一种 client/server 能力暴露方式
  • 一种让模型宿主发现并调用外部工具和资源的标准

它本身不等于某一个 OCR、检索或切分能力。

5.4 两者关系

两者的关系可以这样理解：

AppBuilder 组件可以被包装后通过 MCP 暴露，但组件本身不等于 MCP。

也就是说，一个组件未来完全可以：

  • 作为本地 SDK 能力直接调用
  • 也可以被包成一个 MCP tool 对外提供

所以：

  • 组件是“能力内容”
  • MCP 是“暴露方式”

六、它和 Skills 有什么区别

6.1 一句话区分

  • 组件 是能力单元
  • Skills 是任务方法包

组件偏执行，skills 偏策略。

6.2 组件在回答什么问题

组件更像在回答：

  • 我可以帮你做什么
  • 你给我什么输入
  • 我返回什么输出

6.3 Skills 在回答什么问题

skill 更像在回答：

  • 这类任务应该怎么做
  • 应该先调哪个能力
  • 哪些步骤不能省
  • 优先采用什么策略

6.4 两者关系

它们的关系通常是：

skill 会决定什么时候、按什么顺序去调用组件。

例如一个“企业问答 skill”可能规定：

  1. 先解析文档
  2. 再切分
  3. 再向量化
  4. 再检索
  5. 最后生成答案

这其中：

  • 解析、切分、向量化、检索、生成，都是组件
  • 这条顺序和方法，本身更像 skill

七、它和 tool_eval 的关系

这部分专门回应你前面的语境。

7.1 组件不是 tool_eval 组件本身

如果按 AppBuilder 的定义，组件首先是“可调用能力单元”。

它不是天然就等于：

  • tool_eval 的输入卡片
  • 模型可见说明块
  • 规则组件

7.2 但组件可以进入 tool_eval 链路

当一个 Agent 系统要让模型决定“调哪个能力”时，系统完全可以把某个 AppBuilder 组件描述成工具信息提供给模型。

这时会发生两层转换：

  1. 底层真实能力是 AppBuilder 组件
  2. 上层给模型看的，是这个组件的工具描述

所以更准确的说法应该是：

AppBuilder 组件是 tool_eval 可选择的候选能力来源，但不等于 tool_eval 输入层组件。

这个区别很重要。

八、放在同一个系统里怎么理解

一个完整系统里，三者可以这样协作：

8.1 组件负责能力执行

例如：

  • OCR 组件
  • 检索组件
  • 文档切分组件
  • 问答增强组件

8.2 MCP 负责标准化暴露

如果你希望这些能力被外部 agent、IDE 或其他宿主系统调用，就可以再用 MCP 包装出去。

8.3 Skills 负责策略和方法

如果你希望某类任务更稳定，例如“简历筛选”“企业问答”“代码审查”，就可以用 skill 规定：

  • 先调用哪些组件
  • 哪些参数优先
  • 哪些结果需要二次校验

九、一个最简对比表

维度 AppBuilder 组件 MCP Skills
本质 可调用能力单元 能力接入协议 任务方法包
关注点 做什么能力 怎么暴露能力 怎么组织能力
常见形态 OCR、解析、检索、TTS、问答增强 resources、tools、client/server SOP、模板、策略、规则
是否能直接执行任务 能，通常可以直接 run 不能，它只是协议 不能单独执行，通常要配合组件
是否适合工作流编排 非常适合 间接适合 适合做流程约束
与模型关系 可作为模型外部能力 可作为模型接外部世界的接口 可影响模型如何选择和调用能力

十、一个最准确的总结

如果完全贴着你给的仓库路径来理解，可以这样记：

AppBuilder 的 python/core/components 里的组件，是一组平台封装好的、可直接调用和可编排的 AI 能力单元。

然后再和另外两个概念区分：

  • MCP 不是能力本身，而是能力如何被标准化暴露
  • Skills 不是能力本身，而是任务如何组织这些能力

如果再压缩成三句：

  • 组件 是能力积木
  • MCP 是接口规范
  • Skills 是操作套路

十一、后续学习建议

如果我们后面继续围绕这篇文档学习，我建议下一步最值得补的是这两个方向：

  1. AppBuilder 组件的分类体系
  2. AppBuilder 组件如何进入 Agent / ToolCall / Workflow

第一部分会更偏“认识组件家族”。

第二部分会更偏“组件如何真正跑进 Agent 系统里”。
