RAG 监控、日志与评估体系详解：链路追踪、指标设计、效果评测与持续优化

source: rag-monitoring-logging-evaluation
May 08, 2026

写在前面

很多 RAG（Retrieval-Augmented Generation，检索增强生成）系统在 demo 阶段看起来效果不错，但一上线就会遇到一类更难的问题：

用户说答案不准，但你不知道到底是哪一步出了问题。

可能是文档没解析好。

可能是 chunk 切坏了。

可能是 embedding 没更新。

可能是召回没找对。

可能是 rerank 排错了。

也可能是证据都在上下文里，但模型生成时没有正确使用。

如果没有完整的日志、监控和评估体系，排查 RAG 问题很容易变成“凭感觉调 prompt”。

在完整 RAG 链路里，监控、日志和评估不是附属功能，而是系统能不能长期稳定运行的基础设施：

flowchart TD
  A["原始文档"] --> B["文档解析"]
  B --> C["文本切分"]
  C --> D["embedding 与索引"]
  D --> E["查询理解"]
  E --> F["召回"]
  F --> G["重排"]
  G --> H["上下文组装"]
  H --> I["大模型生成"]
  I --> J["答案后处理"]
  J --> K["用户反馈与评估"]

一、先理解 RAG 可观测性的目标

1.1 不是只看大模型回答对不对

很多系统最开始只记录：

1
2

用户问题
模型答案

这远远不够。

因为 RAG 的答案质量来自一条链路，而不是单个模型调用。

例如用户问：

1

Pro 套餐每月 API 调用额度是多少？

模型回答错了，可能有很多原因：

  • 知识库里没有这份文档
  • 文档解析时表格丢了
  • chunk 只保留了“Pro | 299 | 100 万”，但表头丢了
  • embedding 索引还没更新到最新版本
  • 召回召到了旧版本文档
  • rerank 把 Basic 套餐排到了 Pro 套餐前面
  • 上下文组装没有放入版本信息
  • prompt 没要求基于证据回答
  • 模型看到了证据但理解错了表格含义

如果只看最终答案，就无法判断到底应该修哪一层。

所以 RAG 可观测性的核心目标是：

让每一次问答都能被还原、定位、比较和复现。

1.2 日志、监控、评估分别解决什么

这三个概念经常混在一起，但职责不同。

日志解决的是：

某一次请求具体发生了什么。

例如：

  • 用户问了什么
  • 召回了哪些 chunk
  • 每个 chunk 的分数是多少
  • rerank 后顺序如何变化
  • 最终放进上下文的是哪些证据
  • 模型输入和输出是什么
  • 每一步耗时多少

监控解决的是：

系统整体是否稳定、是否变差、是否异常。

例如：

  • 请求量是否突增
  • P95（95th Percentile，第 95 百分位）延迟是否升高
  • 召回为空比例是否异常
  • embedding 调用失败率是否升高
  • token 成本是否超过预算
  • 用户负反馈是否上升

评估解决的是：

当前方案的效果到底好不好，改动以后是否变好了。

例如：

  • 召回 Recall@20（前 20 个结果的召回率）是否提升
  • rerank NDCG@10（前 10 个结果的归一化折损累计增益）是否提升
  • 上下文证据覆盖率是否提升
  • 答案忠实度是否提升
  • 幻觉率是否下降
  • 新版本是否比旧版本更适合上线

可以简单理解为：

1
2
3

日志：用于定位单个问题
监控：用于发现系统异常
评估：用于判断方案优劣

1.3 RAG 的可观测性必须按链路设计

普通后端服务通常关注：

  • QPS（Queries Per Second，每秒查询数）
  • 延迟
  • 错误率
  • CPU（Central Processing Unit，中央处理器）
  • 内存
  • 数据库连接数

这些对 RAG 也重要，但不够。

RAG 还需要关注效果链路：

flowchart TD
  A["文档是否进入知识库"] --> B["知识是否被正确解析和切分"]
  B --> C["正确 chunk 是否能被召回"]
  C --> D["正确 chunk 是否排在前面"]
  D --> E["正确证据是否进入上下文"]
  E --> F["模型是否基于证据回答"]
  F --> G["用户是否认可答案"]

这条链路里任何一步断掉，最终用户看到的都是“不准”。

所以监控和日志不能只围绕接口层做，而要覆盖从离线知识构建到在线问答的完整过程。

二、RAG 链路日志的基础设计

2.1 先统一请求标识

RAG 日志的第一原则是：

每一次用户问答都必须能通过一个 ID 串起来。

常见 ID 包括：

  • trace_id：一次完整请求链路的全局 ID
  • session_id：一次多轮会话的 ID
  • query_id：当前用户问题的 ID
  • user_id：用户 ID，生产中通常需要脱敏或哈希
  • tenant_id：租户或组织 ID
  • doc_id：原始文档 ID
  • chunk_id：知识片段 ID
  • index_version：索引版本
  • prompt_version：prompt 版本
  • model_version：模型版本
  • experiment_id：实验或 A/B 测试 ID

一次在线请求里，最重要的是 trace_id 和 query_id。

例如：

这样排查问题时，可以从最终答案一路追溯到召回、索引和原始文档。

2.2 日志要分层，不要只存一坨文本

RAG 日志至少可以分成四类。

第一类是请求日志：

  • 用户问题
  • 会话上下文
  • 用户权限
  • 业务入口
  • 实验分组

第二类是链路日志：

  • 查询理解结果
  • filter 条件
  • 各路召回结果
  • rerank 结果
  • 上下文组装结果
  • prompt 构造结果
  • 模型调用结果

第三类是系统日志：

  • 耗时
  • 错误码
  • 重试次数
  • 超时情况
  • 依赖服务状态

第四类是反馈日志：

  • 点赞点踩
  • 用户追问
  • 人工纠错
  • 是否采纳
  • 客服转人工
  • 业务转化结果

不要把所有内容只塞进一个 message 字段。

更好的方式是结构化记录：

2.3 日志要能复现一次回答

一个合格的 RAG 日志，至少应该能回答这几个问题：

  • 当时用户原始问题是什么
  • 查询是否被改写过
  • 使用了哪个知识库和索引版本
  • 召回候选有哪些
  • rerank 前后排序有什么变化
  • 哪些证据最终进入了 prompt
  • prompt 的完整结构是什么
  • 调用的是哪个模型
  • 模型参数是什么
  • 输出答案是什么
  • 后处理有没有改写答案

如果不能复现，就很难判断一次线上失败是偶发问题还是系统性问题。

2.4 原文内容和敏感信息怎么处理

RAG 日志经常包含业务文档和用户问题，里面可能有敏感信息。

所以要区分三类数据。

第一类是可直接记录的数据：

  • trace_id
  • 阶段名
  • 耗时
  • 状态码
  • 分数
  • 排名
  • token 数
  • 模型版本
  • 索引版本

第二类是需要脱敏的数据：

  • 用户 ID
  • 手机号
  • 邮箱
  • 姓名
  • 订单号
  • 合同号
  • 地址

第三类是需要按权限保存的数据：

  • 用户原始问题
  • 检索到的 chunk 内容
  • 完整 prompt
  • 模型完整回答
  • 内部文档原文

生产系统常见做法是：

  • 默认日志只保存 ID、分数、摘要和统计信息
  • 完整内容进入受控的 debug 日志或对象存储
  • debug 日志设置更短的保留周期
  • 对敏感字段做脱敏、加密或哈希
  • 只有具备权限的排障人员可以查看原文

不要为了排查方便，把所有用户问题和内部知识无差别写进普通日志。

2.5 如何平衡日志完整性和存储空间

RAG 日志有一个天然矛盾：

记录得太少，线上问题无法复现；记录得太多，日志成本、存储压力和数据风险都会快速上升。

尤其是 RAG 请求里经常包含：

  • 用户原始问题
  • 多轮会话历史
  • 召回候选列表
  • chunk 原文
  • rerank 中间结果
  • 最终上下文
  • 完整 prompt
  • 模型原始输出

这些内容如果每次请求都全量长期保存，空间会非常大。

更合理的原则是：

ID、版本、分数、排名、耗时全量保存；大文本、完整 prompt、chunk 原文分级保存、采样保存或外置保存。

2.5.2 哪些内容不应该默认全量长期保存

体积大、敏感度高、重复率高的内容，不建议默认全量长期保存。

典型包括：

  • 用户原始问题
  • 多轮对话全文
  • 召回 chunk 原文
  • 完整上下文
  • 完整 prompt
  • 模型原始输出
  • 内部文档原文

2.5.3 用采样控制完整日志体积

不是所有请求都需要保存完整 prompt 和完整上下文。

推荐策略是：

100% 保存失败请求的完整 debug 日志
100% 保存用户点踩请求的完整 debug 日志
100% 保存低置信请求的完整 debug 日志
100% 保存灰度实验样本的完整 debug 日志
1% 到 5% 保存正常请求的完整 debug 日志

低置信请求可以包括：

  • 召回为空
  • 最高 rerank 分低于阈值
  • 上下文证据数过少
  • 模型回答资料不足
  • 无引用答案
  • citation mismatch
  • fallback 触发
  • 总延迟超阈值

RAG 日志里最容易重复的是 chunk 原文。

2
3

2.6 日志中间件和技术架构怎么选

RAG 日志系统不要只选一个数据库硬扛所有需求。

因为 RAG 日志同时有几类不同访问模式：

  • 按 trace_id 查单次请求链路
  • 按时间窗口统计错误率、延迟、召回为空比例
  • 按租户、业务线、模型版本做聚合分析
  • 保存完整 prompt、context、answer 等大对象
  • 把高价值样本送入评估集和标注系统
  • 支持告警和看板

这些需求适合用分层架构解决。

2.6.1 推荐的整体架构

一个比较通用的架构是：

flowchart TD
  A["RAG 应用服务"] --> B["结构化日志 SDK / OpenTelemetry"]
  B --> C["日志采集 Agent"]
  C --> D["Kafka / Pulsar / 云消息队列"]
  D --> E["实时消费与清洗"]
  E --> F["日志检索系统 + OLAP 分析库 + 对象存储 + 指标监控系统"]
  F --> G["看板 / 告警 / 评估平台 / 标注平台"]

可以展开成：

flowchart TD

  C --> D["Kafka"]
  D --> E["Flink / Kafka Streams / Logstash"]
  E --> F["Elasticsearch / OpenSearch：查 trace 和排障"]
  E --> G["ClickHouse / Doris / BigQuery：聚合分析和报表"]
  E --> H["S3 / MinIO / OSS：保存完整 prompt、context、answer"]
  E --> I["Prometheus / Grafana：服务指标和告警"]
  E --> J["评估平台：沉淀失败样本、回归集、LLM-as-Judge 结果"]

其中每一层职责不同。

不要把完整 prompt、聚合指标、trace 检索、长期归档都塞进同一个系统。

2.6.2 日志检索用什么

如果目标是排查单次请求、搜索错误日志、按 trace_id 查看链路，常见选择是：

  • Elasticsearch
  • OpenSearch
  • Loki
  • Grafana Tempo

五、RAG 线上监控怎么做

5.1 监控要分四层

RAG 线上监控建议分成四层。

第一层是服务稳定性：

  • QPS
  • P50 / P95 / P99 延迟
  • 错误率
  • 超时率
  • 重试次数
  • 队列积压

第二层是依赖健康度：

  • embedding 服务成功率
  • 向量数据库延迟
  • 搜索引擎延迟
  • rerank 服务延迟
  • LLM 调用成功率
  • 对象存储或文档源访问状态

第三层是 RAG 链路质量：

  • 召回为空比例
  • rerank 后低分比例
  • 上下文 token 使用率
  • 无引用答案比例
  • 证据不足回答比例
  • fallback 触发比例

第四层是用户体验和业务结果：

  • 点赞率
  • 点踩率
  • 追问率
  • 用户改问率
  • 转人工率
  • 问题解决率
  • 业务转化率

只监控第一层是不够的。

RAG 服务可能接口全部 200，但答案质量已经明显变差。

  • rerank 服务慢了
  • LLM 输出太长
  • 多路召回串行执行了
  • 某个外部知识源超时

  • 使用更快模型
  • 返回“暂时无法查询完整知识”

5.3 成本监控要按请求和租户拆

RAG 成本不只来自 LLM。

常见成本包括：

  • 文档解析成本
  • OCR 成本
  • embedding 成本
  • 向量数据库存储成本
  • 搜索引擎成本
  • rerank 成本
  • LLM 输入 token 成本
  • LLM 输出 token 成本

在线请求至少要监控：

  • input_tokens
  • output_tokens
  • retrieved_candidate_count
  • rerank_candidate_count
  • context_token_count
  • cost_per_query
  • cost_per_tenant
  • cost_per_feature

query embedding 成本
+ rerank 候选数 * rerank 单价
+ LLM input tokens 成本
+ LLM output tokens 成本

如果没有成本监控，很容易出现：

  • top-k 调大后质量没提升，但成本翻倍
  • 上下文组装放太多重复证据
  • 输出答案过长导致成本异常
  • 某个租户知识库过大导致查询成本失控

5.4 质量监控要关注异常比例

线上质量不能完全依赖人工评估。

可以先监控一些自动化代理指标：

  • empty_retrieval_rate：召回为空比例
  • low_rerank_score_rate：最高 rerank 分低于阈值比例
  • no_citation_rate：无引用答案比例
  • insufficient_context_rate：模型回答资料不足比例
  • fallback_rate：降级或兜底比例
  • answer_too_short_rate：异常短答案比例
  • answer_too_long_rate：异常长答案比例
  • citation_mismatch_rate：引用不匹配比例
  • negative_feedback_rate：负反馈比例

这些指标不等于最终质量，但可以作为预警信号。

例如：

1

empty_retrieval_rate 从 3% 升到 18%

可能说明：

  • 新索引构建失败
  • metadata filter 改坏了
  • 查询改写模块异常
  • 向量数据库部分分片不可用

再例如：

1

no_citation_rate 从 8% 升到 35%

可能说明：

  • prompt 版本发生变化
  • 上下文证据包为空
  • 生成模型开始忽略引用要求
  • 后处理把引用过滤掉了

5.5 告警不要只按技术指标设置

RAG 告警可以分成三类。

第一类是硬故障告警：

  • LLM 调用失败率超过阈值
  • 向量库超时率超过阈值
  • 索引构建失败
  • 文档同步任务连续失败

第二类是质量异常告警：

  • 召回为空比例异常升高
  • 低置信答案比例异常升高
  • 点踩率异常升高
  • 某类意图问题解决率下降

第三类是成本异常告警：

  • 单请求 token 成本异常升高
  • 某租户日成本超过预算
  • rerank 候选数异常升高
  • 输出 token 异常增长

告警要尽量带上诊断信息。

例如不要只发：

1

RAG 质量异常

而应该包含：

baseline: 3.1%

影响索引版本: kb_20260516_0200

这样值班人员才能快速定位方向。

六、RAG 评估体系怎么搭建

6.1 评估要按链路拆开

RAG 评估最常见的错误是只评最终答案。

最终答案当然重要，但如果只评最终答案，你无法知道应该优化哪一层。

更合理的评估结构是：

flowchart TD
  A["数据质量评估"] --> B["解析质量评估"]
  B --> C["chunk 质量评估"]
  C --> D["召回评估"]
  D --> E["rerank 评估"]
  E --> F["上下文组装评估"]
  F --> G["生成答案评估"]
  G --> H["端到端用户体验评估"]

每一层都有自己的指标。

例如：

  • 召回看 Recall@K
  • rerank 看 MRR、NDCG@K
  • 上下文看证据覆盖率和 token 利用率
  • 生成看忠实度、正确性、完整性
  • 端到端看解决率、满意度、转人工率

  • 标准证据
  • 相关 chunk ID
  • 问题类型
  • 难度等级
  • 权限范围
  • 期望引用

第一类是真实用户问题：

  • 搜索日志
  • 客服工单
  • 用户追问
  • 点踩样本
  • 高频 FAQ

第二类是专家构造问题：

  • 产品规则
  • 政策条款
  • API 文档
  • 合同条款
  • 业务边界条件

第三类是失败案例沉淀：

  • 线上答错的问题
  • 召回为空的问题
  • 引用错误的问题
  • 用户明确纠正的问题

第四类是合成问题：

  • 从文档自动生成问答
  • 按章节生成覆盖性问题
  • 针对边界条件生成反例

合成问题可以提高覆盖率，但不能完全替代真实问题。

6.3 评估集要分层管理

不要把所有问题混成一个总分。

RAG 评估集最好按维度分层：

  • 按业务域：计费、权限、售后、API、合同
  • 按问题类型：事实查询、步骤说明、条件判断、对比总结、多跳推理
  • 按难度：简单、普通、困难、边界问题
  • 按知识形态：正文、表格、代码、图片 OCR、FAQ
  • 按权限：公开、内部、租户隔离、角色限定
  • 按时间敏感度：长期有效、版本相关、实时数据

这样才知道系统到底哪里强、哪里弱。

例如一个系统总准确率 82%，看起来还可以。

但拆开后可能是：

2
3
4

FAQ 类问题：94%
表格类问题：61%
多版本规则问题：58%
权限过滤问题：97%

这时优化方向就很明确。

6.4 评估集要有训练集和回归集

评估集不能只用一份。

通常至少分成：

  • dev set：日常调参和开发使用
  • regression set：每次上线前必须通过
  • challenge set：困难样本和边界样本
  • fresh set：最近线上新增问题

其中 regression set 要尽量稳定。

它的作用不是追求覆盖所有问题，而是防止改动破坏已有能力。

例如你优化了召回策略，必须确认：

  • 旧的 FAQ 问题没有变差
  • 权限过滤没有失效
  • 引用格式没有破坏
  • 成本和延迟没有超预算

七、检索、重排和上下文怎么评估

7.1 召回评估

召回评估关注：

正确证据有没有进入候选集。

常用指标包括：

  • Recall@K
  • Hit@K（前 K 个结果的命中率）
  • Precision@K（前 K 个结果的精确率）
  • MRR（Mean Reciprocal Rank，平均倒数排名）

最重要的是 Recall@K。

例如 Recall@20 的含义是：

1

在召回 top 20 里，是否包含回答问题所需的 gold chunk。

如果一个问题需要多个证据，可以定义：

1
2

All Evidence Recall@K：所有 gold chunk 都被召回
Any Evidence Recall@K：至少一个 gold chunk 被召回

例如：

1
2
3
4

问题：企业合同订单可以退款吗？
gold chunks：
1. 普通退款规则
2. 企业合同订单例外规则

只召回普通退款规则是不够的。

这时 Any Evidence Recall 可能通过，但 All Evidence Recall 不通过。

7.2 召回评估要分通道看

如果系统有多路召回，不能只看合并后的总分。

应该分别看：

  • BM25 Recall@K
  • Vector Recall@K
  • Hybrid Recall@K
  • Query Rewrite 后 Recall@K
  • Metadata Filter 后 Recall@K

例如：

1
2
3
4

BM25 Recall@20: 72%
Vector Recall@20: 81%
Hybrid Recall@20: 91%
Filter 后 Hybrid Recall@20: 76%

这个结果说明 hybrid 本身不错，但 filter 可能误杀了不少正确证据。

如果只看最终 76%，就会误以为召回算法不行。

7.3 rerank 评估

rerank 评估关注：

正确证据有没有被排到更靠前的位置。

常用指标包括：

  • MRR（Mean Reciprocal Rank，平均倒数排名）
  • NDCG@K（前 K 个结果的归一化折损累计增益）
  • Precision@K（前 K 个结果的精确率）
  • Recall@K（前 K 个结果的召回率）
  • Top-1 Accuracy（首位准确率）

MRR 关注第一个正确结果的位置。

例如：

1
2
3

正确 chunk 排第 1：得分 1
正确 chunk 排第 2：得分 1/2
正确 chunk 排第 5：得分 1/5

NDCG@K 更适合有多级相关性标注的场景。

例如：

  • 3 分：直接回答问题的证据
  • 2 分：有辅助信息
  • 1 分：弱相关
  • 0 分：无关

RAG 里 rerank 不只是把相关文档排前面，还要把“适合作为答案依据”的 chunk 排前面。

所以标注时要区分：

  • 语义相关
  • 可以回答
  • 权限正确
  • 版本正确
  • 条件完整

7.4 上下文组装评估

上下文组装评估关注：

最终进入 prompt 的证据是否足够、干净、完整。

常用指标包括：

  • Context Recall：gold chunk 是否进入上下文
  • Context Precision：上下文中有用证据占比
  • Evidence Coverage：必要证据覆盖率
  • Token Utilization：有效证据 token 占比
  • Redundancy Rate：重复证据比例
  • Citation Availability：证据是否具备可引用来源

例如：

1
2

Context Recall = 进入上下文的 gold chunk 数 / 所需 gold chunk 总数
Context Precision = 有用证据 chunk 数 / 上下文 chunk 总数

一个常见问题是：

1

召回 Recall@20 很高，但 Context Recall 很低。

这说明正确证据被召回了，但没有进入最终 prompt。

原因可能是：

  • rerank 排名靠后
  • token 预算不够
  • 去重误删
  • 上下文压缩丢失
  • 只取 top-k，没有做证据补全

这类问题不能靠调 embedding 解决。

八、生成答案怎么评估

8.1 最终答案不能只看“像不像”

RAG 生成评估至少要看四个维度。

第一是正确性：

答案是否回答了用户问题。

第二是忠实度：

答案是否严格基于给定证据，没有编造。

第三是完整性：

是否包含必要条件、例外、时间、范围、单位。

第四是可引用性：

答案是否给出了正确来源，引用是否能支撑对应结论。

例如用户问：

1

Pro 套餐每月 API 调用额度是多少？

答案：

1

Pro 套餐每月包含 100 万次 API 调用。

如果证据里还写了“按自然月统计”，那这个答案可能正确但不够完整。

如果答案写成“每天 100 万次”，那就是事实错误。

如果答案写对了但引用了 Basic 套餐文档，那就是引用错误。

8.2 常见生成评估指标

常见指标包括：

  • Answer Correctness（答案正确性）
  • Faithfulness（忠实度）
  • Groundedness
  • Completeness
  • Citation Accuracy
  • Refusal Accuracy
  • Format Compliance
  • Safety Compliance

可以用 0 到 2 分或 0 到 5 分标注。

例如 Faithfulness：

1
2
3

2 分：所有关键结论都能被证据支持
1 分：大部分结论有证据，存在轻微信息扩展
0 分：包含明显无证据支持的结论

Completeness：

1
2
3

2 分：覆盖结论、条件、限制、例外
1 分：覆盖主要结论，但遗漏部分条件
0 分：缺失关键信息，可能误导用户

Citation Accuracy：

1
2
3

2 分：引用能直接支持对应结论
1 分：引用相关但不够直接
0 分：引用错误或没有引用

8.3 LLM-as-Judge 可以用，但不能盲信

使用大模型做自动评估很常见。

一个评估 prompt 可以让 judge 模型输入：

  • 用户问题
  • 标准答案
  • 检索证据
  • 被评估答案
  • 评分标准

然后输出：

1
2
3
4
5
6
7

{
  "correctness": 2,
  "faithfulness": 2,
  "completeness": 1,
  "citation_accuracy": 2,
  "reason": "答案正确说明了额度，但遗漏了按自然月统计。"
}

但 LLM-as-Judge 有几个问题：

  • 不同 judge 模型打分不一致
  • prompt 变化会影响分数
  • 对细微业务规则可能判断不准
  • 容易被流畅答案误导
  • 成本较高

所以更稳的方式是：

  • 关键回归集使用人工标注
  • 大规模样本使用 LLM 初评
  • 对低置信或分歧样本人工复核
  • 固定 judge 模型和 judge prompt 版本
  • 定期抽样校准 judge 与人工一致率

不要把 LLM-as-Judge 当成绝对真值。

8.4 幻觉评估要看证据支撑

RAG 里的幻觉不只是“答案离谱”。

更常见的是：

  • 答案包含证据没有提到的条件
  • 把旧版本规则当成新版本
  • 把普通用户规则套到企业用户
  • 把多个文档的内容错误合并
  • 数字、日期、单位写错
  • 引用了 A 文档，却回答了 B 文档的内容

所以幻觉评估的关键是：

答案中的每个关键声明是否能被上下文证据支持。

可以把答案拆成 claims。

例如答案：

1

Pro 套餐每月包含 100 万次 API 调用，按自然月统计，超出后按量计费。

可以拆成：

1
2
3

claim_1: Pro 套餐每月包含 100 万次 API 调用
claim_2: API 调用按自然月统计
claim_3: 超出后按量计费

然后逐条判断：

  • 是否有证据支持
  • 证据 ID 是什么
  • 是否存在冲突证据
  • 是否有版本或权限限制

这种 claim-level 评估比只评整体答案更精细。

九、用户反馈和人工标注闭环

9.1 用户反馈不能只做点赞点踩

点赞点踩有用，但信息量太低。

  • 答案有帮助 / 没帮助
  • 答案不准确
  • 答案不完整
  • 引用不对
  • 没有回答问题
  • 内容过期
  • 权限不该看到
  • 用户手动改写后的正确答案

例如点踩后让用户选择原因：

- 答案缺少关键信息
- 引用资料不对
- 没找到我想问的内容
- 回答太长或太绕

这些反馈可以反向定位问题层级。

例如：

  • “没找到内容”多，优先看召回和知识覆盖
  • “引用不对”多，优先看上下文和引用映射
  • “内容过期”多，优先看索引更新和版本过滤
  • “回答太绕”多，优先看生成 prompt 和输出格式

9.2 点踩样本要进入评估集

这样累计一段时间后，就能知道系统主要瓶颈在哪里。

9.3 人工标注要标证据，不只是标答案

很多团队做评估时只标标准答案。

但对 RAG 来说，还应该标标准证据。

至少包括：

  • 正确答案

最后只能评端到端答案，但不知道中间哪里坏了。

每次改动都要能回答：

10.1 每次上线前做离线回归

RAG 系统里这些改动都应该触发回归测试：

  • rerank 模型变化
  • 上下文组装策略变化
  • prompt 变化
  • LLM 模型变化
  • metadata filter 变化
  • 知识库批量更新

回归测试至少输出：

  • 召回指标变化
  • rerank 指标变化
  • 上下文指标变化
  • 答案指标变化
  • 延迟变化
  • 成本变化
  • 失败样本列表

十一、常见工程坑

11.1 只记录最终答案，不记录中间证据

这是最常见的问题。

用户反馈答案错了，但你只能看到：

1
2

Q: Pro 套餐额度是多少？
A: Pro 套餐每月 80 万次。

你不知道：

  • 是否召回了旧文档
  • 是否新文档没入库
  • 是否上下文里同时有新旧规则
  • 是否模型自己编了一个数字

正确做法是记录：

  • 召回 top-k
  • rerank top-k
  • context selected chunks
  • prompt version
  • model version
  • citation mapping

11.2 日志没有版本字段

RAG 系统版本很多。

如果日志里没有版本字段，评估和排障会非常困难。

至少要有：

  • index_version
  • chunker_version
  • embedding_model_version
  • retrieval_config_version
  • reranker_version
  • context_builder_version
  • prompt_version
  • llm_model_version

否则某个答案为什么变了，很难说清楚。

11.3 评估集只覆盖简单 FAQ

很多评估集只包含：

1
2

问题：如何重置密码？
答案：进入设置页重置密码。

这种问题太简单，容易高估系统效果。

真实 RAG 还需要覆盖：

  • 多条件问题
  • 表格问题
  • 版本问题
  • 权限问题
  • 例外规则
  • 多文档综合
  • 不可回答问题
  • 易混淆问题

否则上线后会发现评估分很高，但用户仍然觉得不好用。

11.4 只看平均分，不看分桶指标

总准确率可能掩盖很多问题。

例如：

1

整体正确率：85%

看起来不错。

但分桶后可能是：

1
2
3
4
5

普通 FAQ：96%
API 错误码：89%
合同条款：71%
表格问答：58%
多版本政策：52%

优化 RAG 一定要看分桶指标。

否则很容易在已经很好的简单问题上继续优化，却忽略真正影响业务的问题。

11.5 用线上用户反馈直接当准确率

点赞率和点踩率不是准确率。

因为：

  • 很多用户不会反馈
  • 用户点踩可能是答案太长，不一定是错
  • 用户点赞也可能只是觉得态度好
  • 不同入口用户反馈习惯不同
  • 新用户和专家用户标准不同

用户反馈适合做趋势监控和样本发现。

准确率评估仍然需要标准答案、标准证据和一致的评测规则。

11.6 调 prompt 掩盖检索问题

如果正确证据没有被召回，prompt 很难救。

排查顺序应该是：

1
2
3
4
5
6

1. 知识库里有没有正确内容
2. 正确内容有没有被解析和切分好
3. 正确 chunk 有没有被召回
4. 正确 chunk 有没有被 rerank 排前
5. 正确证据有没有进入上下文
6. 模型有没有基于证据回答

只有前面都没问题时，再重点调 prompt 和模型。

十二、一个推荐的落地流程

12.1 第一阶段：先把日志打全

如果系统还没有可观测性，第一步不是做复杂评估，而是先补齐链路日志。

最小可用日志包括：

  • trace_id
  • 用户问题
  • 索引版本
  • 召回 top-k chunk ID
  • rerank top-k chunk ID
  • 最终上下文 chunk ID
  • prompt 版本
  • 模型版本
  • token 数
  • 延迟
  • 最终答案
  • 用户反馈

有了这些，至少能排查大部分线上问题。

12.2 第二阶段：建立核心监控

先做最关键的监控：

  • 总请求量
  • 成功率
  • P95 延迟
  • LLM 调用失败率
  • 召回为空比例
  • 无引用答案比例
  • 点踩率
  • 单请求平均 token
  • 索引构建失败数

这些指标可以覆盖稳定性、质量和成本的基本风险。

12.3 第三阶段：构建评估集

从真实问题开始，先积累 100 到 300 条高质量评估样本。

每条样本至少包含：

  • 问题

十三、高频面试题

13.1 RAG 系统线上答案错了，你怎么排查

按链路排查：

  1. 查 trace_id，还原用户问题、索引版本、prompt 版本和模型版本
  2. 看知识库是否有正确文档
  3. 看文档解析和 chunk 是否保留了正确信息
  4. 看召回 top-k 是否包含 gold chunk
  5. 看 rerank 是否把正确 chunk 排到前面
  6. 看上下文组装是否把正确证据放进 prompt
  7. 看模型是否基于证据回答
  8. 看后处理是否改坏答案
  9. 把失败样本加入回归集

核心原则是先定位失败阶段，再优化对应模块。

13.2 RAG 应该记录哪些日志

至少记录：

  • 请求 ID、会话 ID、用户和租户信息
  • 用户原始问题和改写问题
  • metadata filter 条件
  • 各路召回结果和分数
  • 合并去重结果
  • rerank 前后排名和分数
  • 最终上下文证据和 token 数
  • prompt 版本、模型版本和模型参数
  • 模型输出、后处理结果
  • 各阶段耗时、错误和重试
  • 用户反馈和人工标注结果

生产中要注意隐私、脱敏、权限和日志保留周期。

13.3 如何评估 RAG 的召回效果

先构建带 gold chunk 的评估集。

然后计算：

  • Recall@K
  • Hit@K
  • MRR
  • Precision@K

如果问题需要多个证据，还要区分：

  • Any Evidence Recall
  • All Evidence Recall

多路召回要分别看 BM25、向量、hybrid、filter 后的指标，不能只看最终总分。

13.4 如何评估 RAG 最终答案质量

通常从四个维度评估：

  • 正确性：是否回答问题
  • 忠实度：是否基于证据
  • 完整性：是否覆盖条件和例外
  • 引用准确性：引用是否支撑结论

可以结合人工评估和 LLM-as-Judge。

关键回归集建议人工复核，大规模样本可以用 LLM 初评。

13.5 为什么离线评估很好，线上效果仍然不好

常见原因包括：

  • 离线评估集太简单
  • 评估集没有覆盖真实用户表达
  • 没有覆盖多轮对话
  • 没有覆盖权限和版本问题
  • 线上知识库与离线索引版本不一致
  • 线上 latency 限制导致 top-k 或 rerank 被降级
  • 用户反馈标准和离线评分标准不同

所以离线评估、线上监控和 A/B 测试要一起看。

13.6 RAG 的监控指标怎么设计

可以分四层：

  • 服务稳定性：QPS、错误率、P95 延迟、超时率
  • 依赖健康度：向量库、搜索引擎、rerank、LLM 的成功率和延迟
  • 链路质量：召回为空比例、低分比例、无引用比例、fallback 比例
  • 用户体验：点赞率、点踩率、追问率、转人工率、问题解决率

同时要监控成本：

  • input tokens
  • output tokens
  • context tokens
  • rerank 候选数
  • 单请求成本
  • 租户成本

总结

RAG 的效果问题通常不是一个点的问题，而是一整条链路的问题。

所以一个成熟的 RAG 系统，不能只关注“模型回答得好不好”，还要能回答：

  • 知识有没有正确进入系统
  • 文档有没有解析好
  • chunk 有没有切好
  • 正确证据有没有被召回
  • 正确证据有没有排到前面
  • 最终上下文有没有包含必要证据
  • 模型有没有基于证据回答
  • 用户是否认可答案
  • 新版本是否真的比旧版本更好

日志让单次问题可追溯。

监控让系统异常可发现。

评估让方案改动可比较。

这三者合在一起，才是 RAG 从 demo 走向生产系统的关键基础设施。
