从 Agent Loop 到完整 Harness：拆解 Claude Code 的架构与实现

source: claude-code-architecture-and-implementation
Jul 01, 2026

写在前面

Claude Code 看起来像一个终端聊天框，但“聊天”只是入口。它真正有价值的部分，是让模型能够在代码库里反复观察、行动、验证，直到完成任务。

理解这类产品时，一个常见误区是把所有能力都归因于外围编排：只要堆足够多的 Prompt、工作流和条件分支，就能“造出智能”。另一个误区则恰好相反：只谈模型能力，忽略工具、上下文和权限对实际效果的决定性影响。

更准确的表达是：

1

编码 Agent 产品 = 模型 + Agent Harness

模型负责判断下一步做什么；Harness（运行支架）负责提供工作环境，包括工具、知识、观察结果、权限边界和持久状态。

本文结合开源教学项目 shareAI-lab/learn-claude-code，从可以运行的代码出发，解释一个类 Claude Code 系统如何从最小循环逐步长成完整运行时。

需要先说明边界：learn-claude-code 不是 Anthropic 官方仓库，也不是 Claude Code 源码复刻。它是一个用于学习 Harness Engineering 的独立实现。本文所说的“实现”，默认指该教学仓库中的实现；涉及 Claude Code 产品能力时，以 Anthropic 官方文档 为准。

本文核对的教学仓库版本为 0dcafa2ae053a1ddd6a72f265431104b08a5aa13。仓库仍在更新，章节和代码可能继续变化。

一、先把 Agent 还原成一个循环

1.1 最小闭环

learn-claude-code 的第一章只有一个 Bash 工具和一个循环。删去异常处理、终端输出等细节后，核心结构可以概括为：

def agent_loop(messages):
    while True:
        response = model(messages=messages, tools=tools)
        messages.append(as_assistant_message(response))

        calls = find_tool_calls(response)
        if not calls:
            return

        results = [execute(call) for call in calls]
        messages.append(as_tool_results(results))

这个循环只有四步：

  1. 把当前消息和工具定义交给模型。
  2. 模型返回文本或结构化工具调用。
  3. Harness 执行工具，并把结果追加到消息历史。
  4. 再次调用模型，直到模型不再请求工具。
flowchart LR
    U[用户目标] --> M[模型推理]
    M --> D{包含工具调用?}
    D -- 是 --> T[Harness 执行工具]
    T --> O[结果写回 messages]
    O --> M
    D -- 否 --> R[返回最终回答]

这里最重要的设计不是 while True，而是停止权和决策权在模型一侧。Harness 不应把“先搜索、再读文件、再改代码、最后测试”硬编码成唯一流程。面对不同任务，模型可以自行决定工具调用的次序和次数。

当然，模型有决策权不等于它拥有无限权限。能不能执行、是否需要审批、结果如何裁剪，仍由 Harness 控制。后文会看到，这正是权限、Hooks 和上下文管理存在的原因。

1.2 messages 是运行中的状态

在这个最小实现里，messages 不只是聊天记录，它也是 Agent 的短期工作记忆：

  • 用户消息描述目标；
  • assistant 消息保存模型的文字和 tool_use；
  • tool result 保存 Shell 输出、文件内容和错误；
  • 下一轮模型调用基于这些观察继续决策。

因此，工具执行结果必须与对应的调用 ID 正确配对，消息顺序也不能随意破坏。否则模型会失去“我刚才做了什么、环境返回了什么”的因果链。

1.3 为什么 Bash 已经足以形成 Agent

Bash 几乎可以间接完成所有本地编码动作：列目录、搜索、读写文件、运行测试、调用 Git。只要模型会正确使用 Shell，一个工具就能构成可工作的编码 Agent。

但“能工作”不等于“适合生产”：Shell 参数是自由文本；读取大文件缺少输出边界；文件修改难以表达精确意图；所有动作都走 Shell，也不利于权限分类和审计。

所以第二章没有修改 Agent Loop，而是增加 read、write、edit、glob 等原子工具。

二、工具系统：给模型一组清晰的动作接口

2.1 Schema、Handler 和结果协议

一个工具至少包含三部分：

部分 作用
工具 Schema 告诉模型工具名称、用途和参数格式
Handler 在宿主环境中执行真实动作
Tool result 把成功、失败和输出返回给模型

教学实现用分发表把工具名称映射到 Python 函数：

1

TOOL_HANDLERS = {
    "bash": run_bash,
    "read": run_read,
    "write": run_write,
    "edit": run_edit,
    "glob": run_glob,
}

新增工具时，只需要补充 Schema 和 Handler，主循环不必知道工具内部细节。这是一个很小但很重要的架构边界：循环负责调度，工具负责能力。

2.2 好工具应当原子、可组合、可观察

把文件操作拆成 read、write、edit，比提供一个含糊的 manage_project 更适合模型使用：参数更容易生成正确，风险等级更容易判断，日志能明确记录动作，失败后也可以只重试一步。

Handler 不应让异常直接导致进程崩溃。文件不存在、旧文本不唯一、命令超时等情况，都应该转换为模型可理解的观察结果，让 Agent 有机会修正策略。

2.3 路径约束必须在工具层落实

教学代码中的文件工具会解析路径，并检查它是否位于工作目录内。这比在 System Prompt 中写一句“不要访问项目外文件”可靠得多。

Prompt 是行为指导，代码检查才是安全边界。任何涉及文件系统、网络、数据库或外部账户的能力，都应该遵循这个原则。

三、权限与 Hooks：自由行动不等于无边界

3.1 权限决策管线

第三章把工具调用分为三类：

flowchart TD
    C[模型请求调用工具] --> R{权限规则}
    R -- allow --> E[直接执行]
    R -- ask --> A[请求用户批准]
    R -- deny --> X[拒绝并返回原因]
    A -- 批准 --> E
    A -- 拒绝 --> X
    E --> O[结果返回模型]
    X --> O

一个实用的权限系统需要按工具和参数匹配规则，明确区分允许、拒绝和询问，并把拒绝原因返回给模型，使其寻找替代方案。对删除、覆盖、外部写入等不可逆操作，则应提高门槛。

教学代码用字符串和正则识别危险 Shell 命令，适合解释机制，但不是完整沙箱。生产实现还需要操作系统隔离、工作目录限制、环境变量治理、网络策略和审计日志。

3.2 Hooks 环绕核心循环

如果每增加一项横切能力就修改 Agent Loop，核心很快会变成无法维护的条件分支。第四章因此引入四类生命周期事件：

  • UserPromptSubmit：用户请求进入循环前；
  • PreToolUse：工具执行前；
  • PostToolUse：工具执行后；
  • Stop：Agent 停止时。
sequenceDiagram
    participant U as 用户
    participant H as Hooks
    participant L as Agent Loop
    participant T as Tool
    U->>H: UserPromptSubmit
    H->>L: 注入补充上下文
    L->>H: PreToolUse
    H->>T: 允许执行
    T->>H: PostToolUse
    H->>L: 处理后的观察结果
    L->>H: Stop
    H->>U: 总结或记录

权限检查、调用日志、大输出截断和停止总结都可以注册为 Hook。关键原则是：Hook 围绕循环扩展，不重写循环本身。

Hooks 也不能取代权限系统。日志、格式化等 Hook 可以失败后继续，而安全 Hook 往往必须 fail closed；两者需要明确的执行顺序和异常策略。

四、复杂任务：Todo、子 Agent 与上下文压缩

4.1 Todo 是可见的短期计划

跨模块任务容易漂移。第五章增加 todo_write 工具，让模型维护带状态的步骤列表。它把隐含计划变成可检查状态：是否遗漏验证、当前正在做什么、哪些项目已完成、结束时是否仍有未完成项。

教学实现还约束同一时间最多一个 in_progress 项，并在退出时提示未完成 Todo。这是一种轻量的完成度检查，但仍依赖模型诚实更新状态。

4.2 子 Agent 的本质是隔离上下文

第六章将 task 暴露为普通工具。主 Agent 调用它时，Harness 创建全新的 messages，运行一个独立循环，最后只把子 Agent 的最终文本作为工具结果交回主 Agent。

flowchart LR
    P[主 Agent 上下文] -->|task prompt| S[子 Agent 新 messages]
    S --> ST[独立使用工具]
    ST --> SR[最终文本]
    SR -->|一个 tool result| P

子任务中的大量搜索不会污染主上下文，主 Agent 只接收结论。因此，子 Agent 首先是一种上下文工程手段，其次才是并行手段。如果任务很小、共享状态很多，拆分反而会增加信息损失和协调成本。

4.3 上下文压缩不是简单删除历史

第八章实现了分层压缩：

  1. 将较大的工具结果写入磁盘，只保留预览和路径。
  2. 对过长结果做裁剪。
  3. 清理更早的工具输出，保留近期观察。
  4. 若仍超预算，让模型生成结构化摘要并替换旧历史。

好的摘要至少要保留用户目标、已完成修改、关键决定、失败尝试、当前文件状态和下一步。否则 token 数虽然降低，Agent 却可能重复劳动，甚至撤销已经完成的工作。

上下文窗口再大，压缩仍然必要：瓶颈不只是“能不能塞下”，还包括注意力是否集中、请求成本是否稳定、旧输出是否淹没当前证据。

五、知识与记忆：按需加载，跨会话沉淀

5.1 Skill 采用两阶段加载

第七章扫描 Skill 目录中的元数据，只把名称和简介放入初始 System Prompt。模型判断相关后，再调用工具加载完整说明。

flowchart LR
    S[扫描 Skill 元数据] --> C[小型能力目录]
    C --> M[模型选择相关 Skill]
    M --> L[加载完整 SKILL.md]
    L --> A[按工作流执行]

这是一种渐进式披露：先知道“有什么”，需要时再知道“具体怎么做”。Skill 与工具的职责也不同：工具提供动作接口，Skill 提供使用这些动作的领域知识和流程。

5.2 Memory 包含选择、提取和合并

第九章把跨会话记忆拆成三个子系统：

  • Selection：会话开始时选择与请求相关的记忆；
  • Extraction：会话结束后提取值得复用的信息；
  • Consolidation：合并重复内容并清理过时信息。

构建命令、稳定的架构约束、反复验证过的排障结论值得记住；临时日志、猜测、一次性凭证和可从仓库直接读取的内容通常不值得。

记忆是缓存，不是真相源。它必须允许更新、覆盖和删除，使用时也应与当前代码和文档核对。

六、长任务：持久任务图、后台执行与定时调度

6.1 Task System 把计划变成持久状态

Todo 适合单次会话，真正的长任务还需要磁盘持久化和依赖关系。第十章中的 Task 包含 ID、主题、描述、状态、负责人和 blockedBy。

flowchart LR
    A[分析需求] --> B[实现后端]
    A --> C[实现前端]
    B --> D[集成测试]
    C --> D

只有依赖全部完成的任务才可认领。任务图让进度能够跨会话恢复，也为多 Agent 协作提供共同状态。系统必须防御两个 Worker 同时认领同一任务，以及依赖更新形成环；教学实现用文件锁和依赖检查展示了基本处理方式。

6.2 后台任务让循环保持响应

测试、构建和服务启动可能持续很久。第十一章将慢命令放入后台线程，完成后写入通知队列；主循环再把通知注入 messages。

工具第一次返回的是“任务已启动”，之后才收到真实结果。因此还必须处理进程组终止、退出码、超时、通知去重和会话结束时的资源清理。

6.3 Cron 是时间驱动的任务入口

第十二章增加定时任务。调度器只判断何时到期并把 Prompt 放入队列，真正任务仍交给同一个 Agent Loop。Cron 负责触发，Agent 负责决策，工具负责执行。

持久定时任务还要保存到磁盘，并记录某一分钟是否已经触发，以避免重启或重复轮询造成二次执行。

七、多 Agent：协议、原子认领与工作区隔离

第十三章不只是“同时启动几个线程”，而是补齐协作所需的基础设施：持久化队友和收件箱、消息协议、任务依赖与原子认领、负责人状态、任务绑定 Git worktree，以及结果回传和资源清理。

flowchart TD
    L[主 Agent] --> Q[共享任务图]
    A[队友 A] -->|原子认领| Q
    B[队友 B] -->|原子认领| Q
    Q --> WA[任务 Worktree A]
    Q --> WB[任务 Worktree B]
    A <--> MA[Mailbox A]
    B <--> MB[Mailbox B]
    L <--> MA
    L <--> MB

多 Agent 系统的难点不是创建 Agent，而是避免互相踩踏：认领必须原子化；每个 Agent 的当前任务要清晰；并行修改最好进入独立目录；消息需要接收者、类型和确认机制；删除 worktree 前必须检查未提交修改。

如果这些条件不成立，更多 Agent 通常只意味着更多冲突、重复劳动和上下文成本。

八、MCP：把外部能力并入同一个工具池

第十四章展示了一个小型 MCP 客户端和两个 Mock Server。连接过程分为三步：连接 Server 并发现工具；给工具名加命名空间避免重名；将远程 Schema 与本地工具合并，再把调用路由回对应 Server。

flowchart LR
    M[模型] --> P[统一工具池]
    P --> L[本地 read / edit / bash]
    P --> D[mcp__docs__search]
    P --> X[mcp__deploy__release]
    D --> DS[Docs Server]
    X --> DP[Deploy Server]

MCP 改变的是能力来源，不应改变 Agent Loop。对模型而言，本地工具和 MCP 工具都是带 Schema 的动作；对 Harness 而言，差异主要存在于发现、连接、命名、超时、认证和权限边界。

外部工具尤其要警惕信任升级：读取公开文档与部署生产环境显然不是同一风险等级。MCP Server 声明了能力，不代表 Harness 应无条件授权。

九、集成运行时：很多机制，仍然只有一个循环

第十五章把工具、权限、Hooks、Skills、压缩、记忆、任务、后台执行、定时器、团队和 MCP 重新接回一个 Harness。它说明这些机制都可以围绕稳定的核心循环组合。

flowchart TD
    UI[CLI / IDE / Web] --> LOOP[Agent Loop]
    LOOP <--> CTX[Context<br/>messages / compact / memory]
    LOOP --> GOV[Governance<br/>permission / hooks]
    GOV --> POOL[Tool Pool]
    POOL --> LOCAL[文件 / Shell / Git]
    POOL --> EXT[Skills / Subagent / MCP]
    LOOP <--> STATE[Task / Background / Cron / Team]

完整 Harness 可以分成五个平面：

平面 负责什么 典型机制
决策平面 选择下一步和停止时机 模型、Agent Loop
行动平面 改变或查询环境 文件、Shell、Git、MCP
上下文平面 当前证据和长期知识 messages、压缩、Skills、Memory
控制平面 限制和观察动作 Permission、Hooks、日志
状态平面 跨轮次、长任务和协作 Task、Background、Cron、Team

这种划分比按 CLI、IDE、Web 来理解更接近本质：界面可以更换，运行时的几个平面仍然存在。

十、什么时候不该让模型自由编排

“让模型决定下一步”不意味着所有流程都应该交给自由循环。

第十六章引入 Workflow Runtime：当编排形状固定、需要恢复和审计时，把流程写成代码更合适。例如发布流程可能始终要求按顺序完成构建、测试、审批和部署。

教学实现加入输入 Schema 校验、生命周期事件、预算和执行限制、Journal 持久化、断点恢复，并将工作流本身注册为 Agent 工具。

场景 更合适的控制方式
探索陌生代码、定位未知故障 Agent Loop
固定发布步骤、合规审批流程 Workflow
流程固定，但某一步需要判断 Workflow 调用 Agent
Agent 需要启动可恢复流程 Agent 调用 Workflow Tool

原则很朴素：未知路径交给模型探索，已知路径交给代码约束。

十一、Goal Loop：模型说“完成了”还不够

普通 Agent Loop 在模型不再返回工具调用时停止。这是协议层停止条件，却不一定代表用户目标真的完成。

第十七章在外层加入独立 Goal Controller：主会话准备停止时，Evaluator 根据目标和轨迹判断是否达成。如果尚未完成，就生成继续工作的反馈并把控制权交还主循环。

flowchart TD
    G[用户设定 Goal] --> A[Agent Session]
    A --> S[提出停止]
    S --> E[独立 Evaluator]
    E -- achieved --> C[标记完成]
    E -- continue --> F[生成缺口反馈]
    F --> A
    E -- impossible / failed / over limit --> U[交还用户]

它把“对话结束”和“目标完成”区分开，也增加预算、最大续跑次数和失败状态。Evaluator 仍可能误判，所以高风险任务还应使用确定性证据：测试是否通过、产物是否存在、部署状态是否成功，而不是只相信另一轮模型判断。

十二、17 章的演进路线

当前主线从 s01 到 s17，每章隔离一个机制：

章节 新增机制 解决的问题
s01 Agent Loop + Bash 形成观察—行动闭环
s02 原子工具与分发表 扩展能力而不改主循环
s03 Permission 控制允许、拒绝与审批
s04 Hooks 注入横切逻辑
s05 TodoWrite 显式维护短期计划
s06 Subagent 隔离子任务上下文
s07 Skill Loading 按需加载领域知识
s08 Context Compact 控制长会话上下文
s09 Memory 跨会话复用经验
s10 Task System 持久任务和依赖图
s11 Background Tasks 非阻塞执行慢操作
s12 Cron Scheduler 时间驱动任务
s13 Agent Teams 多 Agent 协作与隔离
s14 MCP Plugin 发现并路由外部工具
s15 Integrated Harness 将机制接回统一循环

flowchart LR
    A[能行动] --> B[有边界]
    B --> C[能处理复杂任务]
    C --> D[能记忆]
    D --> E[能长期运行]
    E --> F[能协作和扩展]
    F --> G[能编排并闭环]

越往后代码量增长越快，但最初的 Agent Loop 没有变得神秘。复杂度主要来自真实环境：并发、持久化、权限、恢复、上下文预算和失败处理，而不是某个隐藏的“超级 Prompt”。

十三、自己实现时最该关注什么

13.1 先做最小闭环

先用一个模型、一个 Bash 工具和一个循环验证模型能否完成目标，再根据真实失败增加专用工具。过早加入工作流引擎、多 Agent 和记忆系统，会让问题被基础设施掩盖。

13.2 把安全约束写进执行层

System Prompt 可以要求模型谨慎，但路径越界、危险命令和外部写操作必须由代码、沙箱或审批机制控制。模型输出始终是不可信输入。

13.3 把工具返回当作 API 设计

输出既不能少到无法诊断，也不能大到淹没上下文。应返回退出码、错误摘要和关键内容；超大结果落盘并提供可再次读取的位置。

13.4 用隔离解决上下文和并发问题

子 Agent 用独立 messages 隔离认知负担，Git worktree 用独立目录隔离并行修改。不要让多个执行者在同一可变状态上凭默契协作。

13.5 为长任务设计恢复

后台命令要能终止，任务要能重新认领，定时触发要能去重，工作流要有 Journal，队友异常退出后要能释放资源。Agent 的生产可用性往往取决于这些“不聪明”的代码。

13.6 用证据定义完成

“模型停止调用工具”“Todo 全部勾选”“Evaluator 判断成功”都只是信号。编码任务最终应尽量落到可验证证据：测试、lint、构建产物、Git diff 和外部系统状态。

十四、教学实现没有替你解决什么

learn-claude-code 的价值是让机制足够清晰，而不是提供可直接上线的 Claude Code 替代品。生产系统仍需额外处理：

  • 真正的容器或系统级沙箱；
  • 跨平台 Shell 和文件系统差异；
  • API 限流、重试、熔断和成本治理；
  • Secret 隔离与凭证生命周期；
  • MCP Server 的认证和信任策略；
  • 并发一致性、崩溃恢复和数据迁移；
  • 完整的遥测、审计和质量评估；
  • Prompt Injection 与不可信仓库内容；
  • 用户界面、会话存储和多租户隔离。

阅读这些代码时，最合适的问题不是“它是否 1:1 复刻 Claude Code”，而是“它用最少代码说明了哪个机制，以及进入生产后还缺哪些约束”。

总结

Claude Code 一类编码 Agent 的核心可以浓缩成一句话：模型在循环中做决策，Harness 给它可控的手、眼睛、记忆和工作空间。

从 learn-claude-code 的渐进实现可以看到：

  1. Agent 从 messages → model → tool_use → tool_result → messages 的闭环开始。
  2. 工具扩展行动空间，权限和 Hooks 划定边界。
  3. Todo、子 Agent 和上下文压缩支撑复杂任务。
  4. Skills 与 Memory 分别解决按需知识和跨会话经验。
  5. Task、Background、Cron 与 Team 让任务长期运行并协作。
  6. MCP 把外部能力并入统一工具池。
  7. Workflow 固化已知流程，Goal Loop 检查真实完成度。

最值得学习的不是某一段代码，而是它始终维持的分工：模型负责智能决策，Harness 负责可靠执行。优秀的 Agent 工程不是用更多流程替模型思考，而是让模型在清晰、可观察、可恢复且有权限边界的环境中工作。
