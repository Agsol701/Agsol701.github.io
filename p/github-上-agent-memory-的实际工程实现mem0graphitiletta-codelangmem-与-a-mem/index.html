GitHub 上 Agent Memory 的实际工程实现：Mem0、Graphiti、Letta Code、LangMem 与 A-MEM

source: github-agent-memory-engineering
Oct 10, 2026

写在前面

智能体（Agent）的记忆（Memory）需要解决一组连续的工程问题：何时写入、保存什么、怎样修改、如何召回、如何进入模型上下文，以及重启和并发操作后能否保持正确。

本文从 GitHub 项目的实际代码出发，分析 Mem0、Graphiti、Letta Code、LangMem 和 A-MEM。五个项目覆盖事实条目、时序关系图、文件记忆、框架组件和关联笔记，重点是各自真正执行的调用链及实现边界。

源码调研于 2026-10-09 完成，本文于 2026-10-10 合并整理。链接均固定到当时核对的提交。调研包含约 40 个核心源码、测试和示例；A-MEM 的两个问题通过原函数与模拟依赖最小复现。没有部署这些项目、运行全套测试或进行模型效果与性能评测。

文中的“工程建议”属于基于代码结构提出的设计建议，与项目已经实现的行为分别表述。

二、Mem0：事实条目与追加式记忆

Mem0 主要提供事实抽取与记忆服务接口。本节核对同步 Memory 类及其存储、评分和异常路径；异步类有对应实现。

2.1 系统的位置与源码地图

Mem0 的核心对象连接 LLM、嵌入模型、向量存储（Vector Store）及操作历史存储。它提供应用程序接口（API, Application Programming Interface），调用方控制何时读写。

源码位置 主要职责
mem0/memory/main.py Memory.add/search/update/delete 及核心流水线
mem0/configs/prompts.py 抽取提示词与输入组织
mem0/memory/storage.py SQLite 操作历史、近期消息
mem0/utils/scoring.py 关键词归一化与混合评分
tests/memory/test_main.py 异常、身份字段、时间戳等测试

本节路径都相对于 Mem0 仓库根目录。

应用一般在回答前检索，在适当的对话节点写入。Memory 类返回记忆结果，并不负责把结果自动加入任意 Agent 的上下文。框架集成或调用方需要完成这一步。

2.2 数据模型与作用域

2.2.1 一个事实条目保存什么

写入流水线为每个事实生成 UUID（Universally Unique Identifier，通用唯一标识符）。向量存储的载荷包含 data、hash、text_lemmatized、created_at、updated_at，以及用户提供的其他元数据。抽取结果有归属信息时还会保存 attributed_to。

data 是可读事实，向量支持语义召回，text_lemmatized 用于关键词检索，hash 用于文本去重。事实文本、索引与审计历史承担不同职责。事实组装源码

2.2.2 用户、Agent 与运行隔离

作用域由 user_id、agent_id、run_id 指定，至少需要提供一个。传入多个标识时，这些标识一起成为查询条件；不能把同时传用户和 Agent 理解为自动在两个独立空间各存一份。

代码会清除自由元数据中的身份键，再从显式参数设置身份字段，防止元数据把记录写入调用方没有指定的空间。近期消息使用由身份字段组成的 session_scope；其构造会转义分隔符，避免不同标识组合产生同一个字符串。

这些字段是数据作用域机制。业务服务仍需要验证调用者身份，保证其有权操作对应作用域。作用域构造、作用域测试

2.3 默认写入流水线

2.3.1 入口与两条路径

Memory.add() 将字符串或单条消息规范化为消息列表，再调用 _add_to_vector_store()。

当 infer=False 时，代码绕过事实推断，直接嵌入并保存非系统消息，同时记录角色和命名说话者信息。默认推断路径则使用分阶段批处理。写入入口

flowchart TD
    A["新消息与身份参数"] --> B["获取近期 10 条消息"]
    B --> C["向量召回 10 条相关旧记忆"]
    C --> D["单次 LLM 抽取新增事实"]
    D --> E["批量嵌入事实文本"]
    E --> F["文本哈希去重与载荷组装"]
    F --> G["批量保存向量记录"]
    G --> H["保存操作历史"]
    H --> I["建立实体关联"]
    I --> J["保存近期消息并返回成功条目"]

2.3.2 先读旧记忆，再抽取新事实

系统读取同一作用域最近 10 条消息，将新消息嵌入后召回 10 条旧记忆。旧记忆的标识会映射成短整数字符串，再与新消息、近期消息、自定义指令一起输入模型。

默认系统提示词是 ADDITIVE_EXTRACTION_PROMPT。它让模型提取新增事实，返回 JSON（JavaScript Object Notation）结构中的 memory 列表。代码还会区分只按 Agent 隔离的情况，加入对应抽取指令。上下文与抽取

当前默认流程采用追加式写入。 仓库仍保留其他更新提示词或独立更新接口，但它们的存在不能证明默认 add() 自动执行 ADD、UPDATE、DELETE 三种决策。判断行为要以当前调用链为准。

2.3.3 去重的范围

抽取完成后，代码先尝试批量嵌入，失败时逐条嵌入。然后对每条文本计算 MD5（Message-Digest Algorithm 5）摘要，与本次召回的旧记忆哈希及当前批次的哈希比较。

这是“相同文本去重”。它既不等于全库扫描，也不能识别所有语义等价表述。例如“偏好中文回答”和“喜欢使用中文交流”是否重复，不能仅靠文本哈希判断。

2.3.4 成功结果的判定

批量插入失败后，代码逐条重试，只把确认保存的记录加入返回值和后续历史、实体关联处理中。如果没有任何记录保存成功，则抛出向量存储异常；部分成功时返回成功部分。

因此调用方需要检查返回结果，而不是假定一次抽取中的所有事实都已经保存。批量保存与降级

2.4 检索：向量候选上的多信号排序

2.4.1 检索步骤

_search_vector_store() 先进行词形处理和实体提取，再生成查询向量。向量召回量为 max(limit * 4, 60)，关键词检索使用相同的候选数量级。随后计算 BM25（Best Matching 25）分数和实体加分。

最终候选集合从向量结果构建。关键词结果主要为这些候选提供分数；关键词独有命中没有在这条路径中直接并入最终候选池。实体关联也用于加分。检索源码

2.4.2 阈值与分数

评分函数先使用 threshold 过滤语义相似度，然后将语义分、归一化 BM25 分和实体加分相加，并根据启用的信号归一化。

这意味着关键词很强，但语义分低于阈值的记录仍会被排除。工程上应分别测量“向量是否召回”和“召回后是否排到前列”，不能只看最终 Top-K。

配置重排器（Reranker）时，search() 可进一步重排；重排失败会退回原结果。底层后端不支持关键词搜索时，相关 BM25 信号不可用。评分函数

2.4.3 过期过滤与上下文预算

检索默认过滤已过期载荷，show_expired 可以改变这项行为。这是读取时过滤，不应据此推断数据库会自动物理清理所有过期记录。

返回数量由 limit 控制，但条目数量不等于模型词元（Token）预算。调用方仍要按文本长度、相关性和可信度决定最终注入内容。

2.5 持久化、更新与失败边界

2.5.1 两种存储各自负责什么

向量后端保存事实正文、嵌入及元数据；SQLiteManager 保存历史和消息。SQLite 实现通过线程锁协调同一实例的数据库操作，并提供历史表迁移。

两个存储分开写入。向量记录保存成功后，历史或实体关联仍可能失败。代码有日志与降级处理，但没有在这层提供跨存储事务。SQLite 实现

2.5.2 不同失败的可见性

失败点 当前路径的处理
LLM 调用异常 包装并抛出异常，调用方可安排重试
抽取结果解析失败 记录日志，按没有抽取结果处理
批量嵌入失败 降级为逐条嵌入
批量插入失败 降级为逐条插入
历史记录写入失败 尝试逐条写，仍失败则记录日志
实体关联失败 记录日志，已保存事实继续保留

“不需要记忆”和“模型结果无法解析”在返回空结果时可能难以区分。应用需要结合日志或增加自己的处理状态。异常路径

2.5.3 更新与删除

独立更新、删除接口用于维护已有事实。更新涉及向量记录和历史，实体链接也有相应维护逻辑。调用方需要明确修改对象，不能因为默认写入读取了旧记忆，就认定旧事实已经自动失效。

**工程建议：**为需要强一致性的场景增加业务事件日志，记录期望写入、实际成功和待补偿操作。若要实现请求级幂等，应增加业务请求标识；文本哈希不能替代跨并发请求的幂等协议。

2.6 接入案例与验证方法

2.6.1 个性化助手

假设用户先说“工作报告用中文”，后说“这份英文邮件用英语”。应用可以给抽取器配置适合业务的指令，区分长期偏好和任务约束。回答前检索时，要同时考虑当前明确要求，避免历史偏好覆盖本轮指令。

默认追加式写入可能保留两条信息。是否合并为“工作报告中文、英文邮件英语”，应由显式更新流程或应用的整理策略决定。

2.6.2 多智能体共享

共享项目空间可以使用项目标识作为作用域，再用贡献者元数据记录来源。读时只传项目标识，可以检索项目范围；增加 Agent 标识会进一步收窄范围。具体共享规则应由应用定义。

不要直接将仓库中的演示代码视作对当前返回结构的完整兼容保证；接入时应核对固定版本的返回类型。

2.6.3 应验证什么

**工程建议：**使用固定样例检查同义重复、事实修正、用户隔离、部分写入失败、检索漏召回和重启恢复。仓库测试覆盖身份字段、时间戳、异常等代码行为，但这些测试不能替代真实任务中的抽取质量与召回评估。核心测试

3.2 三个核心数据对象

3.2.1 事件节点

EpisodicNode 表示一次输入经历，保存内容、来源描述、记录时间和参考时间。add_episode() 中，reference_time 进入事件的 valid_at；created_at 是系统当前记录时间。

这两个时间可能不同。例如今天补录昨天的发布记录，其事件时间是昨天，系统记录时间是今天。它们不能简单互相替代。

3.2.2 实体节点

EntityNode 表示用户、项目、服务等对象。同一个实体可以出现在多个事件中。输入的“支付服务”和“payment-service”是否指向同一个节点，需要经过实体解析，而不是只按字符串创建节点。

写入接口允许提供实体类型、排除类型和抽取指令，以限制图谱的业务范围。写入参数及流程

3.2.3 事实关系

EntityEdge 连接实体，包含关系名、事实文本 fact、事实向量、来源事件列表及时间字段。

字段 作用
episodes 为该事实提供来源的事件
valid_at 事实开始成立的时间
invalid_at 事实停止成立的时间
expired_at 系统记录关系失效的时间
reference_time 产生关系的事件参考时间

“业务事实何时结束”和“系统何时发现它结束”可以不同。理解这些字段，比笼统地称为“时序图”更有助于设计查询。关系数据模型

3.3 事件如何进入图中

3.3.1 获取上下文与请求作用域

add_episode() 先解析 group_id 对应的请求作用域，再读取近期事件或调用方指定的先前事件，为抽取提供上下文。

当前代码使用请求级驱动和客户端组合，避免不同 group_id 的并发调用修改共享驱动目标。业务仍应校验调用者能够读写哪些组，group_id 本身不是完整权限系统。作用域处理

3.3.2 实体抽取与消歧

extract_nodes() 产生候选实体，resolve_extracted_nodes() 将其与已有图进行解析，并产生标识映射。后续关系不能继续使用尚未解析的临时实体标识，否则同一个真实对象会被拆成多个节点。

**工程建议：**业务存在稳定服务标识或项目标识时，应在输入及类型约束中保留这些标识，降低仅靠自然语言名称消歧造成的歧义。

3.3.3 关系抽取、重复与矛盾

关系抽取基于新事件及相关先前事件，再对候选关系进行去重与矛盾处理。代码区分已有关系、需要失效的关系和新增关系，后续属性摘要仅使用新增关系，减少重复事实污染实体摘要。

重复与矛盾是不同操作：重复通常涉及复用事实及来源，矛盾涉及有效时间的判断。模型参与事实判定，但最终时间更新还有显式代码规则。关系处理

3.4 事实变化如何处理

3.4.1 失效保留历史

resolve_edge_contradictions() 先检查新旧关系的有效时间是否已经不重叠；这类情况不必再次处理失效。若旧关系开始时间早于新关系开始时间，且满足对应条件，代码将旧关系的 invalid_at 设置为新关系的 valid_at，并记录 expired_at。

因此，后来的矛盾事实并非无条件覆盖所有旧事实。字段是否有值、时间顺序是否成立，都会影响处理。失效规则

3.4.2 一个依赖变更例子

假设事件 E1 说明“服务 A 从 09:00 起依赖版本 v1”，事件 E2 说明“服务 A 从 10:00 起改用 v2”。在关系抽取和矛盾判定正确的前提下，旧依赖关系可以结束于 10:00，新依赖关系从 10:00 生效。

若随后分析 09:30 的故障，应该查询那个时刻有效的关系，而不是直接取最新依赖。这个例子说明了时间建模的用途，并不代表 Graphiti 已经自动建立“依赖变化导致故障”的因果事实。

3.4.3 默认检索不等于当前有效事实查询

基础 search() 未传过滤条件时使用 SearchFilters()。其 valid_at、invalid_at、expired_at 默认为空。

所以，存在失效字段不等于基础检索必然排除旧事实。查询当前状态、查询历史时刻和查询所有演变，需要应用选择不同的过滤条件。基础检索入口、过滤对象

3.5 图检索与排序

3.5.1 多种召回方式

关系搜索根据配置执行 BM25 全文搜索、余弦相似度搜索或 BFS（Breadth-First Search，广度优先搜索）。

配置启用 BFS 且没有提供起点时，代码可以从先前结果的源实体继续展开。每条搜索路径有数量及深度限制；图遍历不是无限制递归。

基础 search() 默认选用全文与向量混合的关系检索；带中心节点时使用节点距离相关配置。更复杂的检索应使用可配置路径，而不是假定每次基础搜索都执行多跳展开。关系搜索

3.5.2 排序方式的差别

方法 实现目的
RRF（Reciprocal Rank Fusion，倒数排名融合） 合并多个召回列表的排名
MMR（Maximal Marginal Relevance，最大边际相关性） 平衡相关性与结果多样性
Cross-Encoder（交叉编码器） 对查询与事实进行进一步相关性判断
Node Distance（节点距离） 利用事实实体与指定中心节点的接近程度

交叉编码器路径会先融合候选、限制待重排量，再执行评分。算法控制候选数量，可避免把整个图交给重排模型。

3.5.3 如何注入上下文

基础搜索返回 EntityEdge 列表。应用可组织事实文本、有效时间和来源事件，再交给回答模型。若只保留 fact，可能失去区分当前与历史事实的条件。

**工程建议：**故障分析上下文应保留事件时间、实体标识、来源和有效区间，并单独标注推测性因果关系。图检索结果是证据集合，不能自动当成已经验证的因果链。

3.6 持久化、顺序与维护

3.6.1 数据库保存边界

批量保存通过 session.execute_write() 执行，将事件、实体及关系交给事务处理。不同数据库驱动使用不同的保存实现。

社区更新在事件图保存后额外执行，且 update_communities 默认关闭。因此不能将社区更新与全部前置抽取操作都视为一个完整事务。批量保存源码

3.6.2 为什么建议顺序写入

源码建议将事件写入放入后台过程，并等待一条事件完成后再加入下一条。因为后续抽取、解析与失效判定依赖已经保存的图状态。

内部异步并发用于加速部分操作，并不意味着同一事实空间可以任意并发写入而保持业务顺序。**工程建议：**按需要保持顺序的业务空间安排队列，监测处理积压及失败重试；不要仅因为入口是异步函数就忽略顺序。

3.6.3 删除不是事实失效

remove_episode() 会查找事件关联关系与实体，再按代码中的条件删除关系、仅被该事件提及的实体和事件本身。物理删除与时间失效有不同语义。

对于多事件共享的事实，不应推断“删除事件”会自动撤销并重算所有派生判断。需要按实际来源规则验证删除后的图。事件删除

3.7 工程案例与验证重点

3.7.1 发布故障关联

可以依次输入发布记录、依赖变更、告警和回滚记录。通过实体类型约束识别服务、版本、依赖和故障事件，再围绕故障时刻及目标服务检索关系。

**工程建议：**先测量实体识别和时间抽取准确率，再测量关联检索。若服务名被错误合并，后续图遍历越多，错误扩散范围反而可能越大。

3.7.2 测试能够证明什么

仓库测试覆盖重复关系处理、整数索引映射、自关系过滤和类型约束等行为。它们有助于验证代码规则，但无法直接证明业务事件中的矛盾识别或历史问答准确率。关系操作测试

应另行构造乱序到达、迟到事件、同名实体、重复投递、有效期重叠及共享来源删除样例，并核对最终图和查询结果。

4.4 写路径：文件修改、校验与提交

4.4.1 模型操作文件

后台记忆工作者使用 Bash、Read、Edit、Write 工具读取和修改文件。提示词要求先读取当前文件，更新已有条目、替换过期信息并维护索引，而不是将所有新事实一律追加。

这是一项运行约定，不是数据库的语义唯一约束。重复、误归纳和错误修改仍需要验证。

4.4.2 提交前校验

Git 钩子（Git Hooks）在提交前检查记忆 Markdown 的格式，并支持配置的大小或深度约束。校验目的在于保持可解析布局及内容预算，不负责验证事实真假。

例如详细目录缺少索引、普通记忆文件前置字段不符合要求，属于格式问题；“用户其实并不喜欢该方案”属于语义问题，两者需要不同处理。钩子实现

4.4.3 本地与远端同步

memory-git.ts 提供本地仓库初始化、选择路径提交、克隆、拉取、推送及可重试网络错误处理。记忆写入可采用本地或远端同步模式。

本地提交成功、远端同步成功、提示词刷新成功是不同状态。**工程建议：**界面和日志应分别呈现，避免“写文件成功”被当成整个记忆传播流程完成。Git 实现

4.5 后台更新与并发协调

4.5.1 为什么使用独立 worktree

Git 工作树（Worktree）允许后台工作者基于同一仓库创建独立修改空间。它读取当前记忆，提交自己的修改，随后由运行框架将提交集成回主仓库。

这减少后台更新直接干扰主 Agent 文件操作的机会，也使集成有明确版本边界。后台说明要求按修改路径暂存，不使用全目录暂存，避免带入无关变化。

4.5.2 文件锁的实际范围

memory-operation.ts 在记忆 Git 目录中创建操作锁，根据进程身份及启动时间识别持有者。它串行化框架管理的后台写入、冲突修复、反思集成和同步。

代码注释明确指出：主 Agent 自己的普通文件编辑不全部经过这把锁。并发编辑仍可能降级为 Git 冲突，不能把文件锁解释成所有写入都具备数据库式串行隔离。锁实现

4.6 长期记忆与会话压缩分别维护

4.6.1 上下文压缩

压缩（Compaction）作用于当前会话消息，提供滑动窗口和全量摘要模式。本节提交的本地默认模式为 sliding_window，默认窗口比例常量为 0.3；它是代码默认值，不是对所有运行配置的保证。

滑动窗口保留近期内容，将被移出的早期消息生成摘要，放到保留消息之前。Token 估计及消息边界决定具体规划，不能简单按消息条数截断。压缩实现

4.6.2 持久历史与模型输入

本地会话存储维护完整逻辑历史和当前上下文消息标识。压缩操作在会话记录中加入压缩事件，更新当前上下文集合。

“从模型上下文移出”和“删除持久历史”并不相同。同样，会话摘要不会因产生了摘要就自动成为长期核心文件；长期记忆需要单独的文件写入和提交流程。会话压缩保存

4.7 Coding Agent 案例与验证

4.7.1 如何组织项目记忆

**工程建议：**核心文件保存项目身份、长期约束和少量稳定约定；详细目录保存架构调查、故障案例和执行经验；根索引提供入口。任务日志保留在会话历史中，只有可复用的信息才写入长期记忆。

例如一次用户更正“只对项目 A 使用这项规则”，应修改原条目并保留范围，而不是追加一句宽泛的“用户喜欢此规则”。文件模式允许精准编辑，但正确范围仍依赖提示词和验证。

4.7.2 需要检查的边界

可以验证未提交内容是否进入核心投影、提交后是否刷新、后台与主 Agent 同时修改是否触发冲突、重启后是否恢复仓库，以及远端不可用时本地修改是否仍可追踪。

5.2 记忆数据与作用域

5.2.1 namespace、key 与 value

长期记忆由命名空间（Namespace）、条目键（Key）和内容（Value）组织。管理工具将内容转成 JSON 可序列化数据，然后调用 Store 的保存或删除接口。

不同路径的内容包装可能不同，应按组件约定读取，不能把任意工具写入的数据直接视为所有管理器都兼容的格式。记忆工具、抽取结果保存

5.2.2 运行时作用域

Namespace 模板可以使用运行配置中的用户或组织标识。例如 ("memories", "{user_id}") 会解析为对应用户的命名空间。

如果所有用户都使用 ("memories",)，就会共享该空间。这种共享可以是业务设计，也可以是配置错误。应用必须将正确身份放入运行配置，并限制读写空间。作用域示例

5.2.3 存储能力来自后端

create_search_memory_tool() 将查询、过滤、数量及偏移交给 BaseStore.search/asearch。是否存在向量索引、如何嵌入、是否持久化，取决于 Store 配置。

示例中的 InMemoryStore 可以跨同一进程中的多个线程共享数据，但不能保证重启后恢复。部署时需要匹配持久化 Store 和检查点后端，分别解决长期条目与线程状态保存。

5.3 写路径一：Agent 调用记忆工具

5.3.1 执行过程中的写入

热路径（Hot Path）表示记忆操作发生在当前任务执行流程中。应用把 create_manage_memory_tool() 暴露给模型，模型根据任务决定创建、更新或删除。

工具校验操作和条目标识，解析 Namespace，然后调用 Store。它提供执行能力，但不替模型判断“这句话是否值得长期保存”。

5.3.2 这条路径的优缺点

优点是操作与本轮推理同步，模型可以立即利用工具结果。代价是增加当前任务的调用开销，并让记忆判断与主要任务竞争注意力。

**工程建议：**对于用户明确要求“记住”或“忘记”的信息，可优先使用显式操作；对于整段对话的事实整理，可使用后台管理器。具体分类规则应根据业务设置，而不是依赖所有模型都能正确自发判断。

5.4 写路径二：抽取器与记忆管理器

5.4.1 抽取与保存分离

MemoryManager 处理消息与已有记忆，返回结构化结果。它使用 LLM 和 Trustcall 的抽取器，并接受 Schema（结构约束）。

这层主要负责形成与修正内容。MemoryStoreManager 则负责从 Store 召回旧记忆、调用抽取器并保存结果。区分这两层，可以单独测试抽取输出而不写数据库。抽取器实现

5.4.2 先搜索，再合并

Store 管理器先解析 Namespace。启用查询生成器时，让模型生成多条搜索请求并并行检索；否则根据不同范围的对话窗口构造查询。

结果排序并限制到 query_limit，形成已有记忆集合，再交给抽取器。未召回的旧事实不一定参与本轮合并，所以不能将这一步视作全库去重。管理器调用链

5.4.3 新增、更新、删除

默认 MemoryManager 允许插入和更新，删除默认关闭。调用方需要显式启用删除策略。默认处理步数为 1；配置更多步骤时，抽取器可以继续修正并通过完成信号结束。

5.4.4 最终写入的事务边界

最终 aput 和 adelete 通过并发调用执行。这层没有把整组操作包装成跨条目的统一事务。

如果某个写入失败，其他并发写入可能已经成功。**工程建议：**需要批次原子性的场景应在应用或存储适配层设计事务、操作日志或可重放任务，不应只因为管理器一次返回就假定操作始终全成或全败。最终保存

5.5 后台反思如何执行

5.5.1 本地执行器

LocalReflectionExecutor 使用优先级队列（Priority Queue）及工作线程执行任务。submit() 接受延迟时间、线程标识和配置，返回 Future（异步结果对象）。

同一线程提交新任务时，代码尝试取消旧任务并设置取消信号。这样可以在用户持续对话时推迟整理，以较完整的上下文执行一次更新。

取消是调度机制，不能据此认为已经开始的模型调用或已完成的数据库写入会自动回滚。后台执行器

5.5.2 延迟与恢复能力

本地队列及待执行任务映射保存在进程内。即使 Store 持久化，队列也不会因此自动变成持久任务队列。

执行错误写入 Future；调用方需要观察该结果、记录错误或安排重试。仅调用 submit() 后忽略结果，会降低后台失败的可见性。

仓库还提供远程执行器路径。它与本地队列机制不同，远程运行服务的恢复保证需要另行核对，不能从本地类的行为推导。执行器选择与远程路径

5.6 读取与模型上下文接入

5.6.1 两种读取方式

应用可以在模型调用前主动搜索，将结果放入系统消息；也可以给模型搜索工具，让它在需要时读取。

官方热路径示例使用提示词函数读取 Store，构造包含记忆的系统消息，再拼接当前对话。这个示例证明“检索后如何注入”，并不表示所有 Agent 会自动采用相同方式。接入示例

5.6.2 召回数量与文本预算

搜索接口提供数量控制，但 Token 预算属于上层输入组织问题。十条短偏好和十条长经历的成本不同。

**工程建议：**先按当前任务查询，再对返回内容做长度和相关性控制；保留当前用户指令的优先级，避免旧记忆变成不可覆盖的规则。

5.7 短期摘要与长期记忆的区别

summarize_messages、asummarize_messages 和 SummarizationNode 处理当前消息列表。它们维护 RunningSummary，后续摘要可以结合已有摘要和新历史。

预处理排除系统消息，并处理消息标识及工具调用与工具结果的配对关系。摘要节点默认使用与输入不同的输出键，让模型输入摘要与图中的原消息状态可以分别管理。摘要源码

这解决当前会话长度问题。长期记忆抽取解决跨会话可复用内容问题。摘要不会自动替代 MemoryStoreManager，长期条目也不会自动保存完整会话状态。

仓库摘要测试覆盖空输入、连续摘要、消息标识、系统消息和工具调用等场景。本节核对了测试内容，没有运行完整依赖环境。摘要测试

5.8 工程落地案例

**工程建议：**以客户支持助手为例，可将明确偏好操作放在热路径，将每轮或一段对话后的事实整理放在后台；使用用户 Namespace；使用持久化 Store；在模型前检索相关条目；用检查点保存线程状态。

应分别验证以下问题：用户隔离是否正确、旧事实是否被召回、抽取是否保留例外条件、并发更新是否丢失修改、后台任务是否在重启后补跑、摘要是否保留未完成的任务状态。

测试要区分内容质量与执行可靠性。模型成功返回结构化内容，不代表内容正确；Store 成功保存，也不代表下一轮检索能找到它。

6.2.2 “原子”不是自动切分保证

原子笔记表示希望每条记录集中表达一个可独立引用的信息单元。默认 add_note() 接收调用方提供的正文，没有在这条路径中保证自动把长对话切成多个原子事实。

例如“版本 v2 在 10:00 发布”和“发布后错误率升高”可以作为两条笔记，但拆分方式需要上层决定。把完整事故报告直接作为正文，也不会仅因进入 MemoryNote 就自动变成多条原子记忆。

6.3 写路径与元数据生成

6.3.1 add_note 的实际流程

add_note() 创建笔记，调用 process_memory()，保存到对象字典，再把正文和元数据加入检索器。首次没有旧记忆时，演化路径直接返回原笔记。

6.3.2 analyze_content 没有自动接入

仓库中存在 analyze_content()，可生成关键词、上下文和标签。但当前 add_note() 直接调用 MemoryNote(content=content, **kwargs)，并未自动调用该分析函数。

因此，如果调用方只传正文，初始语义字段使用默认值。后续演化可能修改部分字段，但不能据此宣称所有新笔记都经过完整语义分析。新增路径

**工程建议：**在应用层显式划分“提取原子事实”“生成元数据”“保存笔记”三个步骤，并分别记录失败，避免把结构缺失隐藏在默认值中。

6.4 检索与关联演化

6.4.1 检索器保存什么

默认 ChromaRetriever 使用 Chroma 客户端和 SentenceTransformer 嵌入函数，默认模型名为 all-MiniLM-L6-v2。

add_document() 保存的是笔记正文；列表或字典元数据转成 JSON 字符串，其余元数据转成字符串。搜索调用 collection.query(query_texts=[query], n_results=k)，再恢复部分元数据类型。检索器源码

这条路径以正文的语义相似性召回。标签和上下文虽作为元数据保存，但不能仅因字段存在，就认定它们同时参与独立的关键词召回或向量编码。

6.4.2 演化决策

process_memory() 检索 5 个附近笔记，将它们与新笔记交给 LLM。模型输出包括是否演化、操作列表、建议关联及新标签、上下文。

当前主要操作：

  • strengthen：扩展新笔记的 links 并更新新笔记标签。
  • update_neighbor：修改旧笔记的标签及上下文。

strengthen 的这条路径没有自动为旧笔记建立反向链接，不能将所有关联理解为双向关系。演化异常会记录日志并返回未演化的笔记，新增流程可以继续。演化代码

6.4.3 查找并返回关联笔记

search_agentic() 先从 Chroma 获取直接命中，再根据笔记链接查找对象字典中的关联笔记。它尝试去重，并对结果标记 is_neighbor。

这个函数返回结构化结果，不负责完整的Agent提示词构造。应用需要控制关联展开数量、Token 预算及来源呈现。

6.5 两个问题的最小复现

6.5.1 关联内容被 Top-K 截掉

search_agentic() 先加入最多 K 条直接命中，再追加关联笔记，最后执行 return memories[:k]。

最小样例：

条件 内容
对象字典 笔记 A、B、C
直接命中 C
C 的链接 B
K 1
实际返回 C，未包含 B

复现使用固定提交中的原 search_agentic() 函数和模拟检索结果，没有更改该函数逻辑。函数确实尝试添加 B，但最终切片把它移出了返回值。

当直接命中已经达到 K 条时，追加在尾部的关联记录通常没有剩余空间。**工程建议：**分别为直接召回和关联展开分配预算，再统一排序，而不是先占满总预算再追加。关联检索源码

6.5.2 检索排名被当作字典位置

find_related_memories() 遍历搜索结果，返回 indices.append(i)。这里的 i 是结果排名，不是笔记在 self.memories 中的位置。

update_neighbor 随后使用 list(self.memories.values())[indices[i]] 定位对象。检索顺序与字典插入顺序不同，就会更新错误笔记。

最小复现固定字典顺序为 A、B、C，检索只命中 C，模拟模型要求将 C 的上下文改为 updated c。实际结果：

笔记 原上下文 更新后
A old updated c
B old old
C old old

复现执行了原 find_related_memories() 与 process_memory()；检索器和模型输出使用模拟对象。结果证明此输入下更新落到了 A，未落到 C。

**工程建议：**整个邻居处理链使用稳定笔记 ID，而非位置；模型输出中的标识应与本轮允许更新的邻居集合校验。排名生成、邻居更新

6.6 对象、索引与持久化边界

6.6.1 默认初始化不是恢复流程

AgenticMemorySystem 初始化空字典，创建普通 Chroma 检索器，并尝试调用客户端 reset()，随后创建新检索器。

仓库提供 PersistentChromaRetriever，但默认系统构造没有选择它，也没有在这条路径中从持久记录恢复对象字典。即使替换检索器，对象字典为空时，某些函数仍会直接返回空结果。

持久化不仅要保存向量，还需要恢复笔记对象及关联。初始化时的 reset 对已有集合的影响也应在实际 Chroma 配置中验证。系统初始化、持久检索器

6.6.2 自动演化与显式 update 不同

显式 update() 修改对象后，删除旧 Chroma 文档并重新添加；自动 update_neighbor 修改对象字典中的旧笔记，但没有在该分支立即执行同样的索引更新。

因此，通过对象读取和通过 Chroma 元数据读取，可能暂时看到不同上下文。自动整理 consolidate_memories() 会遍历字典再次添加记录，但其调用的检索器方法是 collection.add，不能仅根据“整理”名称就保证它对已有 ID 实现了可靠更新。显式更新、整理流程

6.6.3 删除、并发与失败

delete() 先删除 Chroma 记录，再删除对象字典条目。已核对的实现没有在这里自动清理所有其他笔记的入链引用。

显式更新采用删除再添加，也没有将内存对象和 Chroma 写入包装成统一事务。**工程建议：**生产组件应选择明确的权威存储，使用稳定 ID、索引更新操作、恢复流程和写入协调，避免双份数据长期分叉。

6.7 如何将该思路用于工程

6.7.1 发布故障笔记

**工程建议：**分别保存发布事件、依赖变更、告警及处置经验，使用事件标识和明确时间，再让模型提出关联。例如“同一服务、接近时间、相同发布版本”可以形成候选链接。

关联是后续分析线索，不应直接保存为已确认因果。原始正文和来源应保留，模型生成的上下文可单独维护，并记录修改来源。

7.3 如何对应实际任务

  • 发布故障、依赖变化和历史状态：优先研究 Graphiti 的事件与有效期。
  • Coding Agent 的长期规则与项目知识：研究 Letta Code 的核心投影、索引及版本。
  • 已有 LangGraph 应用：研究 LangMem 的 Store 接入、Schema 和后台处理。
  • 关联笔记和演化策略实验：研究 A-MEM，同时修正已确认的实现问题。

八、从项目中提炼落地方法

8.1 分开设计三份状态

**工程建议：**将原始经历、整理后的记忆和本轮模型输入分别管理。原始经历负责追溯，长期条目负责复用，上下文投影负责控制当前任务的输入成本。

摘要不必等于长期事实，索引不必成为权威数据。用户修正一条长期偏好时，要能找到其来源及生效范围，而不是仅在向量结果中追加一句相反的话。

8.2 先定义写入策略，再选择数据库

先确定哪些信息长期保存、哪些仅属于任务、如何处理例外及修正，再选择向量、图或文件存储。存储形式不能替代这些策略。

对明确的“记住”和“忘记”请求，可以设置显式操作；对连续对话抽取，可采用后台处理。对事件时间敏感的数据，输入应保留来源时间，不能只使用系统入库时间。

8.3 使用稳定身份与版本边界

记忆、事件和邻居都应使用稳定标识。检索排名仅是当前查询的顺序，不能作为对象身份。更新还需明确修改哪个版本，以及哪些派生索引需要刷新。

在多智能体场景中，分别定义用户私有、项目共享和智能体专属空间。选择相同空间是一种共享规则，不是自动权限校验。

8.4 为失败设计可观察状态

可以记录写入请求、抽取结果、实际保存条目、索引状态和上下文版本。对于后台任务，还需记录待执行、完成、失败和补偿状态。

当事实已保存但历史失败、文件已提交但尚未刷新提示词、后台任务已提交但进程退出时，系统应该能够区分这些状态，而不是只显示一个“成功”。

8.5 用行为样例验收

建议用以下样例验证实现，再测量真实任务效果：

样例 验证目标
同义内容重复写入 去重范围与语义重复

不同用户提出相同查询 空间隔离
迟到、乱序的业务事件 时间处理和依赖顺序

这些检查分别衡量执行正确性和内容质量。源码机制核对不能代替实际数据上的抽取、检索和回答评估。

九、常见高频面试题

9.1 Agent Memory 是否等于向量数据库？

**答：**不等于。数据库保存和检索内容，Memory 还包括写入选择、更新策略、作用域、上下文接入和维护。

9.2 Mem0 默认写入会自动覆盖旧事实吗？

**答：**本次提交的默认推断路径采用追加式抽取。独立更新接口和历史提示词的存在，不代表默认调用链自动执行更新或删除。

9.3 Graphiti 默认只返回当前有效关系吗？

**答：**不能这样保证。基础入口的默认时间过滤为空，应用需要为当前状态或历史时刻明确设置查询条件。

9.4 Letta 文件改完后，系统提示词会立即变化吗？

**答：**本地核心投影读取已提交快照，还需要提示词编译。文件工具看到的内容与已编译提示词可能不同。

9.5 LangMem 的检查点与 Store 有什么区别？

**答：**检查点保存线程执行状态，Store 保存跨线程组织的长期记忆。两者的持久化需要分别配置。

9.6 本地后台线程等于持久任务队列吗？

**答：**不等于。LangMem 本地执行器的队列在进程内；存储持久化不会自动保存未执行任务。

9.7 A-MEM 的邻居更新为什么会定位错误？

**答：**当前路径将检索排名用于笔记字典位置。两种顺序不一致时会更新错对象，稳定笔记 ID 才能可靠定位。

9.8 多路检索或关联链接能保证相关内容返回吗？

**答：**不能。Mem0 的候选来自向量结果；A-MEM 追加邻居后还会截断。需要核对候选并集、排序和预算，而不是只看机制名称。

9.9 数据库事务、Git 与文件锁分别保证什么？

**答：**事务协调指定数据库操作；Git 管理版本与合并；锁协调其覆盖范围内的写入。它们都不会自动保证语义准确，也不必然覆盖整条模型调用链。

9.10 两个源码问题是否否定 A-MEM 论文？

**答：**不会。这次复现针对固定仓库版本的特定函数，未复评论文实验或其他实现。
