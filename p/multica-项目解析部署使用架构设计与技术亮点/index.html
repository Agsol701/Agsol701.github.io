Multica 项目解析：部署、使用、架构设计与技术亮点

Jun 14, 2026

写在前面

multica-ai/multica 是一个开源的 managed agents platform。

如果用一句话概括：

Multica 不是再造一个 Coding Agent，而是给 Claude Code、Codex、GitHub Copilot CLI、OpenCode、Gemini、Cursor Agent 等已有 Agent 提供一套“任务分配、运行时管理、进度跟踪、团队协作和能力沉淀”的平台。

很多 Agent 工具解决的是“单次任务怎么执行”。Multica 关注的是另一个层面：

  • 谁来接这个任务
  • 在哪台机器上跑
  • 任务状态怎么流转
  • 运行过程怎么实时展示
  • 多个 Agent 怎么像团队成员一样被管理
  • 做过的事情如何沉淀成可复用技能

所以它更像一个面向 AI Agent 的轻量研发协作系统，而不是单纯的命令行代理封装。

这篇文章按“部署、使用、技术解析、技术亮点”四个角度整理 Multica。

1. Multica 解决什么问题

1.1 从“工具”到“队友”

传统 Coding Agent 的使用方式通常是：

1
2
3
4
5
6

打开终端
输入 prompt
等待执行
人工观察进度
复制结果
人工继续下一步

这在个人实验里很自然，但在团队协作里会遇到几个问题：

  • Agent 运行在哪台机器上不清楚
  • 多个任务并行时缺少统一队列
  • Agent 执行过程缺少统一状态
  • 失败、阻塞、重试没有工作流
  • 运行经验无法沉淀给团队复用
  • 人和 Agent 不在同一个任务面板里协作

Multica 的定位就是把这些零散能力平台化。

它把 Agent 抽象成团队成员，把本地机器或云端环境抽象成 Runtime，把工作抽象成 Issue，把重复任务抽象成 Autopilot，把可复用经验抽象成 Skill。

1.2 它不是替代 Agent，而是编排 Agent

Multica 支持多种 Agent CLI，包括：

  • Claude Code
  • Codex
  • GitHub Copilot CLI
  • OpenClaw
  • OpenCode
  • Hermes
  • Gemini
  • Pi
  • Cursor Agent
  • Kimi
  • Kiro CLI

这说明它的核心价值不在模型调用本身，而在“管理不同 Agent 的执行生命周期”。

可以把它理解成：

1

Multica = Issue Board + Agent Runtime Registry + Task Queue + Realtime Logs + Skills + Autopilot

2. 部署方式

Multica 有两类使用方式：

  • 使用官方 Cloud
  • 自托管部署

如果只是想快速体验，可以直接安装 CLI 并连接 Cloud。如果要控制数据、账号、运行环境和内部工作流，建议自托管。

2.1 方式一：使用 Cloud

macOS / Linux 推荐用 Homebrew 安装 CLI：

1

brew install multica-ai/tap/multica

然后执行：

1

multica setup

这个命令会完成三件事：

  1. 配置 Multica Cloud 地址
  2. 打开浏览器完成登录
  3. 启动本地 agent daemon

本地 daemon 会自动检测机器上的 Agent CLI，例如 claude、codex、opencode、gemini 等。

2.2 方式二：Docker Compose 自托管

官方推荐的自托管方式是安装脚本：

1
2

curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash -s -- --with-server
multica setup self-host

这会做几件事：

  • 安装 multica CLI
  • 拉取自托管部署资源
  • 从 GHCR 拉取官方镜像
  • 启动 backend、frontend、PostgreSQL
  • 配置 CLI 指向本地服务
  • 登录并启动本地 daemon

启动后默认地址是：

1
2

Frontend: http://localhost:3000
Backend:  http://localhost:8080

如果想手动部署：

1
2
3

git clone https://github.com/multica-ai/multica.git
cd multica
make selfhost

make selfhost 会自动创建 .env，生成随机 JWT_SECRET 和 POSTGRES_PASSWORD，然后通过 docker-compose.selfhost.yml 启动服务。

如果官方镜像还没发布，或者想基于当前源码构建：

1

make selfhost-build

2.3 登录验证码配置

自托管默认按生产模式运行，没有固定验证码。登录方式有三种：

  1. 配置 RESEND_API_KEY，通过邮件发送验证码
  2. 不配置邮件服务，从 backend 日志里复制验证码
  3. 私有测试环境设置 APP_ENV=development 和 MULTICA_DEV_VERIFICATION_CODE=888888

注意：公开环境不要启用固定验证码。否则知道邮箱的人都可能登录。

2.4 Kubernetes 部署

如果团队已有 Kubernetes，可以使用 OCI Helm Chart：

1
2
3

helm install multica oci://ghcr.io/multica-ai/charts/multica \
  --version <chart-version> \
  -n multica

Chart 默认会创建：

  • multica-postgres
  • multica-backend
  • multica-frontend
  • frontend / backend 两个 Ingress
  • multica-config ConfigMap

敏感配置不由 Chart 直接管理，需要先创建 Secret：

1
2
3
4
5
6
7

kubectl -n multica create secret generic multica-secrets \
  --from-literal=JWT_SECRET="$(openssl rand -hex 32)" \
  --from-literal=POSTGRES_PASSWORD="$(openssl rand -hex 16)" \
  --from-literal=RESEND_API_KEY="" \
  --from-literal=GOOGLE_CLIENT_SECRET="" \
  --from-literal=CLOUDFRONT_PRIVATE_KEY="" \
  --from-literal=MULTICA_DEV_VERIFICATION_CODE=""

有一个部署细节要注意：官方预构建 web 镜像里默认 baked REMOTE_API_URL=http://backend:8080，Chart 会创建一个名为 backend 的兼容 Service。因此默认建议一个 namespace 只部署一个 Multica 实例。

3. 基本使用流程

3.1 启动 daemon

安装并登录后：

1
2

multica daemon start
multica daemon status

daemon 是本地 Agent Runtime，负责：

  • 检测本机可用的 Agent CLI
  • 向 Multica Server 注册 runtime
  • 轮询任务
  • 创建隔离工作目录
  • 启动 Agent CLI
  • 将执行过程、日志、状态回传到平台

默认 daemon 日志在：

1

~/.multica/daemon.log

查看日志：

1
2

multica daemon logs
multica daemon logs -f

3.2 创建 Agent

进入 Web UI：

1

Settings -> Runtimes

确认你的机器已经作为 Runtime 出现。

然后进入：

1

Settings -> Agents

创建一个 Agent，选择：

  • runtime
  • provider，例如 Codex / Claude Code / OpenCode
  • agent name

这个 Agent 会出现在看板、评论、任务分配器里。

3.3 创建并分配 Issue

可以在 Web UI 创建，也可以用 CLI：

1
2
3
4
5

multica issue create \
  --title "Fix login bug" \
  --description "Reproduce and fix the login redirect issue" \
  --priority high \
  --assignee "Lambda"

Agent 被分配任务后，daemon 会自动领取并执行。

常用 Issue 命令：

1
2
3
4
5

multica issue list
multica issue get <issue-id>
multica issue status <issue-id> in_progress
multica issue assign <issue-id> --to "Agent Name"
multica issue comment add <issue-id> --content "Please check edge cases"

3.4 查看执行历史

Multica 不只记录 Issue 状态，也记录 Agent 执行 run。

1
2
3

multica issue runs <issue-id>
multica issue run-messages <task-id>
multica issue run-messages <task-id> --since 42 --output json

这对排查 Agent 行为很有用。因为很多失败不是“最终结果错了”，而是中途工具调用、权限、环境、prompt 约束、上下文选择出了问题。

3.5 Autopilot

Autopilot 用来跑周期性或触发式任务。

例如创建一个每天自动巡检的任务：

1
2
3
4
5

multica autopilot create \
  --title "Nightly bug triage" \
  --description "Scan todo issues and prioritize." \
  --agent "Lambda" \
  --mode create_issue

添加 cron trigger：

1
2
3

multica autopilot trigger-add <autopilot-id> \
  --cron "0 9 * * 1-5" \
  --timezone "Asia/Shanghai"

Autopilot 有两种模式：

  • create_issue：每次运行创建 Issue 并分配给 Agent
  • run_only：直接入队执行，不创建 Issue

5.1 整体架构

可以把 Multica 分成四层：

 3
 4

┌──────────────────────┐
│      Web / App UI     │
│  Issue Board / Agent  │
└──────────┬───────────┘
           │ HTTP / WebSocket
┌──────────▼───────────┐
│      Go Backend       │
│ API / WS / Scheduler  │
└──────────┬───────────┘
           │ SQL
┌──────────▼───────────┐
│ PostgreSQL + pgvector │
└──────────┬───────────┘
           │ Task claim / heartbeat / logs
┌──────────▼───────────┐
│    Agent Daemon       │
│ local / cloud runtime │
└──────────┬───────────┘
           │ spawn process
┌──────────▼───────────┐
│ Claude / Codex / etc. │
└──────────────────────┘

这里最重要的是：Agent 不是跑在 Web Server 里，而是跑在 runtime 上。

runtime 可以是你的本地机器，也可以是云端机器。这样做的好处是：

  • 复用开发者本地已有的 Agent CLI 和认证状态
  • 避免服务端直接持有所有模型供应商凭证
  • 每个团队成员可以贡献自己的计算环境
  • Agent 对代码仓库、ssh key、本地工具链的访问更自然

5.2 Server 负责什么

Go Backend 主要承担控制面职责：

  • 用户认证
  • Workspace 管理
  • Agent / Runtime 管理
  • Issue 生命周期
  • Task 入队、领取、完成、失败
  • 评论、订阅、执行历史
  • WebSocket 实时推送
  • Autopilot 调度
  • Usage rollup
  • 上传与附件存储

它不是把 Agent 逻辑写死，而是把 Agent 执行抽象成可调度任务。

5.3 Daemon 负责什么

daemon 是执行面。

官方 CLI 文档里描述的执行流程可以整理成：

daemon start
  ↓
检测本机 Agent CLI
  ↓
向 server 注册 runtime
  ↓

  ↓

  ↓
创建隔离 workspace
  ↓
启动对应 Agent CLI
  ↓
流式回传状态、日志、结果
  ↓

daemon 默认配置里有几个关键参数：

参数 默认值 作用
MULTICA_DAEMON_POLL_INTERVAL 3s 轮询任务间隔
MULTICA_DAEMON_HEARTBEAT_INTERVAL 15s runtime 心跳
MULTICA_DAEMON_MAX_CONCURRENT_TASKS 20 最大并发任务
MULTICA_WORKSPACES_ROOT ~/multica_workspaces 本地任务工作目录
MULTICA_GC_TTL 24h 完成任务目录清理 TTL
MULTICA_GC_ARTIFACT_PATTERNS node_modules,.next,.turbo 可清理构建产物

这些参数说明 Multica 把 Agent 执行当成长期运行的本地工作负载，而不是一次性命令。

6. 关键模块拆解

6.1 server/internal/daemon

这个模块对应本地 daemon 的核心执行逻辑。

它要解决的问题包括：

  • 检测本机有哪些 Agent CLI
  • 管理 daemon 进程状态
  • 处理任务并发
  • 创建工作目录
  • 调用外部 CLI
  • 收集执行结果
  • 处理超时与中断

在 Agent 平台里，daemon 是最容易出问题的部分。因为它要接触真实文件系统、真实 Git 仓库、真实依赖安装、真实命令执行和真实网络环境。

6.2 server/internal/daemonws

这个模块从命名看是 daemon 和 server 之间的 WebSocket 通信层。

Agent 执行不是瞬时动作，前端需要看到实时状态，例如：

  • agent 已领取任务
  • 正在分析
  • 正在调用工具
  • 输出日志
  • 遇到 blocker
  • 完成或失败

WebSocket 比单纯 HTTP polling 更适合这类长任务状态同步。

6.3 server/internal/service

service 通常承载业务用例层。

在 Multica 里可以理解为把底层 repository、auth、runtime、issue、comment、task 等能力组织成业务动作：

  • 创建 issue
  • 分配 issue
  • task claim
  • 更新状态
  • 写入评论
  • 记录 run message
  • 触发订阅通知

这是平台的业务中枢。

6.4 server/internal/handler

handler 是 HTTP API 层，负责：

  • 参数解析
  • 认证上下文读取
  • 调用 service
  • 返回 JSON
  • 处理 WebSocket upgrade

Go Backend 使用 Chi router，整体会比较接近传统 REST API 项目。

6.5 server/internal/scheduler

调度模块和 Autopilot、Usage rollup 有关。

Multica 自托管文档提到，Usage Dashboard 的 task_usage_hourly 由 backend 进程内 scheduler 定期维护，并通过数据库唯一键避免多副本重复执行。

这点很重要：在多 backend replica 下，定时任务如果没有协调机制，很容易重复写入或重复触发。

Multica 使用 DB-backed scheduler 的好处是：

  • 不额外依赖 pg_cron
  • 不需要单独 Kubernetes CronJob
  • 多副本部署下可以通过数据库约束抢占任务
  • 调度执行记录可审计

6.6 server/internal/skill

Skill 是 Multica 的能力沉淀层。

普通 Agent 运行容易变成一次性消耗：这次修好了，下次还要重新 prompt、重新探索、重新踩坑。

Skill 的意义在于把可复用流程沉淀下来，例如：

  • 项目部署步骤
  • 代码评审规范
  • 数据迁移流程
  • 线上排障清单
  • 某个仓库的特殊约束

这和“团队知识库”类似，但更面向 Agent 执行。

6.7 server/internal/auth

Multica 支持浏览器登录、token 登录、Google OAuth、邮件验证码等模式。

CLI 文档提到 multica login 会创建 90 天 personal access token，并自动发现用户所属 workspace。

对于 Agent 平台来说，认证不只是用户登录问题，还涉及：

  • CLI 如何安全持有 token
  • daemon 如何代表用户或 workspace 执行任务
  • 多 workspace 如何隔离
  • 自托管如何限制 signup
  • 私有部署如何避免任意用户创建 workspace

6.8 server/migrations 与 sqlc

Multica 使用 PostgreSQL，并通过 sqlc 生成类型安全的 Go 数据访问代码。

这种组合的特点是：

  • SQL 仍然是显式的
  • Go 代码有类型检查
  • 复杂查询不用绕 ORM
  • 迁移脚本可审计

对于任务系统、评论线程、执行日志、usage rollup 这类关系强、查询复杂的业务，PostgreSQL + sqlc 是比较务实的选择。

7. 技术亮点

7.1 把 Agent 设计成一等团队成员

Multica 的产品抽象不是“后台任务”，而是“Agent teammate”。

这带来一组很自然的协作模型：

  • Agent 可以被 assign
  • Agent 可以评论
  • Agent 可以上报 blocker
  • Agent 有执行历史
  • Agent 出现在 board 和 activity timeline 里

这个抽象很重要。因为真正落地 Agent 时，团队最缺的不是“再多一个模型调用”，而是“把 Agent 放进现有协作节奏里”。

7.2 Runtime 和 Agent 解耦

Multica 区分：

  • Agent：一个可被分配任务的角色
  • Runtime：实际执行任务的计算环境
  • Provider：底层 Agent CLI 类型

这个拆分让系统具备扩展性：

1
2
3
4

同一个团队可以有多个 runtime
同一个 runtime 可以检测多个 CLI
同一个 workspace 可以有多个 agent
不同 agent 可以绑定不同 provider

这比把“Agent = 某个机器上的某个 CLI”写死更灵活。

7.3 本地 daemon 复用用户环境

很多企业内部仓库并不适合直接交给云端 Agent 执行，因为涉及：

  • 私有代码
  • 内网服务
  • 本地证书
  • SSH key
  • 私有包仓库
  • 数据库访问权限

Multica 的 daemon 模式让执行发生在本地或自有 runtime 上，平台只负责任务控制和状态同步。

这种架构更适合渐进式引入 Agent。

7.4 多 Agent CLI 适配

Multica 支持多个 Agent CLI，本质上把不同供应商的工具变成统一 runtime 能力。

这带来两个好处：

  • 避免锁死某个模型或 Agent 供应商
  • 团队可以根据任务类型选择不同 Agent

例如：

  • Claude Code 处理长上下文代码理解
  • Codex 处理编码任务
  • OpenCode / OpenClaw 处理开源可控场景
  • Gemini 或 Kimi 作为补充 provider

Multica 站在更上层做调度，而不是押注某一个底层 Agent。

7.5 Issue + Run 的双层记录

Issue 是业务层记录，Run 是执行层记录。

这个设计很关键：

  • 一个 Issue 可能经历多次 Agent 执行
  • 一次执行可能失败、重试、被取消
  • 人类评论和 Agent 输出需要分开理解
  • 排查问题时需要看到每次 run 的消息流

如果只记录 Issue 最终状态，就很难复盘 Agent 为什么失败。

7.6 Autopilot 把 Agent 变成定时工作流

Autopilot 让 Agent 不只是被动接任务，也可以处理周期性工作：

  • 每日 standup 汇总
  • 每周依赖升级
  • 定期安全扫描
  • 自动 issue triage
  • 周期性文档同步
  • 发布前检查

这类任务以前通常是 cron + 脚本。引入 Agent 后，任务内容可以更开放，但仍需要调度、记录、失败处理和权限控制。

7.7 Skill 让经验复利化

如果每次 Agent 执行都从零开始，团队收益会被上下文构建成本吃掉。

Skill 的价值在于把经验变成可复用资产：

1
2
3
4
5
6
7

一次解决问题
  ↓
沉淀为 Skill
  ↓
后续 Agent 复用
  ↓
团队整体能力提升

这也是 Multica README 里强调 compound skills 的原因。

7.8 生产部署思路比较完整

从自托管文档可以看出，Multica 不只是提供 demo：

  • Docker Compose 快速部署
  • Helm Chart 部署
  • 生产模式验证码
  • signup 控制
  • workspace 创建限制
  • S3 / CloudFront 文件存储
  • Prometheus metrics
  • CORS 和 WebSocket Origin 配置
  • Usage rollup 自动调度
  • 多 backend replica 协调

这些都是平台工程里真正会遇到的问题。

8. 生产部署注意点

8.1 一定要修改密钥

自托管时至少要确认：

1
2
3
4

JWT_SECRET
POSTGRES_PASSWORD
DATABASE_URL
FRONTEND_ORIGIN

JWT_SECRET 必须是随机长字符串：

1

openssl rand -hex 32

8.2 邮件认证要提前配置

公开或团队部署建议配置：

  • RESEND_API_KEY
  • 或 SMTP 相关变量

不配置邮件时，验证码会出现在 backend 日志里，这只适合临时测试。

8.3 私有实例要限制注册和 workspace 创建

建议流程：

  1. 初始部署时允许创建 workspace
  2. 管理员登录并创建共享 workspace
  3. 设置 DISABLE_WORKSPACE_CREATION=true
  4. 根据需要设置 ALLOW_SIGNUP=false
  5. 后续用户通过邀请加入

否则用户即使登录受控，也可能创建自己的 workspace，导致平台管理员不可见。

8.4 daemon 所在机器就是执行边界

Agent 真正执行代码的是 daemon 所在机器。

因此需要关注：

  • 机器权限
  • 工作目录隔离
  • SSH key 和 token 泄露风险
  • 私有仓库访问权限
  • Agent CLI 的 sandbox 能力
  • 最大并发任务数
  • 磁盘清理策略

默认最大并发任务是 20，小机器上建议调低：

1

export MULTICA_DAEMON_MAX_CONCURRENT_TASKS=3

8.5 WebSocket Origin 和反向代理

Multica 依赖 WebSocket 做实时状态更新。

如果前端和后端域名不同，要正确配置：

1
2
3

FRONTEND_ORIGIN
CORS_ALLOWED_ORIGINS
COOKIE_DOMAIN

反向代理也要支持 WebSocket upgrade。否则界面可能能打开，但实时日志和任务状态不会更新。

8.6 文件存储

如果有上传附件、执行产物、截图等需求，生产环境建议配置 S3 或兼容对象存储。

相关变量包括：

  • S3_BUCKET
  • S3_REGION
  • AWS_ACCESS_KEY_ID
  • AWS_SECRET_ACCESS_KEY
  • AWS_ENDPOINT_URL
  • ATTACHMENT_DOWNLOAD_MODE
  • CLOUDFRONT_DOMAIN

如果对象存储只在内网可访问，可以考虑 proxy 下载模式。

9. 适合场景与局限

9.1 适合场景

Multica 比较适合：

  • 已经在团队里使用 Claude Code / Codex / OpenCode 等 CLI
  • 希望把 Agent 纳入 Issue 流程
  • 有多个 Agent 或多个执行机器
  • 需要自托管，代码和凭证不希望交给第三方运行
  • 希望沉淀团队 Agent 使用经验
  • 想把周期性研发任务交给 Agent

典型任务包括：

  • bug 修复
  • issue triage
  • 文档更新
  • 依赖升级
  • 代码审查初筛
  • 测试补齐
  • 发布检查
  • 安全巡检

9.2 可能的局限

Multica 不是银弹。

使用前要理解几个限制：

  • 它依赖底层 Agent CLI 的能力和稳定性
  • daemon 执行环境需要认真治理
  • 多 Agent 并行会放大权限、成本和冲突问题
  • 自托管需要维护 PostgreSQL、对象存储、邮件、反向代理等基础设施
  • Agent 生成代码仍需要人类 review
  • Skill 沉淀需要团队纪律，否则会变成另一堆没人维护的文档

一句话：Multica 能把 Agent 管起来，但不能替你定义好工程边界。
