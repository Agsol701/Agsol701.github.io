论文精读：A Programming Paradigm for Spatiotemporal Composability——理解 DeepSeek Harness 背后的 Cordis 范式

source: spatiotemporal-composability
Sep 16, 2026

写在前面

DSH（DeepSeek Harness）采用“Everything is a Plugin”的架构，而这套插件架构的理论基础不是简单的事件总线或依赖注入容器，而是 Cordis 提出的时空可组合性。

论文《A Programming Paradigm for Spatiotemporal Composability》试图回答一个很难、但对插件系统和自演化 Agent 极其重要的问题：

一个长期运行的系统，怎样在不重启进程、不破坏其他组件、也不丢失运行时状态的前提下，动态增加、删除和替换组件？

论文把问题拆成两个正交维度：

  • 时间可组合性：组件卸载后，它产生的副作用能否被完整撤销。
  • 空间可组合性：组件依赖能否被声明、解析，并随着提供者变化自动驱动生命周期。

它进一步将 Effect（Effect，效应）与 Coeffect（Coeffect，共效应）从编译期形式系统提升为运行时机制，提出 Revertible Effect（可逆效应）、Reactive Coeffect（响应式共效应）和 Context Paradigm（上下文范式），并通过一个动态组件演算证明恢复精确性、依赖顺序、进展性与汇合性。最后，论文用 Cordis 和 Koishi 展示工程实现。

这篇文章不做逐句翻译，而是按“问题直觉 → 数学模型 → 组件演算 → Cordis 实现 → DSH 联系 → 局限与学习路线”重构论文。阅读时建议始终抓住一句话：

组件能安全热插拔，不只因为它有卸载回调，而是因为它与环境的所有交互都经过一个可追踪、可恢复、可解析依赖的 Context。

1.2 一句话结论

这篇论文给出的核心答案是：

把组件对环境的修改建模成“动作及其逆操作”，把组件对环境的要求建模成“可响应的依赖声明”，再强制两者都通过统一 Context 执行，就可以在一定前提下让动态组件像静态组合一样可推理。

这里的“一定前提”很重要。论文并没有证明任意副作用都能安全撤销，而是要求：

  • 组件的相关副作用必须经过 Context。
  • 每个 Effect 必须提供正确的逆操作。
  • 同一 Coeffect 上允许并发组合的操作必须满足交换性。
  • 依赖关系必须无环，或者由工程层主动拆环。
  • 系统外部已经发生的不可逆输出不属于精确恢复保证。

1.3 四层贡献

论文的贡献可以分成四层：

层次 贡献 解决的问题
局部时间 Revertible Effect 单个组件怎样撤销自己的副作用
局部空间 Reactive Coeffect 单个组件怎样随依赖出现或消失而启停
全局组合 Context Paradigm + Independence 多组件副作用交错后怎样独立撤销
系统语义 Dynamic Composition Calculus 整个系统是否恢复、是否死锁、最终状态是否唯一

前三层回答“机制为什么成立”，第四层回答“很多组件交错运行时，局部保证是否还能扩展成全局保证”。

二、为什么动态组合比普通插件机制难

2.1 静态组合与动态组合

传统静态组合包括函数调用、模块导入和类继承。它们的绑定关系通常在编译期或启动期确定，程序运行期间不会任意变化。

动态组合要求组件在运行时被：

  • 加载；
  • 卸载；
  • 替换；
  • 重新配置；
  • 按依赖自动激活或失活。

一旦允许这些操作，问题就不再只是“能否导入一段代码”，而是“这段代码留下的一切是否都能被安全收回”。

2.2 时间维度：删除代码不等于删除影响

假设插件启动时执行：

4

registerCommand('deploy', handler)
eventBus.on('message', listener)
setInterval(refresh, 10_000)
cache.set('state', value)

仅仅从模块注册表里删掉插件，并不会自动：

  • 注销命令；
  • 移除监听器；
  • 清理定时器；
  • 恢复缓存；
  • 撤销插件创建的子组件。

传统 deactivate() 或 dispose() 方法还存在一个结构性问题：创建副作用与清理副作用分散在两个位置。只要作者漏写一项，系统就会泄漏资源或保留幽灵行为。

论文把时间可组合性定义为：

组件移除时，它对共享环境所做的修改能够被完整、安全地逆转。

2.3 空间维度：依赖不是一次性的构造参数

普通 Dependency Injection（DI，依赖注入）通常在构造对象时解析依赖。但动态系统中的依赖会变化：

  • Provider（提供者）尚未加载；
  • Provider 被卸载；
  • Provider 被另一个实例替换；
  • 同一逻辑依赖在不同 Context 中解析到不同实现；
  • 某个组件只应访问它声明过的能力。

因此，空间可组合性不只是“找到对象”，而是：

组件能够声明依赖，运行时能够持续维护依赖拓扑，并在依赖变化时协调组件生命周期。

2.4 进程与容器只是粗粒度替代方案

操作系统通过销毁进程提供粗粒度时间可组合性，容器编排系统通过 Service（服务）提供粗粒度空间可组合性。

这套方案能用，但粒度不匹配：

  • 为删除一个插件重启整个进程，会丢失缓存、连接和进行中的任务。
  • 为表达进程内组件依赖而拆成多个服务，会引入网络、序列化和运维成本。
  • 为保证可用性而准备多副本，是用资源冗余弥补组件不可独立恢复。

Cordis 的目标是把类似的组合能力下沉到同一地址空间里的组件粒度。

2.5 为什么自演化 Agent 更需要它

普通插件系统的变更由人触发，频率相对低。Self-Evolving Agent Harness（自演化 Agent 运行时）可能持续生成、部署和替换自身组件。

如果每次变更都重启进程：

  • 高频重启会造成累计不可用时间；
  • 进行中的 Agent 任务会被打断；
  • 进程内记忆、连接与缓存会丢失；
  • 错误变更可能破坏负责恢复的同一个进程。

如果没有声明式依赖，组件只能自行监听其他组件的变化，最终形成不可验证的临时协议。论文因此把自演化 Agent 视为时空可组合性的代表性未来场景，而 DSH 正是 Cordis 的实际使用者。

三、理论预备：Effect、Coeffect 与 Context

3.1 Effect：计算对环境做了什么

Effect 描述计算怎样修改环境。一个有副作用的函数可以抽象为：

$$ f : \Gamma \times X \rightarrow \Gamma \times Y $$

其中：

  • $X$ 是输入；
  • $Y$ 是输出；
  • $\Gamma$ 是 Context 类型；
  • $\Gamma$ 的变化编码了副作用。

固定输入后，Effect 可以看成一个 Context 变换：

$$ f : \Gamma \rightarrow \Gamma $$

例如注册监听器、创建服务、写入依赖表，都可以理解成 Context 状态变换。

3.2 Coeffect：计算要求环境提供什么

如果说 Effect 是“计算向外做了什么”，Coeffect 就是“计算从外部需要什么”。

例如一个数据库插件可能提供 database，业务插件声明自己需要 database。后者能否运行，取决于当前 Context 是否提供该 Key（键）。

论文把 Coeffect Context 表示为依赖类型的有限偏函数：

$$ \Sigma \triangleq (k : K) \rightharpoonup V_k $$

其中：

  • $K$ 是依赖 Key 集合；
  • $V_k$ 是 Key $k$ 对应的值类型；
  • $\Sigma$ 是当前已经提供的 Key 到值的映射。

这种写法强调：不同 Key 可以有不同值类型，依赖访问在理论上是类型安全的。

3.3 二者为什么正好对应时空问题

Effect 与 Coeffect 分别指向相反方向：

概念 方向 动态组合问题
Effect 计算修改环境 组件卸载后怎样撤销
Coeffect 计算要求环境 依赖变化后怎样协调生命周期

传统 Effect/Coeffect 系统主要用于编译期分析，且作用域通常由词法结构固定。论文的创新点不是发明这两个词，而是把它们变成运行时可操作的数据结构和协议。

3.4 Context 不是普通参数对象

本文中的 Context 不能只理解成一个装 Service 的 Map。它同时承担：

  • 副作用入口；
  • 逆操作累加器；
  • 依赖表；
  • 依赖解析作用域；
  • 组件父子层级；
  • 生命周期归属边界；
  • 权限与拦截策略载体。

因此，Context 是整个范式的中介层。没有“所有相关交互必须经过 Context”这条纪律，后面的恢复定理就没有约束力。

四、可逆 Effect：把副作用和逆操作绑在一起

4.1 从普通 Effect 到可逆 Effect

论文把一个可逆 Effect 建模为：

$$ e : \Gamma \rightarrow \Gamma \times (\Gamma \rightarrow \Gamma) $$

它接收当前状态 $\gamma$，返回：

  • 新状态 $\delta$；
  • 一个逆函数 $g$。

并要求逆函数在这次应用产生的状态上恢复原状态：

$$ g(\delta) = \gamma $$

注意，这里要求的是针对当前状态的左逆，不要求 $g$ 在任意状态上都是 $e$ 的全局逆。这允许逆操作捕获本次执行前的局部信息。

例如设置配置项时，逆操作可以捕获旧值：

function setConfig(ctx, key, nextValue) {
  const previousValue = ctx.config[key]
  ctx.config[key] = nextValue

  return () => {
    ctx.config[key] = previousValue

逆操作在 Effect 发生的位置被创建，因此创建与清理保持局部性。

4.2 Effect Context 与恢复累加器

论文定义 Effect Context：

$$ \partial\Gamma \triangleq \Gamma \times (\Gamma \rightarrow \Gamma) $$

可以把它理解为二元组 $(\gamma, \varphi)$：

  • $\gamma$：当前 Context 状态；
  • $\varphi$：目前所有逆操作组合成的恢复函数。

初始状态是：

$$ (\gamma_0, id_\Gamma) $$

每执行一个 Effect，就把其逆操作组合到 $\varphi$ 中。恢复时执行：

$$ recover(\gamma, \varphi) = (\varphi(\gamma), id_\Gamma) $$

4.3 为什么逆操作必须反序执行

假设先执行 $f_1$，再执行 $f_2$，对应逆操作为 $g_1$ 与 $g_2$。恢复顺序必须是：

$$ g_1 \circ g_2 $$

也就是先撤销 $f_2$，再撤销 $f_1$。这就是 LIFO（Last In, First Out，后进先出）。

论文定义了一种扭曲组合：

$$ (f_1, g_1) \circ (f_2, g_2)

(f_1 \circ f_2, g_2 \circ g_1) $$

前向操作按正常顺序组合，逆操作按相反顺序组合。这不是实现细节，而是 Effect 能组合的代数基础。

4.4 为什么只有 dispose() 还不够

一个普通的 dispose() 回调只能说明“作者提供了清理入口”，却无法保证：

  • 每个 Effect 都被登记；
  • 清理顺序正确；
  • 清理只执行一次；
  • 中途加载失败时只撤销已完成部分；
  • 父组件卸载时子组件也被撤销；
  • 多个组件交错后仍能单独卸载其中一个。

Cordis 的做法是让 ctx.effect(callback) 成为统一原语。回调返回或 yield 逆操作，运行时统一追踪并按 LIFO 组合。

4.5 Effect Iterator：处理多步和异步加载

真实组件的加载不是单个原子动作，而是一系列可能异步的步骤。论文用 Effect Iterator（效应迭代器）表示：

$$ \mathfrak{I}_\Gamma

\mu\mathfrak{I}.; \Gamma \rightarrow \Gamma \times (\Gamma \rightarrow \Gamma) \times Maybe(\mathfrak{I}) $$

每一步返回：

  • 新状态；
  • 当前步骤的逆操作；
  • 下一步 Continuation（延续），或结束标记。

这对应主流语言中的 Generator（生成器）或异步迭代器。好处是每两个步骤之间都有安全边界：如果依赖在加载中途变化，运行时可以停止继续执行，并仅撤销已经完成的步骤。

4.6 局部时间可组合性到底保证什么

对单个组件而言，只要：

  • 每个步骤返回的逆操作确实能恢复该步骤；
  • 逆操作按 LIFO 执行；

就能恢复到组件加载前的状态。

但这仍然只是局部保证。当组件 A 加载一半、组件 B 插入操作、然后 A 被卸载时，A 的逆操作面对的已不是它当初产生的状态。要扩展成全局保证，还需要 Effect Independence（效应独立性），这会在第七章讨论。

五、响应式 Coeffect：让依赖变化驱动生命周期

5.1 依赖满足谓词

一个组件声明依赖集合 $d \subseteq K$。当 Context 中包含所有依赖 Key 时，称该声明被满足：

$$ \sigma \vDash d \triangleq \forall k \in d.\; k \in dom(\sigma) $$

组件不应该先运行再发现依赖缺失，而应该只在满足谓词成立时激活。

5.2 三类依赖变化

对 Context 从 $\sigma$ 到 $\sigma’$ 的每次变化，运行时按组件声明 $d$ 分类：

$$ notify_d(\sigma, \sigma') = \begin{cases} activating & \sigma \not\vDash d \land \sigma' \vDash d \\ deactivating & \sigma \vDash d \land \sigma' \not\vDash d \\ neutral & otherwise \end{cases} $$
  • activating：依赖刚刚全部满足，启动组件。
  • deactivating：原本满足的依赖丢失，卸载组件。
  • neutral：满足状态未变化，无需切换生命周期。

这就是“Reactive”的含义：依赖声明不是静态文档，而是 Context 每次变化时都参与分类。

5.3 set 本身也是可逆 Effect

论文定义：

$$ set(k, v)(\sigma)

(\sigma[k \mapsto v],; \lambda\sigma’.\sigma’ \setminus k) $$

写入依赖表时，同时返回删除该 Key 的逆操作。因此：

Coeffect 的提供操作本身就是 Effect，而 Effect 又是可逆的。

这一步把时间与空间两个方向真正接在一起：Provider 卸载时，其 Key 会通过逆操作退出依赖表；Key 消失又会触发 Consumer（消费者）失活。

5.4 依赖隔离

Coeffect Isolation（共效应隔离）允许同一个逻辑 Key 在不同 Context 中解析成不同值。

论文使用两层映射：

$$ key \rightarrow realm \rightarrow value $$

其中 Realm（域）可以理解为依赖实例的命名空间。例如：

  • 测试 Context 的 database 指向内存数据库；
  • 生产 Context 的 database 指向 MySQL；
  • 不同租户的 storage 指向不同实例。

隔离不是修改共享表，而是派生新的子 Context，因此恢复时直接丢弃子 Context 即可。

5.5 依赖拦截

Coeffect Interception（共效应拦截）不改变 Key 解析到哪个 Provider，而是改变“怎样调用它”。

它可以承载：

  • 文件路径权限；
  • 数据库读写级别；
  • 限流策略；
  • 日志和审计信息；
  • 租户信息；
  • 调用链元数据。

Context 携带的元数据可以覆盖组件声明的元数据，因此外层编排器能在不修改 Provider 和 Consumer 的情况下收紧权限。

5.6 局部空间可组合性的边界

局部空间可组合性保证：

  • 组件只在依赖满足时激活；
  • 依赖丢失一定会被发现并触发失活。

它还没有证明两件全局性质：

  • Provider 是否会等所有 Consumer 卸载完成后再真正删除资源；
  • Consumer 从激活到卸载期间看到的 Provider 是否保持一致。

这两个性质需要组件生命周期演算中的 Ordering（顺序性）和 Resolution Coherence（解析一致性）定理。

六、Context Paradigm：把 Effect 与 Coeffect 统一起来

6.1 统一 Context

论文将 Effect Context 与 Coeffect Context 递归组合为：

$$ \Gamma^\infty \triangleq \mu\Gamma.\; \Gamma \times (\Gamma \rightarrow \Gamma) \times \Sigma $$

它包含：

  • 当前层以下的 Context；
  • 当前层的逆操作累加器；
  • 当前层的 Coeffect 表。

递归结构允许 Context 形成树：父 Context 聚合子 Context 的 Effect，子 Context 可以覆盖依赖 Realm 或拦截策略。加载组件相当于在树中“插入”，卸载组件相当于通过累加器“拔出”。

6.2 Context Paradigm 的真正约束

论文所谓 Context Paradigm，不只是“代码里有一个 ctx 参数”，而是两条纪律：

  1. 组件对共享环境的相关修改必须通过 Context。
  2. 组件对共享能力的访问必须通过 Context 中某个 Key 的公开操作。

一个 Effect 如果偷偷写全局变量，或者一个组件绕过 ctx.database 直接持有底层连接，它就逃出了范式的边界。

6.3 Key 不只是一个值

每个 Coeffect Key 包含：

  • 值类型 $V_k$；
  • 允许的操作集合 $A_k$；
  • 后续加入的交换性证明。

限制操作集合很重要，因为论文不是按内部存储完全相等来比较状态，而是按公开操作能否区分状态来比较。

6.4 为什么需要观测等价

物理状态往往无法原样恢复：

  • malloc 后再 free，堆布局不一定回到原样；
  • 创建并删除一个对象后，再创建对象可能拿到新 ID；
  • 注册项的内部顺序可能变化；
  • 分配器计数器可能继续递增。

如果外部通过公开接口无法观察这些差异，那么它们对组件语义无影响。论文据此定义 Observational Equivalence（观测等价）：

两个值在该 Key 允许的所有操作序列下，定义域和可观察输出都相同，则视为等价。

记作：

$$ v \simeq_k v' $$

Context 的等价关系由各 Key 的等价关系逐点组合。

6.5 恢复不是字节级回滚

论文中的“恢复”应理解为：

$$ recovered \simeq original $$

而不是：

$$ recovered = original $$

这让理论适用于真实运行时，但也限定了结论：恢复保证只覆盖 Context 所建模、公开操作所能观察的状态。

6.6 接口设计会影响可组合性

观测能力越强，等价关系越细，操作越难交换。

例如分配接口如果保证“返回当前最小空闲编号”，两个并发分配的顺序就能被观察；如果接口只保证“返回一个新鲜句柄”，并且句柄可重命名，那么不同分配顺序可能观测等价。

因此，一个很深的工程结论是：

少暴露不必要的内部顺序和身份，不只是封装得更好，也会直接扩大可安全组合的操作集合。

七、从局部恢复到全局恢复：独立性与交换性

7.1 为什么多组件交错会破坏简单回滚

假设执行顺序是：

1
2
3

A.apply
B.apply
A.dispose

A.dispose 执行时，状态中已经包含 B 的修改。若 A 的逆操作直接恢复一份旧快照，就可能顺便抹掉 B 的修改。

所以正确目标不是“回到 A 启动前的整份状态”，而是：

删除 A 的贡献，同时保留 B 在同一时间段内产生的贡献。

7.2 Effect Independence

论文要求两个 Effect Iterator 的所有相关变换彼此交换，包括：

  • 前向变换与前向变换；
  • 逆变换与逆变换；
  • 前向变换与对方的逆变换；
  • 对方变换不能改变本 Effect 产生的逆操作、输出和后续 Continuation。

核心交换条件可以写成：

$$ f \circ g \simeq g \circ f $$

它比“两个最终前向结果相同”更严格，因为卸载时会混合使用前向操作与逆操作。

7.3 不同 Key 天然独立

如果操作 A 只读写 Key routes，操作 B 只读写 Key timers，它们的 Lift（提升）只修改各自绑定，因此天然交换。

这就是统一 Context 和 Key 局部操作的价值：它把原本全局的独立性问题，分解成各 Key 上的局部证明。

7.4 同一 Key 需要交换性证明

两个组件都向同一事件表注册不同监听器时：

  • 每次注册获得唯一 ID；
  • 逆操作只删除自己的 ID；
  • 注册顺序不会改变接口可观察结果。

这类操作可以交换。

但有序 Middleware（中间件）链通常不能交换，因为 A 在 B 前和 B 在 A 前会产生不同调用结果。此时顺序必须由组件依赖或组件内部的 LIFO 结构显式表达，不能假装它们独立。

7.5 组件提供方承担证明责任

论文让每个 Coeffect 携带“其公开操作两两独立”的 Witness（见证）。这样证明责任落在 Provider，而不是每个 Consumer 身上。

工程实现不会运行形式证明，因此这里是一个设计契约：

  • Effect 作者保证逆操作正确；
  • Coeffect 作者保证声明为可组合的操作确实交换；
  • Runtime 负责按契约追踪、调度和恢复。

7.6 全局恢复的直观结论

在独立性条件成立时，一个组件的逆操作可以跨过其他组件的操作：

$$ g_A(f_B(state)) \simeq f_B(g_A(state)) $$

因此，无论其他组件在中间执行了什么，删除 A 后都能保留 B 的结果。这是后面 Recovery Exactness（恢复精确性）定理的核心。

八、组件演算：Component、Fiber 与生命周期

8.1 Component 的三元组

论文把 Component（组件）定义为：

$$ Component = (d, p, e) $$

其中：

  • $d$：组件需要的 Coeffect Key 集合；
  • $p$：组件可能提供的 Coeffect Key 集合；
  • $e$：组件激活时执行的 Effect Iterator。

这三个量分别对应“读接口”“写接口”和“运行行为”。

8.2 Fiber 是 Component 的运行实例

一个 Component 可以被实例化多次，每个运行实例称为 Fiber（纤程）。这里的 Fiber 不是操作系统线程，而是带生命周期状态的组件实例。

Fiber 记录：

  • Component 的 $d$、$p$、$e$；
  • 父 Fiber；
  • 自己提供的 Coeffect 表；
  • Retirement Flag（退役标记）；
  • 生命周期状态；
  • 当前累积的逆操作；
  • 激活时绑定的 Provider View（提供者视图）。

8.3 四种生命周期状态

论文的核心状态机是：

  • INACTIVE：未激活；
  • RELOADING：正在加载或重新加载；
  • ACTIVE：正在提供服务；
  • UNLOADING：正在撤销 Effect。

8.4 为什么退役与删除分开

运行中的 Fiber 不能直接从注册表删除，否则它的逆操作累加器也会丢失，产生 Effect 泄漏。

因此外部编排器只能：

  1. 标记 Fiber 退役；
  2. 生命周期系统让它进入 UNLOADING；
  3. 执行全部逆操作；
  4. 确认自身表为空、没有子节点；
  5. 最后删除 Fiber 记录。

这类似安全资源释放中的“停止接收新流量 → 排空依赖 → 释放资源 → 删除实例”。

8.5 Target View：当前应该依赖谁

Fiber 的 Target View（目标视图）把每个依赖 Key 映射到当前 Provider Fiber：

$$ target_n(\gamma) : d_n \rightarrow FiberName $$

如果 Fiber 已退役或依赖不满足，则 Target 为 $\bot$。

运行时把 Target View 与 Fiber 激活时提交的 Committed View（已提交视图）比较：

  • 相同：继续当前生命周期；
  • 不同：现有绑定已经过时，进入卸载或转向流程。

比较 Provider 身份而不是值很关键。两个 Provider 即使提供相等值，也不是同一个生命周期来源；旧 Provider 被替换时，Consumer 必须重新绑定。

8.6 依赖撤销顺序

如果 B 依赖 A，那么卸载 A 时必须先卸载 B：

sequenceDiagram
    participant O as Orchestrator
    participant A as Provider A
    participant B as Consumer B

    O->>A: 标记退役
    A->>B: Provider 不再进入新的 target view
    B->>B: UNLOADING，撤销自身 Effect
    B-->>A: 依赖排空完成
    A->>A: 执行自身逆操作
    A-->>O: INACTIVE，可安全删除

Provider 在真正删除绑定前先退出 ACTIVE，让 Consumer 的 Target 变成不满足；但旧绑定仍保留到 Consumer 清理完成，因此 Consumer 在自己的 teardown 中仍能访问原 Provider。

8.7 九条规则的分工

论文给出九条运行规则，可分为两类：

  • Orchestration Rule（编排规则）：插入、退役、删除 Fiber。
  • Lifecycle Rule（生命周期规则）：开始加载、执行迭代、完成加载、转向、离开 Active、执行卸载。

关键思想是：外部编排器只表达“希望谁存在”，不直接操纵内部生命周期状态；生命周期由依赖解析自动推进。

九、四个核心元理论结果

9.1 Preservation：系统不变量保持

Preservation（保持性）说明：如果 Fiber Registry（纤程注册表）在一步之前满足良构条件，那么执行任意规则后仍然良构。

这些条件包括：

  • 不同 Fiber 的 Provision 不冲突；
  • Provider View 指向有效 Fiber；
  • 生命周期状态、累加器和依赖表之间一致；
  • 父子关系保持树结构。

这是后续证明的地基：规则不会把系统推进到结构损坏的状态。

9.2 Recovery Exactness：撤销一个 Fiber 只删除它自己

论文的 Theorem 68 证明：在一个 Fiber 的 Episode（生命周期片段）中，即使其他 Fiber 的步骤交错执行，应用该 Fiber 的累加器后，最终状态仍等价于“只执行了那些其他 Fiber 的步骤”。

直观表达为：

1
2
3
4
5

执行 A 的步骤
穿插执行 B、C 的步骤
撤销 A
≈
从未执行 A，只执行 B、C

Corollary 69 进一步说明，Episode 完整关闭后，Fiber 自己的 Coeffect 表为空，因此可以被安全删除。

这正是全局时间可组合性。

9.3 Ordering 与 Resolution Coherence

Theorem 70 给出依赖顺序：

  • Consumer 只会在依赖已经由 Active Provider 提供时开始激活；
  • Provider 的 Episode 早于 Consumer 开始；
  • Provider 必须晚于 Consumer 结束；
  • Consumer 运行期间，其已提交 Provider 保持可访问。

Theorem 71 给出解析一致性：一个加载过程中的每一步都针对同一份 Provider View 执行。如果 Target 在中途改变，Fiber 不会把新旧依赖混在一次成功加载里，而是转向卸载，撤销已完成步骤。

这两个结果共同构成全局空间可组合性。

9.4 Progress：不会停在半完成状态

在以下前提下：

  • 组件依赖优先关系无环；
  • 每个 Effect Iterator 长度有限；
  • 系统涉及的 Fiber 名称集合有限；

论文证明：

  • 非静止状态下一定有某条生命周期规则可执行；
  • 每个 Fiber 的步骤数有上界；
  • 所有最大生命周期序列最终到达 Quiescent State（静止状态）。

换句话说，系统不会因为生命周期协议自身停在无法推进的中间态。

9.5 Confluence：调度顺序不同，最终组合相同

Confluence（汇合性）是这篇论文最强的结果之一。

在组件对 Provision 是 Total（完全提供）、最终达到静止状态等条件下，只要两次执行包含相同的编排动作，即使生命周期步骤交错顺序不同，最终状态也在 Fiber 重命名和观测等价意义下相同。

工程含义是：

可以像系统是静态组装的一样推理最终状态，而不必枚举所有异步加载和卸载交错。

例如编排器依次执行“增加组件、替换 Provider、删除旧 Provider”，系统最终会到达与“从一开始就按最终配置启动”观测等价的状态。

9.6 这些定理没有保证什么

论文证明的是 Context 内状态，而不是运行过程中已经对外产生的所有历史。

它不保证：

  • 已发送消息能从接收方撤回；
  • 已扣款操作能被物理抹除；
  • 已写入外部共享文件的字节自动回滚；
  • 恶意代码无法绕过 Context；
  • 任意副作用都满足交换性；
  • 实现运行时自动验证形式 Witness。

这些边界决定了 Cordis 是生命周期与组合框架，不是数据库事务、分布式事务或安全沙箱的替代品。

十、Cordis 如何把理论落到工程实现

10.1 三层结构

论文中的 Cordis 分三层：

  1. Core Library（核心库）：Effect 追踪、Coeffect 解析、Fiber 生命周期。
  2. Component Loader（组件加载器）：声明式配置、增量 Reconciliation（协调）。
  3. Application Framework（应用框架）：例如 Koishi、DSH。

Cordis 不规定 Web、Bot 或 Agent 的业务语义，只规定组件怎样动态组合，因此论文称它为 Meta-Framework（元框架）。

10.3 ctx.effect 的本质

ctx.effect 驱动回调或 Generator，把每一步产生的 Disposer（清理器）按 LIFO 组合。它还有两个关键机制：

  • Single-shot disposal：同一个逆操作最多执行一次。
  • Parent composition：子 Context 的恢复函数也被登记为父 Context 的 Effect。

因此，卸载父组件时可以递归卸载它创建的所有子组件。

10.4 生命周期中的双层中断

Cordis 在两个层次检查依赖是否过时：

  • 迭代边界：每执行一个 Effect 步骤前检查 Target 是否稳定。
  • 状态转换边界：一次 Reload/Unload 完成后，再判断应该停在当前状态还是立即反向切换。

如果加载中途 Provider 被替换：

  1. 当前迭代停止；
  2. 已完成步骤的逆操作被保留；
  3. Fiber 进入卸载；
  4. 清理完成后，基于新 Provider View 重新加载。

10.5 Proxy 介导的 Context 访问

Cordis 可以让组件通过 ctx[key] 访问 Coeffect，而不是直接从全局容器读取。

访问时沿 Fiber 父链查找：

  • Key 在已提交 View 中：返回绑定；
  • Key 声明了但当前未激活：抛出 Inactive Access；
  • 一直没有声明：抛出 Undeclared Access。

这让依赖声明同时具有能力请求的含义：组件只能通过受控代理访问自己声明过的能力。

10.6 声明式配置与增量协调

Cordis Loader 把目标系统描述成配置树。每个 Entry（条目）包含：

  • 稳定 ID；
  • 组件模块 URL；
  • Isolation 配置；
  • Interception 配置；
  • 组件 Config；
  • Disabled 状态。

配置变化时，Loader 选择最小扰动：

  • ID 或 URL 变化：重建 Fiber；
  • Isolation 变化：重分配 Realm；
  • Interception 变化：原地更新；
  • Config 变化：交给组件判断是否需要重载；
  • Disabled 变化：卸载或重新加载。

汇合性定理为增量协调提供理论依据：无论中间采用什么合法顺序，静止后的状态由最终配置决定。

10.7 HMR 的三阶段

HMR（Hot Module Replacement，热模块替换）分为：

  1. Module classification：计算哪些模块可热替换，哪些变化必须完整重启。
  2. Stale-entry detection：找出依赖树触达变化模块的配置 Entry。
  3. Transactional reload：备份模块缓存，替换相关 Fiber；若导入失败，则恢复缓存与旧 Fiber。

由于 Fiber 已经界定组件的 Effect 与 Coeffect，Cordis 不要求开发者再手写 HMR Acceptance Boundary（接收边界）。

十一、Koishi 案例与实验证据应该怎样解读

11.1 论文提供的证据

论文以 Koishi 为生产案例。Koishi 是构建在 Cordis 上的开源聊天机器人框架，论文报告其生态经过四年发展，拥有超过 4000 个社区插件。

案例用于支持两点：

  • 表达能力：Context、Effect、Coeffect 和 Fiber 足以承载完整生产系统。
  • 通用性：同一组合模型既用于服务端 Bot，也用于浏览器端管理控制台。

11.2 时间可组合性的实际体现

Koishi 可以在不重启整个进程的情况下：

  • 从控制台禁用一个插件；
  • 撤销该插件经 Context 注册的事件、服务等 Effect；
  • 开发时保存代码后执行 HMR；
  • 保留其他插件的缓存与连接。

这说明 Cordis 的卸载模型已经在开放插件生态中被长期使用。

11.3 空间可组合性的实际体现

Koishi 的适配器、数据库驱动、功能插件来自独立作者。Provider 更换时，只有解析结果发生变化的 Consumer 重新激活；依赖尚不可用的插件保持 Inactive，而不是启动后报错。

这种生态比“所有插件只调用 Host 固定扩展点”更能体现真正的插件间依赖拓扑。

11.4 论文没有做定量实验

论文主动承认：Koishi 案例是存在性与采用度证据，不是受控实验。

它没有提供：

  • 相比其他插件框架的吞吐或延迟数据；
  • Effect 追踪的内存与 CPU 开销；
  • HMR 成功率；
  • 插件作者生产率对照实验；
  • 形式模型与实现的一一机器验证。

此外，Koishi 当前使用 Cordis v3，而论文描述的是重新细化语义和 Loader 的 Cordis v4。二者共享核心模型，但不能把 Koishi 的全部生产历史直接等同于 v4 实现验证。

十二、这篇论文与 DeepSeek Harness 的直接关系

12.1 DSH 确实构建在 Cordis 上

DSH 官方仓库明确说明，它采用“Everything is a Plugin”架构并由 Cordis 驱动；官方 Cordis Primer 也将 Cordis 称为 DSH 底层的插件框架。

DSH 将 Cordis 及 Loader、Group、Include、HMR 等包以 @deepseek-ai/* 命名空间 Vendor（源码内置并固定版本），使框架层可审计、可修改、可固定。

因此这篇论文不是与 DSH 松散相关的理论文章，而是在解释 DSH 插件运行时依赖的核心设计。

12.2 “Everything is a Plugin”意味着什么

在 DSH 中，下列能力都可以作为挂载到共享 Context 的插件：

  • Agent Loop（Agent 循环）；
  • LLM Adapter（大模型适配器）；
  • Tool（工具）；
  • 文件系统能力；
  • Session（会话）与持久化；
  • Context 管理；
  • Web、命令行或自动化入口；
  • 策略、日志和观测组件。

“一切皆插件”不只是项目组织方式。结合论文，它意味着这些能力都应该具备：

  • 明确的依赖声明；
  • 可跟踪的生命周期 Effect；
  • Provider 变化时的响应式协调；
  • 独立卸载与替换的可能性。

12.3 DSH 插件开发为什么强调 inject

一个 DSH 插件声明 inject，并不是为了让 TypeScript 少写一次 Import，而是在声明自己的 Coeffect Specification。

运行时据此决定：

  • 组件当前是否满足激活条件；
  • ctx.<service> 访问是否有权限；
  • 哪个 Provider View 被提交；
  • Provider 变化时哪些插件需要重载；
  • Provider 卸载时应该先排空哪些 Consumer。

12.4 事件监听为什么也是 Effect

DSH 官方开发文档指出，通过 ctx.on() 注册的事件监听器会在插件卸载时自动删除。

这正是可逆 Effect 的直接体现：

12.5 对自演化 Agent 的意义

如果未来 Agent 能生成一个新的工具插件、策略插件或记忆组件，Cordis 范式允许运行时：

  1. 把新组件作为 Fiber 插入；
  2. 等待其依赖满足；
  3. 分步安装 Effect；
  4. 出错或过时时撤销已完成部分；
  5. 替换旧 Provider；
  6. 只重载真正依赖该 Provider 的组件；
  7. 不重启整个 Harness。

但论文当前只把这列为重要未来验证方向，并没有给出 DSH 自主改写自身后长期运行的量化实验。学习时应区分“理论适用场景”“DSH 已采用 Cordis”和“自演化能力已经被完整验证”这三件事。

十三、系统边界、限制与开放问题

13.1 Acquisition 与 Emission

论文把跨越系统边界的操作分成两阶段：

  • Acquisition（获取）：在系统内部获得资源句柄，例如 open、malloc、启动子进程。这通常可以通过 close、free、终止子进程恢复。
  • Emission（发射）：通过句柄把数据发送到外部，例如写文件、发网络包、扣款。一旦外部观察到，通常无法精确撤销。

因此，Context 能跟踪“持有文件描述符”，却不能自动让已经发出的网络包消失。

13.2 两种处理外部输出的方法

对不可直接撤销的 Emission，有两类经典策略：

  • Withholding：等状态确定提交后再输出，类似事务的 Output Commit。
  • Compensation：执行补偿动作，例如退款、删除已创建文件。

补偿动作也可以按 LIFO 组合，但它恢复的是业务定义的更粗等价关系，论文现有的交换性证明不能自动沿用。

13.3 Context 不是安全沙箱

依赖声明与 Proxy 可以约束守规矩组件，却拦不住恶意代码直接访问：

  • Node.js 全局对象；
  • 文件系统；
  • 环境变量；
  • 网络；
  • 底层 Provider 引用。

不可信插件仍需 Software Fault Isolation（软件故障隔离）、独立语言运行时、沙箱进程、WebAssembly 或容器等外部边界。

13.4 循环依赖

如果 A 依赖 B 提供的 Key，B 又依赖 A 提供的 Key，两者都不会满足激活条件，会永久 Inactive。

论文建议把双向交互拆成 Core 与 Integration Component（集成组件）。例如把 Server 与 Access Control 拆成：

  • server-core；
  • access-control-core；
  • 同时依赖二者的请求拦截组件；
  • 同时依赖二者的策略管理组件。

这种拆分原则上能消除循环，但组件数量最坏可能随交互对数呈二次增长，增加命名、配置和理解成本。

13.5 Key 的类型与版本问题

形式模型中，只要 Key 相同就建立依赖连接。在独立构建的插件生态里会产生两个问题：

  • Interface Drift（接口漂移）：同一个 Key 的接口在版本升级后发生不兼容变化。
  • Key Collision（键冲突）：不同作者使用同名 Key 表示完全不同的能力。

论文讨论三类方案：

  • Key 加包命名空间；
  • 使用包管理器的 Peer Dependency（对等依赖）约束版本；
  • 运行时检查 Structural Compatibility（结构兼容性）。

Cordis 当前依赖 Peer Dependency，但语义化版本需要作者守约，也难以在同一应用同时加载同包多个版本。统一的版本化依赖模型仍是开放问题。

13.6 运行时不验证证明义务

Cordis 不会自动证明：

  • Disposer 真的恢复了本次 Effect；
  • 同一 Key 的操作真的交换；
  • 所有共享状态真的都经过 Context；
  • 组件的 Provision 声明与实际安装完全一致。

因此，形式系统证明的是“满足契约的组件在这套演算中具有什么性质”，不是“任意 JavaScript 插件天然安全”。

13.7 单案例、单语言与版本差异

论文实现使用 TypeScript，生产案例只有 Koishi。语言无关性主要来自形式模型与设计讨论，而不是多语言实现对照。

此外，Cordis 仍处于活跃开发期，API 可能变化。学习时应优先掌握：

  • Effect 与 inverse 的配对；
  • Coeffect 声明与响应式解析；
  • Context mediation；
  • Fiber 生命周期与依赖排空；
  • 观测等价与交换性。

不要把论文伪代码中的 API 名称机械当作当前版本的稳定公共 API。

十四、与相邻技术的区别

14.1 与普通 DI Container 的区别

普通 DI Container 重点是“创建对象时怎样找到依赖”。Cordis 还处理：

  • Provider 运行时出现或消失；
  • Consumer 自动激活或失活；
  • Provider 替换后的定向重载；
  • 依赖作用域隔离；
  • 组件 Effect 的回收。

所以 Cordis 可以包含 DI，但不等同于 DI。

14.2 与 try/finally、RAII 和 Bracket Pattern 的区别

RAII（Resource Acquisition Is Initialization，资源获取即初始化）、try/finally 和 Bracket Pattern（括号模式）适合词法作用域内的资源释放。

动态组件的生命周期可能跨越很长时间，且结束点由配置和依赖变化决定，不对应一个固定调用栈。Cordis 把逆操作保存到 Fiber，使动态生命周期也拥有类似结构化资源管理。

14.3 与数据库事务的区别

数据库事务依赖数据库内部日志、隔离和原子提交。Cordis 管理的是应用内异构 Effect：事件监听、Service 注册、定时器、子组件、配置等。

Cordis 不提供通用 ACID（Atomicity, Consistency, Isolation, Durability，原子性、一致性、隔离性、持久性），尤其不保证外部 Emission 回滚。

14.4 与 Saga 的区别

Saga 用补偿事务协调多个不可原子提交的分布式步骤。Cordis 的逆操作主要针对 Context 边界内可恢复状态，并依赖交换性实现组件独立撤销。

当 Cordis Effect 跨越外部边界时，确实可能需要 Saga 式补偿，但这属于论文明确区分的更粗恢复语义。

14.5 与容器编排的区别

Kubernetes 等容器编排工具以进程或服务为粒度处理生命周期和依赖。Cordis 以同一进程内的 Component/Fiber 为粒度。

二者不是互斥关系：一个服务内部可以使用 Cordis 管理插件，外部仍由容器平台管理副本、网络和故障恢复。

14.6 与响应式编程的区别

响应式编程通常追踪数据值随时间变化。Cordis 的 Reactivity 主要作用于依赖满足状态和 Provider 身份，驱动的是组件生命周期。

论文指出，Cordis 没有完整响应式系统中的“Turn”与 Glitch Freedom（无毛刺性）语义；但一个 Coeffect 自身可以承载响应式值，形成组件级与数据级两层响应式结构。

十六、常见高频面试题

16.1 什么是时空可组合性？

答：

时空可组合性描述动态组件系统的两个正交能力。

时间可组合性要求组件移除后，其对共享环境产生的 Context 内 Effect 能被完整撤销，而且不破坏其他组件的结果。

空间可组合性要求组件能够声明 Coeffect，运行时持续解析依赖，并在 Provider 出现、消失或替换时自动协调 Consumer 生命周期。

只有二者同时成立，组件才不仅“能加载”，还可以长期运行中安全地插入、删除和替换。

16.2 Revertible Effect 与普通清理回调有什么区别？

答：

普通清理回调通常与副作用创建逻辑分离，运行时也未必知道每个副作用的逆操作。

Revertible Effect 要求每次 Context 变换在发生时就返回自己的 inverse，运行时立即记录，并按 LIFO 组合。这样加载中途失败也只撤销已完成步骤，父组件卸载还能递归撤销子 Effect。

它仍依赖作者保证 inverse 正确；Cordis 负责结构化追踪，不会自动证明业务逆操作。

16.3 为什么恢复要使用观测等价，而不是状态完全相等？

答：

真实系统中的物理状态经常不可复原，例如释放内存后堆布局不同，重新创建对象后 ID 不同。

只要公开操作无法区分恢复前后的状态，这些内部差异就不影响组件行为。因此论文用 Key 的操作集合定义观测等价，并把恢复定理中的等号改读为 $\simeq$。

这也提醒工程实践：接口暴露越多内部身份和顺序，越难获得交换性与可组合性。

16.4 为什么多个组件能独立卸载？

答：

关键不是每个组件各自有 Disposer，而是它们的 Effect 满足 Independence。

不同 Key 上的操作天然局部，通常可以交换；同一 Key 上的操作则要由 Coeffect Provider 保证交换性。当前向变换、逆变换以及它们的组合都可交换时，一个组件的 inverse 可以跨过其他组件的操作，只删除自己的贡献。

对于真正有顺序要求的操作，必须通过组件内部 LIFO 或 Coeffect 依赖显式编码顺序，不能宣称它们独立。

16.5 Provider 卸载时为什么必须先卸载 Consumer？

答：

Consumer 的 teardown 可能仍需访问 Provider。如果先删除 Provider 的绑定，Consumer 的清理逻辑会在依赖缺失时失败。

Cordis 先让 Provider 离开 Active，使其不再进入新的 Target View；这会触发已有 Consumer 进入 Unloading。Provider 保留旧绑定，等待所有依赖它的 Fiber 排空，然后才执行自己的 inverse。

这形成“Provider 先激活、Consumer 后激活；Consumer 先卸载、Provider 后卸载”的嵌套 Episode 顺序。

16.6 Context Paradigm 的系统边界是什么？

答：

只有被 Context Key 重化、且所有访问都经过公开操作的位置，才位于证明边界内。

组件直接写全局变量、访问外部文件或发送网络消息时，如果这些操作没有被 Context 介导，就不受恢复定理覆盖。资源句柄的获取通常可逆，但通过句柄向外发送的数据通常不可逆。

外部输出需要延迟提交或业务补偿；恶意插件还需要进程、WebAssembly 或容器级沙箱。

16.7 Confluence 对工程有什么价值？

答：

汇合性说明，在论文前提满足时，只要编排动作相同，不同合法生命周期调度最终到达观测等价的静止状态。

开发者因此可以按最终声明式配置推理系统，不必分析每一种异步加载与卸载交错。Loader 也可以采用增量协调，而不必每次销毁整个进程并从头启动。

它保证的是最终 Context 状态，不保证中途对外发出的消息历史相同。

16.8 Cordis 与 DeepSeek Harness 是什么关系？

答：

Cordis 是 DSH 底层的插件框架。DSH 官方仓库明确说明其 Everything-is-a-Plugin 架构由 Cordis 驱动，并将 Cordis Core、Loader、Group、Include、HMR 等包以 @deepseek-ai/* 命名空间内置。

DSH 的插件 Service、inject 声明、事件监听自动回收和生命周期挂载，分别对应论文中的 Coeffect、依赖 Specification、Revertible Effect 与 Fiber 管理。

论文为 DSH 的动态组件架构提供理论解释，但自演化 Agent 持续修改自身组件仍被论文列为未来验证方向，不能把理论适用性误写成已经完成的实验结论。
