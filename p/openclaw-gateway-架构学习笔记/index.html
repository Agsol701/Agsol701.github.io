OpenClaw Gateway 架构学习笔记

一句话理解

OpenClaw 的核心不是把每个消息渠道、设备能力、控制 UI 都做成独立后端，而是用一个长期运行的 Gateway 作为本机控制平面。所有控制端、消息渠道和设备节点都通过同一个 Gateway 协议接入，Gateway 负责鉴权、配对、能力声明、事件广播、Agent 运行调度和本地策略执行。

整体技术架构

OpenClaw 的架构可以拆成四类角色。

  1. Gateway 网关：长期运行的守护进程，是控制平面、消息接入面和策略执行面。
  2. 控制平面客户端：macOS App、CLI、Web UI、自动化脚本，通过 WebSocket 访问 Gateway。
  3. 节点：macOS、iOS、Android、headless 等设备，以 role: "node" 连接 Gateway，并声明可执行能力。
  4. 消息渠道和 WebChat：WhatsApp、Telegram、Slack、Discord、Signal、iMessage、WebChat 等入口由 Gateway 统一管理。

官方文档强调“每台主机一个 Gateway”。这个约束很关键，因为 WhatsApp 等渠道会话、Agent 会话文件、工具权限和设备信任都围绕这个 Gateway 实例形成一个本地主信任域。

flowchart LR
    Operator[控制平面客户端<br/>CLI / Web UI / macOS App] -->|WebSocket RPC| Gateway
    WebChat[WebChat 静态 UI] -->|WebSocket RPC| Gateway
    Node[设备节点<br/>iOS / Android / macOS / headless] -->|role: node<br/>能力和命令声明| Gateway
    Channels[消息渠道<br/>WhatsApp / Telegram / Slack / Discord] --> Gateway
    Gateway --> AgentRuntime[Agent Runtime]
    Gateway --> Policy[认证 / 配对 / Scope / 工具策略]
    Gateway --> Canvas[Canvas Host<br/>/__openclaw__/canvas/]
    Gateway --> A2UI[A2UI Host<br/>/__openclaw__/a2ui/]
    AgentRuntime --> Model[模型和工具执行]

核心组件

Gateway 网关

Gateway 是 OpenClaw 的核心守护进程，默认监听 127.0.0.1:18789。它承担以下职责：

  • 维护消息渠道提供商连接，例如 WhatsApp、Telegram、Slack、Discord 等。
  • 暴露类型化 WebSocket API，支持请求、响应和服务端推送事件。
  • 使用 JSON Schema 校验入站协议帧。
  • 发出 agent、chat、presence、health、heartbeat、cron 等事件。
  • 承载 Canvas 和 A2UI 静态入口，路径分别为 /__openclaw__/canvas/ 和 /__openclaw__/a2ui/。

从技术实现看，Gateway 相当于“单实例控制总线”。它把消息渠道、Agent runtime、设备节点、控制 UI 以及安全策略收敛到一个进程边界内，减少跨服务一致性问题，但也意味着主机和 Gateway 配置本身必须被视为可信边界。

控制平面客户端

控制平面客户端包括 CLI、Web UI、macOS App 和自动化脚本。它们每个客户端维护一个 WebSocket 连接，主要做三类事情：

  • 发起请求：如 health、status、send、agent、system-presence。
  • 订阅事件：如 tick、agent、presence、shutdown。
  • 根据自身权限范围访问配置、模型、日志、Agent 会话和工具审批等能力。

这些客户端在协议层通常是 role: "operator"，并通过 operator.read、operator.write、operator.admin、operator.approvals、operator.pairing 等 scope 做权限分层。

节点

节点是远程或本机能力宿主。节点连接同一个 Gateway WebSocket 服务器，但会在握手时声明 role: "node"，并上报：

  • caps：高级能力类别，例如 camera、canvas、screen、location、voice、talk。
  • commands：可被调用的命令白名单，例如 camera.snap、canvas.navigate、screen.record、location.get。
  • permissions：细粒度开关，例如 camera.capture、screen.record。

这套设计把“设备有什么能力”和“Gateway 允许它做什么”分开。节点的声明只是能力主张，Gateway 仍会在服务端执行允许列表和策略检查。

WebChat

WebChat 是一个静态 UI，通过 Gateway WebSocket API 获取聊天历史并发送消息。在远程访问场景中，WebChat 和其他客户端一样，可以通过 SSH 隧道、Tailscale 或 VPN 接入 Gateway。

WebSocket 协议实现

传输和分帧

Gateway 协议使用 WebSocket 文本帧，载荷为 JSON。协议帧主要分三类：

1

{ "type": "req", "id": "...", "method": "...", "params": {} }

1

{ "type": "res", "id": "...", "ok": true, "payload": {} }

1

{ "type": "event", "event": "...", "payload": {}, "seq": 1, "stateVersion": 1 }

实现上有几个重要点：

  • 第一帧必须是 connect 请求，否则 Gateway 会关闭连接。
  • 握手前帧大小有限制，握手后客户端应遵守 hello-ok.policy.maxPayload 和 hello-ok.policy.maxBufferedBytes。
  • hello-ok.features.methods 和 hello-ok.features.events 是能力发现元数据，不是所有内部方法的完整转储。
  • 有副作用的方法，例如 send、agent，需要幂等键，以便客户端安全重试。

握手流程

Gateway 先向客户端发出 connect.challenge，客户端再提交 connect 请求。请求中包含协议版本范围、客户端信息、角色、scope、能力、命令、认证信息和设备签名。

sequenceDiagram
    participant Client as 客户端
    participant Gateway as Gateway

    Gateway-->>Client: event: connect.challenge
    Client->>Gateway: req: connect<br/>role/scopes/caps/auth/device
    Gateway-->>Client: res: hello-ok<br/>protocol/features/snapshot/auth/policy
    Gateway-->>Client: event: presence
    Gateway-->>Client: event: tick

hello-ok 是握手成功后的关键响应，包含：

  • 协商后的协议版本。
  • Gateway 服务端版本和连接 ID。
  • 可发现方法和事件。
  • 当前状态快照，例如 presence、health。
  • 协商后的角色和 scope。
  • 策略限制，例如最大载荷、最大缓冲区、tick 间隔。
  • 可选的设备令牌和插件表面 URL。

类型和代码生成

协议类型由 TypeBox schema 定义，再生成 JSON Schema，并进一步生成 Swift 模型。这个链路说明 OpenClaw 希望用单一 schema 源头约束多语言客户端，避免手写协议模型漂移。

flowchart LR
    TypeBox[TypeBox Schema] --> JSONSchema[JSON Schema]
    JSONSchema --> Validator[Gateway 入站帧校验]
    JSONSchema --> Swift[Swift 客户端模型]
    JSONSchema --> UI[Web / CLI 类型和表单约束]

Agent 运行链路

Agent loop 是一次真实智能体运行的主路径：接收请求、组装上下文、调用模型、执行工具、流式返回、持久化会话。

sequenceDiagram
    participant Client as 客户端/消息渠道
    participant Gateway as Gateway
    participant Queue as 队列
    participant Runtime as Agent Runtime
    participant Model as 模型/工具

    Client->>Gateway: req: agent
    Gateway-->>Client: ack {runId, acceptedAt}
    Gateway->>Queue: 按 sessionKey 入队
    Queue->>Runtime: runEmbeddedAgent
    Runtime->>Model: 推理和工具调用
    Runtime-->>Gateway: assistant/tool/lifecycle 增量
    Gateway-->>Client: event: agent streaming
    Gateway-->>Client: final res: agent

关键实现点：

  • agent RPC 会先校验参数、解析会话并持久化会话元数据，然后立即返回 runId 和 accepted 状态。
  • agentCommand 负责解析模型、thinking、verbose、trace 默认值，并加载 Skills 快照。
  • runEmbeddedAgent 负责实际运行，包含会话队列、全局队列、模型凭证解析、运行时事件订阅、流式输出、超时中止和用量元数据返回。
  • subscribeEmbeddedAgentSession 将 runtime 事件桥接为 OpenClaw 的 agent 流，包括 assistant 增量、tool 事件和生命周期事件。
  • agent.wait 可以等待某个 runId 的 end 或 error 结果。

这个设计的好处是：RPC 层快速确认接收，真实运行异步执行，并通过事件流持续返回进度。

队列和并发控制

OpenClaw 使用一个轻量的进程内队列来串行化入站自动回复运行，目标是防止多个 Agent 运行同时争用同一会话状态、日志、CLI stdin 或上游模型额度。

队列策略分两层：

  • 会话通道：runEmbeddedAgent 按 session:<key> 入队，保证同一会话只有一个活跃运行。
  • 全局通道：每个会话运行再进入全局通道，例如默认 main，受 agents.defaults.maxConcurrent 控制整体并发。

消息队列模式包括：

  • steer：把运行中途到达的消息注入活跃运行，在下一次模型调用前交付。
  • followup：当前运行结束后逐条处理后续消息。
  • collect：静默窗口后合并消息为一个后续轮次。
  • interrupt：中止当前活跃运行，改跑最新消息。

队列模型体现了 OpenClaw 对 Agent 产品体验的取舍：同一会话要强一致，跨会话可以有限并发，运行中的用户补充信息优先通过 Steering 接入，而不是盲目启动第二个 Agent loop。

配对和本地信任

配对是 OpenClaw 的显式访问审批步骤，主要用于两个地方：

  • 私信配对：控制谁可以通过消息渠道和机器人对话。
  • 节点配对：控制哪些设备或节点可以加入 Gateway 网络。

配对实现中有几个细节值得注意：

  • 所有 WebSocket 客户端，包括操作员客户端和节点，都会在 connect 中携带设备身份。
  • 新设备 ID 需要配对批准，批准后 Gateway 会签发设备令牌。
  • 直接 local loopback 连接可以自动批准，以保证同主机体验顺畅。
  • Tailnet 和 LAN 连接仍需要显式配对批准。
  • 所有连接都需要签名 connect.challenge nonce。
  • 签名载荷会绑定 platform 和 deviceFamily，设备元数据变化时需要修复配对。
  • Gateway 认证配置仍然适用于所有连接，本地和远程都不例外。

私信配对使用短代码。官方文档说明代码为 8 个大写字符，不包含 0O1I 等易混淆字符，默认 1 小时过期，并限制每个渠道待处理请求数量。

安全模型

OpenClaw 的安全边界不是敌对多租户模型，而是“可信主机 + 可信操作员控制平面”模型。

主机信任

如果某人可以修改 Gateway 主机状态或配置，例如 ~/.openclaw 和 openclaw.json，就应被视为可信操作员。官方不建议多个互不信任的操作员共用同一个 Gateway。混合信任团队应使用独立 Gateway，或者至少使用独立 OS 用户和主机边界。

Gateway 和节点信任

Gateway 是控制平面和策略表面，节点是远程执行表面。节点配对后，节点上的操作等价于被该 Gateway 信任的操作员操作。因此：

  • sessionKey 是路由和上下文选择器，不是授权令牌。
  • Exec 审批是操作员意图护栏，不是强多租户隔离。
  • 如果多个用户都能向启用工具的智能体发消息，他们都可能通过提示影响工具调用。

Scope 和审批

操作员 scope 用于控制 RPC 权限。例如：

  • operator.read：读取状态、会话、事件等。
  • operator.write：发送消息、触发 Agent 等写操作。
  • operator.admin：配置、更新、敏感管理操作。
  • operator.approvals：处理工具或 Exec 审批。
  • operator.pairing：处理配对。
  • operator.talk.secrets：读取 Talk 配置中的敏感凭据。

节点命令也有审批时检查。比如涉及 system.run、system.run.prepare、system.which 的节点配对批准，需要更高权限组合。

技术实现要点总结

单 Gateway 架构

OpenClaw 采用单 Gateway 模式，将渠道连接、控制 API、节点网络、Agent 调度和安全策略放在一个长期进程里。实现收益是状态集中、协议统一、部署简单；代价是 Gateway 主机成为强信任边界。

类型化协议

Gateway WebSocket 协议不是自由 JSON，而是由 TypeBox schema 定义，并生成 JSON Schema 和客户端模型。这样可以在入站校验、客户端类型和 UI 表单之间共享契约。

事件驱动运行

agent 请求采用“先 ack，后流式事件”的模式。客户端不需要同步等待完整运行结束，而是通过 event: agent 获取 assistant、tool 和 lifecycle 增量。

能力声明和服务端强制

节点在握手时声明 caps、commands 和 permissions，但 Gateway 将这些视为主张。真正的权限仍由服务端允许列表、scope 和审批策略决定。

会话一致性优先

Agent loop 通过每会话队列和会话写锁保护会话历史、转录和工具状态。跨会话可以并发，同一会话必须串行或通过 Steering 合流。

本地优先的远程访问

默认 Gateway 绑定本地回环地址。远程访问优先推荐 Tailscale 或 VPN，也可通过 SSH 隧道转发 18789 端口。远程场景仍复用相同握手和认证模型。

可以借鉴的工程设计

  1. 对 Agent 系统使用单一控制平面协议，而不是让 CLI、Web、App、节点各自绕不同接口。
  2. 将长任务设计为 ack + event streaming，避免请求阻塞和客户端超时。
  3. 把设备能力声明与服务端授权分离，避免信任客户端自报。
  4. 对有副作用 RPC 强制幂等键，让重试成为协议能力。
  5. 对同一会话强串行化，对跨会话做有限并发，平衡一致性和吞吐。
  6. 将协议 schema 作为源头，再生成校验规则和客户端模型。
  7. 明确产品安全边界，避免把可信单操作员系统误包装成强多租户系统。
