AI Agent Memory 深度解析：原理、实现机制与 LangChain 1.0+ 源码剖析

source: agent-memory
May 15, 2026

写在前面

Agent 要完成连续任务，就需要记住上下文。

但 Agent Memory 不等于把所有聊天记录都塞回模型，也不等于简单做一个 Retrieval-Augmented Generation（RAG，检索增强生成）知识库。

本文将深入讲解 Agent Memory 的设计原理、底层机制、工程实现，并结合 LangChain 1.3+ / LangGraph 1.2+ 的源码进行分析，帮助你从理论到实践全面掌握 Agent 记忆系统。

一、Memory 解决什么问题

1.1 为什么需要记忆

Large Language Model（LLM，大语言模型）本身是无状态的。每次请求都是独立的函数调用 f(prompt) -> response，模型不记得上一次对话。

没有记忆的 Agent 会遇到：

  • 忘记用户偏好（“我上次说了用中文回复”）
  • 重复询问信息（“你的邮箱是什么"问了三遍）
  • 不知道任务进展（多步骤任务断档重来）
  • 无法利用历史经验（同类任务反复试错）
  • 长对话上下文超限（token 溢出截断）

1.2 记忆的本质

从计算机科学角度，Agent Memory 本质是一个带有读写策略的状态管理系统：

+------------------+     write      +----------------+
|   Agent 运行时   | ------------> |  Memory Store  |
|  (当前对话/任务)  | <------------ |  (持久化存储)   |
+------------------+     read       +----------------+

核心问题是：什么时候写、写什么、什么时候读、读什么、怎么淘汰过期信息。

1.3 记忆不是越多越好

错误记忆会导致错误决策。

例如把用户一次临时需求记成长期偏好，后续回答就会被污染。Token 成本也是关键约束——每次 LLM 调用的上下文窗口是有限的，塞入过多记忆等于引入噪声。

2.2 Short-term Memory（短期记忆）

定义：当前会话（conversation/thread）中的消息列表，随会话结束而丢弃。

底层机制：将 List[BaseMessage] 作为状态传递给 LLM。每次 LLM 调用时，短期记忆就是 prompt 中的 messages 数组。

关键特征：

  • 容量受限于 LLM 的 context window
  • FIFO（First In First Out，先进先出）淘汰或基于 token 数截断
  • 会话级隔离，不同 thread 互不可见

工程实现中的典型操作：

操作 说明
append 新消息追加到列表尾部
trim 当 token 超限时裁剪旧消息
summarize 压缩历史为摘要消息
remove 按 ID 删除特定消息

什么是 Reducer？ 来自函数式编程的概念——把两个值合并（reduce）成一个值的函数，签名固定为 f(旧值, 新值) -> 合并后的值。如果 State 字段没有 reducer，节点返回值会直接覆盖旧值；有了 reducer，则按自定义逻辑合并。类比 JavaScript 的 Array.reduce((acc, cur) => ...)——把一系列值逐步合并成最终结果。

def add_messages(left: Messages, right: Messages) -> Messages:
    # left = State 中已有的消息列表（旧状态）
    # right = 本次节点返回的新消息（增量更新）
    # Reducer 模式: 框架自动调用 add_messages(旧状态, 节点输出) 来合并

    # 1. 将两侧都强制转为 BaseMessage 列表
    left = convert_to_messages(left)
    right = convert_to_messages(right)

    # 2. 为没有 ID 的消息自动分配 UUID
    for m in left + right:
        if m.id is None:
            m.id = str(uuid.uuid4())

    # 3. 特殊处理: RemoveMessage(id=REMOVE_ALL_MElasticsearch（ES）SAGES) 清空所有
    if any RemoveMessage with REMOVE_ALL_MESSAGES in right:
        return right[remove_all_idx + 1:]

    # 4. 合并逻辑: 按 ID 去重，right 覆盖 left 中同 ID 消息
    merged = left.copy()
    merged_by_id = {m.id: i for i, m in enumerate(merged)}
    for m in right:
        if isinstance(m, RemoveMessage):
            # 从 merged 中删除指定 ID 的消息
            ids_to_remove.add(m.id)
        elif m.id in merged_by_id:
            # 同 ID 消息覆盖更新
            merged[merged_by_id[m.id]] = m
        else:
            # 新消息追加
            merged.append(m)
    return [m for m in merged if m.id not in ids_to_remove]

设计亮点：

  1. 幂等性：通过 message ID 去重，重复投递同一消息不会导致列表膨胀
  2. 精确删除：RemoveMessage 可以按 ID 删除单条，也可以用 REMOVE_ALL_MESSAGES 清空
  3. pre_model_hook：在 Agent 调用 LLM 前，可通过 hook 对消息做裁剪/摘要，而不改变实际存储的完整历史

2.3 Working Memory（工作记忆）

定义：当前任务的执行状态——Agent 正在做什么、收集了哪些信息、还缺什么。

类比：人类大脑的"工作台”，同时处理的有限信息。

字段 示例

短期记忆 vs 工作记忆：重叠与区别

两者确实存在重叠——工作记忆中的信息往往从短期记忆（对话消息）中提取而来。比如用户说"金额1280元"，这既是短期记忆中的一条消息，也会被提取到工作记忆的 collected_info 字段中。

维度 短期记忆 工作记忆
关注点 对话内容本身（消息序列） 任务执行状态（在做什么、到哪步了）
数据形态 List[BaseMessage] 线性列表 结构化字段（plan、status、facts）
信息来源 用户输入 + LLM 输出 Agent 自身推理从对话中提取
是否裁剪 会（token 超限时裁剪/摘要） 不会（关键状态始终保留）
类比 你和别人聊天的记录 你脑中"正在做第3步，还差一个发票"

为什么要分开设计：

  1. 短期记忆是原始的、线性的，而工作记忆是结构化的、按任务组织的
  2. 短期记忆受 token 限制必须裁剪，但工作记忆中的关键字段（如已收集的参数）不能丢
  3. 在 LangGraph 中两者存储位置相同（都在 Checkpoint 的 State 里），但语义角色不同

简单总结：短期记忆是"聊了什么"，工作记忆是"在干什么"。

    Stores enable persistence and memory that can be shared across threads,

def _cosine_similarity(X: list[float], Y: list[list[float]]) -> list[float]:
    """计算查询向量与候选向量矩阵的余弦相似度"""
    import numpy as np
    X_arr = np.array(X)
    Y_arr = np.array(Y)
    X_norm = np.linalg.norm(X_arr)
    Y_norm = np.linalg.norm(Y_arr, axis=1)
    similarities = np.dot(Y_arr, X_arr) / (Y_norm * X_norm)
    return similarities.tolist()

三、各类记忆的存储载体选型

不同类型的记忆对延迟、容量、持久性、检索方式的要求不同，因此适合不同的数据载体。

+-------------+--------+--------+--------+--------+--------+--------+
| 短期记忆     |  ★★★  |  ★★   |   ★    |    ★     |       |        |
| 工作记忆     |  ★★★  |  ★★★  |   ★★   |    ★★    |       |        |

3.2 各存储载体特性对比

存储载体 延迟 持久性 容量 检索能力 适合的记忆
内存 (dict/list) ~ns 无（进程退出即丢） 受限于 RAM 精确查找 O(1) 短期记忆、工作记忆（开发调试）
Redis ~ms 可配置 AOF/RDB 受限于 RAM key 精确 + 模糊匹配 短期记忆、工作记忆、会话缓存
SQLite ~ms 文件持久化 单文件 TB 级 SQL 查询 单机长期记忆、Checkpoint

Elasticsearch ~10ms 持久化 + 集群 PB 级 全文检索 + Best Matching 25（BM25，经典文本相关性排序算法） 情景记忆、日志型记忆检索
向量数据库 (Milvus/Pinecone/Qdrant) ~10ms 持久化 十亿级向量 ANN 近似最近邻 语义记忆、大规模 RAG
MongoDB ~5ms 持久化 + 副本集 PB 级 文档查询 + Atlas Vector 半结构化长期记忆

# langgraph/checkpoint/memory/__init__.py - InMemorySaver.put()

def put(self, config, checkpoint, metadata, new_versions):
    c = checkpoint.copy()
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"]["checkpoint_ns"]

    # 1. 分离 channel_values，单独存储为 blobs
    values = c.pop("channel_values")
    for k, v in new_versions.items():
        self.blobs[(thread_id, checkpoint_ns, k, v)] = (
            self.serde.dumps_typed(values[k]) if k in values else ("empty", b"")
        )

    # 2. 存储 checkpoint 元数据，建立 parent 链
    self.storage[thread_id][checkpoint_ns][checkpoint["id"]] = (
        self.serde.dumps_typed(c),          # checkpoint 本体（不含 values）
        self.serde.dumps_typed(metadata),   # 元数据
        config["configurable"].get("checkpoint_id"),  # parent_id
    )

设计要点：

  • Channel Values 分离存储：避免每次 checkpoint 都重复存储未变化的大对象
  • Parent 链：形成线性历史，支持回溯到任意历史状态
  • 版本号管理：只有变化的 channel 才写入新 blob

def batch(self, ops):
    results, put_ops, search_ops = self._prepare_ops(ops)

    # 1. 处理搜索: 先对查询做 embedding
    if search_ops:
        query_embeddings = self._embed_search_queries(search_ops)
        self._batch_search(search_ops, query_embeddings, results)

    # 2. 处理写入: 对新数据做 embedding
    to_embed = self._extract_texts(put_ops)
    if to_embed:
        embeddings = self.embeddings.embed_documents(list(to_embed))
        self._insert_vectors(to_embed, embeddings)

    # 3. 应用写入操作
    self._apply_put_ops(put_ops)
    return results

7.1 RAG 是一种记忆实现

RAG (Retrieval-Augmented Generation) 本质上是 Agent 语义记忆 的一种实现方式。

十二、高频面试题

12.1 Agent Memory 和聊天历史有什么区别？

聊天历史是原始对话记录的线性序列（List[BaseMessage]），而 Agent Memory 是经过筛选、结构化、分类后用于支持任务执行的信息系统。Memory 包含短期记忆（当前对话）、工作记忆（任务状态）、长期记忆（跨会话知识）三个层次，而聊天历史只是短期记忆的一部分。

12.2 Agent Memory 和 RAG 有什么区别？

RAG 主要解决外部知识检索增强，数据来源是预处理的文档库，通常不区分用户。Agent Memory 是更广的概念，包含用户偏好、任务状态、历史行为记忆，是动态的、个性化的、实时更新的。在实现层面，RAG 可以看作 Agent Memory 中"语义记忆"子系统的一种实现方式。

12.3 LangGraph 中 Checkpointer 和 Store 的区别？

  • Checkpointer：保存单个 thread 的 Graph 执行状态（含 messages），按 thread_id 隔离，主要用于对话恢复和短期记忆持久化。
  • Store：保存跨 thread 的长期数据，按 namespace 层级组织，支持语义搜索和 TTL，主要用于长期记忆和知识库。
  • 类比：Checkpointer 是浏览器 Tab 的会话恢复；Store 是浏览器的收藏夹和密码管理器。

12.4 为什么不能把所有历史都放进上下文？

  1. Token 超限：LLM context window 有硬上限，超过就会报错或被截断
  2. 成本：token 数量直接决定 API 费用，10 万 token 的上下文远贵于 2000 token
  3. 噪声干扰：无关信息会降低模型对关键信息的注意力（“大海捞针"问题）
  4. 过期信息：旧信息可能已不准确，反而导致错误回答
  5. 延迟：更长的输入意味着更慢的响应速度

12.5 LangGraph 中 add_messages 的设计精妙在哪里？

  1. ID 去重：通过 message ID 实现幂等性，重复投递不会重复记录
  2. 精确删除：RemoveMessage(id=xxx) 支持按 ID 删除任意历史消息
  3. 批量清空：RemoveMessage(id=REMOVE_ALL_MESSAGES) 一步清空后插入新消息
  4. 格式兼容：支持 dict / tuple / BaseMessage 多种输入格式统一处理
  5. Reducer 模式：作为 State annotation，自动处理图节点间的消息合并逻辑

12.6 Memory 最大的风险是什么？如何应对？

风险 影响 应对措施
错误记忆 基于错误前提做出错误决策 置信度评分 + 多次验证后才写入
隐私泄漏 用户 A 的信息被用户 B 看到 Namespace 隔离 + 权限校验
记忆污染 攻击者注入虚假记忆 写入审计 + 来源追踪
过期失效 旧信息不再准确但仍被使用 TTL 机制 + 定期验证
存储膨胀 记忆无限增长导致检索变慢 容量上限 + 淘汰策略

12.7 如何设计一个生产级的 Agent Memory 系统？

关键设计点：

  1. 分层存储：短期（内存/Redis） + 长期（PostgreSQL + 向量索引）
  2. 多租户隔离：基于 namespace 的层级隔离，租户 > 用户 > 类别
  3. 写入策略：只写入用户确认或高置信度的持久信息
  4. 检索策略：结合精确匹配（filter）和语义搜索（vector），按相关性排序
  5. 生命周期管理：TTL + 访问刷新 + 定期清理
  6. 可观测性：记录每条记忆的来源、创建时间、访问频次、置信度
  7. 用户控制：提供查看/编辑/删除记忆的 API 和界面

12.8 pre_model_hook 和直接修改 messages 有什么区别？

pre_model_hook 返回 llm_input_messages 时，只影响本次 LLM 调用的输入，不修改 State 中存储的完整 messages。这意味着：

  • 完整历史仍然保存在 Checkpoint 中，可随时回溯
  • 下次执行时仍能看到完整上下文
  • 只有传递给 LLM 的部分被裁剪/压缩

而直接修改 messages（通过 RemoveMessage）是真正删除，删除后的消息无法恢复。

12.9 向量搜索在 Memory 中的作用是什么？底层如何实现？

向量搜索让 Agent 能根据语义相似度检索记忆，而不是仅靠精确关键词匹配。底层流程：

  1. 写入时：提取指定字段文本 -> Embedding 模型生成向量 -> 存储到向量索引
  2. 查询时：Query 文本 -> Embedding 模型生成查询向量 -> 余弦相似度计算 -> Top-K 返回

核心公式：cosine_similarity(A, B) = dot(A, B) / (norm(A) * norm(B))

在 InMemoryStore 中使用 NumPy 加速矩阵运算，生产环境推荐 pgvector 或专用向量数据库（Pinecone/Milvus）。

12.10 如何处理记忆冲突？

当新信息与已有记忆矛盾时：

  1. 时间优先：通常新信息更可靠，覆盖旧记忆
  2. 来源优先：用户明确陈述 > Agent 推断 > 间接提取
  3. 频次验证：多次出现的信息置信度更高
  4. 标注冲突：无法判断时保留两条，标注冲突，下次交互时向用户确认
  5. 版本记录：通过 updated_at 跟踪变更历史
